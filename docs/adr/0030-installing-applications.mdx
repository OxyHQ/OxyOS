# ADR 0030: Installing applications (Atlas)

Status: **accepted** (decisions 1 to 15, and every choice under [Decided with the platform's author](#decided-with-the-platforms-author), chosen with the platform's author on 2026-10-30; decision 16, one place for the OS's and the applications' updates, asked for by the author the same day; decision 17's Bloom in the framework, decided by the author the same day); steps to come. Builds on:
- [ADR 0001](./0001-native-platform-boundaries): grants from the session authority.
- [ADR 0013](./0013-launching-applications): the registry, launching and launch records.
- [ADR 0015](./0015-application-model): one source, platform adapters.
- [ADR 0019](./0019-settings): the `settings` grant and the rule for an administrator's entries.
- [ADR 0020](./0020-oxy-account-login): `oxyos-accountd`, and applications' tokens.
- [ADR 0023](./0023-installing-oxyos): the read-only `/usr`, images and A/B updates.
- [ADR 0026](./0026-notifications).

It resolves the "Installing applications, an application store" left out by ADR 0013 and ADR 0015 (#35, #36).

## Problem

An OxyOS machine cannot install, update or remove an application.

- **What OxyOS has.** An application is a Desktop Entry in `oxyos/applications` under the XDG data directories (ADR 0013). A Bloom application names a module (`X-OxyOS-Bloom-Module`) and optionally a bundle (`X-OxyOS-Bloom-Bundle`); otherwise it runs from the session's bundle. Today every Bloom application runs from that one bundle: a 9.5 MB Hermes bytecode file with the shell, Settings, the samples and the probes in it ([performance](../performance)). On the development machine the Bloom host and its bundle were copied by hand into `/opt/oxyos`, and Settings' entry into `/usr/local/share/oxyos/applications`, because the `settings` grant goes only to an entry, host and bundle that only root could have written (ADR 0019, decision 3). There is no package, no signature, no installer and no update.
- **What Atlas is.** Atlas (`OxyHQ/Atlas`, atlas.oxy.so) is Oxy's app store. It is an Expo Router application: the storefront (`app/(app)/index.tsx`), an application's page (`app/(app)/app/[slug].tsx`) and settings. It has no backend of its own: its AGENTS.md puts every store rule in oxy-api, read through `@oxy.so/core`'s `oxy.store` (`lib/store.ts`). Its worker only serves the static files. It lists applications it does not distribute:
  - the row's action opens the page, not an install ("an Install that navigated to a website would be a lie", `components/store-cards.tsx`);
  - the page's only action, *Open*, opens the application's `websiteUrl`;
  - the developer is printed as "Oxy" whatever the application.
- **What the store's backend has** (oxy-api, `packages/api/src/db/schema`, `docs/store.mdx`):
  - **The catalogue:** `app_listings` (the slug, the words, the shelf, the review status), `app_categories`, `app_listing_screenshots` (a platform each: phone, tablet, desktop, web), `app_reviews` and `app_review_replies`.
  - **No versions, platforms, builds, hashes or signatures.** The listing's own comment sends versions to `app_updates`.
  - **Oxy Updates** (`app_updates`, `update_assets`, `update_channels`; `routes/updates.ts`, `oxy-ship`) is a self-hosted expo-updates server for the iOS and Android builds. It has content-addressed assets (SHA-256, immutable, `RESTRICT`), byte-stable signed manifests, channels, rollouts and rollbacks. Its platforms are `ios` and `android` only. The publisher pushes straight to devices with no review, and nothing in it is a developer's signature or a capability. Its manifests are signed at serve time with an RSA key the API reads from its environment (`UPDATES_CODE_SIGNING_PRIVATE_KEY`): whoever controls the API controls every device's code.
  - **The precedents:** the closest to a signed release is the inference catalogue's `inference_model_releases`, which has a manifest kept verbatim, an artifact per path with digest and size, and detached Ed25519 signatures over the manifest's RFC 8785 (JCS) form, all append-only by trigger. Oxy ADR 0012 chose Ed25519 for the platform's asymmetric signatures. Oxy ADR 0045 records how each application is recognised per platform (`webOrigins`, `android`, `ios`) and has no `oxyos`.

What a Mac does is the model:
- The App Store application asks; system services (`storedownloadd`, `installd`) download, verify and install.
- Applications are signed, by the developer and by Apple.
- Installed applications live in `/Applications`, and updates come by themselves.
- What an application may use is declared, enforced, and asked for in the system's own dialogs.
- The system's own applications are part of the sealed system and update with it.

Four facts of OxyOS's own shape the design:
1. **The Bloom host is the runtime.** An application's bundle carries React Native's JavaScript side. Its native side is the host: React Native 0.88, Hermes V1, Fabric, and the modules the host provides, as Expo Go's are fixed for each Expo SDK. The two sides must be the same version, so an application is built *for a runtime*.
2. **Hermes runs bytecode as trusted input.** Hermes does not verify bytecode before running it, as a JVM verifies a class. Bytecode crafted by hand can corrupt the VM's memory, so a bytecode file from a third party is as dangerous as native code from it.
3. **`/usr` will be a read-only image** on published installs (ADR 0023, decision 6). Installed applications cannot live in it.
4. **ADR 0019's rule is ownership.** An entry a root-owned installer wrote from bytes it downloaded would pass that rule. If installed entries carried `X-OxyOS-Grants`, any package could ask for `settings`.

## Decision

1. **The package: the developer's JavaScript, its assets, and a manifest that names every file.** An OxyOS application package is a tree of files described by `manifest.json`:
   - **`manifest.json`.** The package's id, which is reverse-DNS and is the registry's id (`so.oxy.mention`). The Oxy application it belongs to (oxy-api's application id: its listing, reviews, consent and app assertions). `version` for people, and `versionCode`, an integer that only grows (decisions 4 and 10 compare it). Its name and localized names. Its icon. Its entry, `{ "bundle": "bundle/index.js", "module": "Mention" }`, where the module is the name it registers with `AppRegistry`. Its runtime, `{ "abi": 1, "api": 3 }` (decision 2). Its architectures, `["any"]` for a package with no native code. Its capabilities, each with a purpose in the person's languages (decision 8). The kinds of file and the URL schemes it opens, for ADR 0027's opening of files. Then **`files`**: every other file with its path, size and SHA-256. The manifest is written in its JCS form (RFC 8785), so its bytes are what is signed, and its digest covers the whole package.
   - **`bundle/index.js`**: Metro's output for the `oxyos` platform, built against its runtime's framework (decision 17), so it holds the application's own modules alone, with its assets in the resource layout the host resolves next to the bundle (`drawable-*`, `raw/`).
   - **The icon**, as the registry already shows icons (a file, or an SVG's drawing).
   - **No bytecode.** Because Hermes trusts bytecode (fact 2), the package carries the developer's JavaScript and the system compiles it at install (decision 5), as Android's ART compiles an APK's dex on the device. The bytecode that runs is then always the output of the runtime's own `hermesc` from source the developer signed. When a runtime's Hermes changes its bytecode version but keeps its React Native, the system compiles again from the same source, with no new release.
   - **Native code: reserved, not accepted.** The format keeps `native/x86_64/…` and `native/aarch64/…`, chosen by the machine's architecture, so it need not change when native parts come. A native part would be loaded into the host and would bypass every capability the host enforces. The store accepts none until a runtime defines a native-extension ABI *and* applications are confined by the kernel (decision 15). Without native code a package runs unchanged on x86-64 and AArch64: one `index.js`, as an APK carries one JavaScript bundle for every ABI.

   Distribution is per file, by content address, never as one archive. The installer never unpacks an archive as root (no path traversal or links from a tar or zip). An update fetches only the files that changed. The store already serves content-addressed objects this way (decision 12).

2. **Runtimes: versioned, side by side, supplied by the OS.** A runtime is a Bloom host build, `/usr/lib/oxyos/runtimes/<abi>/` (the host, React Native's and Hermes' libraries, its `hermesc`, its framework of decision 17, and `runtime.json`, which declares its numbers and names its framework's digests), with two numbers:
   - **`abi`** changes when an application must be rebuilt: a new React Native, a host module whose JavaScript contract breaks, or a framework that drops or changes a public module (a breaking release of one of its packages, decision 17). A package runs only on a runtime of its `abi`.
   - **`api`** grows when a runtime adds without breaking: a new host module, a new option, a module its framework adds. A package runs on a runtime of its `abi` whose `api` is at least its own.

   Like Flatpak's runtimes and Expo's SDKs, the image carries the current `abi` and the one before it, side by side, for a support window. The launcher starts each application with its runtime's host. A runtime leaves the image only when its window ends, and the store then shows what it can no longer run. The store serves a package only to machines that have its runtime, and Atlas says "not available for this computer" otherwise. Runtimes come with the OS image, never from the store: they are system code. The development machine's `/opt/oxyos` becomes this layout under `/usr/lib/oxyos/runtimes/`.

3. **Two signatures, both verified by the system, never by the application.**
   - **The developer's.** Ed25519 over the manifest's JCS bytes, as Oxy ADR 0012 and the inference releases chose, preceded by a context of its own and a zero byte (`oxyos-package manifest v1`; a rotation is signed over `oxyos-package rotation v1`, a release over `oxyos-package release v1`), so a document signed as one kind is never valid as another: `manifest.sig` holds the key id and the signature. A key's id is the unpadded base64url SHA-256 of its 32 bytes, so an id never names two keys. The private key is the developer's, in its CI or on its machine. Oxy never holds it, and for Oxy's own applications it is not any of the store's keys. The developer's public keys are kept on its Oxy application (decision 12).
   - **The store's.** When a release passes review, the store signs it into its metadata (decision 4): the package id, `versionCode`, runtime, architecture, the manifest's digest and length, and the developer key it was signed with. That signature is Oxy's approval for distribution, a Mac's notarization.
   - **Pinning.** At first install the machine pins the developer key the store named for that id. Every update after that must be signed by the pinned key, or by a key the pinned key signed into its lineage (a rotation statement, as APK Signature Scheme v3's lineage). So the store alone cannot change an installed application's code, a developer key alone cannot publish, and a fresh install trusts the store's word about the key, as on every platform.
   - **Who verifies:** `oxyos-installd` (decision 5), as root, before any byte is used. Atlas, the session, the shell and the application never do. Launching verifies nothing over the network, so an installed application starts offline.

4. **The store's metadata follows The Update Framework (TUF 1.0).** Signatures on single releases do not stop a repository, a CDN or a network from serving an old release with a known flaw (rollback), from hiding a new one forever (freeze), or from mixing releases that never coexisted. TUF's metadata does, and it is what PyPI (PEP 458) and Uptane chose for the same problem:
   - **`root`**: the keys of every role. It is signed by a threshold of offline keys held by people, kept in the image (`/usr/share/oxyos/store/root.json`), and rotated by TUF's chain, each new root signed by the old threshold.
   - **`targets`**: the approved releases (decision 3's statement, as each target's custom data). It is signed by the store's release key at approval, in a KMS or HSM, never in the API's environment as the updates key is today.
   - **`snapshot`** and **`timestamp`**: what is current, and how fresh that is. They are signed online with short expiries.
   - **On the machine:** `oxyos-installd` keeps the metadata (`/var/lib/oxyos/apps/store/`) and refuses a version lower than the one it has, or expired metadata, for installs and updates. Running what is installed never depends on it.

5. **The install service: `oxyos-installd`, root, with no network; and a fetcher with only the network.** As `oxyos-accountd` keeps the accounts (ADR 0020, decision 3), one system service keeps the applications. It is split in two, as a Mac's `installd` is apart from its downloader:
   - **`oxyos-installd`** runs as root, with no capabilities (it owns its own state) and no network (`PrivateNetwork=yes`). It has `ProtectSystem=strict` and writes only `/var/lib/oxyos/apps` (its `StateDirectory`). It verifies metadata and every file, compiles, assembles versions, switches them and removes them. It never runs a package's code and never touches a home.
   - **The fetcher**, `oxyos-installd --fetch`, is a unit of its own: `DynamicUser=yes`, the network to the store and nothing else. `oxyos-installd` opens each destination file in its own staging directory and hands the fetcher the descriptor and the URL, so the fetcher can write those bytes and reach nothing else. `oxyos-installd` then checks the length and SHA-256 against the verified metadata before the file goes anywhere.
   - **The compiler** is the runtime's `hermesc`, run by `oxyos-installd` with no network, no privileges, a seccomp filter, and only the source and an output descriptor. Its output is kept as the version's `index.hbc`, with its digest in the install record. It parses untrusted JavaScript, as Hermes would parse source at start, and it runs confined because it does.
   - **Its socket,** `/run/oxyos/installd/socket`, is `SOCK_SEQPACKET` with one JSON message per packet and peers judged by the kernel's credentials, as accountd's is. A user's session acts for that user alone, and root for administration. The conversation:
     - `prepare {id}` is answered with a plan: the release for this machine, its size, its capabilities, whether it would change the pinned key;
     - `commit {plan}` follows the person's confirmation (decision 9);
     - progress is reported while it runs, then `installed` or `failed {reason}`;
     - `uninstall {id}`, `list`, `hold`/`release` (decision 10), and `checkUpdates`.
   - **Failing closed.** A file that does not match, an unknown key, a broken lineage, expired or older metadata, a runtime the machine lacks, or a compile failure leaves nothing installed and the previous version running.

6. **On disk: the bytes once for the machine, the installs for each account.** Each person is an Oxy account and a Unix user (ADR 0020). An application is downloaded once, and each account installs it for itself, as Android's users share an APK:
   - **`objects/<aa>/<sha256>`**: the content-addressed files, root-owned and read-only. Where the root's ext4 has the `verity` feature they are sealed with fs-verity, so the kernel checks every page read and a file changed on disk is noticed.
   - **`packages/<id>/<versionCode>/`**: a version's tree, hard links into `objects/` plus its `index.hbc`, once for the machine whichever accounts run it. A version is assembled whole in a new directory before anything names it. Its facts (names, capabilities, the key that signed it) are its own manifest's and signature's, read from the tree.
   - **`installed/<id>.json`**: what is the machine's about the application, which is only the developer's key it pinned. Key continuity belongs to the id on this machine: the lineage moves the pin, and an account installing later is never handed another key.
   - **`users/<user>/<id>.json`**: that account's install. Its current version, the one before (kept until the current one shows a window), one staged for it, the releases it rolled back, and its decisions on capabilities (decision 8).
   - **`users/<user>/applications/<id>.desktop`**: the entry `oxyos-installd` writes for that account's current version (decision 7).
   - **Each account's files** are owned by root, group the account's, mode 0640, in directories of 0750: no other account learns what one installed. Each file is written whole to a new file and renamed over the old, so switching an account's version is one rename and a crash leaves it on the old one or the new one, never a mix.
   - **An account's cost is a record and an entry,** never another copy of the files or the bytecode.
   - **Any account may install for itself** with no administrator, as on a phone. The package is verified, and other accounts see nothing of it unless they install it too.
   - **No account holds back another's.** Which version an account runs, its consents and its rollbacks are its own: one account consenting to an update, rolling one back or running an old copy changes nothing for the others.
   - **An application's data is the account's,** in `~/.local/share/oxyos/apps/<id>/` and `~/.cache/oxyos/apps/<id>/`, which the host gives as Expo's document and cache directories.

7. **The registry knows three sources, and an id from a trusted one cannot be shadowed.** ADR 0013's search of `$XDG_DATA_DIRS` stays for development, and two fixed, root-owned sources come before it:
   - **The image's:** `/usr/share/oxyos/applications` (decision 13).
   - **The install service's:** `/var/lib/oxyos/apps/users/<user>/applications`, the session's user's own entries, of the versions it runs.
   - **Development:** the XDG directories, as today. An entry there with an id the first two have is ignored: a profile's directory cannot make `so.oxy.mention` run its own code under Mention's name.

   This amends ADR 0019 at its root. Ownership proves that an administrator wrote a file. It does not prove that the file's contents are an administrator's choice, and the install service's entries are root-owned files whose contents come from the network. So:
   - **System grants** (`shell`, `lock`, `shortcuts`, `settings`, `store`) come only from the image's own policy, `/usr/share/oxyos/system-apps.json`. It names each system application's id, the grants it gets and, for a store-updated one, the developer key it must be signed with (decision 13). No entry's `X-OxyOS-Grants` is read, whoever wrote it. Development has no rule of its own: a development machine that runs Settings with its grant has the policy too, naming where its entry, host and bundle are.
   - **An installed application's capabilities** come from its install record (decision 8): the manifest's declared capabilities, narrowed by the account's decisions.
   - **Its identity is verified.** The launch record (ADR 0013, decision 3) of an installed or image application says so (`verified`, with the version and the developer key), and only a verified launch is an application to the platform: for its capabilities, its data directory, and the per-application Oxy tokens of ADR 0020's decision 6. A development entry's launch is marked unverified and gets none of them.

   The launcher starts an installed application with its runtime's host and the version's `index.hbc`, at their real paths, which it judges as ADR 0019 does. While the session runs it, the session holds the version (decision 10). The registry follows the install service's state by inotify, so the dock and Launchpad show an installed application at once.

8. **Capabilities: declared in the manifest, shown at install, enforced by the system, the sensitive ones asked at first use.** An application can use only what it declared, and the store's review reads each purpose. The person sees them all in the install sheet, as a Mac's App Store page shows an application's privacy. Expo's own permission APIs (`requestPermissionsAsync`) are how an application asks, so an Oxy application's code is unchanged (ADR 0015).

   | Capability | What it gives | Decided |
   | --- | --- | --- |
   | `network` | `fetch` and `XMLHttpRequest` to the Internet (the host's `oxyos-net`) | Shown at install |
   | `notifications` | Posting (ADR 0026) | Asked at the first `requestPermissionsAsync`; turned off in Settings |
   | `files` | The home and the person's volumes (ADR 0027's `OxyOSFiles`) | Asked at first use |
   | `camera`, `microphone`, `location` | When the host has them | Asked at first use |
   | `oxy-account` | Short Oxy tokens for this application (ADR 0020, decision 6), with the scopes its Oxy application has | Shown at install, as Oxy's consent screen |
   | `open-files`, `url-schemes` | Being offered a file or a link (ADR 0027) | Shown at install |
   | `background`, `login-item` | Running without a window, or at sign-in | Asked |

   - **System grants** are never a store package's (decision 7).
   - **Who decides.** The person decides in system sheets (decision 9). `oxyos-installd` keeps the answers in `users/<user>/<id>.json`, so no process of the user can grant itself a capability by writing a file. Settings shows and revokes them on a *Privacy* page, with `privacy`, a system grant the image's policy gives Settings alone (`decide` in the service's vocabulary). The session gives the launch record those grants, and the host makes each module available only with its grant, as `OxyOSSettings` is only Settings' (ADR 0019).
   - **When a decision applies.** The launch is told what its account granted (`OXYOS_APP_ORIGIN`, `OXYOS_APP_CAPABILITIES`), read at launch; a capability granted at first use holds at once for the process that asked; a decision changed on the *Privacy* page applies at the application's next launch, as the page says.
   - **What enforces it today: the host, and only the host.** A package has no native code (decision 1), so its JavaScript reaches the system only through the host's modules. Kernel confinement, so that a compromised host is contained, is decision 15's gate.

9. **How Atlas asks: a system grant, a host module, the SDK's installer seam; the confirmation is the system's.**
   - **The grant.** `store` is a new system grant, and the image's policy gives it to `so.oxy.atlas` alone. With it, the Bloom host gives the module `OxyOSStore`: `status(ids)`, `install(id)`, `update(id)`, `uninstall(id)`, `open(id)` and progress events. An install the person confirmed is the session's until it ends, whichever client asked: a `status` asked meanwhile (by the store that asked, or by one opened since) says it is `installing`, with its latest progress, never that the application is not installed.
   - **An id, never bytes.** `RequestInstall` in the protocol carries the id and the serial of the person's press in Atlas, which must be a recent real input, as clipboard and notification activations require (ADRs 0007, 0026). The compositor hands it to the session, which asks `oxyos-installd` to `prepare`. Atlas never hands the system bytes, a URL or a signature. The system fetches and verifies what the store's signed metadata names, as `LaunchApplication` takes an id and never a command (ADR 0013).
   - **The confirmation is the system's.** The shell draws the install sheet over Atlas, the way the lock screen is drawn: a surface no application can draw, cover or press for the person (the compositor sends it only real input). It shows the icon and name from the verified metadata, the developer, the size, and the capabilities with their purposes. *Install* sends `commit`. Atlas learns the outcome and nothing of the sheet. The sheet is modal and has the keyboard while it asks, as a Mac's alert is the key window: the compositor lets the shell's overlay take the keys while a sheet waits, so nothing typed then reaches the application behind it. Escape is Cancel; no key accepts. A press that lands before the sheet is shown goes to what was shown where it landed, as a Mac's window server routes it. The same sheet confirms an uninstall, and an update that adds capabilities.
   - **One API on every platform.** ADR 0015 forbids Atlas from asking which platform it is on, so it uses an installer seam in the SDK, beside `oxy.store`: an installer the runtime registers, as the storage seam (`AuthStateStore`) is registered. On OxyOS the runtime registers one backed by `OxyOSStore`. Where none is registered (the web, iOS, Android), Atlas shows what it shows today. Atlas never imports anything of OxyOS's.
   - **One trust domain, for now.** Until applications are confined (decision 15), a user's processes are one trust domain, as ADR 0019 says of Settings. Store packages cannot reach `oxyos-installd`'s socket, because the host gives them no raw sockets. A native program the user runs could, as it could run anything as the user. With confinement, `oxyos-installd` takes `commit` only from the session's own process.

10. **Updates: automatic, by file, at the next launch, never down, each account's own.**
    - **Checking.** A check reads `timestamp` and, when the snapshot moved, `targets`, and for each application on the machine finds the releases newer than an account's current version, for the machine's runtimes and architecture. Each manifest is fetched and verified once for the machine. Each account's update state (decision 16) is computed from that check and the account's records. A check asked for while one runs joins it. `oxyos-app-updates.timer` runs one daily, and after boot once online, at a random delay.
    - **Downloading.** The fetcher fetches the missing objects at low priority, and not on a connection NetworkManager says is metered unless the person asked. `oxyos-installd` verifies, compiles and assembles the version once for the machine. Automatic updates are each account's option, on by default and turned off in Settings (decision 16).
    - **Running copies are never changed.** The host reads its assets while it runs, so a version stays while any session runs it. A session `hold`s each version it launched on its own connection to `oxyos-installd` and `release`s it when the application exits. Holds die with the connection. An account's new version is switched to when none of that account's sessions runs the application, and another account's running copy defers nothing for it. *Update* in Atlas on a running application asks, in the system's sheet, to quit it first, as a Mac's App Store does.
    - **New capabilities wait, for the account they are new to.** An update that declares a capability shown at install that the account's current version does not, or that is signed by another key of the lineage, is staged for that account until it consents through the sheet, in Atlas's *Updates* or Settings' *Software Update*. It then switches for that account alone. An update that needs no consent switches for every account that has the application. Android does the same, and Chrome with an extension that asks for more.
    - **Rollback is the account's.** The account's version before is kept until the new one has shown a window in one of its sessions. If the new one exits before its first window on the account's first two launches, `oxyos-installd` switches that account back, keeps the release from being offered to it again, and reports it to the store. Other accounts stay on the new version. An application's own data is its own: a version that ran and changed it is not undone.
    - **Never down.** `versionCode` only grows, TUF refuses older metadata, and the store fixes a bad release by publishing a higher `versionCode`.
    - **Deltas.** File-level deltas come from content addressing: an update fetches only the objects it lacks, and the compressed transfer is HTTP's. Binary deltas of the bundle (`zstd --patch-from` against the installed object) come later, if measurements show the bundle dominates.

11. **Uninstalling.** From Launchpad or Atlas, confirmed in the system sheet (*Delete Mention and its data?*). The session removes the account's data directories as the user, which is why `oxyos-installd` needs no access to homes. `oxyos-installd` removes the account's record and entry. A version tree goes once no account's current, previous or staged version names it and no session holds it, and objects go once no tree links them. When no account has the application any more, its record goes too. A system application cannot be uninstalled. Only its store updates can be removed, back to the image's version (decision 13).

12. **What the store's backend must add.** This is a proposal for the oxy repository, decided there by its own ADR, reusing the shared owners rather than a second copy:
    - **Identity, on the application registry** beside Oxy ADR 0045's `android` and `ios`: `oxyos: { packageId, signingKeys[] }`. `packageId` is unique and fixed once a release exists. Signing keys are Ed25519 public keys with status and lineage, and a key added after the first release needs a rotation statement signed by an existing key.
    - **`app_releases`**: application, platform `oxyos`, `version`, `version_code`, `runtime_abi`, `runtime_api`, the manifest verbatim with its digest, the developer key and signature, localized release notes, the review status (`draft`, `pending_review`, `approved`, `published`, `withdrawn`, `revoked`), the rollout percentage, and who submitted and approved it. The signed columns are append-only by trigger, as the inference releases' are.
    - **`app_release_files`**: release, architecture (`any`, `x86_64`, `aarch64`), path, SHA-256, size. The bytes are content-addressed objects on the store's CDN, reusing Oxy Updates' `update_assets` (content address, immutability, `RESTRICT`, the init and complete upload flow with size checked against the object store) under a store prefix.
    - **`app_release_capabilities`**: each capability with its purpose, for the review and the store page.
    - **`app_installs`**: account, application, device, `version_code`, when installed and removed. This is *Purchased* and the restoring of a person's applications on a new machine, and an install count, which is not a count of `app_grants`.
    - **The TUF repository**: `root`, `timestamp`, `snapshot` and `targets` with consistent snapshots, public and unauthenticated (the store is public; Atlas's AGENTS.md). Targets are re-signed at each approval or revocation, timestamps on a schedule. The release and online keys live in a KMS or HSM, and the root is offline with a threshold.
    - **Publishing.** `oxy-ship` gains `oxy-ship oxyos build|sign|publish`: Metro for the `oxyos` platform against the runtime, the manifest, the developer's signature with its key, the upload, the release created. The Console gets a *Releases* page (keys, releases, rollout, review). Moderation gets a release queue beside the listing queue, with approve, reject and revoke.
    - **Reads.** `StoreListingDetail` gains the listing's developer (the owning account's name, where Atlas now prints "Oxy") and, for OxyOS, the current release for a given runtime and architecture: version, size, capabilities, release notes, date. `@oxy.so/core`'s `oxy.store` reads it, and the installer seam of decision 9 sits beside it.
    - **Revocation.** A release found harmful is revoked. `targets` then carries its revocation, and `oxyos-installd` stops launching it, tells the person why, and installs the store's replacement.
    - **App assertions** (Oxy ADR 0045) gain `oxyos`. The attester is the platform: a verified launch record (decision 7) and the machine's device credential, held by `oxyos-accountd`. That is the per-application token of ADR 0020's decision 6, decided in the SDK's repository.

13. **What comes with the OS, and what comes from Atlas.** Three kinds of application, as a Mac has its sealed system's applications, the App Store's, and in between those it ships and the App Store updates:
    - **Platform applications**, in OxyOS's repository and the image, updated only with the OS: the shell (with the lock screen and Launchpad), the login screen, Settings (with its `settings` grant), and the install sheet. They are packages in the same format under `/usr/lib/oxyos/apps/<id>/`, compiled at image build by the runtime's `hermesc`. The image's integrity covers them (dm-verity on published installs), and their entries are in `/usr/share/oxyos/applications`. The one bundle of today splits into them.
    - **System applications**, in their own repositories, in the image as a starting version and updated through Atlas, not removable: **Atlas**, the App Store, and **Stash**, the file manager ("Files", a Mac's Finder; its repository is Stash's, not OxyOS's). The image build takes the release the store published, pinned by its digest, and verifies the developer's and the store's signatures at build. The image's policy names each one's developer key and system grants (Atlas: `store`; Stash: `files` granted without asking). `oxyos-installd` installs a higher `versionCode` from the store over the image's version, as Android updates a system application from Play into `/data`. An OS update never takes one back down, and removing the updates returns to the image's version.
    - **Store applications**, everything else (Mention, Alia, Allo, Inbox, Homiio and the others), from Atlas.

14. **Atlas on OxyOS: the App Store.**
    - **Its build.** In Atlas's repository, from the same source as its web and native builds (ADR 0015, decision 4): Metro for the `oxyos` platform against the runtime, through `@oxy.so/app-preset` once the preset has an OxyOS target. It is published through the store as `so.oxy.atlas`, signed with its developer key. Its entry module is `Atlas`.
    - **Its place.** Pinned in the dock by the image's policy, as the App Store is, with the `store` grant from that policy alone (decision 7).
    - **What it does there.** The storefront's reads are public and need no token. *Get* becomes the system sheet, then a progress ring, then *Open* (`OxyOSStore.open`, a launch through the session). An application with a newer release shows *Update*. One the machine cannot run says *Not available for this computer*. Atlas gets an *Updates* page (pending updates, release notes, updates waiting for consent), the same state Settings' *Software Update* shows (decision 16) and a *Purchased* page (`app_installs`). An application's page shows its capabilities, size, version history and compatibility.
    - **Its account.** Writing a review needs the account, so it waits for ADR 0020's decision 6. Until then Atlas on OxyOS says reviews are not available yet and signs in to nothing.

15. **Third-party applications wait for confinement.** Until each application is confined by the kernel, a package's code runs with everything its account can do, once it gets past the host. Confinement is its own decision (#35, #36): a scope of its own per launch (systemd's `app-…` naming), Landlock to its data and what it was granted, a seccomp filter, no tracing between applications. Until it exists:
    - the store publishes OxyOS releases only of Oxy's own applications (`applications.type` `first_party` with `isOfficial`), whose code is Oxy's;
    - the format, the signatures, the service and the store are made whole now, so opening the store to third parties is a policy change, not a redesign.


16. **One place for updates: Settings' Software Update, the OS's and the applications' together.** A person checks for updates once, in one place, as a Mac's *General › Software Update* updates macOS and an iPhone's App Store updates every application. *Software Update* (*Actualización de software*), a page of Settings beside *About*, lists the OS's own update and every application update the account has: store applications, and the system applications updated through Atlas (Atlas itself, Stash, decision 13).
    - **One check, one state.** `oxyos-installd` keeps the applications' update state for each account (decision 10): what is available, its size to fetch (only the objects the machine lacks), its version and release notes, whether it needs the account's consent, when the store was last read, and whether a check is running. `checkUpdates` asks for a check now. A check asked for while one runs joins it, so two pages asking at once make one check. A connection may watch the state, and is told each change.
      - Settings' *Software Update* and Atlas's *Updates* (decision 14) both show that state through the session, and neither checks on its own. An update applied in one disappears from the other at once.
      - The timer of decision 10 is the same check.
    - **What the page shows,** in Bloom's grouped sections as every Settings page:
      - *Check for updates*, then the list: the OS first, then each application with its icon, name, new version, size and what is new (its release notes in the person's language: the store's text, signed with the store's metadata, never the developer's);
      - *Update All*, and *Update* for each item;
      - an application update that declares a new capability, or rotates its developer's key, says so: *Update* opens the system's consent sheet (decision 9) for this account, and *Update All* asks each of those in turn, after updating the rest;
      - a running application updates at its next launch, or the sheet asks to quit it first (decision 10);
      - *Automatic updates*: *Download and install applications' updates* (this account's, kept by `oxyos-installd`, on by default), and the OS's, which are the machine's, not one account's, so they are a system setting changed through the OS's update service, as ADR 0019's decision 2 changes the system's settings.
    - **A grant for it.** `updates` is a system grant that the image's policy gives to Settings and to Atlas (decision 7). With it the Bloom host's `OxyOSSystem` asks for the state, a check, `update(ids)` and `updateAll()`, and is told the state as it changes. `store` (installing and removing, decision 9) stays Atlas's alone. The automatic options come with their timer (step 7): no switch is shown before what it switches exists.
    - **The OS's own update is not `oxyos-installd`'s.** ADR 0023's decision 6 is what is decided:
      - development installs update with apt;
      - published installs update as whole signed A/B images of `/usr` with systemd-sysupdate and boot counting.

      That image-update decision is its own ADR and is not written yet: the published layout, the image's signing and update server, and the service that checks and applies. When it exists, its service gives the page the OS's row (available, size, what is new, *Restart to update*) and is checked by the same *Check for updates*. Until then, on a development install, the OS's row says the system updates with apt and offers nothing to apply. Settings never runs apt, and never shows a fake OS update.
    - **Not two stores of truth.** The page keeps no list of its own: what is installed, what is available and what the account consented to are `oxyos-installd`'s. A preference file of the user's cannot change what is updated.

17. **The runtime's framework: React Native, React and Bloom once, shared by every application.** As macOS and iOS ship their frameworks once and every application links them, each runtime carries one framework of JavaScript, compiled once for it, which every application's JavaScript runtime evaluates before the application's own bundle. An application's package is then its own code: it carried React Native, React and Bloom itself before, 6.7 to 8.2 MB of bytecode each, of which its own modules were 0.2 to 0.4 MB (1.6 to 3 %).
    - **What it is.** `<runtime>/framework/`: `framework.hbc` (compiled by the runtime's build, as the rest of the runtime, never on the machine), its assets, and `framework.json`, its manifest: every module's key and id, which of them are public, and the version of each package in it. `runtime.json` names the bytecode's and the manifest's SHA-256. It is the image's, under its verity as the host is; nobody else signs it, and an application's signatures cover its own files alone.
    - **What is in it.** React Native's JavaScript and React, which must be the host's native side's exactly (fact 1); the Babel helpers any application's code calls; the packages whose native side the host implements (reanimated and worklets, gesture-handler, svg, safe-area-context, screens, Expo's core, asset, font, blur, haptics, image, constants, linking, keep-awake, glass-effect, file-system, document-picker; svg's CSS); what the host gives Expo applications (AsyncStorage, NetInfo, expo-crypto, expo-secure-store, expo-web-browser, expo-clipboard, expo-notifications, expo-application); what an Expo Router application's entry runs on (expo-router, `@expo/metro-runtime`); the stylesheet's runtime (react-native-css, nativewind); every runtime export of Bloom, its icons among them; and the host's own JavaScript (Bloom's platform adapter for OxyOS, Expo's native side). Its entry lists each as a getter, as React Native's own `index.js` exposes its modules, so each is defined and none runs until an application requires it; React Native's `InitializeCore` and the framework's own start (Expo's native side, and its assets resolved beside it) run first.
    - **Ids are a contract.** A module's id is 52 bits of the SHA-256 of a key, never Metro's numbering of one build:
      - a package's public module: `name@major:subpath|conditions`, the export of its `package.json` and the conditions Metro resolved it with (`react-native.import`, `react-native.require`: one subpath may be an ESM and a CommonJS file); every file of a package with no `exports` is public, `name@major/path`;
      - a private one (a file no export names): `name@version/path`, the framework's own, which no application may name;
      - the runtime's own modules, `oxyos/path`; an application's, `app/path`.

      The major version is in the key, so a module keeps its id across its package's compatible releases. Two keys with one id stop the build, and so do two files with one key (two copies of a package).
    - **Applications are built against it.** Metro builds an application with the framework's manifest: its bundle holds only its own modules and the statement running its entry, with no prelude, polyfills or `InitializeCore`. The build stops if the application needs a module of a framework package that the framework does not provide, another version of one, or a private module. A framework package is exactly the framework's version: the application's own tree's copy is never used, and an application whose dependencies do not accept that version stops the build rather than bringing a second copy. When a package has an ESM and a CommonJS file for one export (react-native-css's components), the application gets the one the framework has, whichever way it imports it. The only modules of a framework package an application builds for itself are those that hold the application: expo-router's context of its routes (`_ctx`, a `require.context` of its `app/`) and the qualified entry over it. Every build is a production build as Expo's own: `__DEV__` and `process.env.NODE_ENV` are inlined and what is development-only folds away, React Native's developer tools (`react-devtools-core`) among it; React Native's own modules see the platform as `android` (they run its Android implementation), everything else as `oxyos`. The package's `runtime` names the framework's `abi` and `api` it was built against, so the store and the launcher need nothing more (decision 2). On-device compilation (decision 1) compiles the application's own JavaScript alone.
    - **`api` only adds, mechanically.** The framework of a runtime's next `api` is built against the previous one's manifest and is refused if a public module it had is missing or has another id: that needs a new `abi`. A framework rebuilt with ninety-nine modules more kept every one of the first's 2,564 public ids, and the applications built against the first ran on it unrebuilt.
    - **How the host runs it.** The host maps the framework's bytecode and the application's from their files (React Native's `JSBigFileString`) rather than reading them into memory, and evaluates the framework first, in the same turn, through React Native's own `loadScript` (its `beforeLoad`). Hermes runs bytecode from the buffer it is given, so the framework's pages are the file's, shared by every process. `OxyOSRuntime` gives JavaScript the runtime's `abi`, `api` and the framework's URL; the framework's assets (Bloom's fonts, React Native's images), marked by its build, are resolved beside the framework through React Native's `addCustomSourceTransformer`, every other asset beside the application's bundle.
    - **Measured** on the shell, the login screen, Settings, Inbox and Allo, with the real host, on a developer's machine at a load of 37 to 45 (a Chromium build ran), before and with the framework, two rounds each:

      | | Before | With the framework |
      | --- | --- | --- |
      | The five packages, as downloaded | 74.4 MiB | 5.1 MiB |
      | Installed, with their bytecode | 111.4 MiB | 6.2 MiB |
      | An application's bytecode | 6.7 to 8.2 MB | 0.18 to 0.30 MB |
      | The runtime | 50.3 MiB | 65.3 MiB (the framework 15.0: 4,671 modules, 13.8 MB of bytecode) |
      | The shell, Settings, Inbox, Allo and a probe running: PSS | 225.9, 223.9 MiB | 197.3, 196.9 MiB (−12 %) |
      | The same: USS, private | 199.6, 198.0 MiB | 162.4, 162.0 MiB (−18 %) |
      | First frame, p50 (Settings, Inbox, WindowProbe, Allo), ms | 124/145, 515/405, 249/322, 160/161 | 134/95, 374/333, 203/216, 152/136 |

      Each process has 10.2 to 10.7 MiB of the framework's 13.2 MiB resident, file-backed and shared, about 2.1 MiB of PSS each among five; before, each copied its whole bundle into memory. Evaluating the framework, 4,671 modules defined, takes 7 to 16 ms, less than reading and copying an application's whole bundle took (30 to 78 ms), so no application starts later. Each further application costs its own few hundred kilobytes rather than the framework again.
    - **Bloom is in the framework, its version the runtime's.** Bloom is 13.9 MB of the framework's 23.7 MB of JavaScript (59 %: all of it, where each application used 2.3 to 4.5 MB of it, 20 to 32 % of its bundle). With Bloom in the framework, an application cannot use a Bloom newer than its runtime's, as an iOS application uses the SwiftUI of the iOS it runs on. The rule:
      - a Bloom minor or patch release is a new `api` of the same runtime (its public modules keep their ids, the major being in their keys), and an application built against it declares that `api`;
      - a Bloom major release is a new `abi`, side by side with the one before for the support window (decision 2);
      - OS updates (decision 16) carry Bloom's releases, so an application waits for the OS update that carries the Bloom it was built with, and Atlas offers it to a machine once that machine has the update.

      Rejected: Bloom in each application (the framework React Native, React and the native packages alone). The framework would be about 5.7 MB of bytecode and each application 1.3 to 2.6 MB more (the Bloom it uses, with colorjs.io and the stylesheet runtime beside it), private to each process; on the five, that is about 18 MB of bytecode against 15, a difference each further application adds to, and the memory and Bloom's platform adapters (ADR 0015: windows, the menu bar, popups) would be each application's version rather than the platform's. Also rejected: several Bloom versions side by side in one runtime. Bloom's minor releases only add, so the newest serves every application built for an older one, and side-by-side versions would share nothing between applications on different ones.

      That application releases wait for an OS release is a product choice, decided by the platform's author (*Decided with the platform's author*, 16): Bloom stays in the framework, as SwiftUI is iOS's. Oxy releases Bloom and OxyOS, so the OS carries each Bloom release on Bloom's own cadence.
    - **Release builds.** Every application carried `react-devtools-core` (0.76 MB), which a release build should not: React Native's transformer gave babel-preset-expo no `isDev`, so `__DEV__` stayed a variable and its guarded requires stayed in. With Expo's transformer they fold away, and the framework has neither `react-devtools-core` nor LogBox's development side: 13.85 MB of bytecode and 4,671 modules before, 13.06 MB and 4,647 modules after with expo-router's entry and the Expo modules above added; with svg's CSS (Stash), 13.62 MB and 4,810 modules.
    - **Seen, not changed:** `expo-router` (1.25 MB), which Bloom imports for every application, router or not (its adaptive colors import `expo-router` itself, its panel-routing, scroll and tab-pager adapters `expo-router` and `expo-router/ui`). It is in the framework once; Bloom's import of it is Bloom's to remove.

## Rejected

- **Debian packages (apt) for applications.** Their maintainer scripts run as root, and they install for the whole system with no per-application capabilities or developer signature. Published installs do not take packages into `/usr` (ADR 0023, decision 6).
- **Flatpak, Snap.** Their runtimes, portals and sandboxes serve GTK, Qt, X11 and Wayland applications through D-Bus portals that assume a Wayland session, which the image rules exclude. OxyOS's applications are bundles for one host. The ideas are taken, not the stacks: Flatpak's side-by-side runtimes, OSTree's content addressing, Snap's store-signed assertions.
- **AppImage.** It has no install service, signature chain or updates.
- **Oxy Updates as it is.** It pushes publishers' code to devices without review, signs at serve time with a key in the API's environment, and has no developer signature, capability or install. Taken from it: the content-addressed store and its upload, the byte-stable signed documents, the rollout percentage.
- **Shipping Hermes bytecode in the package.** Hermes trusts bytecode (fact 2). Compiling on the machine also makes a new Hermes bytecode version cost no release.
- **One archive per release.** It means an extraction parsed as root, and no sharing of unchanged files between versions.
- **Atlas installing by itself, or verifying.** Then any application with the same rights could install, the confirmation would be Atlas's, and verification would be the application's.
- **All capabilities granted at install** (Android before 6). A person grants everything at once and never thinks of it again. Sensitive ones are asked at first use, as a Mac and iOS ask.

## Decided with the platform's author

The author took each recommendation; the decisions above are written to them:

1. **Two signatures**, the developer's and the store's (decision 3), not the store's alone.
2. **A lost developer key** is reset only by a statement the offline root's threshold signs, never an online key: rarely, and recorded in the store's metadata for anyone to see.
3. **TUF** for the store's metadata (decision 4).
4. **Keys:** the root offline, held by people as hardware keys with a threshold (2 of 3 to begin with); the release, snapshot and timestamp keys in a KMS or HSM, never in an environment variable.
5. **Confirming an install is the system's sheet alone,** with no password, for every install, update with new capabilities and uninstall (decision 9). The sheet is the proof a person chose it: no application can draw, cover or press it.
6. **Installs for each account,** over bytes shared by the machine, with no administrator (decision 6).
7. **Capabilities** as decision 8's table: declared and shown at install, the sensitive ones asked at first use, revocable in Settings.
8. **Runtimes:** the image carries the current `abi` and the one before, for at least six months after a new one ships (decision 2).
9. **No native code in packages,** for anyone, until a native-extension ABI and confinement exist (decision 1).
10. **Third parties** only once applications are confined (decision 15).
11. **The image** carries Atlas and Stash as system applications (decision 13); other applications are offered from Atlas, none installed by default at setup.
12. **Nothing installs outside Atlas,** beyond development entries with no grants and no Oxy identity (decision 7).
13. **Revocation** by the store of an installed release, telling the person (decision 12).
14. **Installs are recorded for each account** on the server (`app_installs`), shown in the account's data (decision 12).
15. **The installer seam is the Oxy SDK's,** beside `oxy.store` (decision 9).
16. **Bloom is in the framework** (decision 17), as SwiftUI is iOS's: a Bloom minor release is a new runtime `api`, a major release a new `abi`, and an application built with a newer Bloom waits for the OS update that carries it.

## Steps

0. **The system grants' policy** (decision 7), first and on its own: system grants from `/usr/share/oxyos/system-apps.json` alone, never from an entry's ownership, amending ADR 0019.

   *Done.* `oxyos_apps::Policy` reads the policy strictly; the registry lists its applications first, from the entries it names, and no other directory's entry takes their ids; a launch has a system application's grants only running what the policy names, an administrator's, by its real path; no entry's `X-OxyOS-Grants` is read. ADR 0019's decision 3 and its tests say how ([ADR 0019](./0019-settings)).
1. **The format.** `crates/oxyos-package`: the manifest (parsing, JCS, digests, the files list, the runtime and capabilities), the developer's signature and its lineage, with tests on packages written by the tests: a file changed, a file missing, a file not listed, a path leaving the tree, a bad signature, a key not in the lineage. A development key and a test TUF root.

   *Done.* `crates/oxyos-package`: `manifest.json` read only as its RFC 8785 canonical form (no key twice, no unknown field, integers to 2^53 − 1, every size bounded), its id, Oxy application, versions, names (no control or bidirectional characters), icon, entry, runtime, capabilities (decision 8's eleven; a system grant refused by name) and its sorted files; paths of a plain ASCII alphabet that cannot leave the package or mean two files; no native code and no bytecode as the entry; the tree checked by descriptor (`O_NOFOLLOW`, nothing unlisted, no link) and a stream checked while copied. Ed25519 (`ring`) for the developer's signature, a key's lineage and the store's statement of a release, each over a context of its own so one kind is never valid as another. 28 tests, every refusal among them, and 30,000 mutations of a valid manifest, signature and statement, none panicking, none verifying.
2. **`oxyos-installd` from a local repository.** The service, the fetcher, the compiler's confinement, the layout of decision 6, `prepare`, `commit`, `uninstall`, `hold` and `release`, TUF's checks with the `tuf` crate or an implementation of the specification checked against its conformance tests, and the units, verified with `systemd-analyze`. Tests: each failure leaves nothing installed; a crash at each point leaves the old or the new version; another account sees nothing; rollback; never down. The development compositor installs from a directory served by the tests.

   *Done.* `crates/oxyos-install` holds the logic, testable without root, and `tools/oxyos-installd` the service and, with `--fetch`, its fetcher; nothing installs either.
   - **The store's metadata** is TUF 1.0's top-level roles. The root is updated one version at a time, signed by the old threshold and its own. The timestamp, snapshot and targets are each the version, length and hash the role before names, never older than the machine's, not expired. Rotated timestamp or snapshot keys drop the machine's copies. Ed25519 over TUF's canonical JSON, read strictly; a key counts once, under the id its form hashes to. Consistent snapshots in python-tuf's layout. A repository python-tuf 6.0.0 wrote is read as it wrote it. Delegations are not read yet.
   - **A release** is a target whose custom data carries the store's statement (signed by a targets key), the developer's signature, key and lineage, its release notes by language (the store's text, which TUF signs with the targets and the developer does not), and the store listing it belongs to (`listing`, its slug, the store's text signed the same way). `resolve {listings}` answers each listing's package for this machine, or none (none too for a listing two packages claim), so a store hands the machine a slug and nothing else. Its manifest is the target's bytes, and its files are objects checked against the manifest. It must be signed by the key the machine pinned for the id or the one its lineage hands over to, run on a runtime of the machine's, and be no older than the account's version nor one the account rolled back.
   - **The runtime's `hermesc`** compiles the package's JavaScript from standard input to standard output. As root it runs in a transient unit (a dynamic user, no network, no capabilities, `@system-service` with no socket of any family), and only after the tree is verified; a test starts that unit as root, with its real properties, in CI and on a machine (a transient unit refuses properties a unit file takes: systemd 257 refused `RestrictAddressFamilies=none`); its output must begin with Hermes's magic number.
   - **A version** is assembled once for the machine, whole, in a hidden directory of hard links into the objects, checked, and renamed into place with the record that names it. Every file is written whole. A crash leaves each account on its old version or its new.
   - **Each account its own** (`users/<user>/<id>.json` and `users/<user>/applications/<id>.desktop`, root's with the account's group, 0640): its current version, the one before (kept until the current one shows a window in one of its sessions), one staged for it, its rollbacks and its decisions. An update needing consent waits for each account's own and switches for it alone; one needing none switches for every account. A hold defers only its own account's switch. Two launches that never showed a window roll back that account alone. `installed/<id>.json` keeps only the pinned key, which an account installing later must match.
   - **The update state** of each account (decision 16): for each update its from and to versions, the size to fetch (only the objects the machine lacks), its release notes, and whether it waits for the account's consent (for which capabilities, or a rotated key) or for its running copy; when the store was last read; whether a check runs. A check asked for while one runs joins it. A watching connection is sent its account's state at each change. `update`, `updateAll` and `consent` act for the account alone. The automatic updates are each account's option (on by default), and `automaticUpdates`, root's, is what the timer will run.
   - **Removal:** an account's removal takes its record and entry; a version tree goes once no account names it and no session holds it, objects once no tree links them.
   - **The service** runs as root with only `CAP_CHOWN` and no network, on `/run/oxyos/installd/socket`, a user acting for its own account alone. The fetcher is a dynamic user with the network alone, writing only into descriptors passed with `SCM_RIGHTS`, for root alone. Their units rate 1.3 and 1.5 (`systemd-analyze security`).
   - **Tests:** 32, on directories of the tests' own through the real fetcher, and the real `hermesc` when `OXYOS_TEST_HERMESC` names it. Among them: two accounts, one consenting and switching while the other stays and keeps its tree; a rollback, a hold and a removal each one account's; two checks at once making one; a watcher told what another connection applied.
   - **Not yet:** the service as root on a real system, HTTPS, delegations, fs-verity and the update timer's unit (step 7), and the session's side (step 3).

3. **The registry and the launcher.** The three sources and their order, verified launch records, runtimes under `/usr/lib/oxyos/runtimes/`, holds. Settings, the shell and the login screen become packages of their own instead of one bundle. Scenarios: an installed application in the dock at once, launched and marked verified; a development entry with an installed id ignored; an installed entry asking for `settings` gets nothing.

   *Done*, with decision 17's framework.
   - **Runtimes** are `<runtimes>/<abi>/`, as `cmake --install` lays the host out: the host (finding its libraries in `lib/` by `$ORIGIN`), `hermesc`, `framework/` and `runtime.json`. `runtime.json` is read in one place, `oxyos_package::RuntimeDescription` (strictly: `abi` from 1, `api`, and the framework's digests), by the session's launcher and the install service alike. An entry names its runtime (`X-OxyOS-Runtime`). The session starts it with that runtime's host from `/usr/lib/oxyos/runtimes`, never an environment variable's, and refuses one the machine lacks ("runtime 2 is not on this machine"). A development entry naming none keeps the session's host. A system application naming one runs only if the policy's host is that runtime's. The development compositor alone takes `--runtimes DIR`.
   - **A package's bytecode** is known to its JavaScript by its source bundle's URL (the manifest's `entry.bundle`), beside its assets: for the applications the session launches and for the shell and the login screen it starts.
   - **The registry's three sources** (decision 7): the policy's system applications, then the install service's entries for the session's account (`/var/lib/oxyos/apps/users/<user>/applications`, the user the account database gives the session's real uid; root's, at their real paths, each naming its version with `X-OxyOS-Package-Version`, a Bloom bundle on a runtime), then the development directories. An id from the first two is never another source's. An entry whose bundle is not there is not installed: said, not listed.
   - **Launch records** say where each application came from (`Origin`: `System`, `Installed { version_code }`, `Development`; only the first two verified). An installed one carries its account's capability decisions, as the install service keeps them, for step 4's host modules; no entry's `X-OxyOS-Grants` gives it anything.
   - **The session and the install service.** A thread of the session's own holds each installed version it launches on one connection to `oxyos-installd`. It says `shown` when one of that version's processes first shows a window (the compositor's `pids_showing_windows`) and `exited` with whether it showed one. It releases a version when its last process ends, and holds again what still runs if the connection is lost. The compositor's loop never waits for it.
   - **The shell follows the registry.** A watch (inotify over the policy, the account's entries and the development directories, each followed even before it is there, `oxyos_applications_watch_*` in the C ABI) wakes the shell's host, which lists the applications again, so one installed or removed is in the dock and Launchpad at once.
   - **The one bundle split.** The shell, the login screen, Settings, Inbox and Allo are packages of their own (`sample/entries/`, `sample/packages/`, `sample/packages.mjs`), built against the framework (`sample/framework.mjs`, whose entry listing what it provides is generated from the Bloom checkout's exports at each build and never tracked; what a framework provides is its `framework.json`), signed with a development key, and compiled with the runtime's `hermesc` through the install service's own code (`oxyos-pack compile`). Their entries are the ones the install service writes (`oxyos-pack entry`, its `entry_text`). The probes stay one development bundle. Stash's entry names where the image will carry its package and is not installed: Stash has no OxyOS build yet.
   - **Scenarios** run on runtimes and packages (`regress.py --runtimes DIR --packages DIR`), and every one of them passes as before (the lock screen's and the 120 Hz drag's timing bounds also fail on the one-bundle build at this load, and `terminal` needs `--uinput`). `installed-application.json` (1600×1000 at 1.25) runs on an install service's state written for the run (the development compositor's `--installed-fixture`, taken as the service's): Launchpad finds the installed Inbox, whose id the development registry also has, and Return starts the installed version, given no `settings` although its entry asks for it. Without the installed state, the development entry starts and the run fails; given `settings`, it fails too.
   - **Tests:** the runtime's layout and refusals, `X-OxyOS-Runtime`, the runtime's host, a package's script URL, not installed, the policy's host against the runtime's; the three sources' order and refusals, an installed launch's origin, decisions and grants, its reaping; the watch over sources not there yet; the scene's windows shown; the session's holds, notes and release of a version's last process; `oxyos-pack` (a package's files listed and signed, the system's refusals refused here, compiling through the install service's code, the canonical form).
   - **Not yet:** the image (the policy naming Settings, the shell and the login screen as packages under `/usr/lib/oxyos/apps/<id>/` beside their entries in `/usr/share/oxyos/applications`, and the runtime under `/usr/lib/oxyos/runtimes/`), which waits for the session in the image (ADR 0023, step 5); the per-application Oxy identity of a verified launch (ADR 0020, decision 6).
4. **The system sheet, `store` and `OxyOSStore`.** `RequestInstall` and its answer in the protocol and the C ABI; the shell's install, uninstall and consent sheets; the host module; capabilities enforced by the host's modules (`network` in `oxyos-net`, `files`, `notifications`), with Expo's permission APIs mapped onto them. Scenarios: an install confirmed and refused; a press that was not the person's refused; an undeclared capability absent. With them, Settings' *Software Update* page (decision 16): the `updates` grant, `OxyOSUpdates` over `oxyos-installd`'s one update state, *Check for updates*, the list with sizes and what is new, *Update All* and *Update*, consent for new capabilities through the sheet, and the same state on Atlas's *Updates*; the OS's row as decision 16 says until the image-update ADR exists. Scenarios: one check from Settings shows an application's update in Settings and in Atlas; updating it in one removes it from both; an update with a new capability asks the sheet and updates only once consented; two pages asking at once make one check.

   *Done* in part; what remains is said.
   - **Grants.** `store` (Atlas), `updates` (Settings and Atlas) and `privacy` (Settings) are system grants of the image's policy, read strictly, carried by launch records into the scene; the development compositor gives them by `--grant ID=GRANT,...`.
   - **The protocol and the C ABI.** One vocabulary for what the store, Settings and applications ask, rather than a request each: `SystemRequest` (JSON in chunks, citing an input the client received) answered by `SystemText`; `SheetText`, `SheetAnswer` and `SheetDismissed` for the shell's sheets; `RequestCapability` and `CapabilityResult`. The scene checks the grant and notes the input; it sends a sheet to the shell alone, never while locked, and accepts an answer only from the shell citing an input the shell received. The session reads the vocabulary strictly (`oxyos_compositor::installs::Ask`, unknown keys refused), checks each request's grant, and refuses what changes anything without an input.
   - **The session's side,** `oxyos_compositor::installs`, in the session and the development compositor (`--installd SOCKET`): each request on a thread with a connection of its own, so the compositor's turn never waits; install after the sheet; removal after the sheet, the account's data removed as the account (never the home itself, never outside it); updates with each new capability's consent asked in turn; Privacy's list and decisions; opening; the update state watched once and told to every client with `store` or `updates`. `oxyos-installd` gained `decide`. Its threads stop and are waited for when it goes.
   - **The Bloom host:** `OxyOSSystem` (requests citing the latest press, sheets, capabilities, what the launch may use); `fetch` and `XMLHttpRequest` refused to an installed version without `network`; `OxyOSNotifications` refusing posts without `notifications`; expo-notifications' permission requests asking the session, denied as Expo says it.
   - **The shell's sheet** (`apps/shell`: `SystemSheet`, `sheet.ts`) over everything but the lock screen, on the display with the dock, Cancel first; **Settings' *Software Update* and *Privacy*** (`apps/settings`), Spanish and English.
   - **Tests:** the scene's (who asks, the input noted, the sheet the shell's alone and accepted only with its input, nothing while locked, capability requests); the session's side over a service of the tests' own (an install committed only once the sheet is accepted, removal and data, consent, the vocabulary's strictness, data directories only under the home); `decide`; the policy's grants; the host's launch environment; the shell's and Settings' models. `scenarios/store.json`: a store probe's install, check and status cross the host, the compositor and the session's side and come back, the service absent and said so.
   - **The store's vocabulary names an application by its id or its listing** (`install {listing}`, `status {listings}`), which the session resolves through the install service. When the person asked for a change (install, removal, update) and the install service is not there, the shell's sheet says so with one button (`unavailable`), and the store is told the person was told (`told`), so it says nothing more.
   - **Left:** scenarios with a running `oxyos-installd` and a repository holding a real package (an install confirmed and refused in the sheet, the dock showing it, removal, Software Update and the store probe showing one state, a consent, a permission asked at first use), which need a tool to publish a package into a test repository; the scenario of a press that is not the person's confirming nothing.
5. **The store's backend, in oxy** (its ADR and PRs, decision 12): identities and keys, releases, files, capabilities, installs, the TUF repository and its keys, review, `oxy-ship oxyos`, the Console's *Releases*, the reads in `@oxy.so/core`, the installer seam.
6. **Atlas on OxyOS, in Atlas** (decision 14): its OxyOS build, *Get*, *Open*, *Update*, *Updates*, *Purchased*, capabilities on the page.

   *Done* in part.
   - **The installer seam** is `@oxy.so/core`'s (7.10): `setStoreInstaller`/`getStoreInstaller`, by a listing's slug, with the account's updates and errors that say whether the machine already told the person (OxyHQ/oxy#2037; oxy ADR 0053's sketch without its `platform`, decision 9's "never asks which platform").

## Not in this decision

- Confining applications by the kernel (#35, #36), and the per-application Oxy token (ADR 0020, decision 6; Oxy ADRs 0029, 0045 and 0050).
- Paid applications, purchases and in-app purchases, subscriptions, family sharing.
- A native-extension ABI for packages.
- Binary deltas, staged rollouts by machine, crash reports.
- Web applications installed from Astro.
- Managed machines (an organization's policy, MDM).
- The OS's own updates, which are ADR 0023's images.
