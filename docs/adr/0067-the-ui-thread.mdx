# ADR 0067: The UI thread

Status: **accepted; being implemented**, a pull request a step ([Steps](#steps)). An explicit adaptation of React Native's own threading on Android ([React Native's Android implementation on OxyOS](../react-native-android-adaptation)), for the Bloom host (`tools/rn-host-spike`). Builds on [ADR 0003](./0003-accessibility-protocol) (the accessibility tree), [ADR 0018](./0018-several-displays) (each display's refresh), [ADR 0031](./0031-gpu-buffers) (the host's painter), [ADR 0039](./0039-keyboard-access) (keyboard access and the order of focus), [ADR 0042](./0042-scrolling) (scrolling) and [ADR 0046](./0046-interactive-gestures) (gestures). [ADR 0066](./0066-quality-of-service)'s per-thread priority names "the host's thread that commits frames": that is the UI thread.

## Problem

The Bloom host ran JavaScript, Reanimated's worklets, Animated's native driver, scroll physics and gestures, mounting, drawing and presenting on one thread. Whatever JavaScript did held everything else up: on seldon (10 November 2026, the development compositor at 60 Hz), JavaScript held for 500 ms left a gap of 504 to 516 ms in a native-driver animation, in a Reanimated animation and in a touchpad's glide alike (the glide drew 10 frames instead of 39, then jumped to its end). Every slow render (Dropsea's list view takes 130 to 157 ms on the ThinkPad) froze whatever was moving in its window.

A Mac's applications commit their layer trees to a render server, which runs their animations whatever their main thread does, and its scroll views go on scrolling while the main thread is busy (AppKit's responsive scrolling). React Native on Android and iOS keeps a smaller version of the same split, the one its libraries are written for: JavaScript on a thread of its own; the native driver, Reanimated's UI runtime, native scroll views, gestures and the mounting layer on the UI thread. A busy JavaScript stops only what JavaScript drives.

## Decision

1. **Two threads, as Fabric is designed.** The host's loop, on the process's main thread, is the **UI thread** (`ui-thread.h`); React Native's runtime runs on the **JavaScript thread**, `oxyos-js` (`js-thread.h`), React Native's `MessageQueueThread` and its `PlatformTimerRegistry`: a task runs as soon as the thread is free, a timer fires on it when it is due, and it sleeps when it has neither. The loop never waits for JavaScript.

   | UI thread (the loop) | JavaScript's thread |
   | --- | --- |
   | the compositor's events, input routing, hit testing, the frame clock (the display's refresh, ADR 0018) | Hermes, React's renders and handlers, its effects |
   | scroll physics, the touchpad's glide, overscroll and scrollbars; gesture handlers' recognition | Fabric's commits of React's trees, with their Yoga layout and the text they measure |
   | Animated's native driver (`NativeAnimatedNodesManager::onRender`) | Animated's operations as JavaScript sends them (queued for the UI thread, as React Native's C++ module queues them) |
   | worklets' UI runtime and Reanimated's frames (`performOperations`), its commits | `runOnUI` and `runOnUISync` (worklets' own: a job for the UI thread, or the UI runtime's lock taken) |
   | mounting every commit, drawing (Skia), presenting; popups, shell regions, modals | timers, `requestAnimationFrame`'s callbacks, device events, promises the host resolves |
   | the accessibility tree, published from the mounted tree; text editing; the window | the host's modules' methods (holding the UI thread's state, decision 4) |

   The runtime is made on JavaScript's thread, so Hermes' sampling profiler samples it and its stack guard bounds it; the thread has the main thread's stack size (8 MiB) and the crash report's alternate stack. A fatal signal names the thread it hit (`oxyos-js`, or the loop's, named after the executable).

2. **Commits are mounted as Android's mounting layer mounts them** (`Mounter`). A commit's transaction is pulled on the thread that made it, once it is to be rendered: on JavaScript's thread at the end of the task that committed (React Native's rendering update), so that a layout effect's commit is shown with the commit before it; on the UI thread at once, for a commit made there. It is handed to the UI thread in one queue, in the order the coordinator gave the transactions, and the loop applies the queue once JavaScript is idle, has answered the keys typed together (decision 6) and has been handed what came for it meanwhile (a press, a key, a scroll, an input method's candidates), all it ran shown together as when the two took turns, or, for that, once what it did has waited a refresh, then reports each mount (React Native's mount hooks: Reanimated resumes its commits there). A call JavaScript makes into the host that reads the tree as JavaScript left it applies the queue first, its state held (decision 4), as when each task's commits were mounted as it ended: a drag's image is of the item its press just selected. A transaction pulled to be applied later keeps its surface's transactions pending (`hasPendingTransactions`) until the last is applied.

3. **An accessibility event goes behind the commits made before it; a view command, before them.** An accessibility event (`AccessibilityInfo.sendAccessibilityEvent`) goes into the same queue; one that comes while a commit made before it is not yet handed over waits for it, as Android's mounting layer runs its `SendAccessibilityEventMountItem` behind the mount items queued before it (ADR 0039, decision 26: a menu bar's title focused by the commit that asks for the keyboard). A view command (a text input's focus or blur, a scroll view's `scrollTo`) runs before the transactions waiting, as Android's `MountItemDispatcher` runs view commands first: JavaScript sent it against the views as they are, which the transactions after may remove (a focused field blurred as its popover closes); one for a view not mounted yet runs again once they are applied, as Android retries it.

4. **The host's state is the UI thread's, and has one lock.** The view tree, the window and its surfaces, popups, accessibility, text editing and every service the host's modules reach are the UI thread's. The loop holds `UiThread::Lock` while it works and lets it go while it sleeps and whenever it waits for another thread (`runOnQueueSync`, `waitIdle`); a module's method holds it while it runs on JavaScript's thread (`HostModule`, `UiLocked<>` for a codegen module, and making a module), so the two never touch that state at once. JavaScript running holds nothing: only its calls into the host do, each for as long as the call. Nothing holding the lock waits for JavaScript.

5. **How events cross.** From the UI thread to JavaScript, everything goes through one hand-over (`ToJavaScript`): what the loop dispatches to views (input, layout, a scroll, an image loaded) through Fabric's event queue, whose beat JavaScript's thread induces; device events; `requestAnimationFrame`'s frames, begun by the UI thread's frame clock; a key to answer; the modules' answers, through their call invoker. Each is a task of the loop's on JavaScript's thread, and the loop hands them over at the end of a turn, and only while JavaScript is idle (a key offered, first: decision 6): what came while JavaScript worked reaches it together, as a turn's work did when the two took turns, and React batches what it changes into one render. A state JavaScript is told whole (the session's preferences, the displays, the window's size, the editing state, the input method's candidates, a "read again" signal) and not yet delivered is replaced by the newer, keeping its place, as Fabric coalesces a unique event. Fabric's beat is induced by the loop alone, at the end of its turn: a turn of the compositor's, read whole (`TurnEnd`, ADR 0033, version 41), reaches JavaScript in one batch, never split between two of its stretches; JavaScript's thread wakes the loop as it settles with a beat asked for (what applying its work dispatched). From JavaScript to the UI thread: each hand-over (a commit, a command, a worklet's job, Animated's frames starting, a frame callback asked for, the thread settling with the loop's work waiting) wakes the loop, which polls an eventfd beside its other descriptors. Events keep their order within each direction; across directions nothing is ordered but what decisions 3 and 6 order.

6. **A key offered to JavaScript waits for its answer, without holding anything else up.** A key press is offered to JavaScript first (Bloom's menu shortcuts, ADR 0021). The offer runs on JavaScript's thread as soon as it is free, before what is queued there, as the loop asked JavaScript for each key's answer in its turn; the key, and every event of the compositor's after it, wait for the answer in the order they came, as a browser holds key events behind the one its page has not answered, while the loop goes on animating, scrolling and drawing. A key JavaScript took, and its release, go no further. Keys typed together are answered back to back, the offer's task waiting for the loop to offer the next key held behind it (`KeyBurst`, at most 50 ms), their microtasks run after the last, and what JavaScript did with them is rendered and shown together once it has answered the last, as when the loop handled a turn's keys before JavaScript rendered: eight arrows typed at once move a list's selection once, said once, and a quick Super+Tab never flashes the switcher it opened and closed.

7. **A scroll view's offset is the UI thread's.** The touchpad's glide, the wheel and the keyboard's scrolling move the offset on the UI thread, which commits it at once (Fabric's immediate state update) and mounts it, as an Android `ScrollView`'s offset is its view's: the list is drawn at it that frame, however busy JavaScript is. JavaScript hears it as `onScroll`, and Reanimated's scroll handlers and Animated's native events take it on the UI thread as it is dispatched.

8. **A resize's first frame carries the new layout; a live resize waits for JavaScript only as long as a refresh.** A window resized is laid out at its new size on the UI thread, the layout's events handed to JavaScript at once; the window presents nothing new until JavaScript has run all of it and what that set off (its thread idle, and what it committed applied). The first frame of a resize (a zoom, a size set, a live resize's start: configures after a pause) waits for that however loaded the machine, at most a second, as long as a hold, so it never shows the window at its new size without what JavaScript lays out there (a sidebar's text); the frames of a live resize after it wait at most a refresh, so a slow application never holds the resize past the display's next refresh. JavaScript's thread wakes the loop as it settles.

9. **The accessibility tree is the mounted tree's.** The UI thread builds and publishes each surface's tree from the views it mounted; JavaScript's accessibility focus moves are handled behind the commits made before them (decision 3), and its announcements (`announceForAccessibility`) are said at once, as on the one thread, unless what it did in an earlier batch is still held back (decision 2): then behind that work, once the frame showing it has published it (a focus a press moved, then what JavaScript announced as the session answered); an assistive technology's actions are handled on the UI thread and reach JavaScript as events (`onAccessibilityAction`, through Fabric's beat). The assistive technology is told what a turn of the compositor's did once all of it is handled: while a key of it waits for JavaScript's answer, the window's tree waits with it (an input method's commit and the Space it gave back said as one, "한"), at most 100 ms, as long as Android holds a window's content changes. A busy JavaScript delays what it answers, never what the tree says of what is shown.

10. **Each thread's work is measured on its own clocks** (`frame-diagnostics.h`). The UI thread's frames are what a refresh holds: a frame is slow when the UI thread's work (events, laying out, animation, mounting, drawing, presenting), with its wait beyond a refresh, passes a refresh. JavaScript's work comes in stretches, each in the report (`js_timing`) and said in the log when it passes a refresh, with the frames the window presented meanwhile; each frame line counts JavaScript's work since the frame before. An input is timed to the frame that shows JavaScript's answer: the first presented once JavaScript has run what the input's turn handed it and the loop applied what that committed; one that handed it nothing, to the next frame.

11. **Bloom is unchanged.** Its APIs, its components and its layout engine are untouched; nothing of OxyOS's is in Bloom. React Native's, worklets' and Reanimated's own C++ run as their Android builds run them: the UI scheduler says which thread is the UI thread, worklets' `JSScheduler` runs a job at once only on JavaScript's thread, Animated's manager steps on the UI thread.

## Consequences

- JavaScript's handlers answer a turn later than the input in the worst case, as on Android and iOS; nothing a person watches waits for them. A key's answer is waited for in order (decision 6), a press's in the frame that shows it. Text typed faster than JavaScript answers each key reaches its field a key or a few at a time, each shown, and echoed by the screen reader, as the field takes it.
- JavaScript reacts sooner than it did, so what reaches it a moment apart can reach it in two batches where one long turn gathered it before. What the session tells as a whole is coalesced (decision 5), and what may have changed is told only when it did: Settings' applications, which the registry's watch says may have changed whenever a file beside them is written (a preference kept), are told again only when their listing differs. A drop target is told the drag left it together with the drop, once the drop's content has arrived, so what it starts as the drag leaves (the dock's gap closing on a spring) and what it does with the drop (the icon in the gap at once) are one batch: a frame of the UI thread's never falls between them.
- The compositor's ping (ADR 0034, decision 3) is answered as the UI thread reads its events: an application whose JavaScript is stuck goes on animating and scrolling, and is not said to be not responding until its loop is stuck too. Whether the answer should follow JavaScript (a step below) is the hang detection's decision.
- A module's method that blocks (a synchronous file read, ADR 0028) holds the UI thread's state as long; those that reach no state of the UI thread's may be made to hold none, a module at a time.

## Checks

- **`stall.json`** (`sample/StallProbe.tsx`): JavaScript held 500 ms while a 3 s native-driver `Animated.timing` runs, while a Reanimated `withTiming` runs, and 30 ms into a touchpad's glide: the frames go on through the block, and each motion's own (the native driver's props, Reanimated's commits mounted, the glide's offset); every run holds half the block's refreshes drawn and no gap of 6 refreshes. **`perf-stall.json`**, the same in the gate's timing phase, holds a frame each refresh: the gaps' 95th percentile within 1.5 refreshes, none over 2 (`regress.py --speed-budgets`).
- **`frame-diagnostics.json`**: a press whose JavaScript holds its thread 120 ms is said as JavaScript's stretch, not as a slow frame, and its answer's frame is timed from the press; every run of every scenario checks each thread's diagnostics against its report (`check_diagnostics`).
- The whole gate: input, focus, accessibility, text and input methods, unchanged. The scenarios that force an order (`host_order` focus-first, grant-first, window-focus-first: ADR 0039, decisions 26 and 27) apply what JavaScript hands over only once it is idle, after everything it ran with its commits, as the two took turns.
