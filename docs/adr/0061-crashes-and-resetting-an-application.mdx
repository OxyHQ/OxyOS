# ADR 0061: Crashes and resetting an application

Status: **accepted; implemented** (the session's side, the Bloom host's report, the shell's notification and sheets, the scenarios); Settings' *Reset…* in Storage's list of applications waits for Settings › General › Storage ([ADR 0059](./0059-storage)), step 5. Decided on 8 November 2026, at the platform author's request for macOS's parity "done from the root". Builds on [ADR 0013](./0013-launching-applications) (launch records), [ADR 0015](./0015-application-model) (an application never draws the platform's), [ADR 0026](./0026-notifications), [ADR 0030](./0030-installing-applications) (an application's data, decisions 6, 8 and 11; the session's vocabulary over `SystemRequest`), [ADR 0050](./0050-keychain-autofill-and-passkeys) (the keychain) and [ADR 0058](./0058-the-platform-api).

## Problem

An application that crashed on OxyOS vanished: its window went, the session wrote `exited` to its log, and nobody told the person anything. A JavaScript error nothing caught did not even end it: the Bloom host logged `[js exception]` and kept a window whose React tree the error had unmounted, drawn by nothing. An application that crashed at every launch (its preferences corrupted, the most common cause of a crash loop on a Mac) could only be fixed by finding and deleting `~/.local/share/oxyos/apps/<id>` in a terminal, and the session's own shell crashing ended the whole session, every application with it.

A Mac has:

- **The crash reporter.** *“Mention” quit unexpectedly.* with *Ignore*, *Report…* and *Reopen*, after every crash, whatever the person was doing; *Report…* shows the report (`~/Library/Logs/DiagnosticReports`) and sends it to Apple. It nags: the same alert for the tenth crash as for the first.
- **Resetting** an application's preferences: no button. The person deletes `~/Library/Preferences/<bundle-id>.plist` and `~/Library/Containers/<bundle-id>` in Finder, or uses a third-party cleaner. iOS has *Offload App* and deleting the application, which loses the application too.
- **launchd** starts the Dock, the menu bar and Finder again when they crash, and logs the person out when the window server does.

Android shows nothing for a first crash since Android 9, and *“Mention” keeps stopping* (*App info*, *Close app*, *Send feedback*) only when it crashes again soon after; *Clear storage* resets an application in its settings.

## Decision

1. **An application quits unexpectedly when it ends on its own and fails.** The session started it (ADR 0013), so the session reaps it and knows how it ended: a process that exits with a status other than 0, or is ended by a signal, is an unexpected quit, **unless the session asked it to end** (the person's force quit, a quit before a reset, a file chooser whose request ended, the session ending; `Launcher` notes each one it signals, `Exited::asked`). An exit with status 0 is the application quitting itself (its last window closed). A process the session did not start (a development compositor's own application, a client of another socket) is nothing of this.

2. **The Bloom host says why it ends, into a file the session gives it.** Before it starts a process (an application, its shell), the session makes an empty file the user's alone (0600) in a folder of its own in the runtime directory (`$XDG_RUNTIME_DIR/oxyos-PID-reports`, 0700, gone with the session) and names it in `OXYOS_CRASH_REPORT` (`oxyos_apps::ReportFile`). The host opens it as it starts, before anything can fail (never making it, never following a link), and writes into it only as it ends for a fault:
   - **A fatal signal** (`SIGSEGV`, `SIGBUS`, `SIGILL`, `SIGFPE`, `SIGABRT`): the signal, the address or sender, the thread, the registers and the stack, as its handler already wrote them to the log, now to both with `dprintf` into descriptors already open (async-signal-safe); then `_exit(128 + signal)`.
   - **A fatal JavaScript error** — React Native's (`isFatal`, by its C++ error handler or `ExceptionsManager.reportException`, and `reportFatalException`): its message and stack, then the host **ends** (`_exit(70)`, sysexits' `EX_SOFTWARE`), as a release build of React Native ends on Android and iOS. A window whose tree an error unmounted is never left on the screen. Soft exceptions and warnings are logged, as before.

   The session reads at most 32 KiB of it (a line says when more was cut) as it reaps the process, and removes it. Any program the session starts may write its own: a native client's report is its own business.

3. **The person is told once, and the more it matters the more it asks.**
   - **The first unexpected quit** of an application in ten minutes is a **notification about it**: posted by the session as the application's (its icon and name in the banner and the Notification Center), *“Mention” quit unexpectedly*, with *Reopen* and *Report…*, no sound. Pressing it is Reopen. It nags no one: it goes by itself, and a background application or one at login quitting tells the person without taking their keyboard. The scene keeps it as the session's own (`post_session_notification`): pressed, the session is told (`take_session_activations`) and the application nothing; only the session and the shell withdraw it. (ADR 0026, amended below.)
   - **A second within ten minutes** ([`REPEATED`]) is the **system's sheet**, `crash`, at once, in the notification's place: *“Mention” keeps quitting unexpectedly*, *It quit 2 times in the last 10 minutes. If it keeps quitting, resetting it may help.*, and *Reopen* (the answer, which the keyboard starts on, as a Mac's default button: Space presses it), *Ignore* (Escape), and at its foot's start *Reset…* and *Report…*. Each further quit within ten minutes of the one before is the sheet again; one sheet for an application at a time, a quit while it asks only reported.
   - Every application the session launched is told so: a system one, an installed one, a development entry. The login screen launches nothing; the shell is decision 6's.

4. **Reports stay on the person's computer, in their hands.** Each unexpected quit writes a report, in English as every system's are: what quit (its name, id and kind: a system application, an installed version, a development entry), when, after how long, why (*signal 11 (SIGSEGV)*, *exit status 70*), how many times in ten minutes, the system (`/etc/os-release`'s name and the kernel's release), then what it reported of its end. It is written to `$XDG_STATE_HOME/oxyos/crash-reports/` (`~/.local/state`), the folder 0700 and each file 0600, as `<id>_<YYYY-MM-DD-HHMMSS>.crash`; at most ten are kept for an application and fifty in all, the oldest going first. **Nothing is sent anywhere**: OxyOS has no report service and asks for no consent to one. *Report…* shows the report in the sheet itself, its text selectable, with *Copy*, which puts it on the clipboard at the person's press (ADR 0007), and *Done*; the person shares it themselves (a developer's issue, an email), and the file is where they can find it.

5. **Reset erases the application's own data and keeps everything else.**
   - **The application's own data** is defined once, `oxyos_apps::data::OwnData`: its data directory (`$XDG_DATA_HOME/oxyos/apps/<id>`, Expo's document directory, its AsyncStorage's `async-storage.json`, anything it keeps there) and its cache directory (`$XDG_CACHE_HOME/oxyos/apps/<id>`). It is what Reset erases, what Storage counts for it (ADR 0059) and what an uninstall removes (ADR 0030, decision 11, amended below). Its notifications in the Notification Center go too (what they spoke of is gone with its data).
   - **Kept, because they are the person's, not the application's:**
     - *Their documents and files*, anywhere: Reset touches nothing outside the two directories, and a link inside one is removed as a link, never followed.
     - *Their keychain* (ADR 0050): a credential associated with the application was saved by the person, at their yes, in their vault, which is synchronised with their other devices; erasing it on one computer would erase it everywhere, and no application reads its items (it is only offered them in its fields), so they cannot be what makes it crash. iOS keeps an application's keychain items when it is deleted, for the same reason.
     - *Their decisions about it*: its capabilities granted or refused (ADR 0030, decision 8, kept by the install service, revocable in Settings' *Privacy*), the dock, *Open at Login*, its notifications' sound (`oxyos-preferences`): choices the person made in the system's own sheets and pages, which no application can corrupt.
     - *Its crash reports*: the person's record, which the Report of a reset application's next quit is read against.
     - *The application*: its install, its version, its entry.

     A window's place is not kept by the session for an application yet; when it is, it is the application's own state and Reset erases it.
   - **The session resets, never Settings or the shell themselves.** `{"resetApplication": {"id": ID, "reopen"?: bool}}` in the session's vocabulary (no new protocol message), from the shell (`shell`, its notice's *Reset…*) or Settings (`settings`, its Storage), citing the person's input; refused `notPermitted` from anyone else, from an application about itself (its asking would be cut short), and at the login screen; `needsInput` without an input; `notFound` for an id the registry does not list (the shell, the login screen, a path); `busy` for one already being asked or reset. The session asks the person in the system's sheet, `reset`, which no application can draw or press: *Reset “Mention”?*, *Mention's data and settings on this computer will be erased, and it will open as new. Your documents and files, and your passwords, are kept.* (and *Mention will quit first.* while it runs), *Cancel* and the destructive *Reset*, no key answering it. Refused, the asker is told `{"refused": {"reason": "cancelled"}}`.
   - **Accepted, it quits first, then is erased whole or not at all.** The application is held (`Launcher::hold`: nothing starts it, however asked: the dock, a notification, a file opened, a login item); every process the session started for it, by its launch records and never by a name, is asked to end (SIGTERM, `Launcher::quit`) and, after three seconds ([`QUIT_GRACE`]) on the session's clock, ended (SIGKILL). Once none runs, each directory is renamed into `.erasing` beside it (no id begins with a dot), the cache first and the data last, whose rename is the moment it is reset: a crash or a power cut at any point leaves the application as it was or reset, never half of it. What was set aside is deleted off the session's turn (a large cache takes time), and whatever a crash left in `.erasing` is deleted at the next session's start (`oxyos_apps::data::sweep`); a `.erasing` that is not a folder of its own is never looked into and nothing is set aside into it. The asker is told `{"reset": {"id"}}` (or `{"failed": {"reason"}}`, the data left where it was); from the notice (`reopen`), the application is opened again, as new; its count of quits starts over.

6. **The shell and the login screen are started again, never in a loop.** The shell is the session's own program (ADR 0009): when it ends with a failure, or while the session is locked, the session starts it again (its report written, as an application's, never notified: the shell is what would show it) — at once the first time, then after a wait that doubles each time it fails again without having run a minute, from one second to at most a minute ([`ShellRestarts`]), and never given up on. Every application goes on running meanwhile (until now the session ended with them). Locked, the session stays locked under the compositor's covers until the shell is back and shows the lock screen (ADR 0010: it fails closed). A shell that ends with status 0 while unlocked still ends the session, as before. The login screen is the shell of a locked session (ADR 0020), and is started again the same way: never faster than a doubling wait.

## Steps

1. **The session learns how a launch ended.** `Launcher::reap` gives each `Exited` (its status, how long it ran, whether the session asked it to end, its report); `quit`, `kill`, `runs`, `hold`, `release`; `ReportFile` and `OXYOS_CRASH_REPORT`; the Bloom host's report and its ending on a fatal JavaScript error (`crash-report.h`).

   *Done.* `oxyos-apps`'s `Exited`, `ReportFile`, `REPORT_BYTES` and `Launcher::with_crash_reports`; `tools/rn-host-spike/crash-report.{h,cpp}` (`openCrashReport`, `crashReportFd`, `endForFatalJavaScriptError`), the fatal signal's handler writing into the report too, and both of React Native's error paths (`ReactInstance`'s `JsErrorHandler` callback, `ExceptionsManager`) ending on a fatal error.

2. **Reports, the notification and the sheet.** `oxyos_compositor::crashes`: `Counter`, `report_text`, `Reports` (written, bounded, listed), `Crashes::exited`; the scene's session notifications (`post_session_notification`, `take_session_activations`, `withdraw_session_notification`, `withdraw_application_notifications`); the shell's `crash` sheet with its report view; `oxyos-session` and the development compositor serving it.

   *Done.* As decision 3 and 4 say; the shell's `sheet.ts` (`crash`, `reset`, `actions`, `report`, `focusAnswer`), `SystemSheet` (a wide sheet with its other buttons at its foot's start, the report shown in it, Escape and *Done*), `Shell` putting the keyboard on Reopen (`focusTarget`), `ShellProbe` asking for the reset and copying the report through `OxyOSClipboard`.

3. **Reset.** `oxyos_apps::data` (`OwnData`, `set_aside`, `SetAside::delete`, `sweep`, `bases`); `resetApplication` in the session's vocabulary, its sheet, the quit and the erasure; the shell's *Reset…*.

   *Done.* `Crashes::handle` and `Crashes::serve` (the requests, the sheets' answers, the notifications pressed, the resets waiting for their application to quit, `deadline` waking the turn).

4. **The shell started again.** `ShellRestarts` in `oxyos-session`, a report for the shell, the shell's `ReportFile`.

   *Done.*

5. **Settings' Reset.** In Settings › General › Storage's list of applications (ADR 0059), each row's detail offers *Reset…*, which asks the session (`resetApplication`) with Settings' grant, citing the press; the session's sheet confirms it. Its sizes are `OwnData`'s, one definition.

## Tests

- **`oxyos-apps`** (4): an exit the session did not ask for that failed is abnormal (status 3, a signal, a fatal JavaScript error's report and status 70; status 0 and a quit or a force quit never), a report past its bound cut and said so, every report file gone once read, `quit` ending every process of an application by its launch records, `kill` only what it started, a held application not started; erasing setting an application's own directories aside and nothing else (another application's data, a link to the person's documents inside it not followed), nothing to erase no error; a crash's leftovers swept at the next start, a `.erasing` that is a link only unlinked, never looked into, and nothing set aside into it; an application's own data its two directories.
- **`oxyos-compositor`'s `crashes`** (10): quits counted within ten minutes; a report's text (a signal, an exit status, what it reported or nothing); reports private (0700, 0600), named by id and time, a second at the same second beside the first, at most ten for one application and fifty in all, the oldest first; asked exits and status 0 nothing, the first quit a notification as the application's with Reopen and Report… and nothing more, which the application cannot withdraw, the second within ten minutes the sheet at once in its place, with its report and file, and a third while it asks only reported; the notification's Report… the sheet at the report, no application told anything; Ignore opening nothing, an acceptance citing no input of the shell's no answer, Reopen opening it once, a quit long after a notification again, its press reopening it; who may reset (the shell and Settings with an input; not another grant, not without an input, not at the login screen, not the asker itself, not an id the registry does not list or a path, not a request with more in it), the sheet saying whether it runs, a second request meanwhile busy; a reset refused (cancelled, nothing touched), then accepted from the notice: both processes asked to quit, nothing started meanwhile, its data and cache gone and another's kept, its notification withdrawn, the shell told and the application reopened, its count started over; an application ignoring SIGTERM ended after `QUIT_GRACE` and then reset; the shell's waits (0, 1, 2 … 60 s, starting over after a minute); the notification in Spanish.
- **The scene** (`scene/tests/notifications.rs`): the session's own notification shown as the application's with its actions, the application told nothing and unable to withdraw it, an action and the notification itself pressed told to the program once and never to the application (no response, nothing started), the application's own withdrawn on a reset and the session's kept until it withdraws it.
- **The shell** (`tests/sheet.test.ts`, 3): the `crash` sheet's words, answer, Ignore, actions and report in English and Spanish; at the report, of a quit that happened once; the `reset` sheet destructive, saying what is erased and kept, and that a running application quits first.
- **Scenarios**, with `so.oxy.crashprobe` (`sample/CrashProbe.tsx`: an installed application that reads its AsyncStorage as it starts and, when that cannot be read, ends with a fatal JavaScript error; its storage file corrupt in the run's home): `app-crash` and `app-crash-scaled` (opened from the dock, it quits: the notification once, its banner's Reopen opening it again; it quits again: the sheet once, the keyboard on Reopen; Report… shows what it reported, Copy puts it on the clipboard, Done goes back; Reopen opens it again and the sheet comes back; Ignore leaves it closed; each step's exact deliveries, the reports written in the run's state folder), `app-reset` and `app-reset-scaled` (from the sheet, Reset… asks the session's own sheet; Cancel leaves its data; Reset erases its data and cache and nothing else of the home, and opens it again, now ready).

## Not in this decision

- **Sending reports.** OxyOS has no report service, and this decision adds no network path. A future one is its own decision: an explicit consent per report, its contents shown first, going nowhere by default.
- **Symbolised stacks.** A native crash's frames are offsets into the host's objects (its handler's `backtrace_symbols_fd`); symbolising them needs the build's unstripped objects, a developer's tool.
- **Processes an application starts itself.** A Bloom application has no other process. A native client's own children are not in the launch records: they are reached once each launch runs in a scope of its own (systemd's, ADR 0030, decision 15's confinement).
- **The window server crashing.** The session is the compositor: if it ends, the login program shows the login screen again (ADR 0020), as a Mac logs the person out.
- **Resetting the OS's own programs** (the shell, the login screen): they keep no data of their own beyond the person's preferences, which Settings changes.
