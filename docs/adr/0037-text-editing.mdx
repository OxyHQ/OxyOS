# ADR 0037: Text editing as on a Mac

Status: **accepted; implemented** (except what [Remains](#what-remains) lists). Builds on [ADR 0008](./0008-input-method) (input methods, the field's state and transactions), [ADR 0014](./0014-screen-reader) (the screen reader), [ADR 0021](./0021-menu-bar) and [ADR 0024](./0024-system-shortcuts) (Ctrl is the applications' ⌘, Super the system's), [ADR 0033](./0033-protocol-versions) (protocol versions). Key repeat is [ADR 0036](./0036-key-repeat).

## Problem

The owner's assessment: "Recibir texto compuesto no significa tener IME completo. Siguen faltando composición en curso, selección, cursor y otros comportamientos de edición." Receiving composed text is not a complete input method; a field must show a composition in progress, select, place and draw its caret, and edit as a Mac does.

React Native's `TextInput` on OxyOS is Android's component (its props, state and shadow node, built unchanged); the Bloom host (`tools/rn-host-spike/textinput.cpp`) plays Android's `EditText` and its input connection. So the reference for what JavaScript receives is Android's `InputConnection` as React Native's `ReactEditText` reports it, and the reference for what the person sees and types is macOS's `NSTextInputClient` and the Cocoa text system's key bindings.

## Decision

1. **Compositions stay the compositor's, from the proven engine.** Dead keys and compose sequences are xkbcommon's compose tables, as they were; nothing is hand-written. What the person sees follows a Mac: a dead key shows its accent as the composition (underlined), the next key replaces it with what they compose, Escape and Backspace cancel it, and **a key that composes nothing with dead keys types their accents and then itself** (´ then x types "´x", ´ then an arrow types "´" and moves), as macOS, Windows and GTK do (`Typed::Interrupted` in `oxyos-input`, two actions: the accents committed, then the key, which is the application's, press and release). A sequence begun with the compose key that composes nothing is cancelled, as GTK cancels it.

2. **React hears what Android's input connection makes it hear.** A composition is part of the field's text while it lasts, as Android's composing span is: `change` (and so `onChangeText`) fires with it, as `ReactEditText`'s `TextWatcher` fires for `setComposingText`, and `keyPress` follows `ReactEditTextInputConnectionWrapper` (a commit of one character is that key, a composition the character before its caret). The compositor is told the text without the composition (ADR 0008). Committing the composed character fires `change` once; cancelling, `change` back.

3. **A Mac's keys, with Ctrl as ⌘.** On OxyOS Super is the system's ⌘ and Ctrl the applications' (ADR 0024, decision 1; ADR 0021's `Mod`), so a Mac's ⌘ editing keys are Ctrl's and its ⌥ keys are Alt's:

   | Keys | Does |
   | --- | --- |
   | Alt+← Alt+→ | the word's start, the word's end (⌥←→) |
   | Ctrl+← Ctrl+→, Home End | the line's edges as drawn (⌘←→) |
   | Ctrl+↑ Ctrl+↓, Ctrl+Home Ctrl+End | the text's edges (⌘↑↓) |
   | Alt+↑ Alt+↓ | the paragraph's start or end, the one before's or after's when there (⌥↑↓) |
   | Alt+Backspace, Alt+Delete | deletes the word before, after (⌥⌫, ⌥⌦) |
   | Ctrl+Backspace, Ctrl+Delete | deletes to the line's start, end (⌘⌫, ⌘⌦); at the edge, one character |
   | Shift with any move | extends the selection |
   | Ctrl+A, C, X, V, Z, Shift+Z | select all, copy, cut, paste, undo, redo |

   Without Shift a move by word or line starts from the selection's side it moves towards. A secure field is one word. This replaces Android's Ctrl-by-word, which a Mac does with ⌥; Ctrl+Alt with an arrow stays the screen reader's (ADR 0014).

4. **The caret is crisp and blinks.** It is drawn on whole device pixels at the window's scale (its left edge at the device pixel nearest the layout's x, at least one device pixel wide), so at 1.25 it is as sharp as at 1. It blinks as Android's `Editor` does, 500 ms lit and 500 ms dark, lit anew at every change of the text, selection or composition, and rests lit once the field has waited 10 s (GTK's `cursor-blink-timeout`, which Chromium on Linux follows), so an idle machine is not woken twice a second; a selection does not blink. The host wakes only for the next change of the caret, and only the field is drawn again.

   Whether carets blink is the person's: `caret_blink` in the preferences (ADR 0019, on by default), told to every client at the end of `Preferences` (**protocol version 11**, ADR 0033: added at the end, a version 10 reader reads that carets blink; the C ABI's `OXYOS_PREFERENCES_STEADY_CARET`). The person turns it off in Settings, at Accessibility › "Prefer non-blinking cursor" ("Preferir cursor sin parpadeo"), where macOS 14 places its own: on is `caret_blink` off, and every running application's caret follows at once (`settings-caret-blink.json` and `settings-caret-blink-scaled.json`: a field of another application stops blinking and blinks again as the switch changes). Scenarios run with it off, as Chromium's tests run with no caret blink, since a blinking caret never lets a frame settle; `text-caret-blink.json` turns it on and counts the blinks.

5. **The caret's rectangle already reaches the compositor.** `TextInputCaret` (request 33, ADR 0008) carries it in surface coordinates with every change of the field, and the compositor places an input method's candidates next to it. No new request was needed; scenarios check the rectangle the compositor holds at 1 and 1.25.

6. **A field out of the key window keeps its focus, hides its caret and greys its selection**, as NSTextView does: the key window is the one the person's keys are for. An application's window is key while the compositor says it is the active one (`Activated`, ADR 0016), which it stays while the keyboard is on its own popups (a menu, which a Mac's key window keeps through) or on the shell's bar and its menus acting for it (ADR 0021); it is not key while another window, the launcher, an overlay of the shell or the lock screen has the keyboard (none of which leaves it active), nor while a file chooser's sheet it asked for has it (ADR 0029, decision 8), the sheet being key over its window as a Mac's sheet is over its main window. The shell has no window: its field is key while the keyboard is on the region it is drawn in or on one of its popups. Out of the key window the caret is not drawn and its blink stops (no wake-ups), and a selection is drawn in macOS's `unemphasizedSelectedTextBackgroundColor`, #dcdcdc in the light appearance and #464646 in the dark one, whatever `selectionColor` asks (NSTextView applies its selected-text attributes only in the key window). Back in the key window the caret is lit anew, as at any change. The field keeps its focus and JavaScript hears nothing, as an NSTextView stays its window's first responder and Android's `EditText` keeps its focus when its window loses it; only the field is drawn again.

7. **The screen reader says the editing** ([#236](https://github.com/OxyHQ/OxyOS/pull/236), ADR 0014): what is typed, what is deleted, what the caret passes over and what a selection takes or gives back, as TalkBack and VoiceOver say it, never for a secure field.

8. **A text field's context menu is the platform's, as on a Mac.** A secondary click on a text input, or a Control-click (a secondary click there, as a Mac takes one: its pointer events say button 2, and it is no touch), focuses the input if it has not, selects the word whose character is under the pointer unless the click is within the selection (off a word, past a line's end, or in a secure field, the caret goes there), and opens its menu at the pointer: **Undo, Redo — Cut, Copy, Paste — Select All**, each with its chord as the session shows it (Ctrl+Z, Ctrl+Shift+Z, Ctrl+X, Ctrl+C, Ctrl+V, Ctrl+A), in the session's language. A row that does not apply now is disabled, as `NSTextView` validates its menu: Undo and Redo with the input's history, Cut with a selection in an editable, non-secure input, Copy with a selection in a non-secure one, Paste in an editable input while the clipboard holds text, Select All while the input has text. A Mac's own menu has no Undo and Redo (its Edit menu has); Windows' and GTK's add them, and here they are where the person reaches for them. An input that takes no focus (`editable={false}`, as Android's disabled `EditText`) has no menu.

   **Where it lives: the platform, for every React Native `TextInput`, not Bloom's `TextField`.** A text field's menu is its platform's everywhere: AppKit's `NSTextView`, Android's `EditText` (its selection actions, which every React Native Android application has without a line of JavaScript) and a browser's `<input>` (Bloom on the web has none of its own: react-native-web's input gets the browser's). Bloom renders its fields on React Native's `TextInput` in dozens of places (`TextField`, `Textarea`, search fields, composers, tag and OTP inputs), and an application may use `TextInput` itself; a menu in `TextField` would leave the rest without one or be written again in each. So the host, which plays `EditText` (`textinput.h`), owns it: `TextEditing::contextMenu` focuses and selects, and asks for the menu with the input's bubbling `oxyosTextMenu` event (in the base view config, `BaseViewConfig.oxyos.js`), carrying the point in the input and which commands apply. The runtime wraps every application's root (React Native's `AppRegistry.setWrapperComponentProvider`, `sample/oxyos/framework-init.js`) in `TextFieldMenus` (`sample/oxyos/text-menu.js`), which hears that event from any input and draws the menu as the dock draws its own ([ADR 0034](./0034-the-dock), decision 1): Bloom's `ContextMenu` in the platform's popup, hanging from the input itself at the point (Bloom's `anchorRef`, 15.91.0, OxyHQ/Bloom#588: a controlled menu with no trigger, so a field inside a popup gets a child popup of it), announced as a menu, driven by Bloom's popup keys (arrows passing over disabled rows, Home, End, Return, Escape). A row chosen is a command to the input (`oxyosEdit`, through React Native's `dispatchCommand`), which the host performs exactly as the input's own key, citing the person's latest input (the row's press or key) for the clipboard ([ADR 0007](./0007-clipboard)). The input keeps its focus and selection throughout, and the keyboard comes back to it as the popup closes. The runtime's framework refuses a Bloom older than 15.91.0 (`framework.mjs`).

## Tests

- `oxyos-input`: a dead key then a key it composes nothing with types both, press and release the application's; an arrow after a dead key gets the accent and its move; Escape and Backspace cancel a dead key and reach no one; a compose-key sequence that composes nothing types nothing, Compose 1 2 types ½.
- `oxyos-protocol`: `Preferences` written for version 10 is version 10's bytes and read back with carets blinking; the C ABI's flag.
- The director types keys through the session's keymap and compose table (`strokes` steps, `Keyboard::actions`, `Compositor::apply_input`, the same path the seat's devices take), so a scenario types a Spanish keyboard's dead keys without virtual devices.
- `scenarios/text-editing-mac.json` and `text-editing-mac-scaled.json` (the same at 1.25), on the Spanish layout: each step checks the field's text and selection as React receives them, exactly the events React received, focus, and the field the compositor holds (its text without the composition, its selection, its caret's rectangle): ´ shown as a composition, é composed, ´ then x typing "´x", ´ then Escape cancelled, Shift+Alt+Left selecting a word and typing replacing it, undo and redo, Ctrl+Left, Alt+Right, Ctrl+Shift+Right, copy and paste through the clipboard, Alt+Backspace and Ctrl+Backspace, select all, a double and a triple click, a drag, Alt+Up and Alt+Down by paragraphs, Ctrl+Down and Ctrl+Shift+Up.
- `scenarios/text-caret-blink.json`: ten blinks after focus, ten again after a character, none for a selection.
- `scenarios/settings-caret-blink.json` and `settings-caret-blink-scaled.json` (the same at 1.25): Settings' "Prefer non-blinking cursor" pressed on and off beside another application with a field focused (the director's `companion`, whose frames now count when a step settles, so its blinks are counted whole): the switch's state, its node and its drawing, `caret_blink` told to both applications at once and kept in the preferences file, no blink in that field while it is on (a character typed lights a caret anew and still gives none), none when it goes off while Settings is the key window (decision 6), ten once the field's window is key again and ten again after a character; the exact React events of each application and the input the compositor delivered each.
- `scenarios/text-field-menu.json` and `text-field-menu-scaled.json` (at 1.25), on `sample/TextMenuProbe.tsx` (a Bloom field, a plain `TextInput` and a secure field) in Spanish, with a second application that must receive nothing: a secondary click on a word of an unfocused field focuses it with the word selected and opens the menu in a popup (the assistive technology's menu and rows, which are disabled); Down passes the disabled rows; Return copies (the clipboard's text), the menu goes and a key typed then replaces the kept selection; the plain `TextInput` gets the same menu with Paste enabled; Escape closes it changing nothing; a Control-click within the selection keeps it and opens the menu with no touch; Paste chosen with the pointer; a click past the text's end puts the caret there, Undo enabled and Cut and Copy not; Undo from the keyboard; the secure field with Cut and Copy disabled and Select All; Cut. Each step checks the text and selection React receives, exactly the React events, focus, the field the compositor holds and what each client was delivered.
- `scenarios/text-inactive-window.json` and `text-inactive-window-scaled.json` (the same at 1.25): PressProbe's field holds a selection and EditingProbe's, a second application beside it, a caret. A press in the other application's field activates it, as a click does on a Mac, and the shell's Super+Tab brings PressProbe back; each step checks that the window left draws no caret or its selection in grey and the active one its caret or its accent selection (pixels), exactly what both React trees received (the window left nothing), what each client was delivered, the input each holds focused and the field the compositor holds. PressProbe's context menu, open in a popup with the keyboard, leaves its selection in the accent colour. `scenarios/text-inactive-sheet.json`: a file chooser's sheet over the window that asked greys the selection of the window's field and hides its caret, the window still active, and its cancellation brings both back, the field hearing nothing.
- `scenarios/text-editing.json` moved its word steps from Ctrl to Alt; `text-selection.json`, `text-selection-scaled.json` and `text-input.json` pass unchanged. All of them are in the deploy gate.

## What remains

- **Input methods for Chinese, Japanese and Korean, emoji and handwriting.** The protocol, the role and the candidates popup exist (ADR 0008, steps 1 to 3), but no input method does: one is a separate service (a port of an existing engine's core), and the session has no way to grant the role yet. Until then OxyOS has dead keys and compose sequences only; it does not have a full input method framework.
- **Backspace in a compose-key sequence** cancels the whole sequence (xkbcommon's state cannot step back one key); GTK takes back the last key. A dead key followed by another dead key it does not compose with types the first accent and loses the second.
- **Dragging selected text** ([ADR 0035](./0035-drag-and-drop)), spelling and text substitutions are not built; the context menu has none of a Mac's Look Up, Spelling, Substitutions, Transformations, Speech or Services.
- **Astro** (Chromium, ADR 0029) keeps Chromium's Linux key bindings: Ctrl+arrows move by word there.
- **Home and End** go to the line's edges, as on Linux, Windows and in most Mac editors; a Mac's `NSTextView` only scrolls with them.
