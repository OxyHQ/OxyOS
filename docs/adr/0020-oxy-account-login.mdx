# ADR 0020: Signing in with an Oxy account

Status: **accepted** (decisions 1 to 7, chosen with the platform's author; decision 2 was the author's choice of the account's own password over a password of the machine, amended on 2026-11-08 by the owner's choice of the account's password, asked once, together with a PIN for the computer, [decision 2's amendment](#amendment-2026-11-08-a-pin-for-this-computer)); step 1 implemented; step 2 implemented and verified off hardware, the online setup with the SDK's own sign-in included (its ThinkPad trial to come); steps 3 and 5 implemented on the service's, the session's and the login program's side and verified off hardware and on the applications' side (the Bloom host's module, the SDK's host in applications and Settings' account page), verified off hardware too (the ThinkPad trial to come); step 4's removing an account implemented, its switching to come. Decision 6's server and SDK half is Oxy ADR 0058. Resolves the open decisions of [Oxy account and session on OxyOS](../account-session) for [#35](https://github.com/OxyHQ/OxyOS/issues/35). Builds on [ADR 0001](./0001-native-platform-boundaries) (the session authority, grants), [ADR 0006](./0006-seat) (logind), [ADR 0010](./0010-lock-screen) (PAM, the throttle, failing closed) and [ADR 0015](./0015-application-model).

**9 November 2026 ([ADR 0064](./0064-sleep-restart-shut-down-and-log-out)):** decision 5's sign out has a second door, the menu bar's Log Out *name*… (and Shift+Super+Q), which asks every application to quit first; and the login screen has Sleep, Restart and Shut Down at its foot, acting at once through logind as its own session, and shows the power key's choice itself.

## Problem

OxyOS requires an Oxy account, as a Chromebook requires a Google account. The account is set up on the machine online, through the Oxy SDK's own sign-in, and from then on works offline: cold boot, sign-in and unlock with no network. There is no local-only account, no guest and no anonymous desktop.

Today the session is started from a terminal login as a Unix user, and the lock checks that user's Unix password with PAM. Nothing ties the user to an Oxy account. The SDK's own sign-in (Oxy ADR 0030) is an email and a code or link, an optional password, and an optional authenticator: an account need not have a password at all, and nothing on the machine could check one offline. On a phone, every Oxy app reads one shared device credential. On OxyOS that would hand every process a secret that can mint tokens for the account.

## Decision

1. **Each Oxy account set up on the machine is one Unix user.** The account's Oxy user id names it (`oxy-<id>`); its home is the user's, and its display name and picture are the account's (the user's name is never shown: [the 2026-11-09 amendment](#amendment-2026-11-09-the-persons-name-never-the-unix-users)). The Unix user is how the kernel, logind, PAM and file permissions keep people apart; it is never a second account. Nothing signs in to the desktop except an enrolled account.
2. **Offline, the account's own Oxy password signs in and unlocks.** This is how a Chromebook uses the Google password.
   - **At setup** the person signs in to Oxy online. An account without a password sets one then, through the SDK's own flow for adding one (a fresh code to the account's email, Oxy ADR 0030 D6). The person then gives the password once more, and the system checks it with Oxy online (`POST /auth/signin/password`).
   - **The machine keeps a verifier, never the password.** The Unix user's password is set to it: a yescrypt hash in `/etc/shadow`, the system's established primitive, readable by root alone. PAM checks it, as it checks the lock's password today ([ADR 0010](./0010-lock-screen)): offline, with no network request, throttled as the lock throttles.
   - **Online, the password is checked with Oxy too.** At sign-in and unlock the local check decides; when the network is up, the system also checks with Oxy, after the local check, without delaying the session.
     - **The password was changed elsewhere.** Oxy accepts a password the machine does not know: the verifier is replaced with it, and the old one stops working.
     - **Oxy refuses a password the machine accepts:** the password was changed elsewhere, so the machine asks for the new one the next time it is online and keeps the old one only while offline.
     - **The account was removed from the machine elsewhere, or deleted.** At the next online check the person is signed out and the machine forgets the account's credential. The next sign-in needs Oxy online, as the first did.
   - **An authenticator** (Oxy ADR 0030's second factor) is asked for at setup and in every online sign-in Oxy asks it for, never offline. Offline the machine has only the verifier, as a Chromebook does.
   - **Limits.** Remote revocation and a changed password take effect only once the machine is online: it never promises otherwise. No mandatory reconnect period is set; that would be a product decision of its own.
3. **The account's credential is the system's, held by one service.** `oxyos-accountd` is a system service. It runs as root, because it creates users and sets their verifiers, and nothing else runs with it; systemd confines it to what that needs (its own state, the user database, the network to Oxy's API). It holds each enrolled account's device credential (the SDK's `{deviceId, deviceSecret}`, Oxy ADR 0029) in its own directory, `/var/lib/oxyos/accounts`, readable by it alone: a **platform credential** (Oxy ADR 0058, 2.1), which the platform's own sign-in issued to it alone.
   - **What it does.** It runs the online steps of decision 2 (setting up, checking the password, the verifier, revocation). It mints the account's short access tokens with the SDK's own contract (`POST /session/device/token`).
   - **What nobody else sees.** No application, shell or compositor ever holds the device credential. The login screen's setup client sees the credential its own sign-in obtained, and only until the service's platform sign-in retires it (Oxy retires the proving credential in the same transaction as it issues the platform credential): from then on the only live secret is the one the service alone received.
   - **Its own ADR.** How applications get what they need from it is decision 6.
4. **The login screen is OxyOS's own, on the seat.** `oxyos-login` is a system service that starts on the seat when the machine boots, after the boot logo (ADR 0017). It runs the compositor ([ADR 0006](./0006-seat)) with the login screen, a Bloom client like the lock screen, and knows nothing of passwords:
   - **What it shows.** The enrolled accounts (picture and name), and a password field.
   - **How it signs someone in.** A password goes through the compositor to PAM (service `oxyos-login`, the same path as the lock's). Once PAM accepts it, the login program opens the person's logind session (`pam_systemd`) and starts `oxyos-session` as that user, handing the seat over. Signing out returns to it.
   - **Adding an account.** "Add an account" (and the first boot) runs setup: the SDK's own sign-in dialog, in a Bloom client of the login screen, online only. The credential it obtains goes straight to `oxyos-accountd`, through the SDK's storage seam (an OxyOS `AuthStateStore` that hands it over and keeps nothing). If the machine is offline, setup says it needs the network and does nothing else: a first enrollment never succeeds offline.

   It is a first-party login program, not a display manager or greeter of another desktop (GDM, LightDM); no X11, Wayland or toolkit is involved ([ADR 0001](./0001-native-platform-boundaries)).
5. **Lock, sign out and remove are distinct.**
   - **Lock** keeps the session and needs the password (ADR 0010).
   - **Sign out** ends the session and returns to the login screen. The account stays enrolled and can sign in offline. Settings signs out with the session's `{"signOut": {}}` (its `settings` grant, citing the person's press; never at the login screen): the session answers `{"signingOut": {}}`, then ends as the keymap's end of the session ends it (`oxyos_compositor::sign_out`).
   - **Remove** (from Settings, or by Oxy's own device list online) ends the account's sessions, revokes its device session online when possible, forgets its credential, its verifier and, once confirmed, its home.
   - **Erase All Content and Settings** (*added by [ADR 0054](./0054-recovery-and-erasing), decision 4*): every account removed at once with the computer's settings, for an administrator who confirms it with their password: each account's device session ended online when possible, then the disk crypto-erased by the recovery.
   - **Administrators** (*added by [ADR 0054](./0054-recovery-and-erasing), decision 8*): an enrolled account whose user is in the `sudo` group, polkit's administrators on Debian. The first account set up becomes the machine's administrator; on a machine set up before, the enrolled account with the lowest uid; once only (an administrator removed later is not replaced by the next account).
   - **More than one account.** Several accounts may be enrolled. Each is its own user, its own session and its own credential, and switching shows the login screen. One person's data, tokens and surfaces never reach another's session.
6. **Applications never get the device credential.** The machine's Oxy session is the platform's, as [ADR 0015](./0015-application-model) makes everything else the platform's. An application signs in to nothing: it is given short tokens for itself by the platform, through the SDK, which on OxyOS asks `oxyos-accountd` instead of running its own sign-in.
   - **Its own decision, and the SDK's.** The SDK has no token scoped to an application yet: every holder of a device credential receives the same bearer. A token for one application, given to a platform that proves which application asks, is a server and SDK change that amends Oxy ADRs 0029, 0045 and 0050, and is decided in the SDK's repository.
   - **Who is asking.** On OxyOS the application is known by its launch record ([ADR 0013](./0013-launching-applications)).
   - **Closed by Oxy ADR 0058** (the platform-held session): the service mints each application a short token of its own (`POST /session/device/app-token`, the application named by its desktop entry id, OxyOS's own Settings and shell by `self`), and applications ask the service for it on the session socket (step 5). An application never runs a sign-in of its own.
   - **Amended on 2026-11-08: a PIN for this computer.** See [the amendment](#amendment-2026-11-08-a-pin-for-this-computer): the password, when the account has one, is asked once at setup, after the QR's approval, and becomes the verifier as above; a PIN for the computer signs in and unlocks too; an account without a password is never asked to make an Oxy password.
7. **Failing closed.** If `oxyos-accountd`, the login screen or the setup client fails, nobody is signed in. A failed or offline setup leaves no account. A verifier that cannot be read refuses, as PAM does. No path opens a desktop without PAM's acceptance for an enrolled account's user.

## Amendment (2026-11-08): a PIN for this computer

The owner's choice, after the first ThinkPad trial asked a person whose Oxy account has no password to make one: decision 2's options (a) and (c) together.

1. **How the person signed in decides** (amended again the same day, the owner's correction; Oxy's own model, Oxy ADR 0030, where a Commons account, signed in by its QR, has no email and no password):
   - **By the QR** (the phone's approval): no password is asked, offered or made, even of an account that has one. The person sets a PIN (required), and Oxy's device-proof route (`POST /session/device/platform`, Oxy ADR 0058) redeems the setup client's credential, the one the QR's claim issued it, once and within ten minutes of the claim, for the platform credential. The PIN is the account's local credential; its password does not sign in here (an enrolled account set up again keeps what it had).
   - **By the password, typed in the SDK's sign-in:** the setup takes that password as it was typed (the SDK hands it to the platform's setup store with how it signed in, `@oxy.so/services` 14.15.2) and never asks it again. It becomes the verifier, the platform credential coming from the platform's password sign-in; the PIN is optional ("Use a PIN to unlock faster").
   - **Another way** (the email's code, a new account): an account with a password gives it once (the PIN optional); one without sets a PIN.
   - No setup asks an account to make a password (the SDK's `OxyPasswordPanel` step is gone). Sign-in methods that cannot be read are said and asked again, never taken for "no password"; an SDK that does not say how it signed in is taken as another way.
2. **A PIN for this computer**, as Windows Hello's PIN or an iPhone's passcode: 4 to 16 digits, chosen at setup after the approval (typed twice) and in Settings. It signs in at the login screen and unlocks the lock offline, and is never sent to Oxy; Oxy online is the fallback. Where a password becomes the local credential the PIN may be left for later; both existing, either signs in and unlocks.
   - **Its verifier** is the service's (`crates/oxyos-account/src/pin.rs`): Argon2id in the PHC string format at the keybag's parameters (64 MiB, three passes, one lane, ADR 0050), a 16-byte salt from the system's CSPRNG, in the account's `.local` file beside its account file (mode 0600 in the service's 0700 directory, written whole), as the password's verifier is in `/etc/shadow`. A verifier of other parameters is refused, never checked with weaker ones. A PIN is never the password itself.
   - **How it is checked.** The lock surface says its next password is a PIN (`AuthenticatePasscode`, protocol version 32); the session checks it under PAM service `oxyos-pin` (the lock) and the login program's worker under `oxyos-login-pin`, each `pam_exec` of `oxyos-pin-check`, which asks `oxyos-accountd` (`verifyPin`: a peer may check its own account's PIN, root any account's). Only PAM's acceptance signs in or unlocks, as before. A PIN is never checked online, never taken for the password, and never opens the keychain (its keybag is the password's).
   - **Its throttle and lockout** are its own: the service's (five wrong PINs in a row free, then 30 s doubling, as the lock's, ADR 0010), on top of the login program's and the lock's per-PIN throttle; the count survives the service. The tenth wrong PIN in a row locks it out: it signs nothing in until the password signs in (the online check's acceptance forgets the count) or the account is set up again online (Oxy asked), or Settings sets a new one proved by the password. The login screen then offers the password, or, without one, signing in with Oxy.
3. **Settings › Oxy Account › Sign-In on This Computer**: set up, change and remove the PIN, and turn the password's sign-in off and on (`setPin`, `removePin`, `setPasswordSignIn` on the session socket, Settings' alone), each proved by the password (PAM) or the current PIN. The password turned off locks the user's verifier: the PIN is the account's one local credential, the online check refuses the password without asking Oxy (it never turns itself on again), and the PIN cannot be removed. Turned on again, the password is checked with Oxy online and becomes the verifier. Removing the PIN needs the password signing in.
4. **The device-proof route** (Oxy ADR 0058, amended): `oxyos-accountd` posts `{device, platformClient}` and keeps the holder secret the answer issues, as from the password route; every proof Oxy will not redeem (replayed, stale, another client's, an account no longer on the device) is one refusal, and setup then asks to sign in again. The route redeems only a QR claim's credential: an email code's or a password's keeps the password route. A setup with neither a password nor a PIN is refused `pinRequired` before Oxy is asked.
5. **Not yet:** the lock's online fallback for a locked-out PIN without a password (today the lock screen says to sign out and sign in with Oxy at the login screen); a keychain sealed under a PIN-only account's PIN.
6. **The QR is scanned once** (amended the same day, the owner's rule, after a ThinkPad setup redeemed the proof, failed at `useradd`, ended the platform credential, and its retry found the proof spent): a transient failure never asks for a second scan. `oxyos-accountd` does everything on the machine that can fail before the redemption (the PIN's verifier, the account checked online, its user and home made), so a failure there leaves the proof unspent; it redeems with a key of its own that the login screen never sees (Oxy ADR 0058 R7) and asks again with it while the route fails on its way (unreachable, a timeout, a 5xx), so an answer lost after Oxy redeemed is redeemed again, the credential first issued revoked; and a platform credential the machine then cannot take is kept by the setup's conversation, in memory, and set up again on its retry without asking Oxy, ended online only when the conversation ends without success. The login screen gets `failed: unreachable` (Oxy could not be reached; the sign-in is kept, try again), `failed: localFailure` (the machine could not be set up and was put back; the sign-in is kept, try again) and `refused: credentialRefused` (sign in again), and each step as it starts (`securing`, `verifying`, `preparing`, `signingIn`, `finishing`). The setup also seeds a home it made with the appearance the setup assistant asked for; an account set up again keeps its own, and the session is the preferences' one writer once it runs. The protocol is `crates/oxyos-account/src/ipc.rs`'s; tested in `tests/qr.rs` and `tests/ipc.rs`.
7. **Nothing is left live that nobody holds, and a rate limit is waited for** (amended the same day, the owner's rule, closing what item 6 left: a credential whose answer was lost after every retry, and a 429 that ended the setup). Every platform credential is pending until the machine confirms it (Oxy ADR 0058 R8; OxyOS's platform client says `confirms: true`, on the device-proof route, the password's and the second factor's sign-ins, and the online check's rotation): it mints nothing, expires with the QR's window (a password's sign-in's, ten minutes after it), and the credential it replaces works until it is confirmed. `oxyos-accountd` takes the account on the machine first (user, home, file, verifier), then confirms it (`POST /session/device/platform/confirm`, asked again while it fails on its way), and only then answers `enrolled`; a step `confirming` is told after `finishing`. Oxy unreachable for the confirmation is `failed: unreachable` with the machine's setup kept, and `"retry"` only confirms again; Oxy refusing it (it expired) undoes the machine's setup and is `refused: credentialRefused`. A setup abandoned before its confirmation ends nothing online: what it was issued expires by itself, and a setup the machine took whose confirmation never came back stays (confirmed with its answer lost, it works; not, the account is one Oxy signed out, set up again online). The online check's rotation keeps the machine's credential until the new one is confirmed. When Oxy rate-limits the redemption (a 429) with a wait that ends within the QR's window as Oxy told it (item 8), `oxyos-accountd` tells it (`{"waiting": {"retryAfterSeconds"}}`), waits, and asks again with the same key, the setup going on as before; the login screen shows the wait calmly and counts it down (its wording is the login screen's). A wait that would outlast the window is `refused: credentialRefused`. Tested in `tests/qr.rs`, `tests/ipc.rs`, `tests/platform.rs` and the client library's.
8. **The window is Oxy's, never the machine's guess** (amended 2026-11-09, the owner's rule, closing what item 7 left: `oxyos-accountd` counted the QR's ten minutes from its own setup's start, later than the claim, so a wait it allowed could outlast the real window and one it refused could have fitted). Oxy tells the window wherever an answer of the device-proof route concerns a proof it knows (Oxy ADR 0058 R9): the 200 carries `redemptionWindow` and `confirmWindow`, and the account budget's 429 carries `redemptionWindow`, each `{expiresAt, expiresInSeconds}`. `oxyos-accountd` reads only the seconds and measures them on its own monotonic clock from the answer's arrival, less two seconds for the way back, so no machine's clock setting matters; it keeps the latest window told. A 429 whose wait ends before that window does is waited for and told as before; one that would outlast it is `refused: credentialRefused`. Before any answer has told a window (a 429 of the device id's or the IP's budget, asked before the proof is looked at), no window decides: the wait is waited, at most ten of them. A confirmation is asked again only while its `confirmWindow` lasts, and a retry of the person's asks once more all the same, since a credential already confirmed is confirmed whatever the hour. Nothing is counted from the setup's start any more. The login screen's messages are unchanged. Tested in `tests/qr.rs` and `tests/api.rs`.

Tested: `crates/oxyos-account`'s `pin` tests and `tests/pin.rs` (the verifier and its parameters, the throttle, the lockout surviving the service, a PIN never sent to Oxy, setup with a PIN, a QR's setup by the device-proof route with its PIN alone (and refused without one before Oxy), the route's request and its one refusal, Settings' changes and their proofs, the password turned off refused by the online check), the login program's manager (a PIN under its own service and throttle, never online, no keychain), the scene and the client library (`AuthenticatePasscode`), and the scenarios `login-setup-pin` (the QR of an account with a password: a PIN typed twice, no password asked or offered, signing in with the PIN), `login-setup-password` (the password typed in the SDK's sign-in, never asked again; the PIN optional and left for later; the password signing in), `login-setup-no-password` (the owner's account, no password and no email: the QR, the PIN alone, no password or email ever shown, signed in with the PIN), `login-pin-locked` and `lock-pin` (the lock with the PIN, and the password beside it).

## Amendment (2026-11-08): the setup assistant

The owner's first QR sign-in on the ThinkPad (2026-11-08, 09:00:54 EET) showed "Your account couldn't be checked. Try again." between the phone's approval and the PIN. What happened, from the greeter's journal, `oxyos-accountd`'s and Oxy's API logs:

- The claim was answered at once (09:00:53.96 on the API, 09:00:54.02 on the screen). Right after it the link stalled for over ten seconds: the SDK's device-set registration (`POST /session/device/add`) and two directory reads timed out at the SDK's 5 s (09:00:59 and 09:01:04), though the API answered every request of that minute in under 120 ms.
- The setup did not go on at the claim: it waited for the SDK to finish its own work after a sign-in (`user` resolved only after the registration timed out), then read the account's sign-in methods, which a sign-in by the QR does not need, once, with no second try. That read timed out too, and the screen said the account could not be checked; nothing changed by itself once the link came back. "Try Again" read them, and the PIN followed.
- Reproduced: `login-setup-qr-stalled.json` plays the same stall (`qr.stall_after_claim_ms`) against the screen as it was, which showed the chooser with no word of the approval for ten seconds, then the same error.

An earlier attempt that morning (08:32) stranded a QR's proof: `oxyos-accountd` redeemed it, then could not make the user's home, undid the user and ended the platform credential, and the retry was refused (`Oxy does not know the device credential`): a second scan. Both are fixed at their source, and the setup becomes an assistant.

1. **One assistant, the SDK's frame.** Adding an account is a Mac's Setup Assistant: one page at a time, in the Oxy SDK's own frame (`OxySetupFlow`, `@oxy.so/services` 14.17.0, Oxy ADR 0064), whose sign-in page is the SDK's own chooser unchanged (`oxySignInStep`: `OxyAuthChooser`, the QR side from `md`, the same component every app's account dialog shows). OxyOS adds its pages as the flow's steps; the SDK draws the header, Back, Continue and the progress, moves focus to each page and says it ("Create a PIN, step 3 of 5"). Only the pages that apply, in order (`apps/login/src/setup.ts`):
   - **Welcome**, on the computer's first account.
   - **Transfer Your Data**, on the computer's first account where it migrates ([ADR 0059](./0059-backups), decision 7, added 8 November 2026): another computer's accounts brought over from its backup, which ends the assistant with them listed to sign in again, or **Not Now**, to set up as new.
   - **Connect to the Internet**, only while offline (or **Accounts Can't Be Added** without a client id), saying why setup needs the network once and that it works offline after.
   - **Sign in with Oxy**: the QR or a way typed in.
   - **The Oxy password once more**, only for a sign-in that typed none (the email's code) of an account that has one.
   - **Create a PIN** (typed twice): required after the QR and for an account without a password, optional ("Not Now") where a password becomes the local credential.
   - **Choose Your Look**: light, dark or auto, the new account's first appearance ([ADR 0019](./0019-settings)).
   - **Setting Up Your Account…**: the accounts' service's stages as it reaches them (`securing`, `verifying`, `preparing`, `signingIn`, `finishing`; `OxyOSAccountSetupStage` events from the host), a second factor asked on the same conversation, then "Opening your desktop".
2. **Nothing after the approval waits on the network.** A sign-in by the QR or by the password goes on to the PIN the moment the SDK hands its credential over: nothing more of Oxy is needed before the PIN. Another way reads the sign-in methods, tries again by itself while the link stalls (after 2, 4 and 8 s), and only then says so: Oxy could not be reached to finish signing in, the sign-in is kept, check the connection.
3. **Back and forward.** Back goes to the page before; past the sign-in it gives the sign-in up (the platform forgets the credential, a new provider shows the chooser fresh). There is no Back while the account is being set up, once it is, or from a failure the service keeps (going back would abandon its conversation, and with it what it kept).
4. **Every failure says why and what next, and keeps what it can** (the accounts' service's answers, item 6 of the PIN amendment): Oxy unreachable keeps the sign-in, the PIN and the choices, and Try Again asks the service to retry with what it kept (`retryEnrollment`), never a new sign-in; the machine unable to set the account up says nothing was changed and Try Again sets it up with the credential already issued; only a sign-in that can no longer be used (its ten minutes past, refused) asks to sign in again, and says why. A password typed in the sign-in that Oxy refuses later is a sign-in to do again, never a field the person did not ask for.
5. **Straight to the desktop.** Set up, the new account signs in with what the person just chose, the PIN (else the password), through the login program and PAM exactly as at the login screen; the screen holds them only until then and forgets them. Never asked a second time. If the login program refuses (it should not), the account is listed and chosen, its field focused, as any account.
6. **The appearance** goes with the setup (`appearance` of the enroll request); the service seeds the new home's preferences with it, as `/etc/skel` seeds a home, before any session exists. The session is the file's one writer from then on.
7. **Keyboard and reader** ([ADR 0039](./0039-keyboard-access), [ADR 0014](./0014-screen-reader)): every control in Tab order, the fields focused as each page comes, the progress said by the flow (its dots hidden), each stage's state in its label ("Creating your home folder, in progress"), the appearance a `ChoiceList` (one stop, arrows between choices). Spanish and English, at 1 and 1.25.
8. **No privacy or analytics page:** OxyOS collects none. **Not yet:** joining a Wi-Fi network from the Connect page (the session's password sheet is refused while locked; [ADR 0038](./0038-networks)'s setup network step), choosing the system's language where none is set (setup chooses it, [ADR 0023](./0023-installing-oxyos)), and the keychain and backups offers, which need the person's own session (the keychain's recovery key, [ADR 0050](./0050-keychain-autofill-and-passkeys); [ADR 0059](./0059-backups)): they belong to the first session's own welcome.
9. **A wait is not a failure, and the confirmation is a stage** (item 7 of the PIN amendment; Oxy ADR 0058 R8). When Oxy asks the accounts' service to wait before redeeming again, the Setting Up page stays as it is, its stages where they were, and says under them "Oxy is busy right now. Setup goes on by itself in 12 seconds.", counting down: no problem page, no Try Again, nothing asked. A reader says it once as it begins, not each second. The service's next stage ends it. The credential's confirmation is the service's last stage, "Confirming this computer with Oxy"; a retry after Oxy could not be reached for it shows that stage alone.

Tested: `apps/login/tests/setup.test.ts` (each answer's way forward, the pages for each path, Back from each page, the stages); scenarios against the played Oxy API and accounts' service: `login-setup-qr` (QR → PIN → look → set up → desktop), `login-setup-qr-stalled` (the owner's stall: the PIN at once, no error), `login-setup-qr-unreachable` (the service failing once: Try Again, no second scan), `login-setup-qr-waiting` (Oxy asking for a moment: the wait counted down, then set up; one approval), `login-setup-qr-waiting` (Oxy asking for a moment: the wait counted down, then set up, one approval), `login-setup-qr-refused` (the SDK's own read refused after the claim, oxy#2224: the setup goes on), `login-setup-qr-first` and `-scaled` (the welcome; at 1.25), `login-setup-pin` and `login-setup-no-password` (the PIN required, a Commons account), `login-setup` (the email's code: the password once, refused then right, the authenticator's code), `login-setup-password` (the password typed, the PIN left for later, signed in with the password), `login-first-boot` and `login-screen` (offline: the Connect page), `login-setup-keys` and `-scaled` (the keyboard and the reader, in Spanish, at 1 and 1.25).

## Amendment (2026-11-09): the person's name, never the Unix user's

## Steps

1. **`oxyos-accountd`'s setup:**
   - enrolling an account from a device credential, through the SDK's contracts;
   - the Unix user, its home and its verifier;
   - the online password check.

   Tested against the Oxy API's development server, and offline (setup refused, no account left behind).

   *Done.* `crates/oxyos-account` holds the logic and `tools/oxyos-accountd` the service; nothing installs either yet.
   - **Online, before the machine changes.** The device credential mints a token pinned to the account (`POST /session/device/token` with `accountId`: the credential is live and the account is signed in on that device; a pinned mint never moves the device's active account). With it, `GET /users/me` must name that account; its username is what the password signs in with, so the person gives only the password and it can sign in no other account. `POST /auth/signin/password` carries the device's proof, so the session lands on the same device rather than a new one, and an authenticator's challenge is answered on the same proof (`POST /auth/signin/second-factor`). The answer must name the account and the device. The sign-in's own token and the holder secret it issues are dropped unread; the credential kept is the one handed over. HTTP is `ureq` with rustls and the platform verifier, as `oxyos-net` uses it, without cookies or redirects; plain HTTP is accepted only to this machine (a development server).
   - **The user's name.** An Oxy id is a legacy 24-character hex id or a uuid v7 (the SDK's `ids.ts`); `oxy-` and a uuid is 40 characters, past the 31 a user name may have (utmp; systemd refuses longer). So decision 1's `oxy-<id>` is `oxy-` and the id's bytes in lowercase base32: 24 characters for a legacy id, 30 for a uuid, lossless, and within `[a-z0-9-]`. Anything else is not an account and never reaches Oxy.
   - **On the machine,** one setup at a time: `useradd --create-home --user-group` (an ordinary uid, a home at login.defs' `HOME_MODE`, the password locked), the account's file (`/var/lib/oxyos/accounts/<user>.json`, mode 0600 in a 0700 directory, written to a new file, flushed and renamed over the old), and last the verifier with `chpasswd`, the password on its standard input. `chpasswd` hashes as the system is set to (PAM's `common-password`, `pam_unix … yescrypt` on trixie), takes the user database's lock and replaces the shadow file whole; `pam_chauthtok` from the service would run the same modules but need a PAM binding and a conversation of its own in a root process, so the system's tool is the more robust path to the same verifier. A failure undoes the setup (the new user removed with its group and home, an enrolled account's file put back), and because the verifier is last, a user a failed setup leaves behind (if `userdel` fails too, which is reported) has a locked password. A user of the account's name the service did not make (uid 0 included) is never taken over, nor is an enrolled account whose user is gone or changed uid: the setup is refused before Oxy is asked. Setting an enrolled account up again keeps its user and replaces its credential and verifier. A password must be at most 512 bytes (PAM's longest answer, the most the lock sends), without a NUL or a line break.
   - **The socket,** `/run/oxyos/accountd/socket`: `SOCK_SEQPACKET`, one JSON message per packet. Only root or the login program's user (`oxyos-login`, read from `/etc/passwd` at each connection; until step 2 makes it, root alone) may enroll, by the kernel's peer credentials; anyone else is told `notPermitted`, once its first message is read. A conversation is `enroll {deviceId, deviceSecret, accountId, password}`, answered `enrolled {accountId, user, uid, profile}`, `refused {reason, retryAfterSeconds?}` or `secondFactorRequired`, then `secondFactor {code}` (a wrong code may be followed by another); closing the connection abandons it. Every answer follows the message it answers, and the service never closes a connection with a message unread: Linux resets a Unix socket closed with its receive queue not empty, and the client would read `ECONNRESET` rather than the answer (a refusal sent before reading failed a third of the time). At most four conversations at once, and apart from them four refusals, each waiting at most five seconds for the peer's message, so peers that may not enroll cannot keep those that may out; a connection past them is closed unanswered.
   - **Its unit,** `tools/oxyos-accountd/oxyos-accountd.service`: root with five capabilities (owning and removing homes), `ProtectSystem=strict` with `/etc` writable (the passwd tools and `pam_unix` replace the user database by renaming in `/etc`, which no single-file bind allows) and lastlog, `/home` writable and `/root` and `/run/user` inaccessible (`InaccessiblePaths`), `NoNewPrivileges`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`, the `@system-service` filter, the kernel, clock and device protections. `systemd-analyze verify` accepts it; `systemd-analyze security --offline` rates it 2.6 (OK), what remains being root, the network, `chown` and the homes. It once hid the homes with `ProtectHome=tmpfs` and bound `/home` back (`BindPaths=/home`): under `ProtectSystem=strict` systemd (257, trixie) makes that bind read-only, `ReadWritePaths=/home` or not, so on the ThinkPad `useradd` could make no home (exit 12) and no account could be set up, and the QR's single-use credential, already issued, was spent on a setup that was undone. `systemd-analyze` and the tests without root saw none of it; only starting the unit does. So an ignored test starts the unit itself, as root, with a drop-in that runs a probe in place of the service (`tools/oxyos-accountd/src/unit_sandbox.rs`, run by CI's verify job with `sudo`): it makes a user with its home through `SystemUsers`, sets its verifier, makes it an administrator, locks and removes it, and checks that `/usr`, `/var/lib` and `/boot` refuse a write and that `/root` and `/run/user` show nothing.
   - **Secrets** (password, device secret, tokens, codes, the challenge) are overwritten in memory when dropped and never printed, as are the request bodies, answers, socket messages and files the crate writes them into or reads them from; copies inside `ureq`'s and `serde_json`'s buffers are not its to overwrite.
   - **Tested** (62 tests, without root or network): every refusal (offline from each call, a wrong password, Oxy's lockout, an unknown credential, an account not on the device or another account's or device's answer, a wrong code then the right one, unusable passwords and ids) leaves no user and no file; each failure halfway is undone, and a failed undo is said; the file's and directory's modes; no secret in `Debug`, errors or the service's log. The real `useradd`, `chpasswd` and `userdel` run on a root of the tests' own (`--prefix`): the verifier is a yescrypt hash that `crypt(3)` verifies, and the password is never in an argument or the environment. Debian trixie's tools (shadow 4.17) do that without privileges; Ubuntu 24.04's (shadow 4.13), on CI's runner, cannot: its `chpasswd` has no `--prefix`, its `useradd` opens the host's lastlog despite one, and its `userdel` keeps a home it could not give the user (`not owned by …, not removing`). So those tests first probe exactly that (a `chpasswd` with `--prefix`, then a user made, verified and removed with nothing reaching outside the root) and skip, saying why, where it fails; CI runs them in a Debian trixie container too, where the probe must pass (`OXYOS_ACCOUNT_PASSWD_TOOLS=required`). As root, as the service runs, `useradd` gives the home to the user and `userdel` removes it; trixie's `userdel` only warns of the mail spool Debian never makes (`CREATE_MAIL_SPOOL=no`). The HTTP client runs against a server of the tests' own answering in the API's shapes, and against a closed port (offline). Two ignored tests (`cargo test -p oxyos-account dev_server -- --ignored`, how to run them in `src/tests/dev_server.rs`) passed against the Oxy API (`b749b3539`) run on this machine with a database of its own: a password setup, after a wrong password and an account not on the device; an authenticator's setup, after a wrong code; the kept credential mints afterwards.
   - **Not yet verified:** the service as root on a real system, so its sandbox around `pam_unix` as the service itself calls it (the unit's test runs the passwd tools in it); TLS to `api.oxy.so` (no production account was used); a production account's sign-in.
   - **Of the SDK,** seen here and not changed: the mint's `expiresAt` is the session's expiry (seven days, sliding with each mint), not the access token's, whose JWT `exp` is fifteen minutes later; there is no refresh token, so a token is refreshed by minting again, and every holder of a device credential gets the same bearer. Whatever caches tokens (decision 3's minting) reads `exp`. Every password sign-in issues a new holder secret that stays valid; the one setup drops is never stored.
2. **The login program:** `oxyos-login` on the seat, its login screen (Bloom), PAM `oxyos-login`, and starting the person's session. Then on the ThinkPad:
   - the first setup, online;
   - a cold boot offline;
   - signing in and unlocking offline;
   - a wrong password throttled.

   *Done, off hardware.* `tools/oxyos-login` is the program, `apps/login` the screen; nothing installs either (the image rules), and no ThinkPad trial has run yet.
   - **Its processes, as a login manager's** (GDM's daemon, session worker and greeter; LightDM's daemon, session child and greeter, minimal):
     - **The login program** (`oxyos-login.service`, root). It must be: only root checks another user's password (`pam_unix` as anyone else checks only the caller's own, through `unix_chkpwd`), opens a logind session (`pam_systemd`'s `CreateSession` is root's) and becomes the user. It decides with a state machine (`manager.rs`) fed what happened and answering what to do, so every order is tested without a seat, PAM or a process; `run.rs` does it.
     - **A worker** per PAM transaction (`oxyos-login --worker`, root), a process of its own because `pam_systemd` makes the process that opens a session its leader and moves it into the session's scope, and a module's state lives and dies with one transaction. It talks to the login program on a socket pair, its standard input. A person's worker gets the password, authenticates and checks the account (service `oxyos-login`), says what came of it, and once told the login screen has ended opens the session: `PAM_TTY` `/dev/tty1`, logind's class, type, seat and terminal in PAM's environment, credentials established, the session opened, then `oxyos-session --shell HOST,BUNDLE,OxyOSShell` started as the user, BUNDLE the shell's package (`/usr/lib/oxyos/apps/so.oxy.shell/index.hbc`, `--shell-bundle`; the login screen runs the login screen's, `so.oxy.login`, `--login-bundle`; both on runtime 1's host, `--host`, as ADR 0030 installs them) (the groups `getgrouplist` gives, read before the fork; the ids set and checked to be irrevocable; its home; a session of processes of its own; an environment of the user's own variables, the modules' (`XDG_SESSION_ID`, `XDG_RUNTIME_DIR`, the locale) and the Bloom host's name, nothing inherited). When it exits, or the login program asks, the program is stopped (SIGTERM to its group, SIGKILL after 5 s), the session closed and the credentials deleted. A password PAM wants changed (`PAM_NEW_AUTHTOK_REQD`) does not sign in: the login screen cannot change one yet.
     - **The login screen**: a worker opens a session of class `greeter` for the login program's own user, `oxyos-login` (`oxyos-login.sysusers`: a system user with no password, no shell and no group but its own; `oxyos-login.tmpfiles` its home), with the service `oxyos-login-greeter`, which no other user may use (`pam_succeed_if`) and which authenticates nobody (`pam_deny`: the worker never asks it to) and so establishes no credentials: the worker opens that session without `pam_setcred`, which runs the auth stack and would fail it (`Login::open_greeter_session`; the first ThinkPad trial, 7 November 2026, looped on "Failure setting user credentials" until it did). In it runs `oxyos-session --greeter --shell HOST,BUNDLE,OxyOSLogin`: the same compositor, taking the card and devices through logind as a session does ([ADR 0006](./0006-seat)), locked before any client connects and never unlocked (`Compositor::login`), with the Bloom host's `OxyOSLogin` as its shell and its lock surfaces all there is to see. It launches nothing and holds no sleep. Its screen reader is the one the login program's unit names (`OXYOS_READER`, passed on with `OXYOS_WALLPAPER` and nothing else of its environment): off, and turned on with Super+F5 before anyone signs in, as Cmd+F5 turns VoiceOver on at a Mac's login window ([ADR 0014](./0014-screen-reader), decision 6). **The screen reader at the login screen** is named in the unit but commented out, with the wallpaper, until the unit is installed: the image ships no session, login program, reader or eSpeak NG yet (ADR 0014, decision 3; the image is a console base, `docs/iso-build.mdx`), and a program the system lacks leaves Super+F5 doing nothing at the login screen (the session says it cannot start it in its log and goes on). Before it is enabled the reader must be heard at the login screen on a machine: it speaks as the `oxyos-login` system user, whose greeter session needs a PipeWire of its own (`user@.service` for the greeter session with `pipewire-pulse`, as GDM's greeter has), never the signed-in user's. Enabling it is one line, with the reader installed at `/usr/libexec/oxyos/oxyos-reader` and `espeak-ng` in the manifest. The password field says each answer once, a wait as it starts, at its reminders and as it ends ([ADR 0010](./0010-lock-screen)).
   - **The screen.** `apps/login`'s `LoginScreen` is the lock screen's look before anyone has signed in, from the lock screen's own parts, now shared (`LockBackdrop`: the wallpaper dimmed, the date and the time in its material; `UserPicture`; `PasswordField`, the secure field that shakes and says why): the enrolled accounts, picture and name, side by side when there are several (Bloom's `ChoiceList`, as a Mac's login window: one list and one keyboard stop on the chosen account, ← → Home End moving the keyboard among them without choosing, Return or Space choosing the one focused, whose field then takes the focus, each said once with its place, "Bea Ramos, 2 de 3"), the chosen one's password field under them, a field of its own for each account, and "Añadir cuenta". The accounts are `oxyos-accountd`'s new `list` (its user, name and picture, never a credential; root and `oxyos-login` alone may ask, as for `enroll`), which the Bloom host reads (`OxyOSShell.accounts()`, `oxyos_accounts` in the client library, which asks the service as the login screen's user). A picture is the user's file in `/var/lib/oxyos/pictures` (readable by the login screen, as AccountsService keeps its icons), when there is one: nothing writes one yet, so the screen shows initials. Accounts that cannot be read are said so and asked for again; nobody can sign in without them.
   - **The password's path** is the lock's ([ADR 0010](./0010-lock-screen)) with the account named: a new request, `AuthenticateAccount { surface, user }` (100), from a lock surface while locked, before the password's chunks; the scene keeps it with that one password (`Submitted`), and the `Authentication` path is given it. The session's own path (PAM for its own user) rejects any other account; the login screen's (`oxyos_compositor::login::LoginProgram`) hands the password to the login program on `/run/oxyos/login/greeter` (`oxyos_auth::greeter`: `SOCK_SEQPACKET`, the socket `oxyos-login`'s with mode 0600 and the peer's uid checked at each connection), and nothing else. JavaScript holds the typed password only as the lock screen's does. Accepted, the compositor shows the splash; it never unlocks.
   - **Who may be checked, and how often.** The login program asks `oxyos-accountd` at each attempt whether the account is enrolled; one that is not is refused without PAM, all such names sharing one throttle, and with the service unreachable nobody signs in (decision 7). The throttle is the lock's (`oxyos_auth::Throttle`), one per account and kept by the login program, not the screen: five rejections free, then 30 s doubling to 15 min, an acceptance resetting it; a failure that was no guess (PAM broken, the worker gone) rejects without counting. One password is checked at a time.
   - **The seat's handover**, in LightDM's order, on one terminal: accepted, the login screen is told, shows the splash and ends; if it has not within 5 s it is stopped, and killed (with what it started) after 5 s more. Only once its worker has exited, its logind session closed and the card's DRM master let go with its descriptor, is the person's session opened; logind takes a running session over a closing one on the same terminal. The worker first shows the terminal (`VT_ACTIVATE`, `oxyos_vt::show`) so the session is the seat's active one. Signing out (the session's program ending), or a session that fails to open, starts the login screen again; one that crashes is started again no sooner than a second after it last started, a check it had going abandoned.
   - **logind's type** is `tty`, what OxyOS's sessions were verified with ([ADR 0006](./0006-seat), [ADR 0010](./0010-lock-screen)): logind's graphical types (x11, wayland, mir) name display servers OxyOS does not have, and the session does not claim to be one. So logind still refuses the idle lock's idle hint (ADR 0010, step 4), as it does from a terminal's login, and judges idleness by the terminal, which the session does not touch; the lock does not depend on it.
   - **At boot** ([ADR 0017](./0017-boot-logo)) `oxyos-login.service` is `Type=notify`: Plymouth is deactivated before it starts; the login screen's first frame, the splash, is told to the login program (it runs in a session of its own, outside the unit, so it cannot tell the service manager itself), which sends `READY=1`; `plymouth quit --retain-splash` follows. It conflicts with `getty@tty1.service` and `plymouth-quit.service`, as decision 5 of ADR 0017 has the session's unit do, and is the system's `display-manager.service`. `systemd-analyze verify` accepts it. `oxyos_seat::notify` is the session's sd_notify, moved there for both.

Setup first reads the platform from `oxyos-accountd` (`platform`: Oxy's API and OxyOS's public client id) and reaches that API: offline, it says it needs the network, offers to look again and does nothing else; a service that names no client id sets nothing up and says so. Online, the SDK's own sign-in runs in the login screen, on a card of its own over the dimmed wallpaper: the account dialog's own chooser, the one an Oxy app shows on the web (`OxyProvider` and `OxyAuthChooser` from `@oxy.so/services` 14.15.2, `sample/SetupSignIn.tsx`, in the login package's bundle, not the runtime's framework), bare on the card, which it sizes as it sizes the dialog (`OxySurfaceFrame`). OxyOS is a computer to the SDK, so the chooser is its split card: the Commons QR a phone scans beside the form (the email's code or the password, the authenticator, or a new account with the SDK's own sign-up), the email or username field focused. A QR approved on a phone signs in like any other way in: the screen claims the session and the credential goes to the host. The SDK hears the approval at once: it joins the API's Socket.IO `/auth-session` namespace over React Native's `WebSocket` (the host's `WebSocketModule`, [the adaptation](../react-native-android-adaptation)) and asks the status as soon as it is told; its status check every twelve seconds is only the fallback. The provider's `authStateStore` (Oxy ADR 0058, B3) keeps nothing: the credential a sign-in commits goes at once to the Bloom host (`OxyOSAccountSession.holdCredential`), which holds it, never JavaScript. Then the account's sign-in methods are read (never guessed: unread, the screen says so and reads them again), and the SDK's provider is unmounted (the service's platform sign-in retires the secret it held): the person chooses a PIN for this computer, typed twice (an account with a password may leave it for later), and, when the account has a password, gives it once more, in the login screen's own secure field (the amendment of 2026-11-08 above; an account without a password is never asked to make one, and a sign-in by the QR sets a PIN alone, its credential redeemed by Oxy's device-proof route); the host sends them with the credential to `enroll`, answering a second factor on the same conversation (the authenticator's code, a wrong one said and another taken), and forgets both. 3. **The online checks:** a password changed elsewhere (both ways), revocation on reconnect, the account removed. Tests with the development server.

   *Done, off hardware* (`crates/oxyos-account`'s `platform.rs`, the service's socket, the login program, the lock).
   - **The platform credential.** `oxyos-accountd` is configured by its unit: `OXYOS_OXY_API` (`https://api.oxy.so` by default), `OXYOS_OXY_CLIENT_ID` (OxyOS's public client id, the registry's, not a secret: production's, `oxy_dk_ee7af26b21c2ff9e70f59e43dc2359106280665d779b74a8`, is the unit's) and `OXYOS_SESSION_PROGRAM` (step 5). Without a client id setup is refused (`notConfigured`) before Oxy is asked, and passwords are not checked online; nothing else changes. Setup's password sign-in now names the platform (`platformClient: {platform: "oxyos", clientId}`, no web `Origin`), and its second factor names it again; the holder secret the sign-in issues is the credential kept, its device the one handed over. Oxy retires the handed-over credential in the same transaction (Oxy ADR 0058, R1), so step 1's "the sign-in's own holder secret is dropped" no longer holds: it is the one kept. A setup that fails after the sign-in leaves that platform credential pending, to expire by itself (item 7 of the 2026-11-08 amendment, Oxy ADR 0058 R8), and an account set up again ends the one it replaces (each is a device of its own), best effort and said if it fails. The account's file (version 2, version 1 still read as ready) keeps the profile from the last online read, the credential or none, and a flag.
   - **The service's socket** gains `"platform"` → `{"platform": {"api", "clientId"}}` (the login screen's setup reads it), `{"check": {"user", "password", "local": "accepted" | "rejected"}}` → `{"checked": {"result": "accepted" | "rejected", "reason"?: "passwordChanged" | "signInAgain"}}`, and `list` entries gain `"state": "ready" | "signInAgain"`. Root and the login program's user alone, as before.
   - **The checks.** A password PAM rejected is asked of Oxy: the device's own token is minted first (the credential is live, and the profile is read anew), then the platform's sign-in; accepted, the verifier is replaced with the password (`chpasswd`) and the answer is `accepted` (the password was changed elsewhere); refused or offline, `rejected`. A password PAM accepted is `accepted` at once, and asked of Oxy on a thread of its own, never delaying the session: Oxy refusing it flags the account `passwordChanged`; while flagged and online, a locally accepted password waits for Oxy (`rejected`, `passwordChanged`, when Oxy refuses it; `accepted` when Oxy cannot be reached: the old password works only offline); an accepted password clears the flag. An account whose authenticator Oxy asks for gets a challenge, which a check cannot answer and which proves only the first factor: a password PAM rejected is then `rejected` (`passwordChanged`: it is set up again online, with the authenticator) and never becomes the verifier; one PAM accepted stays accepted (it is the verifier already). Neither rotates the credential. Every online sign-in rotates the platform credential: the new one replaces the old in the file, written whole under the machine's lock and only if the file still holds the credential it was made from (a setup or another rotation may have replaced it; the new one is then ended online), and the old session's cached tokens are dropped. An account's online calls are made one at a time.
   - **Revocation.** A mint answering that the device's session is gone (`invalid_device_secret`, `no_active_session`, `account_not_on_device`, R4), from a check or an application's token, signs the account out on the machine: its credential forgotten (only if it is still the one that failed), its verifier locked (`usermod --lock`), every session of its user ended (`loginctl terminate-user`). It lists as `signInAgain`, every check of it is `rejected` with `signInAgain`, its snapshot is signed out, and setting it up again online keeps its user and home. A rotation whose answer was lost on the way (Oxy rotated, the machine never heard) is found so too: fail closed, the account signs in again online.
   - **The login program** asks `check` after its worker's PAM answer, in its state machine: PAM's answer and the service's go together; a password PAM rejected and Oxy accepted (the verifier replaced) is checked by PAM again with a new worker, which opens the session; one PAM accepted is refused only on the service's word; the service unreachable, nobody signs in and it counts as no guess. Its worker that accepted waits to open the session until the service answers, and is ended if the service refuses.
   - **The lock** gives PAM's answer and the password to the service's session socket (step 5), on the checker's thread: the service's answer stands; unreachable, PAM's does. It is an addition, never a gate, but for an account the service has flagged or signed out.
   - **Tested** (without root or network). `oxyos-account`, 104 tests: the sign-in naming the platform and the credential kept (the handed-over one retired), `notConfigured` asking nothing, a failed setup's credential ended online, the second factor naming the platform; the file's version 2, a version 1 file read, an account signed out kept without a credential and listed so, found by user and by uid; a password changed elsewhere becoming the verifier, a wrong one or none offline changing nothing, a locally accepted one accepted at once and flagged when Oxy refuses it, then refused while flagged online and accepted offline, and cleared by the new one; every online sign-in rotating the credential and retiring the old one, nothing half-written beside the file; an authenticator's challenge never making a new password the verifier; revocation from a mint (credential forgotten, verifier locked, sessions ended, signed out, rejected with `signInAgain`, set up again with the same uid); the socket's `platform` and `check` and their wire shapes. `oxyos-login`: five new state machine tests (the service asked before anyone signs in and a stale answer ignored, a password changed elsewhere checked again and signed in, the service's refusal ending the waiting worker and counting, the service unreachable not counting, an accepting worker gone before the answer opening nothing), and the program as a process with a stand-in service that replaces the verifier as the service does (`tests/development.rs`: a changed password signs in, an account Oxy signed out does not). `oxyos-auth`: the lock's online check given PAM's answer, its answer standing, PAM's when it has none.
   - **Against Oxy's API** (`cargo test -p oxyos-account dev_server -- --ignored --test-threads 1`, how to run them in `src/tests/dev_server.rs`), passed against a development server of Oxy's API with ADR 0058's server half (OxyHQ/oxy#2202) and a database of its own: a password setup and an authenticator's setup each keeping the platform credential, the handed-over credential refused afterwards; Dropsea's token by its desktop entry id and OxyOS's own by `self`, cached and minted again, an unknown entry id refused; an online check rotating the credential and the old one refused; a wrong password rotating nothing; the account removed (its device signed out at Oxy); and a device signed out at Oxy found by the next mint and the account signed out on the machine. 5. **Applications' tokens:** the SDK's decision (decision 6), then the OxyOS side.

   *Done, off hardware* (the service and the session; the SDK's host mode and the Bloom host's module that speaks to it are their own work).
   - **The session socket,** `/run/oxyos/accountd/session` (`SOCK_SEQPACKET`, one JSON message per packet, mode 0666 in the service's 0755 directory). Every peer is known by the kernel (`SO_PEERCRED`, and `SO_PEERPIDFD`, Linux 6.5; trixie has 6.12), never by what it sends; one that is neither of the two below is answered `{"refused": {"reason": "notPermitted"}}` once its first message is read.
   - **The registrar** is the session program the login program started: its uid is an enrolled account's user; the file its process runs (`/proc/<pid>/exe` of the pid its pidfd names, read again after) is `OXYOS_SESSION_PROGRAM`'s by device and inode, owned by root and writable by no group or other; and its parent is a root process running `OXYOS_LOGIN_PROGRAM`'s file (`/usr/libexec/oxyos/oxyos-login`: the worker, which starts the session with a clean environment). The same file run by the user itself (from a terminal, under `LD_PRELOAD`) has the user's process for a parent, and registers nothing; so a session started from a terminal (ADR 0006's, the ThinkPad's development one) gets no tokens for its applications. It presents itself as its connection opens (`{"present": {}}`, answered `"accepted"`, or refused `notPermitted` and closed), and the service keeps what it verified of it (`/run/oxyos/accountd/registrars`, the service's own, 0700, one file per process: its pid and start time, the file it runs and its parent's by device and inode; the unit keeps the directory across restarts, `RuntimeDirectoryPreserve=yes`, and a boot empties it). Started again under a running session (a package upgrade restarts it), the service takes a registrar whose program's file the upgrade replaced if the kernel shows exactly what it kept: the same process, the same file running (a replaced file is still the process's, so its inode is no other file's meanwhile), the same parent running the same file, root's and written by no one else; never anything the session says. It sends `{"register": {"desktopEntryId", "system"}}` with the launched process's pidfd (`SCM_RIGHTS`); a process that is not its own child (`PPid`) or not its user's is refused (`notPermitted`), a descriptor that is no pidfd or an id that is no desktop entry id (`so.oxy.dropsea`, the registry's shape) is `invalidRequest`; else `"registered"`. A registration lives while its process does (the service polls the pidfd) and while the registrar's connection is open (closing it drops every registration made on it). `{"check": {"password", "local"}}` from the registrar checks its own account's password (the lock's). At most four registrars per user and 512 registrations per registrar; registrars are counted apart from applications, which have at most 16 connections per user (and 64 in all), so no user's applications can keep a lock from its check.
   - **An application** is a process whose pidfd's pid is a live registration's, of its user: a child of a launched process, another user's or one nobody registered is refused. It may ask, on one connection, `"snapshot"` → `{"snapshot": Snapshot}` (the SDK's `OxyHostSnapshot`: `status` `signed_in` | `signed_out` | `unavailable`, `revision`, `account` `{id, handle, displayName?, avatar?, languages?}` or null (`languages`: the account's locales, primary first, as the platform last read them online), `online`); `"subscribe"` → the snapshot now and again on every change until it closes (at most four per registration; a message sent on it is answered `invalidRequest` and ends it); `{"token": {"reason": "boot" | "preflight" | "response-401"}}` → `{"token": {"accessToken", "expiresAt"}}` or `{"token": null}` (offline, signed out, refused, an application Oxy does not recognise); and `{"remove": {}}` (step 4). An application connection waits at most a minute for its next message.
   - **Tokens** are minted with the platform credential (`POST /session/device/app-token {deviceId, deviceSecret, accountId, attestation}`, the answer read in `sendSuccess`'s envelope or bare), cached per account and application, minted again a minute before their `expiresAt` and at once for `response-401`. Settings and the shell registered as system applications are OxyOS itself (`{"platform": "oxyos", "self": true}`, one token for both); any other application by its desktop entry id (`{"platform": "oxyos", "desktopEntryId"}`). Offline the token is null and the snapshot still signed in, `online: false`. Subscribers are told every change, but the revision changes only with the snapshot's status or account (signed in, signed out, removed, another account), because the SDK's host mode takes a new revision for a switch of account; a profile read anew or Oxy reached or not keeps it. Revisions start from the service's start in milliseconds, so they still rise across a restart. Mints are rationed per account and application, since the SDK asks again with backoff while it has no token: after a refusal none is tried for a minute (15 s after Oxy was unreachable), and at most ten in 15 minutes (Oxy allows twelve).
   - **The session** (`oxyos-session`) keeps one registrar connection for its life, on a thread of its own (`RegistrarThread`), so a launch never waits for the service: the launcher (`oxyos_apps::Launcher::with_registrar`) opens each started process's pidfd right after the spawn, while the process is its unreaped child, and hands it over at the launch record; a system or installed application is registered, a development entry (no Oxy identity) is not. Each shell it starts is registered as `so.oxy.shell`, a system application. If the service goes (restarted) or does not take the session, the thread connects again for as long as the session runs, never giving up: after 1 s, waits doubling to 30 s (to five minutes while the service refuses it), and at each launch; connected, it presents the session and registers every process still running. It says once per outage and cause what it could not do, and says when it is connected again. Without the service nothing is registered and applications get no token meanwhile. An application's Bloom host follows the snapshot again by itself when a subscription it had ends, or when the service was not there (`account-session.cpp`: after 0.5 s, waits doubling to 30 s), and tells the application the session is unavailable only if it stays unfollowed for more than three seconds, so a service restarting under it is never seen; one refused from the start (a process the service does not know) is told at once, as before. The login screen registers nothing. The development compositor has no registrar: its scenarios run as before.
   - **Tested.** On real sockets with real processes (the test is the registrar, its program standing for the session program; applications are child processes speaking the socket): a registered application's snapshot and tokens, cached and minted again, and rationed; Settings and the shell as system applications getting OxyOS's own token and Settings not registered so getting its id's; an unregistered process, a launched one's child and the registrar asking for a token refused;    - **Limits.** A process of the session's user that can trace the running session program could make it register what it likes, and one that can trace an application could take its token: the registrar is trusted as the session is. Manage Account is not offered yet: it is the SDK's own account screens, which Settings shows once it runs the SDK in host mode (`@oxy.so/services` with the platform's host).
   - **Tested.** The client library against a service of the tests' own (each answer and each refusal, a strict snapshot, a token never printed, a subscription that ends, a setup's second factor on its connection). Scenarios against a played service (regress.py's `account`): `account-session.json`, an application's token minted for its own entry and the account renamed elsewhere reaching it unasked; `account-session-offline.json`, signed in offline and no token; `account-session-refused.json`, a process the service does not know refused, the session unavailable to it; `account-session-unrecorded.json`, no host in a process the session did not start; `dropsea-signed-in.json`, Dropsea (on the SDK's host mode) taking the platform's session, its own SDK asking for a token of Dropsea's at boot and running no sign-in; `account-session-requests.json`, managing the account opening Settings at its Oxy account page; `account-session-sign-in.json`, signing in again locking the session; `settings-account.json`, Settings' account page, removing cancelled then confirmed; `settings-account-sign-out.json`, signing out cancelled then confirmed; `settings-account-keys.json` (and `-scaled`), the account item and its page from the keyboard with the reader on, in Spanish. Settings' scenarios without a played service show no account item, as before.
   - **What needs the ThinkPad:** `oxyos-accountd` with the session socket and the session's registration of each launch (steps 3 and 4's side); then an application's token minted for its own entry against production, and Settings' Sign Out… and Remove from This Computer… on an enrolled account.

## Not in this decision

- Disk encryption bound to the password (a home encrypted with a key the password unlocks, as `systemd-homed` or fscrypt can do), the TPM, and biometrics. The verifier in `/etc/shadow` protects sign-in, not data at rest.
- Accounts without a password by their nature: a Commons account, whose self-custody key signs in (Oxy ADR 0030 D1) and which cannot have a password. It needs a way in offline of its own.
- A guest or kiosk mode, which the product does not have.
