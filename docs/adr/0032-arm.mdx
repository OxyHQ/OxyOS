# ADR 0032: ARM (AArch64)

Status: **proposed**. Steps 1 and 2 implemented and run; the rest to come. Builds on [ADR 0004](./0004-gpu-composition) (composition on a Vulkan device, the CPU reference), [ADR 0017](./0017-boot-logo) (the boot logo), [ADR 0023](./0023-installing-oxyos) (installing: the gate, systemd-boot under Debian's shim, the whole disk) and the [base image configuration](../iso-build).

## Problem

OxyOS has been built, tested and booted only on x86-64 PCs with UEFI; ADR 0023 left every other machine out. The platform's author asks that it also install on ARM laptops and boards: "Microsoft Surface, Google Pixelbook, Raspberry, etc.".

Those are not one kind of machine:
- **The Pixelbook is not ARM.** Google's Pixelbook (2017) is an Intel Core i5/i7 (Kaby Lake) Chromebook. It runs the x86-64 image only once its coreboot firmware has a UEFI payload, which ChromeOS's does not; replacing firmware is not something OxyOS does. ARM Chromebooks exist (MediaTek Kompanio, Qualcomm), and are treated below.
- **Snapdragon X laptops** (the Surface Laptop 7 and Pro 11, Lenovo's ThinkPad T14s Gen 6 and Yoga Slim 7x, Dell's XPS 13 9345, HP's OmniBook X, ASUS's Vivobook S15) have UEFI, but ACPI tables only Windows can use: Linux runs them from a **device tree**, one per machine, which the firmware does not provide.
- **The Raspberry Pi 5 and 4** have no UEFI: their own firmware, on the boot medium's FAT partition, starts the kernel. They are boards, with HDMI displays, not laptops.
- **Generic UEFI arm64** (Arm SystemReady machines: Ampere workstations, QEMU's `virt`) boots exactly as a PC does: UEFI, a bootloader on the ESP, ACPI or a device tree from the firmware.

What upstream supports moves quickly, and what Debian Trixie ships is a year behind it (kernel 6.12, Mesa 25.0.7, systemd 257). Each claim below names the version it holds from, as checked on 2026-10-30 against the kernel's tree, Mesa's, and Debian's archive (madison and packages.debian.org).

## Decision

1. **Two architectures, one OS.** OxyOS is built for `amd64` and `arm64` (AArch64), Debian's ports, from the same sources and Debian Trixie, through the same gate (ADR 0023, decision 8) for each. No 32-bit ARM (`armhf`), no big-endian, no other port.
   - **The code is architecture-neutral and tested on both.** CI runs every native check on x86-64 and natively on AArch64 (GitHub's Arm runners, `ubuntu-24.04-arm`). The workspace has no SIMD intrinsics or `target_arch` code of its own; its wire and file formats are little-endian by construction (`to_le_bytes`), and both architectures are little-endian. What differs is found by running, not assumed (step 1 found three things).
   - **`c_char` is signed on x86-64 and unsigned on AArch64.** Code never casts it to or from `u8`/`i8`: a C string is read as a C string.
   - **The same pixels on both.** The Bloom host (C++: React Native's Fabric and Yoga, the host's drawing) is built with `-ffp-contract=off`: Clang otherwise fuses `a * b + c` into one multiply-add wherever the target has one (every AArch64, x86-64 only with `-mfma`), which rounds once instead of twice and moves layout and drawing by a level here and there. Rust never contracts. Hermes keeps its own setting (`-ffp-contract=on`, controlled in its source, as React Native ships it on Android's arm64), and its JIT stays off (`HERMESVM_ALLOW_JIT=0`, the default): Hermes's JIT exists only for arm64, and turning it on would run different code on the two architectures.
   - **Page sizes of 4 and 16 KiB.** Debian's arm64 kernel uses 4 KiB pages; Debian also ships `linux-image-arm64-16k`, and Raspberry Pi OS boots a Pi 5 with 16 KiB pages. Nothing in OxyOS assumes a page size (no `mmap` of its own, no offset arithmetic on pages), and every loadable segment of the binaries and libraries built is 64 KiB-aligned (GNU ld's and LLD's AArch64 default), so they load on 4, 16 and 64 KiB kernels. React Native and Hermes support 16 KiB pages (Android 15 requires it). 64 KiB kernels are not a target.

2. **The order: generic UEFI arm64, then the Raspberry Pi 5 (and 4), then Snapdragon X laptops.** Each tier is a class of machine with a named reference machine on which it is validated, as the ThinkPad P14s is for x86-64 (ADR 0004):
   1. **Generic UEFI arm64**, reference: QEMU `virt` with AAVMF (EDK II), where the boot acceptance tests run, with and without Secure Boot. It is the baseline because it is the PC's boot path on another instruction set: the same ISO, the same installer, the same chain of trust. Everything else adds to it.
   2. **Raspberry Pi 5**, then the Pi 4, reference: a Raspberry Pi 5 with 8 GB. The most widespread ARM machine people can buy for OxyOS, with a conformant Vulkan driver.
   3. **Snapdragon X laptops**, reference: the **Lenovo ThinkPad T14s Gen 6** (X1E-78-100), the best-supported one upstream: device tree since Linux 6.12, its signed firmware in Debian (`firmware-qcom-soc`), its keyboard and touchpad on HID over I2C, its audio in alsa-ucm-conf. Then the **Surface Laptop 7**, which needs two things the T14s does not (decision 5 and 7).

   A tier is supported once its reference machine passes the same checks the ThinkPad does (the boot logo, the session's regression on the display, suspend and resume where the hardware has it); until then it is in development, and nothing is published for it.

3. **How each boots.**
   - **Generic UEFI arm64: as a PC.** The live medium is an ISO with GRUB for UEFI (`grub-efi-arm64`), started by Debian's shim. Trixie's `shim-signed` 1.51 on arm64 is signed by Microsoft (`shimaa64.efi`, with both the 2011 and the 2023 UEFI CA), so machines that trust Microsoft's third-party CA boot it with Secure Boot on. An installed system is ADR 0023's: systemd-boot (`systemd-boot-efi-arm64-signed`, signed by Debian, which shim trusts), Boot Loader Specification entries, boot counting. No BIOS path exists on arm64.
   - **Snapdragon X: UEFI, and a device tree chosen for the machine.** systemd-boot loads the kernel with the machine's device tree: as unified kernel images with the device trees of every supported machine in `.dtbauto` sections, systemd's stub choosing by the firmware's compatible string or the machine's SMBIOS hardware IDs (`.hwids`, systemd 257, in Trixie). Not GRUB: its `devicetree` command is disabled under Secure Boot's lockdown, and an EFI driver that installs the tree (DtbLoader) does not work behind shim and GRUB. This needs the UKIs ADR 0023's decision 4 already plans, signed by OxyOS's key; until then a Snapdragon development install boots a Type 1 entry with a `devicetree` line and Secure Boot off. The live medium's boot on Snapdragon is the same UKI, so a Snapdragon live medium waits for OxyOS's signing (step 5).
   - **Raspberry Pi: its own firmware, no UEFI.** The Pi's boot firmware (Debian's `raspi-firmware`) on a FAT partition reads `config.txt` and starts the kernel and initramfs directly with the board's device tree; `raspi-firmware`'s hooks copy each new kernel, initramfs and device tree there. No GRUB, no systemd-boot, no shim: the Pi has no UEFI Secure Boot (its own signed-boot mode burns a customer key into OTP, which OxyOS does not do). The community UEFI firmware is not used: the Pi 5's (`worproject/rpi5-uefi`) is archived, and the Pi 4's (`pftf/RPi4`) limits memory to 3 GB by default and favours ACPI.
4. **Kernels: Trixie's where it suffices, Trixie's backports where a tier needs newer.**
   - Generic UEFI arm64 and the Pi 4 run Trixie's kernel (6.12, `linux-image-arm64`).
   - **The Pi 5 needs Linux 7.1 or later.** Trixie's 6.12 has the Pi 5's device tree with only its CPU, serial port, SD card and GPIO: PCIe landed in 6.16, the RP1 south bridge (USB, Ethernet, the GPIO header) in 6.17 and 6.18, the GPU's node in 7.1. Debian's own page says the Pi 5 needs Forky. The Pi image takes `linux-image-arm64` from `trixie-backports` (7.2 today), which Debian signs and supports with security updates as it does Trixie's.
   - **Snapdragon X needs Linux 7.0 or later for this tier as a whole**, from `trixie-backports` likewise: Trixie's 6.12 has the T14s's, Surface Laptop 7's, Yoga Slim 7x's and Vivobook S15's device trees and the Adreno X1-85 (6.11), but not external displays over USB-C (the PS8830 retimer driver, 6.15), the XPS 13 9345 (6.13), the X1P chips' GPU (6.17) or the Surface Pro 11 (7.0).
   - **One arm64 system.** When step 4 begins, the arm64 image takes its kernel, and later Mesa and the Qualcomm firmware, from `trixie-backports`, pinned to those packages (the rest stays Trixie's), for every arm64 machine alike: tiers differ in how they boot and what firmware they find, not in their packages. Until then, and for the console base of step 2, it is Trixie's 6.12.

5. **Graphics: Vulkan on the machine's GPU, or the CPU reference; never lavapipe on a display.** ADR 0004's rule holds on every architecture: the session composes on a Vulkan GPU whose buffers the display can scan out, and otherwise on the CPU reference into dumb buffers. Mesa's lavapipe proves the Vulkan path in CI and in QEMU, never a session's performance.
   - **Raspberry Pi 4 and 5: V3DV.** Mesa's V3DV is Vulkan 1.3 conformant on both (Mesa 24.3; Trixie has 25.0.7), its display the `vc4` driver (the Pi 5's HDMI since 6.14). The GPU (`v3d`, a render node) and the display (`vc4`) are **two DRM devices**, and `vc4` scans out only contiguous memory, which `v3d`'s buffers are not. So on the Pi the scanout buffers are allocated on the display device and imported into Vulkan (`VK_EXT_external_memory_dma_buf` with `VK_EXT_image_drm_format_modifier`), the reverse of the path the ThinkPad uses today (Vulkan's buffers exported to i915, one device). That import is step 3; until it exists the Pi composes on the CPU.
   - **Snapdragon X: Turnip.** The Adreno X1-85 has the kernel's `msm` driver since 6.11 and Mesa's freedreno and Turnip since Mesa 24.2; Turnip advertises Vulkan 1.4 on it in Mesa 25.0 (no conformance submission yet). The X1P's X1-45 needs Mesa 25.2 (`trixie-backports` has 25.2.6 and 26.1.6). The display is `msm`'s DPU; eDP works on Trixie's kernel, USB-C displays from 6.15.
   - **QEMU `virt`: no GPU.** virtio-gpu gives the guest no Vulkan, so the session composes on the CPU; the acceptance tests check the boot logo and the console there, as they do on amd64.
   - **Mali (ARM Chromebooks): no.** Mesa's PanVK refuses Valhall v9 (Mali-G57, the MediaTek MT8188/8192/8195 Chromebooks) and loads on Bifrost (MT8183/8186) only with `PAN_I_WANT_A_BROKEN_VULKAN_DRIVER=1`.

6. **Images: one configuration, an image for each architecture, and the Pi's own kind of image.** `config/` stays one live-build configuration; the architecture is chosen when building (`tools/image/build.sh build --arch arm64`), the one manifest marks what only one architecture installs with live-build's `#if ARCHITECTURES` blocks, and the image is `oxyos-base-<version>-<commit>-arm64.iso` beside the amd64 one ([base image configuration](../iso-build)). The arm64 build runs in the same Debian container image (pinned by digest for each architecture), as arm64, under QEMU's user-mode emulation on an x86-64 machine or natively on an ARM one, so live-build builds for the machine it runs on and nothing is cross-installed.
   - **The generic arm64 ISO** is the amd64 ISO's twin: UEFI only, GRUB and shim on the medium, the same live system, boot logo and services.
   - **The Raspberry Pi gets a disk image, not an ISO** (step 4): the system written whole to the card or NVMe drive it runs from, a FAT partition with the Pi's firmware, kernel and device trees, and the root, which grows to the medium at the first boot (systemd-repart's `GrowFileSystem=`). That is how a Pi is installed (as Raspberry Pi Imager writes one): there is no other disk to install to, and nothing to boot an installer from but the medium itself. It is built by the same container and gated by the same audit; QEMU has no Pi 5 (its `raspi4b` lacks the Pi 4's PCIe, USB and GPU), so its boot is tested on the reference Pi.
   - **Snapdragon X machines use the generic arm64 ISO**, once it carries the backports kernel and Mesa (decision 4) and boots through the signed UKIs of decision 3: their differences are a device tree and firmware, not a different system.

7. **Firmware: Debian's, named, redistributable; what a machine alone holds is copied from it, never shipped.** The amd64 rule ([base image configuration](../iso-build#package-manifest)) holds: the manifest names each firmware package, from Debian's `non-free-firmware`, nothing is downloaded while building or installing, and server and data-centre firmware is refused.
   - **arm64's firmware** is that of the devices ARM machines have which Debian packages. Most firmware packages serve both architectures (a PCIe GPU or Wi-Fi card is the same in an x86-64 PC and an AArch64 workstation, a USB adapter in any machine; the Pi's Wi-Fi is Broadcom's, `firmware-brcm80211`); what only PCs have (CPU microcode, Intel's integrated graphics, IPU cameras, SOF audio DSPs, old PCI cards) is amd64's alone, in the manifest's `#if ARCHITECTURES amd64` block.
   - **Qualcomm's** (`firmware-qcom-soc`: the Adreno's, and for the T14s Gen 6 and Yoga Slim 7x their signed DSP and GPU zap firmware; Snapdragon X's Wi-Fi, ath12k's WCN7850, is already in `firmware-atheros`) joins the arm64 image with step 5, with the daemons the DSPs need (`pd-mapper`, `qrtr-ns`, `tqftpserv`, `rmtfs`), started only on a Qualcomm machine (bound to its remoteproc devices): unconditional, as Debian ships them, they would fail and mark every other machine's boot degraded.
   - **Firmware signed for one OEM's machines and not redistributable**, the Surface Laptop 7's and Pro 11's GPU zap shader and ADSP/CDSP images among them, exists only on that machine's Windows partition. The installer copies it from there (as Debian's `qcom-firmware-extract`, in Forky, does) **before** erasing the disk (ADR 0023, decision 2), into the installed root, and refuses to erase a machine whose firmware it cannot read (a BitLocker-encrypted Windows: it says so, and the person decrypts or suspends BitLocker first). Without it there is no GPU, sound or battery reading on those machines. The live medium uses the same files from the internal disk, read-only, when it can.
   - **The Pi's boot firmware** is Debian's `raspi-firmware`, on the Pi's image only.

8. **Input, audio and power, per tier.** The same stacks as on amd64 (libinput through logind, PipeWire, UPower, logind's suspend), with what each machine's drivers give:
   - **Snapdragon X.** Keyboards and touchpads on HID over I2C work (the T14s, the XPS 13); the Surface Laptop 7's and Pro 11's are on Microsoft's Surface Aggregator and HID over SPI, which mainline does not drive yet, so their built-in keyboard and touchpad do not work (USB ones do) and the Surface waits for that driver. Audio needs the machine's ADSP firmware, its ALSA topology and its UCM profile (`alsa-ucm-conf` 1.2.14 in Trixie has the T14s's and the Yoga Slim 7x's). The battery is reported through the ADSP (`pmic_glink`), so it too needs that firmware. Suspend is s2idle and not yet reliable on these machines: the tier's checks include it. The webcams have no mainline driver (no CAMSS on X1E as of 7.3): none.
   - **Raspberry Pi.** HDMI audio only on the Pi 5 (no headphone jack), HDMI and the jack on the Pi 4; no suspend (the hardware has no suspend to RAM): the session never offers it there, as it does not on a desktop without it. Input is USB and Bluetooth.
   - **Generic UEFI arm64** is whatever the machine's ACPI or device tree gives, as on a PC.

9. **Installing (ADR 0023) on each.**
   - **Generic UEFI arm64:** unchanged. The installer writes the tested image to the whole disk with systemd-repart, encrypts the root, installs systemd-boot (`systemd-boot-efi-arm64-signed`) behind Debian's Microsoft-signed `shimaa64.efi`; the acceptance tests run it in QEMU with AAVMF and Secure Boot on (`AAVMF_CODE.secboot.fd` with `AAVMF_VARS.ms.fd`, Microsoft's keys), as with OVMF on amd64.
   - **Snapdragon X:** as generic, plus the firmware copied first (decision 7) and the device tree in the boot entries (decision 3). Secure Boot needs Microsoft's third-party CA, which Secured-core PCs, Snapdragon X laptops among them, ship disabled ("Allow Microsoft 3rd Party UEFI CA" in Lenovo's firmware); whether the Surface's firmware offers it on its Snapdragon models is not confirmed. The installer checks the firmware's Secure Boot state and, where the third-party CA is not trusted, says how to enable it rather than turning Secure Boot off itself.
   - **Raspberry Pi:** the image is written to its medium (decision 6), and the first boot is setup (ADR 0023, decision 5) as on any machine. The root can be encrypted (LUKS2, unlocked in the initramfs with the account's password, as decision 3 of ADR 0023); there is no Secure Boot to bind it to.

## Steps

1. **The software builds and passes its tests on AArch64.** The workspace's checks on both architectures in CI; the Bloom host built for AArch64 and its regression run there.

   *Done and run* (results below).
2. **The arm64 console base:** `config/` building an arm64 image, `tools/image/acceptance` booting it in QEMU (`qemu-system-aarch64`, `virt`, AAVMF, virtio-gpu with an EDID of the size under test), and the contents audit on it.

   *Done and run* (results below).
3. **Scanout buffers on the display device, imported into Vulkan** (decision 5), for split display and render devices; the session on QEMU `virt` (CPU composition) with graphical acceptance, as ADR 0023's step 5 brings the session into the image.
4. **The Raspberry Pi 5 image** (decision 6): the disk-image build, `raspi-firmware`, the backports kernel (decision 4), the first boot's growth, the acceptance tests on the reference Pi 5 and its display, the host's regression on it with real timing. Then the Pi 4.
5. **Snapdragon X:** the backports kernel, Mesa and `firmware-qcom-*` in the arm64 image; UKIs with `.dtbauto` and `.hwids` signed by OxyOS's key (ADR 0023, decision 4); the installer's firmware copy and Secure Boot check; the T14s Gen 6 validated; then the Surface Laptop 7, once HID over SPI is upstream.

### Results of step 1

On the development machine (WSL2, x86-64), AArch64 runs through QEMU's user-mode emulation (`qemu-aarch64` 10.0, binfmt): the workspace cross-built (`aarch64-unknown-linux-gnu`, Debian's arm64 multiarch libraries), the Bloom host cross-built with Clang 19 for `aarch64-linux-gnu` against the same React Native, Hermes and Bloom revisions, and Hermes bytecode bundled once (it is the same on both). CI runs the checks natively on `ubuntu-24.04-arm`.

- **Workspace:** `cargo build`, `cargo test` (every test), `cargo clippy -D warnings` pass for AArch64 as for x86-64. The boot logo's test, which compares what the session's code draws with the committed theme's PNGs (drawn on x86-64), passes: the splash is byte for byte the same.
- **The host's regression:** of the 44 scenarios that run without a display or a seat, 37 pass every check under emulation. The other 7 fail only on time, as QEMU runs the host 10 to 15 times slower: frames counted during an animation (`modal`, `launcher`, `launcher-reduce-motion`, `material`, `native-animated`: 26 frames of a 600 ms animation where 30 to 42 are expected) or content looked for before the slower first frame (`shell`, `settings`). Native AArch64 hardware is their test (step 4).
- **The same pixels.** Every snapshot of the scenarios that pass on both architectures was compared byte for byte with x86-64's, the wall clock frozen and the time zone the same in both runs (the menu bar's clock and the solar wallpaper read them): 338 of 349 are identical. The other 11 are frames caught at another moment of a resize or an animation, or before the first frame: two of those scenarios (`window-resize-scaled`, `window-zoom-scaled`) differ between two x86-64 runs as well.

Running found three things, fixed here:
- **moxcms's NEON colour conversion took the blue of every second pixel from the first.** In moxcms 0.7.11 the AArch64 fixed-point paths (`rgb_xyz_q2_13_opt`, `rgb_xyz_q1_30_opt`) wrote pixel 2n+1's blue from pixel 2n's register (`vr0` for `vr1`), so on ARM an image with an ICC profile (Display P3 wallpapers) had its blue wrong by up to 4 levels on half its pixels, in pairs. x86-64's SSE and AVX paths were right. `crates/oxyos-image`'s test that converting a slice at a time gives the whole image's pixels failed on AArch64 only. moxcms 0.8.1 has the fix (0.9 needs Rust 1.89, above the workspace's).
- **`c_char` cast to `u8`**, a no-op on AArch64 that Clippy refuses (`unnecessary_cast`): the Vulkan device's name is read with ash's `device_name_as_c_str()`.
- **Fused multiply-adds in the host:** without `-ffp-contract=off`, 8 or 9 pixels of each of the sample's 59 snapshots differed by one level (an antialiased edge); with it, none.

And two assumptions of the build: `tools/rn-host-spike` named `/usr/lib/x86_64-linux-gnu`; it now takes Debian's multiarch directory of the machine it builds on (`build.sh`) and of the compiler's target (`CMakeLists.txt`, `CMAKE_LIBRARY_ARCHITECTURE`).

### Results of step 2

On the same machine, the arm64 build in the pinned Debian container run as arm64 under QEMU's user-mode emulation; the acceptance tests in `qemu-system-aarch64` (TCG, `virt`, `-cpu max`, 1920×1200 on virtio-gpu), at commit `1f6cc4d8fc17` with this change's configuration ([base image configuration](../iso-build)):

- **Built.** `oxyos-base-1.0-…-arm64.iso`, 998.5 MiB: 382 packages, 1119.5 MiB installed (505.7 MiB of firmware), a 532.1 MiB squashfs and a 104.8 MiB initramfs, in 2 h 6 min emulated with the caches warm (the amd64 build: 22 min).
- **Audited.** No forbidden package or file, every package in the manifest's closure; the residue is amd64's (the X11 client libraries `libpulse0` links). Two Intel firmware packages (`firmware-intel-graphics`, `firmware-intel-misc`) are on arm64 because `firmware-misc-nonfree` recommends them: Debian's packaging, documented in the manifest.
- **Booted.** All 18 checks pass with UEFI (AAVMF) and all 18 with Secure Boot (AAVMF's Microsoft keys; Debian's Microsoft-signed `shimaa64.efi` and signed GRUB; the system reports `SecureBoot` 1). The Oxy mark is the theme's `splash-1920x1200.png` byte for byte, 16 to 18 s after Enter (emulated), nothing drawn before it; the console follows, the boot ends `running` with no failed unit, the base's services and PipeWire up.
- **amd64 unchanged.** The amd64 image of the same commit is the same size and passes UEFI (18), Secure Boot (18) and SeaBIOS (17) with KVM.

Booting found one thing, fixed here for both architectures: **no boot logo where the firmware names a serial console.** QEMU's `virt`, like many arm64 machines, tells the kernel its serial port is the console (ACPI's SPCR table, the device tree's `stdout-path`), so the kernel enables it without a `console=` argument, and Plymouth, seeing a serial console, showed its text view on every display: black until the login prompt. The live and installed command lines now have `plymouth.ignore-serial-consoles` ([ADR 0017](./0017-boot-logo)); the kernel and systemd still write to that console, and the configuration check and the acceptance tests require the argument.

## Not supported

- **ARM Chromebooks** (MediaTek Kompanio, Qualcomm SC7180/SC7280). They boot only through coreboot's depthcharge, a vboot-signed kernel partition and developer mode's warning at every start, with no UEFI and no way to the chain of trust ADR 0023 decides; their Mali GPUs have no usable Vulkan (decision 5). Debian's installer can start on them; OxyOS does not target them.
- **The Surface Pro X** (SQ1, SQ2: Snapdragon 8cx, SC8180X): mainline has no device tree for it, and the out-of-tree work stopped in 2022.
- **Snapdragon X2** (Linux 7.3's first device trees, Mesa 26.0): later, as its own tier, once it reaches the backports.
- **Apple Silicon** Macs: not asked for. Their boot (iBoot, m1n1, U-Boot) and 16 KiB-only kernels are Asahi Linux's; a decision of its own if it is.
- **Raspberry Pi 3 and older**, 32-bit ARM and big-endian systems; kernels with 64 KiB pages.
- Booting Snapdragon X with ACPI instead of a device tree.
- The Pi's signed boot, and TPM-backed unlocking on any ARM machine (as on amd64, ADR 0023).
