# ADR 0003: Accessibility in the OxyOS display protocol

Status: **accepted; implemented** (protocol, compositor, the Bloom host's publication, actions and announcements); the screen reader that speaks is [ADR 0014](./0014-screen-reader). Issues: [#33](https://github.com/OxyHQ/OxyOS/issues/33), [#34](https://github.com/OxyHQ/OxyOS/issues/34). Builds on [ADR 0001](./0001-native-platform-boundaries).

## Problem

A screen reader must read and operate every application on OxyOS. OxyOS has no X11 or Wayland, and the Linux accessibility bus (AT-SPI over D-Bus) is not part of the session. Each surface's accessibility tree must reach the assistive technology from the application that owns the surface, crossing process boundaries the same way pixels do.

An application must not see another application's tree. An ordinary client must not be able to read or operate other clients.

## Decision

The display protocol carries accessibility, as it carries buffers. The compositor is the broker. It knows the surfaces, their geometry, their stacking and the session's grants.

1. **Applications publish one snapshot per surface.** The application sends:
   - `AccessibilityBegin { surface, nodes }`;
   - one `AccessibleNode { surface, index, parent, role, state, actions, rect }` per node: `actions` what it offers beyond activate and focus (increment, decrement, scroll forward, scroll backward, dismiss, set selection), as Android's node info lists them;
   - `AccessibleText { surface, index, field, text }` chunks for each node's name, its value, and its custom actions' labels (one per line);
   - for a text field, `AccessibleSelection { surface, index, start, end }`: its selection, in bytes of its value, between characters;
   - `AccessibilityCommit { surface }`.

   The committed snapshot replaces the previous one atomically.

   Messages stay within the protocol's fixed 64-byte packets, and text travels in the same whole-character chunks as `Text`.

   Rules for a snapshot:
   - Nodes are in reading order, each parent before its children (`parent < index`, or none for a root).
   - Rectangles are surface-local and logical.
   - The node with the application's accessibility focus carries the `focused` state.
   - A live region (Android's `accessibilityLiveRegion`) carries `live-polite` or `live-assertive`: an assistive technology announces what changes in it.
   - While a modal is shown, the window's snapshot is the topmost modal's alone, and a view marked modal for assistive technologies (`accessibilityViewIsModal`) is all of its surface's snapshot ([ADR 0039](./0039-keyboard-access), decision 2): what a modal covers cannot be reached.

   Limits:
   - 4096 nodes per surface;
   - 1024 bytes per text field;
   - roles and states from fixed sets.

   A malformed snapshot is a protocol error, like any other malformed request.
2. **Only an assistive technology reads trees.** A client whose credentials the session authority grants `accessibility` receives every surface's committed snapshot:
   - `AccessibilityTree { client, surface, parent, nodes }`, `parent` the surface's parent surface (a popup's), 0 for a toplevel: an assistive technology tells a popup appearing by it, as TalkBack tells a popup window's state change ([ADR 0014](./0014-screen-reader));
   - the nodes, with rectangles in global coordinates and what they offer;
   - their text, custom actions' labels and selections;
   - `AccessibilityCommitted { client, surface }`.

   When the surface goes away it receives `AccessibilityRemoved { client, surface }`. A newly connected assistive technology receives the current snapshots.

   While the session is locked ([ADR 0010](./0010-lock-screen)) it holds the lock surfaces' trees alone, as the screen shows them alone. Locking sends `AccessibilityRemoved` for every other tree it holds; nothing they publish while locked reaches it (nor a reader that connects meanwhile); unlocking sends each as it is then.

   Ordinary clients never receive any of these events, and clients still never learn each other's geometry.
3. **Actions go back to the owner.** The assistive technology sends `AccessibilityAction { client, surface, index, action, custom, start, end }`. The compositor checks it:
   - the target exists;
   - the node is in its committed snapshot;
   - the node offers the action: activate and focus any node; increment, decrement, scrolling, dismiss and set-selection where its `actions` say so; a custom action by an index among its labels; a selection within its value, between characters;
   - the session is not locked, unless the target is a lock surface.

   An action not offered is answered with nothing. Otherwise the compositor sends `AccessibilityAction { surface, serial, index, action, custom, start, end }` to the owning application. Any action's serial but a focus move's is the user's input, as a key press's is, so a menu it opens may grab with it; a focus move is navigation and authorizes nothing. Actions:
   - **activate:** what a double tap on the node does;
   - **focus:** move accessibility focus to the node;
   - **increment, decrement:** an adjustable node's value;
   - **scroll forward, scroll backward:** a scrolling node, by a page;
   - **dismiss:** close the node's dialog or popup;
   - **custom:** one of the node's own actions, by its index among the labels it published;
   - **set selection:** select `start..end`, bytes of its value.

   The application performs the action as its platform would. The Bloom host does as Android does: activation is React Native's accessibility click, which Pressability turns into `onPress` (or the node's `activate` accessibility action where it declares one); increment, decrement and custom actions are React Native's accessibility actions by name (`onAccessibilityAction`); scrolling moves the scroll view by its viewport, through the wheel's path; dismiss is a modal's close request (as Escape) or a popup's dismissal; set selection focuses the input and selects.
4. **Announcements go to assistive technologies alone.** An application announces with `AccessibilityAnnounce { surface, index, last, politeness, text }`: the text in chunks (`index` 0 begins it, `last` sends it), at most 1024 bytes, polite (after what is being said) or assertive (at once), from one of its own live surfaces. The compositor sends it whole, in chunks, as `AccessibilityAnnouncement { client, surface, index, last, politeness, text }` to every assistive technology, never to any other client; while locked, only the lock surfaces' announcements are sent. The Bloom host announces `AccessibilityInfo.announceForAccessibility` assertively, as an announcement is what the application says now. A live region's changes are not announced by the application: the assistive technology compares what a live region says between two snapshots of a surface, as TalkBack does Android's.
5. **What applications must not publish.** Secure text (`secureTextEntry`) values and selections are never sent. The name of a secure field is its label.

## Consequences

- The screen reader is an ordinary protocol client with a grant, like the shell. It can be written for OxyOS without D-Bus. An AT-SPI bridge remains possible as such a client if Orca support is wanted later.
- Applications other than the Bloom host publish nothing until they implement the messages. A surface without a snapshot is presented to the assistive technology as empty, never guessed from pixels.
- The screen reader that speaks is OxyOS's own, `tools/oxyos-reader`, with eSpeak NG ([ADR 0014](./0014-screen-reader)); the development compositor's reader still checks what an assistive technology holds and would say. Text navigation by character, word or line is the screen reader's own, over a field's value and selection; the protocol carries both.
- `scenarios/accessibility-actions.json` (`sample/A11yProbe.tsx`) works the actions and announcements through what the reader holds and would say: increment, decrement and a custom action by its label change a level a polite live region announces; an announcement is heard at once; a list scrolls on and back by a page and offers each only while it can; a field's selection is set in bytes and held; a dialog's first node dismisses it; a label the node does not have, a direction it cannot scroll, a selection inside a character and an increment of a button are refused. Without the host reading `accessibilityActions` it fails at its first step.
- `scenarios/desktop-accessibility.json` works the desktop as a screen reader would, through the trees the development compositor's assistive technology receives (not the compositor's own state) and its actions alone: the dock opens the launcher, its search and applications are read, the Oxy menu locks the session, the lock screen is all it holds, a wrong password is an alert, and unlocking gives it the window and the panels back. Taking out the lock's hiding fails it.
