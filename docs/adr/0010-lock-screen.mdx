# ADR 0010: The lock screen

Status: **accepted; implemented** (steps 1 to 3, see step 3 for the ThinkPad's results). Builds on [ADR 0001](./0001-native-platform-boundaries) (roles, grants, the secure lock), [ADR 0006](./0006-seat) (the session on a logind seat) and [ADR 0009](./0009-session-shell) (the session's shell).

## Problem

A session cannot be locked. The compositor's core already holds the lock (`Scene::lock`, `Scene::unlock`): while locked it renders only lock surfaces, or an opaque cover of its own on an output without one, dismisses popups and grabs, and delivers input only to lock surfaces; a client with the `lock` grant makes a lock surface per output (`CreateLockSurface`); `unlock` is reachable from no protocol request. What is missing is everything around it:

- nothing locks the session: no shortcut, no menu item, nothing before the machine sleeps;
- nothing draws a lock screen;
- nothing checks a password, and so nothing may call `unlock`.

[`native-architecture.mdx`](../native-architecture) sets the rules: the lock belongs to the compositor and the session authority; it covers every output and blocks protected content and input before it is acknowledged; a failed or crashed lock screen leaves the session protected; authentication succeeds only through a narrow trusted path; the shell is never an authentication authority.

## Decision

1. **Locking is cheap; unlocking is not.** Locking only protects, so several things may ask for it:
   - the compositor's own shortcut, **Ctrl+Super+Q**, as macOS's Ctrl+Cmd+Q, handled by the compositor before any client sees the key;
   - the shell (its `shell` grant), from its menu ("Bloquear pantalla");
   - logind: its `Lock` signal (`loginctl lock-session`), and `PrepareForSleep(true)` before the machine sleeps. The session holds a logind *delay* inhibitor for sleep and releases it only once the lock's covers are on every output, so the machine never wakes to an unlocked screen, as a Mac locks before it sleeps.

   A lock is immediate: the scene stops showing and delivering to every ordinary surface at once, and the compositor's covers are on the next frame of every output, whatever any client does. Only `unlock` undoes it.

2. **The lock screen is the shell's, and has no authority.** The session grants the shell `lock` as well as `shell`. While locked, the shell makes one lock surface per output and draws the lock screen in it with Bloom, as macOS's: the wallpaper dimmed, the time and date large in the wallpaper's material (the wallpaper, blurred and lightened, seen through their glyphs; as the lock screen appears they settle from a little above, fading in, and each digit turns as it changes), the user's picture and name, and a password field (a secure field, whose text the compositor, the report and accessibility never see, [ADR 0008](./0008-input-method)). A wrong password shakes the field and says so; Caps Lock on is shown. The lock surface is an ordinary client surface: what it shows unlocks nothing.

3. **A password reaches PAM through the compositor, and only PAM unlocks.** New requests, `AuthenticateSecret { surface, secret }` (the password in chunks, as text is, at most 512 bytes, Linux-PAM's longest answer) and `Authenticate { surface }`, are accepted only from a lock surface; given while the session is not locked, a password is dropped. The session authority (`oxyos-session`, the user's own process) checks it with **PAM**, the system's established mechanism, as the session's user, under the service `oxyos` (`/etc/pam.d/oxyos`: the system's `common-auth` and `common-account`). The check runs off the compositor's thread (PAM may take seconds: `pam_faildelay`), one at a time; the answer is an event, `AuthenticationResult { surface, outcome, wait_s }` (`accepted`, `rejected`, `busy`, `throttled`, and the seconds until another may be tried). Only `accepted` calls `Scene::unlock`. After five rejections in a row each further attempt waits longer (30 s, then doubling to 15 min), as macOS's does; an unlock resets it. The secret is overwritten in memory once PAM has it, and never logged or reported. Clients with the `lock` grant are told when the session locks and unlocks (`LockState`), and when they connect while it is locked.

4. **Failing closed.** If the lock screen's client goes away while locked (it crashed, or was killed), the session stays locked under the compositor's covers and the session starts the shell again; until a lock surface returns, nothing but the covers is shown and nothing reaches any application. No failure path calls `unlock`.

## Steps

1. **The session's side.** `Authenticate` and `AuthenticationResult` in the protocol; the lock triggers (the shortcut, the shell's request, logind's `Lock` and the sleep inhibitor); the PAM check in a new crate (`oxyos-auth`), its throttle, and restarting the shell while locked. Tested against real PAM with a test configuration directory (`pam_start_confdir`): a service of `pam_permit` accepts, one of `pam_deny` rejects; the throttle and the secret's handling are unit-tested.

   *Done.* `oxyos-auth` declares the part of Linux-PAM's interface it calls (`pam_start`, `pam_authenticate`, `pam_acct_mgmt`, `pam_end`) and links `libpam.so.0`, rather than `pam-client`: that binding builds its declarations with `bindgen` from PAM's development files, and the five functions are a stable, documented C interface. The tests go further than `pam_permit` and `pam_deny`: `pam_exec` with `expose_authtok` checks the password the conversation gave against the right one, so a mangled or truncated password fails, as do an empty one, a refused account and a broken configuration. The compositor, the scene and the C ABI are tested with the authentication path replaced by a fixture.
2. **The lock screen.** The host makes lock surfaces (`CreateLockSurface`, as it makes shell surfaces), the shell draws the lock screen in them, and the shell's menu locks. A scenario locks the session, checks that no application surface is shown or reached, that a rejected password shakes and says so, and that an accepted one unlocks with the windows as they were. The development compositor answers `Authenticate` from its own fixture, never PAM; it is not a session, and the session never has that fixture.
   *Done.* The shell's root draws a `lock` region (`apps/shell/src/components/LockScreen.tsx`) while the compositor says the session is locked (`LockState`); the Bloom host draws it in a lock surface of its own and sends the password from it (`OxyOSShell.authenticate`), and the compositor's answer reaches the lock screen as `OxyOSShellAuthentication`. The field is focused at once (`autoFocus`, which the host now honours as Android does) and stays focused through each attempt (`submitBehavior="submit"`); typing again clears what the last attempt said; Caps Lock on is said under the field (the compositor tells the focused surface, `CapsLock`, from the keymap's locked modifier). The Oxy menu has "Bloquear pantalla". The password reaches JavaScript as a string, as a secure field's text does on Android: Hermes cannot overwrite it, so it lives in the shell's memory until it is collected; past the shell it is held as decision 3 says. `scenarios/lock-screen.json` locks from the menu and checks that only the lock screen is shown and reached, that Caps Lock on is said and then no longer, that a wrong password is rejected and said so with the field still focused, that the right one unlocks with the panels and the window as they were and the window taking its presses again, and that neither password appears in any report or in what the compositor holds; with another password for the fixture the run fails. On the ThinkPad a password typed at a person's pace was rejected every time: Enter arrived before the field's last characters had reached React's state, and the lock screen sent that state. It sends what the field holds as Enter is pressed (`nativeEvent.text`), and the scenario now types a password and Enter in one turn. Writing it found the host reporting a secure field's text in clear when the field lost focus; fixed, and `scenarios/secure-field.json` checks it.
   *The clock's material* (`apps/shell/src/components/LockClock.tsx`): the wallpaper is expo-blur's `BlurTargetView`, and the date and the time are each a masked view (the platform's `Masked`, React Native's MaskedView) whose mask is their glyphs over a `BlurView` of that target (radius 25, light tint), which the Bloom host blurs as Dimezis' view does on Android (`docs/react-native-android-adaptation.mdx`); each digit sits in a box of its own and turns (rises and fades, 420 ms) when it changes, and the clock settles in (600 ms) as the lock screen appears. An assistive technology reads the time and the date whole. The browser preview, which masks no views, draws the glyphs white. Drawing only the mask's opaque box keeps a frame of the lock screen at 10 ms median while it animates; `scenarios/material.json` checks the material and the turn.
3. **On the ThinkPad.** Locking with the shortcut and before sleep, a wrong and a right password with the real PAM, and the shell killed while locked.

   *Done*, on a ThinkPad (Debian trixie, Intel Iris Xe) running `oxyos-session` from a logind session on a terminal, `/etc/pam.d/oxyos` installed:
   - **Real PAM:** the owner's password unlocks through `pam_unix` (and `unix_chkpwd`, as the session's own user), and wrong ones are rejected and throttled. Two faults surfaced here and are fixed with regressions: the lock screen sent React's state rather than what the field held as Enter was pressed, losing the last characters typed at a person's pace; and the trial ran the session with a Spanish keymap while the system's (`/etc/default/keyboard`), which the password is typed with at a login, is US: the session now takes the system's keyboard.
   - **The shortcut:** Ctrl+Super+Q pressed on a virtual keyboard through the kernel, libinput and the keymap, as a person's, locks the running session (logind's `LockedHint` turns yes).
   - **Before sleep:** `systemctl suspend` with the RTC set to wake the machine (`rtcwake -m no`): the session, unlocked before, held logind's delay inhibitor until it was locked on screen, the machine slept and woke, and the session was locked and holding a new inhibitor. (`rtcwake -m mem` alone suspends without logind, so no session hears of it; it is no test of this.)
   - **logind's lock:** `loginctl lock-session` locks it, and `LockedHint` follows.
   - **Cost:** locked and idle, the compositor uses 0.03 % of a core, the shell 1 %, the application 0.8 %. On the device path (KMS, the GPU, virtual devices) `lock-screen.json` passes with 24–36 ms median input-to-frame latency.
   - `pam_unix`'s account check logs `setuid failed: Operation not permitted` as a non-root caller; the check still answers (the unlock above went through it).

   The shell killed while locked was not repeated on the ThinkPad; the session's restart path is the one the scene's and compositor's tests exercise.

## Not in this decision

- **The login screen** (before a session exists, as macOS's login window): a separate program that authenticates and then starts the user's session. It needs its own decision.
- An idle timeout that locks after a set time; notifications and media controls on the lock screen; biometrics.
- Switching to another terminal while locked: the lock protects the graphical session; a text terminal's login is the system's own.
