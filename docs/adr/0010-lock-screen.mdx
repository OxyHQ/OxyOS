# ADR 0010: The lock screen

Status: **accepted**; steps 1 (the session's side) and 2 (the lock screen) implemented, step 3 (on the ThinkPad) not yet. Caps Lock is not shown yet (decision 2): the shell does not know the keyboard's lock state. Builds on [ADR 0001](./0001-native-platform-boundaries) (roles, grants, the secure lock), [ADR 0006](./0006-seat) (the session on a logind seat) and [ADR 0009](./0009-session-shell) (the session's shell).

## Problem

A session cannot be locked. The compositor's core already holds the lock (`Scene::lock`, `Scene::unlock`): while locked it renders only lock surfaces, or an opaque cover of its own on an output without one, dismisses popups and grabs, and delivers input only to lock surfaces; a client with the `lock` grant makes a lock surface per output (`CreateLockSurface`); `unlock` is reachable from no protocol request. What is missing is everything around it:

- nothing locks the session: no shortcut, no menu item, nothing before the machine sleeps;
- nothing draws a lock screen;
- nothing checks a password, and so nothing may call `unlock`.

[`native-architecture.mdx`](../native-architecture) sets the rules: the lock belongs to the compositor and the session authority; it covers every output and blocks protected content and input before it is acknowledged; a failed or crashed lock screen leaves the session protected; authentication succeeds only through a narrow trusted path; the shell is never an authentication authority.

## Decision

1. **Locking is cheap; unlocking is not.** Locking only protects, so several things may ask for it:
   - the compositor's own shortcut, **Ctrl+Super+Q**, as macOS's Ctrl+Cmd+Q, handled by the compositor before any client sees the key;
   - the shell (its `shell` grant), from its menu ("Bloquear pantalla");
   - logind: its `Lock` signal (`loginctl lock-session`), and `PrepareForSleep(true)` before the machine sleeps. The session holds a logind *delay* inhibitor for sleep and releases it only once the lock's covers are on every output, so the machine never wakes to an unlocked screen, as a Mac locks before it sleeps.

   A lock is immediate: the scene stops showing and delivering to every ordinary surface at once, and the compositor's covers are on the next frame of every output, whatever any client does. Only `unlock` undoes it.

2. **The lock screen is the shell's, and has no authority.** The session grants the shell `lock` as well as `shell`. While locked, the shell makes one lock surface per output and draws the lock screen in it with Bloom, as macOS's: the wallpaper dimmed, the time and date large, the user's picture and name, and a password field (a secure field, whose text the compositor, the report and accessibility never see, [ADR 0008](./0008-input-method)). A wrong password shakes the field and says so; Caps Lock on is shown. The lock surface is an ordinary client surface: what it shows unlocks nothing.

3. **A password reaches PAM through the compositor, and only PAM unlocks.** New requests, `AuthenticateSecret { surface, secret }` (the password in chunks, as text is, at most 512 bytes, Linux-PAM's longest answer) and `Authenticate { surface }`, are accepted only from a lock surface; given while the session is not locked, a password is dropped. The session authority (`oxyos-session`, the user's own process) checks it with **PAM**, the system's established mechanism, as the session's user, under the service `oxyos` (`/etc/pam.d/oxyos`: the system's `common-auth` and `common-account`). The check runs off the compositor's thread (PAM may take seconds: `pam_faildelay`), one at a time; the answer is an event, `AuthenticationResult { surface, outcome, wait_s }` (`accepted`, `rejected`, `busy`, `throttled`, and the seconds until another may be tried). Only `accepted` calls `Scene::unlock`. After five rejections in a row each further attempt waits longer (30 s, then doubling to 15 min), as macOS's does; an unlock resets it. The secret is overwritten in memory once PAM has it, and never logged or reported. Clients with the `lock` grant are told when the session locks and unlocks (`LockState`), and when they connect while it is locked.

4. **Failing closed.** If the lock screen's client goes away while locked (it crashed, or was killed), the session stays locked under the compositor's covers and the session starts the shell again; until a lock surface returns, nothing but the covers is shown and nothing reaches any application. No failure path calls `unlock`.

## Steps

1. **The session's side.** `Authenticate` and `AuthenticationResult` in the protocol; the lock triggers (the shortcut, the shell's request, logind's `Lock` and the sleep inhibitor); the PAM check in a new crate (`oxyos-auth`), its throttle, and restarting the shell while locked. Tested against real PAM with a test configuration directory (`pam_start_confdir`): a service of `pam_permit` accepts, one of `pam_deny` rejects; the throttle and the secret's handling are unit-tested.

   *Done.* `oxyos-auth` declares the part of Linux-PAM's interface it calls (`pam_start`, `pam_authenticate`, `pam_acct_mgmt`, `pam_end`) and links `libpam.so.0`, rather than `pam-client`: that binding builds its declarations with `bindgen` from PAM's development files, and the five functions are a stable, documented C interface. The tests go further than `pam_permit` and `pam_deny`: `pam_exec` with `expose_authtok` checks the password the conversation gave against the right one, so a mangled or truncated password fails, as do an empty one, a refused account and a broken configuration. The compositor, the scene and the C ABI are tested with the authentication path replaced by a fixture.
2. **The lock screen.** The host makes lock surfaces (`CreateLockSurface`, as it makes shell surfaces), the shell draws the lock screen in them, and the shell's menu locks. A scenario locks the session, checks that no application surface is shown or reached, that a rejected password shakes and says so, and that an accepted one unlocks with the windows as they were. The development compositor answers `Authenticate` from its own fixture, never PAM; it is not a session, and the session never has that fixture.
   *Done.* The shell's root draws a `lock` region (`apps/shell/src/components/LockScreen.tsx`) while the compositor says the session is locked (`LockState`); the Bloom host draws it in a lock surface of its own and sends the password from it (`OxyOSShell.authenticate`), and the compositor's answer reaches the lock screen as `OxyOSShellAuthentication`. The field is focused at once (`autoFocus`, which the host now honours as Android does) and stays focused through each attempt (`submitBehavior="submit"`); typing again clears what the last attempt said. The Oxy menu has "Bloquear pantalla". The password reaches JavaScript as a string, as a secure field's text does on Android: Hermes cannot overwrite it, so it lives in the shell's memory until it is collected; past the shell it is held as decision 3 says. `scenarios/lock-screen.json` locks from the menu and checks that only the lock screen is shown and reached, that a wrong password is rejected and said so with the field still focused, that the right one unlocks with the panels and the window as they were and the window taking its presses again, and that neither password appears in any report or in what the compositor holds; with another password for the fixture the run fails. Writing it found the host reporting a secure field's text in clear when the field lost focus; fixed, and `scenarios/secure-field.json` checks it.
3. **On the ThinkPad.** Locking with the shortcut and before sleep, a wrong and a right password with the real PAM, and the shell killed while locked.

## Not in this decision

- **The login screen** (before a session exists, as macOS's login window): a separate program that authenticates and then starts the user's session. It needs its own decision.
- An idle timeout that locks after a set time; notifications and media controls on the lock screen; biometrics.
- Switching to another terminal while locked: the lock protects the graphical session; a text terminal's login is the system's own.
