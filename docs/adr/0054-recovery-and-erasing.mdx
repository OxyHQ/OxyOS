# ADR 0054: Recovery and erasing

Status: **accepted** (decisions 1 to 9, taken with the platform's author's delegation); steps 1 and 2 implemented, step 1 run in QEMU ([results](#results)). Builds on [ADR 0023](./0023-installing-oxyos) (the image written whole, the disk, LUKS2, systemd-boot under shim, the gate), whose step 4 (the development installer) is implemented here and whose decisions 2 and 7 this amends; [ADR 0020](./0020-oxy-account-login) (enrolled accounts, `oxyos-accountd`, Remove), which it amends with administrators; [ADR 0017](./0017-boot-logo) (Plymouth and its passphrase field) and [ADR 0019](./0019-settings) (Settings).

## Problem

A computer must be able to come back: from an update that does not start, a file system that is damaged, a forgotten password, and to its first day before it is given away. A Mac has macOS Recovery (⌘R at startup, or by itself when the system does not start) and *Erase All Content and Settings*, which erases in an instant because the data volume is encrypted and erasing its key is enough. ChromeOS has Powerwash and a recovery image. OxyOS had neither, nor an installer that laid a disk out for one: an install was ADR 0023's step 4, still to do, and the only way to start over was the live medium.

What has to be decided: where the recovery lives and how it is verified; how it is reached, including when nobody can reach it by hand; what erasing destroys and what it keeps, who may ask for it and how it fails; what the recovery offers; and how the disk is laid out for all of it.

## Decision

1. **The recovery is the tested image itself, on a partition of its own, read-only.**
   - **The partition.** *OxyOS Recovery*, 3 GiB, between the EFI system partition and the root, of OxyOS's own GPT type (`ec68fd51-3b26-41e5-a32e-b0dff6fc5484`: no other system's tools take it for theirs, and systemd's discovery mounts no partition of a type it does not know). ext4, holding the live medium's `/live/`: the squashfs the installer copied, its dm-verity hash tree and root hash, its kernel and live-boot initramfs. 3 GiB holds today's image (0.8 GiB with its hash tree) with room for the session and runtime and for the next image beside the current one.
   - **Its boot entry.** `oxyos-recovery.conf` on the EFI system partition, a Boot Loader Specification Type 1 entry of its own, never counted: the medium's kernel and live-boot initramfs under `/oxyos-recovery/` on the EFI system partition (systemd-boot reads only the EFI system partition), booting the image on the recovery partition (`live-media=/dev/disk/by-partuuid/…`) read-only, with no persistence, into `oxyos-recovery.target` (`systemd.unit=`). No `components`: live-config makes no live user and logs nobody in.
   - **Why the image itself.** The image that passed the gate (ADR 0023, decision 8: built here, booted in QEMU, audited) is the one the recovery runs and the one it writes back. A second, smaller system (an initramfs-only userspace, busybox) would be a second image to build, test and audit, without NetworkManager and the Wi-Fi firmware to get online, and what it installed would not be what it ran.
   - **Rejected:** the recovery on the EFI system partition (FAT, no room for an image, and shared with other systems' loaders); a recovery only from the network (no published images yet, by the image rules; and a machine without a network must still come back); Debian's rescue mode (a root shell, not a recovery).
2. **Reaching it: the menu, a key held, and failed starts.**
   - **systemd-boot, as ADR 0023 chose.** Its menu is hidden (`timeout menu-hidden`) and lists only OxyOS's kernels and the recovery (`auto-entries no`, `auto-firmware no`); the command line cannot be edited at it (`editor no`): what a person at the keyboard chooses is which entry starts, not what the kernel is told.
   - **A key held as the machine starts.** Holding Space (or any key) as the machine starts shows the menu, the startup picker: OxyOS, *OxyOS Recovery*, and *Reboot Into Firmware Interface* (`auto-firmware`), the firmware's own settings, where a USB installer or another disk is started; the arrows choose and Enter starts. systemd-boot finds no other disk's loaders itself, has no pointer, and draws text. A graphical picker that lists every disk, as a Mac's Startup Manager does, is a boot manager of its own: rEFInd, the proven one, is not signed by anyone shim trusts, so under Secure Boot it needs a key enrolled by hand at the console (MOK) or OxyOS's own signing; it comes with OxyOS's own boot chain (ADR 0023, decision 4), not before, and no boot manager is written here. A single key that starts the recovery directly, as ⌘R does, needs a per-entry hotkey systemd-boot does not give Type 1 entries; patching it would replace Debian's signed binary and break Secure Boot until OxyOS signs its own boot chain (ADR 0023, decision 4). It comes with that chain. GRUB has per-entry hotkeys, but neither Boot Loader Specification entries nor boot counting, which are why ADR 0023 chose systemd-boot, and which the next point needs.
   - **By itself, after failed starts.** systemd-boot counts tries in an entry's file name and systemd-bless-boot marks a boot good once it reaches `boot-complete.target` (systemd's automatic boot assessment). An entry with no tries left is sorted last, so the recovery, never counted, comes first. OxyOS counts **every** boot, not only a new kernel's: after each complete one, `oxyos-boot-tries.service` gives the entry that booted its three tries back (`/etc/kernel/tries`). Three starts in a row that never complete, whenever they happen, end in the recovery. A boot is complete when the system reaches its default target (`boot-complete.target` is ordered after `multi-user.target`; the login screen, once it is in the image); a start left at the disk's password prompt and switched off counts as failed, as Windows counts an interrupted start. The recovery's *Restart* gives every OxyOS entry its tries back.
   - **From the running system,** `systemctl reboot --boot-loader-entry=oxyos-recovery.conf` (logind's one-shot entry), which a *Restart in Recovery…* of Settings will call.
   - **The live medium** remains the recovery of last resort: it installs, and it is the same image.
3. **Integrity: Secure Boot's chain, and dm-verity on the image.**
   - The firmware starts Debian's Microsoft-signed shim, which starts Debian-signed systemd-boot, which starts Debian-signed kernels, the recovery's as well as OxyOS's (ADR 0023, decision 4, kept).
   - The image carries a dm-verity hash tree (live-build's `LB_DM_VERITY`). live-boot reads every block of the squashfs through it, on the live medium and in the recovery, whose entry carries the root hash on its command line (`dm-verity-root-hash=`): a block that does not match is never read. The installer checks the medium's image against its root hash before writing anything, and the recovery's copy after copying it (`veritysetup verify`).
   - What this does not yet cover, said plainly: under Debian's chain the initramfs and the command line, the root hash on it included, are not signed (ADR 0023, decision 4). Verity here catches corruption and a damaged copy; against someone who can rewrite the EFI system partition, the answer is OxyOS's own signatures: a unified kernel image signing kernel, initramfs and command line together, and the root hash's signature (`.roothash.p7s`, which live-boot and the kernel check against the platform's keys), with OxyOS's shim (the publication gate).
4. **Erase All Content and Settings.**
   - **Where.** Settings › General › Transfer or Reset › *Erase All Content and Settings…*, as on a Mac. Only for an **administrator** (decision 8), after the administrator's own password. Its assistant says what is erased (every account on the computer with its files, apps and settings; Wi-Fi networks and the computer's settings), that OxyOS stays installed and the computer restarts into setup, and which accounts are signed out of this computer online and which cannot be because it is offline (their device session dies with the erased credential and expires on Oxy's side, or can be removed from the account's devices).
   - **The order, failing closed.** `oxyos-accountd`, on the session socket, for Settings registered as a system application alone: the asking account is an administrator, its password is checked locally against its verifier with the lock's throttle (never accepted on Oxy's word alone); then the erase is **armed** (`oxyos-erase.service`); then every enrolled account's device session is ended online when Oxy can be reached (ADR 0020's Remove, `POST /session/device/signout`), each failure or an offline machine noted and not stopping it; then the machine restarts. Anything that fails before arming changes nothing.
   - **Arming** (`oxyos-recovery arm-erase`, run by `oxyos-erase.service`) writes the erase request on the EFI system partition (`/oxyos-recovery/erase.json`: the disk's partition table UUID, the root partition's UUID, whether it is encrypted; written whole and flushed) and condemns every OxyOS entry (no tries left). From then on every start is the recovery's, whatever happens in between: a power cut, a key held, a person choosing OxyOS at the menu (the system boots, but does not give its entry tries back while an erase is pending).
   - **Impossible from an application.** Writing the EFI system partition and starting a system unit need root (polkit's default for `org.freedesktop.systemd1.manage-units` is an administrator's authentication); no application has either. The account service asks for it only for Settings, only for an administrator, only with their password.
   - **Carried out by the recovery**, which starts at once with the request and erases with no question (it was confirmed in Settings): the request rewritten `erasing`, then **the root destroyed**: for the LUKS2 root, `cryptsetup erase` overwrites every keyslot, so the volume key, and every byte the volume ever held, can no longer be read by anyone, at once (a crypto-erase, what a Mac's effaceable storage does); `wipefs` removes the header; the partition is then discarded. Then the old kernels' entries go and systemd-repart makes the root again (`--factory-reset=yes`, the root's definition carrying `FactoryReset=yes`) from the recovery's own image, encrypted with a new install key; it is set up exactly as an install sets it up; the request is removed; the computer restarts into a first boot, which is setup's (ADR 0023, decision 5).
   - **A root never encrypted** (encryption declined at install) cannot be crypto-erased: it gets a secure discard where the disk offers one, else a discard, else zeroes written over it, which on flash may not reach every cell. That is why encryption is on by default.
   - **Requests that are not this disk's.** An `armed` request is carried out only on the disk and the root it names: one left on a disk installed again since, or copied to another, erases nothing (it is removed, and the entries get their tries back). An `erasing` request resumes on its disk whatever the root is now, since it may be half erased: a power cut never boots what is left. A request that cannot be read erases nothing.
   - **What it keeps.** The EFI system partition's boot loader and the recovery partition, untouched; and OxyOS itself. On this development layout the system and the data share the root, so the system is written back from the recovery's image: the same OS, at the version of the image the recovery holds (packages a development install updated with apt since are those of the image again). On the published layout (ADR 0023, decision 6: the system as read-only A/B images) the system's slots are not touched at all and only the data is erased, as on a Mac.
5. **What the recovery offers.**
   - **Erase and Reinstall OxyOS:** decision 4's erase, from the recovery itself, for a computer that no longer starts (after the person types the confirmation word). It goes through the same request, so a power cut resumes it.
   - **Check and Repair the Disk:** `fsck.vfat` on the EFI system partition and a forced, repairing `e2fsck` on the root; an encrypted root is opened only with what opens it at boot (an account's password or the recovery key).
   - **Forgot your password?:** help, never a bypass. The password is the Oxy account's: it is reset online (Oxy signs a person in by email and the new password is set in Accounts › Security, Oxy ADR 0030); the disk is opened meanwhile with the recovery key; the first online sign-in with the new password replaces the verifier and the account's keyslot (ADR 0020, decision 2; ADR 0023, decision 3). Nothing in the recovery opens an account or the disk without one of them.
   - **Wi-Fi** (NetworkManager, its password on nmcli's standard input) and **Language** (English and Spanish today, as the rest of OxyOS).
   - **Restart** (OxyOS's entries get their tries back) and **Shut Down**.
   - **Not yet, and why.** *Reinstall OxyOS keeping your data* needs the system apart from the data, which is the published layout's (ADR 0023, decision 6): on the development layout one root holds both, and copying a system over a system that apt changed is not a reinstall. *Reinstall from the network* needs published images signed by OxyOS (with their TUF metadata, as applications' are, ADR 0030): none are published, by the image rules. Both arrive with decision 6's ADR, the recovery's choices already being where they go.
6. **The recovery's interface is a Bloom application on the compositor in a minimal mode;** until the session and runtime are in the image (ADR 0023, step 5), it is a program on the console.
   - **The target.** `oxyos-recovery.target` starts the compositor with a single full-screen client, the recovery (a Bloom application of this repository, as the login screen is), unprivileged, asking a root service (`oxyos-recovery serve`, a socket of its own, as `oxyos-accountd`'s) to do the work the library already does: no shell, no dock, no other application, no X11, Wayland or toolkit.
   - **Until then,** `oxyos-recovery console` on the system console (`/dev/console`: the screen, or the serial port the firmware or kernel names), root, the same choices as text. It is a real program doing the real work, the development installer's counterpart (ADR 0023, decision 7), not a placeholder.
7. **The disk and the development installer** (ADR 0023, decisions 2 and 7, amended; its step 4).
   - **Three partitions**, each known by its type: the EFI system partition (1 GiB, FAT32), OxyOS Recovery (3 GiB, decision 1), the root (the rest, ext4 with `encrypt`, LUKS2 by default, `FactoryReset=yes`). systemd-repart lays them out from definitions the program writes (`crates/oxyos-recovery`, `layout::definitions`), and fills them: the recovery with the medium's `/live/`, the root with the image's tree. repart leaves the contents of other partitions' mount points out of the root, so `/boot`, where Debian keeps the kernel, is copied by a line of its own.
   - **The program** is `oxyos-recovery install --developer --disk DISK [--no-encrypt] [--developer-user NAME]`: ADR 0030 has since given `oxyos-install` and `oxyos-installd` to applications, so ADR 0023's console installer is a subcommand of the recovery's program, which shares its whole procedure with the erase. It refuses the medium it booted from, a read-only or small disk and a machine that did not start through UEFI, and asks for the disk's name to be typed.
   - **Setting the root up**, the same for an install and an erase: opened and mounted with the EFI system partition at `/efi`; the live packages purged (`live-boot`, `live-config`, `live-tools`, `user-setup` and their documentation) with GRUB, the medium's boot loader (in the image, not installed into the build's chroot and purged after by live-build, since purging GRUB there runs systemd-boot's trigger, which fails where there is no EFI system partition; and Debian's systemd-boot installs shim only where no signed GRUB claims the partition); `/etc/fstab`, `/etc/crypttab`, `/etc/kernel/{cmdline,tries,entry-token}`, the hostname, an empty machine id (the first boot makes one); shim and systemd-boot installed by Debian's own `systemd-boot` maintainer script (`dpkg-reconfigure`), which also gives the firmware its entry for shim; OxyOS's `loader.conf`; the initramfs made, Debian's hook having kernel-install write each kernel's counted entry. Everything mounted is undone whether it succeeds or not.
   - **Encryption** as ADR 0023 decision 3: a random install key unlocks the first boot (`/etc/cryptsetup-keys.d/oxyos-root.key`, copied into the initramfs by cryptsetup-initramfs's `KEYFILE_PATTERN`, the initramfs readable by root alone) until setup replaces it. A development user's password takes its place at install, with a recovery key made by `systemd-cryptenroll` and shown once.
   - **The debian-installer leaves the image** (`LB_DEBIAN_INSTALLER="none"`), with its preseed for the installer and its menu entries.
8. **Administrators** (ADR 0020, amended). An administrator is an enrolled account whose user is in the `sudo` group: Debian's administrators, polkit's (`AdminIdentities`), so the system's authorizations and OxyOS's agree. The first account set up on a machine becomes its administrator; a machine set up before this decision makes the enrolled account with the lowest uid its administrator. That happens once (`oxyos-accountd` records it): an administrator removed later is not replaced by whoever is enrolled next, or anyone setting an account up at the login screen could become one and erase the machine. Making others administrators is Users & Groups', to come.
   - **The password is checked by PAM**, under a service of the account service's own (`/etc/pam.d/oxyos-accountd`), with the lock's throttle per account (five tries, then 30 s, 60 s…), never on Oxy's word alone.

9. **Converted machines boot like installed ones** (added 8 November 2026). A machine converted to OxyOS by hand on the partitions it had (the ThinkPad: Debian's installer's EFI system partition, an ext4 root of the generic Linux type, a swap partition, GRUB through shim) is brought to an install's boot, not given a second one: systemd-boot behind Debian's signed shim, its entries written by kernel-install and counted, the recovery's entry as an install has it. GRUB's menu hidden was weighed and set aside: it would keep two boot paths for one OS, and GRUB has no boot counting (decision 2).
   - **The recovery's partition** is taken from the swap: the swap partition is made again smaller, keeping its UUID (`mkswap -U`), so `/etc/fstab` and the resume configuration stay as they were, and *OxyOS Recovery* (OxyOS's type, 3 GiB) takes the space before it. Its file system holds the image's `/live/`, copied, checked by checksum and with `veritysetup verify`, and left read-only.
   - **The EFI system partition is mounted at `/efi`**, as an install's: OxyOS's programs find it there.
   - **systemd-boot** (Debian's signed `systemd-boot-efi-amd64-signed`) is put on the EFI system partition beside GRUB, shim beside it (`EFI/oxyos/`, Debian's `shimx64.efi` started with `\EFI\systemd\systemd-bootx64.efi` as its second stage, as Debian's own `systemd-boot` maintainer script does), with `/etc/kernel/{cmdline,entry-token,tries}` and kernel-install writing each kernel's entry; the firmware's entry for it is made without being put in the boot order and started once (`efibootmgr --bootnext`), so a failure starts GRUB again. Only once it has started the system, with its login screen, does it become the default, and GRUB's packages and entry go; Debian's script then finishes the partition as an install has it (`dpkg-reconfigure systemd-boot`: the fallback loader is shim).
   - **The recovery's entry** is written by `oxyos-recovery recovery-entry --system-root PARTUUID` from the recovery partition (its image checked against its root hash): an install's entry, which also names the machine's root (`oxyos.recovery.root=PARTUUID=…`), since the recovery cannot find it by its type.
   - **What the recovery does there.** It finds a *converted* layout (`disks::Kind::Converted`): it checks and repairs the disk, helps with a password, gets online and restarts (giving OxyOS's entries their tries back). It never erases: the disk is not laid out as an install, systemd-repart's definitions do not describe it, and the erase refuses it in the library itself, as `oxyos-erase.service` does on the running system (Settings then says erasing is not available). A converted machine is erased by installing OxyOS onto it from the installation medium, which also gives it an install's layout.

## Steps

1. **The installer, the recovery and the erase in the image** (this repository): `crates/oxyos-recovery` (the layout, the disks, the entries and their counting, the erase request, installing, erasing, checking the disk, the network) and `tools/oxyos-recovery` (the program and its units: `oxyos-boot-tries.service`, `oxyos-erase.service`, `oxyos-recovery.target`, `oxyos-recovery-console.service`, `boot-complete.target`'s ordering), packaged as OxyOS's first own program by `tools/image/build.sh packages` ([OxyOS's own programs](../iso-build#oxyoss-own-programs)); the manifest's installing packages; dm-verity on the image; the debian-installer out; `tools/image/acceptance --recovery`.

   *Done and run in QEMU* ([results](#results)).
2. **Settings and the account service:** administrators; `erasePreview` and `eraseAll` on the session socket (`eraseAll` answers `erasing` or `refused` with its reason; the erase stays armed for the service across its own restart, which then mints no tokens and refuses a second erase; a preview for someone who is not an administrator lists only their own account); the C ABI and the Bloom host's module; Settings › General › Transfer or Reset and its Erase Assistant ([#360](https://github.com/OxyHQ/OxyOS/pull/360)).

   *Done, off hardware* (the service's, the C ABI's and Settings' tests); its trial with an enrolled account is the ThinkPad's.
3. **The recovery's Bloom application** and `oxyos-recovery serve` (decision 6), with the session in the image (ADR 0023, step 5); *Restart in Recovery…* in Settings.
4. **Reinstall keeping the data, and from the network** (decision 5), with ADR 0023's decision 6.
5. **OxyOS's own signatures** for the recovery's kernel, initramfs and command line, and the root hash's signature (decision 3), with the publication gate.

### Results

On a developer's machine (WSL2, KVM), the image of commit `3f206ecad2a2` built by `tools/image/build.sh` (451 packages, a 789 MiB squashfs with a 6.3 MiB hash tree, a 944 MiB ISO) and audited (no violation; the known residue only), then `tools/image/acceptance --recovery`:

- **UEFI: 52 of 52 checks** in 726 s. **Secure Boot** (OVMF with Microsoft's keys: shim, then Debian's systemd-boot, then Debian's kernel, the recovery's as well as OxyOS's, `SecureBoot` 1 in both): **52 of 52** in 505 s. The image's own boot tests still pass: UEFI 18 of 18, Secure Boot 18 of 18, BIOS 17 of 17.
- **Install:** 97 s onto a 24 GiB virtual disk (332 s with another machine and a build sharing the host): the image checked against its root hash, the disk laid out, the recovery's copy checked, the system set up. The disk's layout, types and labels as decision 7 says; two keyslots (the developer's password and the recovery key), the install key gone; the live packages and GRUB purged; the firmware's entry for shim.
- **The installed system:** Plymouth's passphrase field on the boot logo, a bullet a character typed on the keyboard; `running`, no failed unit; after the first complete boot the entry has its three tries again (`+3`) beside the recovery's.
- **The recovery by a key:** Space held on the keyboard shows the menu (OxyOS, OxyOS Recovery and nothing else); the recovery boots its partition read-only through dm-verity (the root hash on its command line), into `oxyos-recovery.target`, no live user and no login, `running`, no failed unit; *Restart* goes back to OxyOS.
- **The recovery by failed starts:** three starts cut off at the password prompt leave the entry `+0-3`; the fourth start is the recovery, which says OxyOS could not start; *Restart* gives the tries back (`+3`).
- **Erase All Content and Settings:** `oxyos-erase.service` writes the request and condemns the entry; the next start is the recovery, which erases and installs again in 83 to 135 s; the first start after it asks for no password (the install key), is `running` with no failed unit, a first boot with a new machine id, no user, no home, no account; a new LUKS2 volume, which neither the old password nor the old recovery key opens and in whose first 64 MiB the old volume's UUID is nowhere; the recovery's entry and partition untouched; no request left; the new kernel's entry counted.
- **Erase and Reinstall** from the recovery's menu: the same, from the menu, after the confirmation word.

What building and running found, fixed here:
- live-build's dm-verity stage runs `veritysetup` on the build's own system and, without it, writes an empty root hash and no hash tree, saying nothing: the build container installs it, and the build fails without a hash tree and root hash.
- With `LB_UEFI_SECURE_BOOT="auto"` live-build installs shim and GRUB into the chroot for the medium and purges them after, shim included though the manifest has it, taking the installer with it; and purging GRUB there runs systemd-boot's trigger, which fails where there is no EFI system partition (`esp_path="$(bootctl --print-esp-path)"` under `set -e`). GRUB is now in the manifest (`enable`), and the installer purges it.
- live-build's stock `1010-enable-cryptsetup` hook rewrote the `conf-hook` OxyOS sets: it is not linked any more.
- `boot-complete.target` must be ordered after `multi-user.target`, or systemd-bless-boot marks a boot good three seconds in; and the entry's tries are given back from `systemd-bless-boot.service` (a target is ordered after what it wants, so wanting the unit from `multi-user.target` made a cycle that dropped it).
- live-boot asks to remove the medium at every shutdown of the recovery, and live-config made its live user there: the recovery's entry says `noeject` and `live-config.nocomponents`.
- OVMF's PS/2 driver gives systemd-boot no keys from QEMU: the tests' machine has a USB keyboard, as a laptop's firmware presents its own.

Seen, not changed: systemd-boot's menu has no per-entry hotkey for Type 1 entries (decision 2); the passphrase field shows at most eleven bullets for a longer password (ADR 0017's theme).

## Not in this decision

- Activation Lock (an erased computer that only its owner's account may set up again); Find My.
- A firmware password; locking the boot menu.
- Erasing and recovering other systems' disks; dual boot.
- Machines already installed by hand (the ThinkPad): adding a recovery to one is a repartition of a disk in use, described in the step that does it, never done in place by this program.
