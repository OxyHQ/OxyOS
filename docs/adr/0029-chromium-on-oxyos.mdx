# ADR 0029: Chromium on OxyOS (Astro)

Status: **accepted; steps 1 and 2 implemented** (the Ozone platform, the software buffer path, key text and client-owned buffers; the OxyOS engine and its package); **step 4 in part** (the clipboard and text input), and of step 6 the keyboard layout and cursor images. Builds on [ADR 0001](./0001-native-platform-boundaries) (surfaces, configure, popups, buffers), [ADR 0005](./0005-damage) (damage), [ADR 0007](./0007-clipboard), [ADR 0008](./0008-input-method), [ADR 0013](./0013-launching-applications), [ADR 0016](./0016-windows) (windows that are not Bloom's draw their own controls), [ADR 0021](./0021-menu-bar) and [ADR 0003](./0003-accessibility-protocol). The Astro side is in [OxyHQ/Astro](https://github.com/OxyHQ/Astro) (`engine/oxyos`, `docs/port-windows-linux.md`).

## Problem

Astro is Chromium (155, with Helium and Astro's series). On Linux its window is Chromium's Webium window serving Astro's interface (`apps/webui`), and Chromium reaches a display only through Ozone, whose platforms are X11, Wayland, DRM (a kiosk that owns the display) and headless. OxyOS has none of the first two by design ([ADR 0001](./0001-native-platform-boundaries)), DRM would take the display from the compositor, and headless shows nothing. So Astro does not run on OxyOS, and nothing says how a program that is not a Bloom application — with its own processes, renderer and GPU process — should.

## Decision

1. **Astro reaches OxyOS through an Ozone platform of its own, `oxyos`** (`ui/ozone/platform/oxyos`, Astro's `engine/oxyos` layer), built as Chromium's own platforms are, never through X11, Wayland or a shim. Chromium registers it through its hook for platforms outside its tree (`ozone_extra_path`), so no Chromium file changes; `--ozone-platform=oxyos` selects it. It speaks the protocol only through the client C ABI (`oxyos-client-ffi`), linked into the browser as one relocatable object whose only global symbols are that ABI's, so the client's Rust runtime stays private and never meets Chromium's own. The browser process holds the one connection: surfaces belong to a connection, and Chromium's GPU and renderer processes are sandboxed, so they never connect.

   | Chromium | OxyOS |
   | --- | --- |
   | `PlatformWindow` (a browser window) | A toplevel, created when shown at the size Chromium asks; the compositor's `Configure` decides its size, scale and state from then on |
   | `PlatformWindowDelegate::State`, viz's sequence number | Each configure is applied as a state; the frame viz draws for it carries its sequence number back, and is submitted with that configure's serial: one configure in flight ([ADR 0016](./0016-windows)), every configure answered (one that changes nothing drawn asks Chromium for a frame) and no frame of another size ever submitted for it |
   | Activation, close, minimize, zoom, full screen | `Activated`, `CloseRequested`, `Minimize`, `SetMaximized`, `SetFullscreen` |
   | `app-region: drag` (`HTCAPTION`) | `BeginMove` with the press's serial; the window's edges are the compositor's band ([ADR 0016](./0016-windows), decision 5) |
   | The frame | The compositor's: corners, shadow and edges, no title bar. Chromium draws none (`ShouldUseNativeFrame`), and Astro draws its own controls, as ADR 0016 says of windows that are not Bloom's |
   | Size limits, title, application id | `SetSizeLimits`, `SetTitle`, `SetAppId` (the launch record's id wins, [ADR 0013](./0013-launching-applications)) |
   | Menus, `<select>` lists, tooltips, bubbles | Popup surfaces placed by Chromium's own anchor (`OwnedWindowAnchor`: its anchor, gravity and adjustments are the positioner's, value for value); a menu grabs with the press's serial; a tooltip takes no input |
   | Capture | The located events of a window's popups go to the capturing one, as Wayland's grabber does |
   | Cursors | Pointer shapes for the types OxyOS has a shape for; the others (copy, alias, a context menu, progress, a cell, vertical text, panning), a page's custom cursor and `cursor: none` as images (`SetPointerImage`) |
   | Mouse, wheel and touchpad | `Pointer` and `Scroll` (precise deltas) |
   | Keys | `KeyText` (decision 2), the session's layout for what no text says (`KeyboardLayout`) |
   | Screen | The window's own: its scale from its configure, its size as the display's (applications are not told outputs yet) |

2. **A key's text comes with the key.** A browser's keydown carries its meaning (`key`), and OxyOS types through the session's layout and compose table in the compositor, sending a key and then its text as two events. A client cannot know whether a text follows the key it has just read without waiting, and waiting is guessing. So a connection may ask for key text (`SetKeyText`): every key then arrives as `KeyText`, with what it typed (compose included), and that text is never sent again as `Text` or in a text input transaction. Text no key typed (an input method's) comes as before, and Chromium inserts it as characters. A key that typed nothing (a dead key, Ctrl with a letter) gets its meaning from the session's layout, which the protocol tells applications (`KeyboardLayout`, decision 6), and from the US layout's position until it is told.

3. **Buffers are the GPU process's; the browser attaches them and the compositor reads them in place.** The connection gains client-owned buffers in the C ABI (`oxyos_client_attach_buffer`, `oxyos_client_submit_buffer`, `oxyos_client_detach_buffer`), the protocol's `AttachBuffer`, `Damage`, `Submit` and `Released` without the library's copy. Chromium's GPU process hands each buffer to the browser over Mojo (`ui.ozone.mojom.OxyOSSurface`: attach, detach, present with damage and viz's sequence number), and the browser submits it with the serial of the configure it answers.
   - **Now, and always as the fallback: software.** With no GL, Chromium composites in software (viz's `SoftwareOutputDevice`, the path it takes on any machine without a usable GPU). The `oxyos` canvas draws into sealed shared memory Chromium makes (a memfd sealed against growing and shrinking, which is what the compositor accepts), two or three buffers, copying into the one it reuses only what changed since it last held a frame. A swap is acknowledged when the compositor's `Feedback` says the frame was presented or discarded, so Chromium draws at the display's pace, and a buffer is drawn into again only once `Released` names it. This path stays when the GPU path arrives, for machines and sessions without one; it is never thrown away. Until the platform has GL, Chromium starts in its GPU modes and falls back to this one (about 80 ms of GPU processes that exit at start).
   - **Next: the GPU, with DMA-BUF and explicit synchronization**, the same shape for Chromium and the Bloom host, decided in [ADR 0031](./0031-gpu-buffers) (which waits for a frame's acquire point before latching it rather than in the compositor's GPU submission, its decision 6):
     - *Formats and modifiers:* the compositor tells each client, on connecting and when it changes, the device it composes on (the render node) and, per DRM format, the modifiers it can import into Vulkan (`VK_EXT_image_drm_format_modifier`), as linux-dmabuf v4's feedback does; a client allocates only from that list.
     - *Buffers:* `AttachDmabuf` (up to four planes, each a descriptor with its offset and stride, the format and the modifier), checked by the compositor by importing it (`VK_EXT_external_memory_dma_buf`) before it answers; the same `Submit`, `Damage` and `Released`.
     - *Fences:* explicit only. A submit carries an acquire point and a release point on DRM syncobj timelines the client registered (as wp-linux-drm-syncobj does); the compositor imports the acquire point as a Vulkan semaphore and waits on the GPU, never on the CPU, and signals the release point when composition no longer reads the buffer. `Released` stays for buffers without timelines. A frame whose fence never signals is dropped by deadline, not waited on (ADR 0001's "the compositor never waits on a client").
     - *Chromium:* the `oxyos` platform gains `GLOzone` over EGL/ANGLE with GBM buffers (as its Wayland platform does), native pixmaps exported as DMA-BUF descriptors through the same Mojo path, and later overlays (sub-surfaces).
   - Damage is Chromium's own, accumulated over frames not submitted ([ADR 0005](./0005-damage)).

4. **The sandbox is Chromium's.** The renderer, GPU and utility processes keep Chromium's Linux sandbox (namespaces and seccomp-BPF); none of them talks to the compositor. The GPU process only makes memfds and seals them, which its seccomp policy allows. Astro is an ordinary application to the session: no grant beyond an application's ([ADR 0013](./0013-launching-applications)); its identity is its launch record's.

5. **Packaging: an engine built for OxyOS, in `/opt/astro-browser`.** The Linux engine Astro ships today still carries Chromium's X11 and Wayland platforms, so it needs `libX11`, `libxcb` and the rest, which OxyOS never installs. The package for OxyOS is its own engine build: the `oxyos` platform alone (`ozone_platform_x11=false`, `ozone_platform_wayland=false`), no GTK or Qt, in its own output directory, its dynamic libraries audited against the image's as the image's own contents are. It installs as today's package does, into `/opt/astro-browser`, with a launch entry in the session's registry (`/usr/share/oxyos/applications/so.oxy.astro.desktop`: `Name=Astro`, `Exec=/opt/astro-browser/astro-browser --ozone-platform=oxyos`, its icon Astro's, the one `tools/shell-preview/assets/apps/astro.png` shows). The client is built from the OxyOS commit the engine pins (`engine/oxyos/oxyos-pin`); while the protocol is experimental the image and the engine are built from the same commit. Once the protocol is versioned for applications, OxyOS ships the client as a shared library with a stable C ABI, and Astro links it instead.

6. **The menu bar, text input, the clipboard and accessibility go through the same platform**, each by its own decision's protocol:
   - *Menu bar* ([ADR 0021](./0021-menu-bar)): Astro's commands (the table its ⋯ menu shows, the macOS menu bar's) go from the page to the engine and from the engine to the window (`oxyos_client_set_menus`); a choice (`MenuItemActivated`) comes back to the page as the same command. Astro then hides its ⋯ button, as on macOS.
   - *Text input* ([ADR 0008](./0008-input-method)): a `LinuxInputMethodContext` for `oxyos` (with Chromium's `InputMethodAuraLinux`) describes the focused field (purpose, hints, surrounding text without the composition, in UTF-8 bytes, and the caret) and applies the input method's transactions, in order: the deletion around the selection (whole characters, counted again in UTF-16 for Chromium), the commit, then the composition with its segments (composing thin, converting thick, an error a red squiggle) and its cursor. Key text keeps plain typing as it is. A transaction for an older state than the field last told applies its commit and composition but not its deletion, as Bloom's fields do. Chromium tells a field's text only when its caret moves, so after a commit or a deletion the field is told what it will hold (the edit applied to what it last told), as Chromium's Wayland platform predicts it; a password tells only its purpose. A dead key's composition and the character it composes come as the session's compose table makes them, as a transaction of one each.
   - *The keyboard layout*: the session tells every client its XKB layout (`KeyboardLayout`, event 180: `layout\tvariant\toptions`, on connecting and whenever it changes). The platform compiles it with xkbcommon (the default rules and model, as the compositor's) for Chromium's `XkbKeyboardLayoutEngine`, which gives a key that types nothing its meaning: Ctrl with the key at US Q is Ctrl+A on AZERTY, a dead key is `Dead`, and every key's key code is the layout's. A key's text still comes from the compositor; the layout fills in only what no text says, and until it is told, the US position does as before.
   - *Clipboard* ([ADR 0007](./0007-clipboard)): a `PlatformClipboard` over the protocol's offers and pastes, with the serial of the input that asked (the latest press or key, as Chromium's writes and reads follow the input that made them). The C ABI copies any type (`oxyos_client_copy`: up to 16 media types with their contents, the most faithful first), and the client library answers each paste of them. Chromium's types go as they are (`text/html`, `image/png`, `chromium/x-web-custom-data`, `chromium/x-source-url`), but not X11's text atoms (`UTF8_STRING`, `STRING`, `TEXT`), which nothing on OxyOS reads; Chromium's `text/plain` is pasted from whichever plain text type the clipboard holds (a Bloom application copies `text/plain;charset=utf-8` alone). There is no primary selection: OxyOS has none (ADR 0007, decision 7). A paste is read on a worker thread until its owner closes the pipe, with a deadline of 5 seconds, after which it is nothing: Chromium's GLib message pump never reports a pipe's end without data (`G_IO_HUP` alone), so a read on the UI thread hung whenever the owner closed after its last write was read. Chromium is never told it owns the clipboard (`IsSelectionOwner`): its own copy is read back through the compositor, as any other application's, so what it pastes is always what the clipboard holds.
   - *Accessibility* ([ADR 0003](./0003-accessibility-protocol)): Chromium's accessibility tree (the window's views and each tab's web contents) published as the window's snapshot, its roles, states, names, values and actions mapped to the protocol's, its actions back as Chromium's `AXActionData`. A web page's tree is larger than a snapshot's 4096 nodes; this needs the protocol's incremental updates first.

## Steps

1. **The platform, phase 1.** `ui/ozone/platform/oxyos` in Astro (window, popups, connection and event source, keyboard, screen, the GPU process's canvas and the browser's surface host over Mojo), client-owned buffers and key text in OxyOS, and a scenario.

   *Done.*
   - **OxyOS:** `SetKeyText`/`KeyText` (request and event 150) in the protocol and the scene, and in the C ABI `oxyos_client_set_key_text` and KEY's `text`; `oxyos_client_attach_buffer`, `oxyos_client_submit_buffer` and `oxyos_client_detach_buffer`, the buffer checked as the compositor checks it before it is sent. `tools/rn-host-spike/regress.py` runs a native client that is not a Bloom application (`client`, with `--client PROGRAM`).
   - **Astro:** the platform, its Mojo interfaces, the client staged into Chromium's tree by `engine/patches/build/oxyos-client.sh` (the pinned OxyOS commit, linked into one object with only the C ABI global) and Chromium unit tests in `ozone_unittests` (`OxyOS*`: the configure queue, the conversions, the keyboard).
   - **Tests:** in the scene, a key with its text and no `Text` after it, text no key typed still `Text`, the input method's given-back key carrying its text; through real sockets, a caller's sealed buffer attached, submitted with clipped damage, read where the caller drew it, released and detached, unsealed memory and a layout past its end refused before anything is sent. `scenarios/astro.json` runs Astro's engine on the development compositor with a page (`scenarios/pages/astro.html`): a press on its button, a `<select>` opening its list as a popup surface that takes the keyboard and closing on a choice, keys typed with the session's layout reaching a field with each keydown's `key` right, Ctrl+A and Backspace, and the window's right edge dragged 100 px at 125 Hz. It passes three runs out of three; with a compositor that ignores `SetKeyText` the typing step fails.
   - **Measured** (the development compositor on the CPU, a shared 32-core machine): the first frame 131 to 168 ms after launch; the drag sends 24 configures, each answered by a frame of its size and none drawn scaled, the left, top and bottom edges never moving, a motion to the frame answering it 31.5 ms median and 48.8 ms at most; a step's input to its frame about 15 ms median.
   - **Not verified:** a session on a real display (`oxyos-session` on a seat; the development machine has no DRM), and the engine on the image, which needs step 2.
2. **The OxyOS engine build and package** (decision 5), with its library audit and launch entry, booted in the image's acceptance tests.

   *Done* (Astro's `AC_TARGET_PLATFORM=oxyos`, `out/Release_GN_oxyos_x64_dev`, `astro-browser-*-oxyos-x86_64.tar.xz`, entry `so.oxy.astro`), installed on the reference ThinkPad.
3. **The GPU** (decision 3, [ADR 0031](./0031-gpu-buffers)): formats and modifiers, `AttachDmabuf`, syncobj timelines and Vulkan import in the compositor, tested on the reference GPU (the ThinkPad's Iris Xe) and lavapipe; `GLOzone` in the platform; the Bloom host on the same buffers.
4. **The menu bar, text input and the clipboard** (decision 6), each with a scenario.

   *Cursor images are done* (of step 6).
   - **OxyOS:** `SetPointerImage` (request 190): a surface's pointer image from an attached buffer (premultiplied ARGB8888, at most 256 on a side), its hotspot and the scale it was drawn for. The compositor reads the pixels when the request arrives, so the buffer may go at once, and keeps them for the surface until a shape replaces them; the scene keeps only which surface has which image (`Scene::pointer_image`). A display puts the image on its cursor plane (`Display::replace_pointer_image` reuses one slot), resized to its scale by the nearest pixel, or shows the arrow if its plane cannot take it; the session forgets it when it chooses the display's own pointer images again. The C ABI's `oxyos_client_set_pointer_image` puts the pixels in a buffer of their own, sets the image and destroys the buffer. The development compositor reports the image under the pointer (`pointer_image`).
   - **Astro:** a cursor type OxyOS has a shape for stays a shape; for the others the platform's cursor factory gives Chromium no platform cursor, so Chromium loads its own image of it, and every image, a page's custom cursor among them, is sent with its hotspot and scale (larger than 256 pixels, it is resized and its scale with it). `cursor: none` is a transparent pixel. `ozone_unittests`: the shapes, the types that are images, a bitmap's premultiplied pixels and scale, one larger than a plane takes.
   - **Scenario:** `scenarios/astro-cursors.json` (`pages/astro-cursors.html`): `pointer` is the hand; a 32×32 PNG custom cursor with hotspot 4,4 is that image at scale 1; `copy` is Chromium's image; `none` a transparent pixel; `text` the shape again; at scale 1.5 the custom cursor is Chromium's 48×48 image with its hotspot at 6,6. Three runs out of three, with `astro.json`, `astro-clipboard.json` and `astro-text-input.json` on the same build. Control: a compositor that does not keep a client's image fails the four image steps.
   - **Not verified:** the cursor plane on the ThinkPad (the development machine has no DRM).

   *Text input is done.*
   - **OxyOS:** `KeyboardLayout` (event 180) in the protocol, the scene (`Scene::set_keyboard_layout`: told to each client on connecting and on a change) and the C ABI (`OXYOS_EVENT_KEYBOARD_LAYOUT`, in chunks); the session tells its layout, the development compositor its `--layout`, and `regress.py` passes a scenario's `layout` without `--uinput` too.
   - **Astro:** `OxyOSInputMethodContext`, the conversions in `oxyos_text_input` (the field told, its purpose, a transaction in UTF-16, the field after an edit) and the keymap (`oxyos_keymap`), with `ozone_unittests` (`OxyOSTextInput*`, `OxyOSKeymap*`: a French layout's Ctrl+Z at US W and its `q` at US A, Spanish's dead acute, the US position before any layout).
   - **Scenario:** `scenarios/astro-text-input.json` (`pages/astro-text-input.html`, layout `fr`): a focused field told empty, typing one transaction, a composition shown and left out of the field told, converted with a segment selected, committed, a deletion of whole characters, a dead key's composition and its character, Ctrl at US Q as Ctrl+A, and a password field telling nothing. Three runs out of three, with `astro.json` and `astro-clipboard.json` passing on the same build. Controls: with the layout `us`, the shortcut step fails; without the field told after an edit, the deletion counted the old text and removed two characters too many.
   - **Not Chromium's:** Astro's own shortcuts are matched by the physical key (`ac_window_keys.cc`, its window's `code|modifiers`), so on AZERTY the key at US W still closes a tab although Chromium now says it is Ctrl+Z. That is Astro's shortcut table's decision, not the platform's.

   *The clipboard is done.*
   - **OxyOS:** `oxyos_client_copy` (and `Client::copy` refusing more types than an offer takes, so a bad copy never closes the connection). For scenarios, the session can copy content it holds as a client of the scene it plays (`Scene::copy_for_session`, no input asked of it) and read what the clipboard holds through its owner's pipe (`Compositor::read_clipboard`); the development compositor plays another application's clipboard with them: a `clipboard` step copies, and every step reports what the clipboard holds as a receiver reads it (`regress.py`'s `clipboard` expectation).
   - **Astro:** `OxyOSClipboard`, with `ozone_unittests` (`OxyOSClipboard*`: the types offered and their order, the text a paste asks for, the clipboard as last told, a copy and a clear, a paste read to its end, a type not held, an owner that never finishes, a pipe ended with nothing in it).
   - **Scenario:** `scenarios/astro-clipboard.json` (`pages/astro-clipboard.html`): Ctrl+C copies a field's text (`text/plain;charset=utf-8` and `text/plain`, with `chromium/x-source-url`) and a rich text's HTML; the Async Clipboard API copies a 3×2 PNG; the session reads each from Astro's pipe. Another application then copies a PNG, HTML and text, and Ctrl+V pastes all three into the page (the image decoded at 2×2) and the text into a plain field. It passes four runs out of four, and `astro.json` three out of three, on a machine loaded at 60 to 75. With the paste read on the UI thread, about one run in three hung 5 seconds and pasted nothing.
5. **Accessibility** (decision 6), after the protocol's incremental updates.
6. **What applications are not told yet:** their output (size, scale, refresh, for Chromium's display list and frame pacing), touch and pinch as Chromium's gestures, drag and drop between applications, and file choosers (Chromium has none without GTK; an OxyOS file chooser is its own decision).
