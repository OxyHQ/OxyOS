# ADR 0029: Chromium on OxyOS (Astro)

Status: **accepted; steps 1 and 2 implemented** (the Ozone platform, the software buffer path, key text and client-owned buffers; the OxyOS engine and its package); **step 4 implemented** (the clipboard, text input and the menu bar), with the keyboard layout, cursor images and outputs (protocol version 5, [ADR 0033](./0033-protocol-versions)); **implemented within Astro's windows:** drag and drop (decision 7, between applications designed); **file choosers (decision 8): the protocol, the session's side and the sheet implemented** (protocol version 7), Stash's picker mode, the host's Expo pickers and Chromium's dialog each in its own change; **designed, not implemented:** accessibility's incremental updates (decision 9). Builds on [ADR 0001](./0001-native-platform-boundaries) (surfaces, configure, popups, buffers), [ADR 0005](./0005-damage) (damage), [ADR 0007](./0007-clipboard), [ADR 0008](./0008-input-method), [ADR 0013](./0013-launching-applications), [ADR 0016](./0016-windows) (windows that are not Bloom's draw their own controls), [ADR 0021](./0021-menu-bar) and [ADR 0003](./0003-accessibility-protocol). The Astro side is in [OxyHQ/Astro](https://github.com/OxyHQ/Astro) (`engine/oxyos`, `docs/port-windows-linux.md`).

## Problem

Astro is Chromium (155, with Helium and Astro's series). On Linux its window is Chromium's Webium window serving Astro's interface (`apps/webui`), and Chromium reaches a display only through Ozone, whose platforms are X11, Wayland, DRM (a kiosk that owns the display) and headless. OxyOS has none of the first two by design ([ADR 0001](./0001-native-platform-boundaries)), DRM would take the display from the compositor, and headless shows nothing. So Astro does not run on OxyOS, and nothing says how a program that is not a Bloom application — with its own processes, renderer and GPU process — should.

## Decision

1. **Astro reaches OxyOS through an Ozone platform of its own, `oxyos`** (`ui/ozone/platform/oxyos`, Astro's `engine/oxyos` layer), built as Chromium's own platforms are, never through X11, Wayland or a shim. Chromium registers it through its hook for platforms outside its tree (`ozone_extra_path`), so no Chromium file changes; `--ozone-platform=oxyos` selects it. It speaks the protocol only through the client C ABI (`oxyos-client-ffi`), linked into the browser as one relocatable object whose only global symbols are that ABI's, so the client's Rust runtime stays private and never meets Chromium's own. The browser process holds the one connection: surfaces belong to a connection, and Chromium's GPU and renderer processes are sandboxed, so they never connect.

   | Chromium | OxyOS |
   | --- | --- |
   | `PlatformWindow` (a browser window) | A toplevel, created when shown at the size Chromium asks; the compositor's `Configure` decides its size, scale and state from then on |
   | `PlatformWindowDelegate::State`, viz's sequence number | Each configure is applied as a state; the frame viz draws for it carries its sequence number back, and is submitted with that configure's serial: one configure in flight ([ADR 0016](./0016-windows)), every configure answered (one that changes nothing drawn asks Chromium for a frame) and no frame of another size ever submitted for it |
   | Activation, close, minimize, zoom, full screen | `Activated`, `CloseRequested`, `Minimize`, `SetMaximized`, `SetFullscreen` |
   | `app-region: drag` (`HTCAPTION`) | `BeginMove` with the press's serial; the window's edges are the compositor's band ([ADR 0016](./0016-windows), decision 5) |
   | The frame | The compositor's: corners, shadow and edges, no title bar. Chromium draws none (`ShouldUseNativeFrame`), and Astro draws its own controls, as ADR 0016 says of windows that are not Bloom's |
   | Size limits, title, application id | `SetSizeLimits`, `SetTitle`, `SetAppId` (the launch record's id wins, [ADR 0013](./0013-launching-applications)) |
   | Menus, `<select>` lists, tooltips, bubbles | Popup surfaces placed by Chromium's own anchor (`OwnedWindowAnchor`: its anchor, gravity and adjustments are the positioner's, value for value); a menu grabs with the press's serial; a tooltip takes no input |
   | Capture | The located events of a window's popups go to the capturing one, as Wayland's grabber does |
   | Cursors | Pointer shapes for the types OxyOS has a shape for; the others (copy, alias, a context menu, progress, a cell, vertical text, panning), a page's custom cursor and `cursor: none` as images (`SetPointerImage`) |
   | Mouse, wheel and touchpad | `Pointer` and `Scroll` (precise deltas) |
   | Keys | `KeyText` (decision 2), the session's layout for what no text says (`KeyboardLayout`) |
   | Screen | The session's outputs (`ApplicationOutput`: size, scale, refresh, work area), side by side in Chromium's display list as no global space is told; the window's display the output it is on (`SurfaceOutput`), its frames paced at that output's refresh (`Refresh`, Chromium's VSync interval) |

2. **A key's text comes with the key.** A browser's keydown carries its meaning (`key`), and OxyOS types through the session's layout and compose table in the compositor, sending a key and then its text as two events. A client cannot know whether a text follows the key it has just read without waiting, and waiting is guessing. So a connection may ask for key text (`SetKeyText`): every key then arrives as `KeyText`, with what it typed (compose included), and that text is never sent again as `Text` or in a text input transaction. Text no key typed (an input method's) comes as before, and Chromium inserts it as characters. A key that typed nothing (a dead key, Ctrl with a letter) gets its meaning from the session's layout, which the protocol tells applications (`KeyboardLayout`, decision 6), and from the US layout's position until it is told.

3. **Buffers are the GPU process's; the browser attaches them and the compositor reads them in place.** The connection gains client-owned buffers in the C ABI (`oxyos_client_attach_buffer`, `oxyos_client_submit_buffer`, `oxyos_client_detach_buffer`), the protocol's `AttachBuffer`, `Damage`, `Submit` and `Released` without the library's copy. Chromium's GPU process hands each buffer to the browser over Mojo (`ui.ozone.mojom.OxyOSSurface`: attach, detach, present with damage and viz's sequence number), and the browser submits it with the serial of the configure it answers.
   - **Now, and always as the fallback: software.** With no GL, Chromium composites in software (viz's `SoftwareOutputDevice`, the path it takes on any machine without a usable GPU). The `oxyos` canvas draws into sealed shared memory Chromium makes (a memfd sealed against growing and shrinking, which is what the compositor accepts), two or three buffers, copying into the one it reuses only what changed since it last held a frame. A swap is acknowledged when the compositor's `Feedback` says the frame was presented or discarded, so Chromium draws at the display's pace, and a buffer is drawn into again only once `Released` names it. This path stays when the GPU path arrives, for machines and sessions without one; it is never thrown away. Until the platform has GL, Chromium starts in its GPU modes and falls back to this one (about 80 ms of GPU processes that exit at start).
   - **Next: the GPU, with DMA-BUF and explicit synchronization**, the same shape for Chromium and the Bloom host, decided in [ADR 0031](./0031-gpu-buffers) (which waits for a frame's acquire point before latching it rather than in the compositor's GPU submission, its decision 6):
     - *Formats and modifiers:* the compositor tells each client, on connecting and when it changes, the device it composes on (the render node) and, per DRM format, the modifiers it can import into Vulkan (`VK_EXT_image_drm_format_modifier`), as linux-dmabuf v4's feedback does; a client allocates only from that list.
     - *Buffers:* `AttachDmabuf` (up to four planes, each a descriptor with its offset and stride, the format and the modifier), checked by the compositor by importing it (`VK_EXT_external_memory_dma_buf`) before it answers; the same `Submit`, `Damage` and `Released`.
     - *Fences:* explicit only. A submit carries an acquire point and a release point on DRM syncobj timelines the client registered (as wp-linux-drm-syncobj does); the compositor imports the acquire point as a Vulkan semaphore and waits on the GPU, never on the CPU, and signals the release point when composition no longer reads the buffer. `Released` stays for buffers without timelines. A frame whose fence never signals is dropped by deadline, not waited on (ADR 0001's "the compositor never waits on a client").
     - *Chromium:* the `oxyos` platform gains `GLOzone` over EGL/ANGLE with GBM buffers (as its Wayland platform does), native pixmaps exported as DMA-BUF descriptors through the same Mojo path, and later overlays (sub-surfaces).
   - Damage is Chromium's own, accumulated over frames not submitted ([ADR 0005](./0005-damage)).

4. **The sandbox is Chromium's.** The renderer, GPU and utility processes keep Chromium's Linux sandbox (namespaces and seccomp-BPF); none of them talks to the compositor. The GPU process only makes memfds and seals them, which its seccomp policy allows. Astro is an ordinary application to the session: no grant beyond an application's ([ADR 0013](./0013-launching-applications)); its identity is its launch record's.

5. **Packaging: an engine built for OxyOS, in `/opt/astro-browser`.** The Linux engine Astro ships today still carries Chromium's X11 and Wayland platforms, so it needs `libX11`, `libxcb` and the rest, which OxyOS never installs. The package for OxyOS is its own engine build: the `oxyos` platform alone (`ozone_platform_x11=false`, `ozone_platform_wayland=false`), no GTK or Qt, in its own output directory, its dynamic libraries audited against the image's as the image's own contents are. It installs as today's package does, into `/opt/astro-browser`, with a launch entry in the session's registry (`/usr/share/oxyos/applications/so.oxy.astro.desktop`: `Name=Astro`, `Exec=/opt/astro-browser/astro-browser --ozone-platform=oxyos`, its icon Astro's, the one `tools/shell-preview/assets/apps/astro.png` shows). The client is built from the OxyOS commit the engine pins (`engine/oxyos/oxyos-pin`); while the protocol is experimental the image and the engine are built from the same commit. Once the protocol is versioned for applications, OxyOS ships the client as a shared library with a stable C ABI, and Astro links it instead.

6. **The menu bar, text input, the clipboard and accessibility go through the same platform**, each by its own decision's protocol:
   - *Menu bar* ([ADR 0021](./0021-menu-bar)): Astro's commands go from its interface to the engine and from the engine to the window (`oxyos_client_set_menus`); a choice (`MenuItemActivated`) comes back to the interface as the same command. Astro then hides its ⋯ button, as on macOS.
     - *Whose menus:* the interface's own command table, the one its shortcuts, its ⋯ menu and its Settings › Shortcuts use (`apps/demo/src/shims/web/motion/shortcuts.ts`, which mirrors the macOS bar's `Menus.swift`), with each command's chord as the person set it, its check and its disabled state from the store (`menuState`). The interface builds File, Edit, View, Tabs, History, Bookmarks, Extensions, Window and Help from it (`apps/webui/src/host/menuBar.ts`): the macOS bar's menus, but the application's own menu, which on OxyOS is the shell's (About, Hide, Quit). Its Settings and Import go to the end of Edit until the shell's application menu offers an application's settings (ADR 0021). The bookmarks bar, the recently closed tabs and the profiles are in it as on macOS. Chords are OxyOS's (`Mod` is Ctrl; the macOS Control key is `Super`).
     - *How it reaches the window:* the platform gives each toplevel an `OxyOSMenuBar` (`ui/ozone/platform/oxyos:menu_bar`, a `PlatformWindow` property as Chromium's Wayland extensions are), which Astro's engine finds through the page's `WebUIBrowserWindow` (`ac_menu_bar.cc`); on X11 or Wayland there is none, and the interface keeps its ⋯ button. The window sends its menus when it is created and whenever they change, and a choice from an older commit is never delivered. The interface sends them only when they change, at most every 200 ms.
     - *Edit's commands* (Undo, Redo, Cut, Copy, Paste, Paste and Match Style, Select All) act on the focused frame, a tab's field included, through the page's `WebContents` (Chromium routes them to the focused inner contents); the others are the interface's commands, as a shortcut runs them.
   - *Text input* ([ADR 0008](./0008-input-method)): a `LinuxInputMethodContext` for `oxyos` (with Chromium's `InputMethodAuraLinux`) describes the focused field (purpose, hints, surrounding text without the composition, in UTF-8 bytes, and the caret) and applies the input method's transactions, in order: the deletion around the selection (whole characters, counted again in UTF-16 for Chromium), the commit, then the composition with its segments (composing thin, converting thick, an error a red squiggle) and its cursor. Key text keeps plain typing as it is. A transaction for an older state than the field last told applies its commit and composition but not its deletion, as Bloom's fields do. Chromium tells a field's text only when its caret moves, so after a commit or a deletion the field is told what it will hold (the edit applied to what it last told), as Chromium's Wayland platform predicts it; a password tells only its purpose. A dead key's composition and the character it composes come as the session's compose table makes them, as a transaction of one each.
   - *The keyboard layout*: the session tells every client its XKB layout (`KeyboardLayout`, event 180: `layout\tvariant\toptions`, on connecting and whenever it changes). The platform compiles it with xkbcommon (the default rules and model, as the compositor's) for Chromium's `XkbKeyboardLayoutEngine`, which gives a key that types nothing its meaning: Ctrl with the key at US Q is Ctrl+A on AZERTY, a dead key is `Dead`, and every key's key code is the layout's. A key's text still comes from the compositor; the layout fills in only what no text says, and until it is told, the US position does as before.
   - *Clipboard* ([ADR 0007](./0007-clipboard)): a `PlatformClipboard` over the protocol's offers and pastes, with the serial of the input that asked (the latest press or key, as Chromium's writes and reads follow the input that made them). The C ABI copies any type (`oxyos_client_copy`: up to 16 media types with their contents, the most faithful first), and the client library answers each paste of them. Chromium's types go as they are (`text/html`, `image/png`, `chromium/x-web-custom-data`, `chromium/x-source-url`), but not X11's text atoms (`UTF8_STRING`, `STRING`, `TEXT`), which nothing on OxyOS reads; Chromium's `text/plain` is pasted from whichever plain text type the clipboard holds (a Bloom application copies `text/plain;charset=utf-8` alone). There is no primary selection: OxyOS has none (ADR 0007, decision 7). A paste is read on a worker thread until its owner closes the pipe, with a deadline of 5 seconds, after which it is nothing: Chromium's GLib message pump never reports a pipe's end without data (`G_IO_HUP` alone), so a read on the UI thread hung whenever the owner closed after its last write was read. Chromium is never told it owns the clipboard (`IsSelectionOwner`): its own copy is read back through the compositor, as any other application's, so what it pastes is always what the clipboard holds.
   - *Accessibility* ([ADR 0003](./0003-accessibility-protocol)): Chromium's accessibility tree (the window's views and each tab's web contents) published to the session, its roles, states, names, values and actions mapped to the protocol's, its actions back as Chromium's `AXActionData`. A web page's tree is larger than a snapshot's 4096 nodes and changes a few nodes at a time, so it needs the protocol's incremental updates first (decision 9).

7. **Drag and drop: within Astro first, between applications by the clipboard's own means.** The protocol has no drag and drop today ([ADR 0007](./0007-clipboard), decision 7, left it to its own decision), and Chromium's drags reach a platform only through its `WmDragHandler` (`StartDrag`, which runs a nested loop until the drop) and each window's `WmDropHandler` (enter, motion, drop, leave). The `oxyos` platform has neither, so a page's drag (a link, an image, selected text, an HTML5 `draggable` element) ends at once with no operation, inside the page too.
   - **Within Astro, with no protocol:** the platform's `WmDragHandler` runs the drag itself. While the source's press is held the compositor keeps sending its pointer to the surface it pressed (the scene's implicit capture), so the platform turns those motions into `WmDropHandler` calls on its own window: enter with the dragged `OSExchangeData` (Chromium's own, never serialized), each motion's operation back to Chromium (`LocationDelegate`), the drop at the release with its modifiers, leave on Escape or when the pointer leaves the window. The drag image is a popup of the source window moved with each motion (`Reposition`); the capture keeps the pointer the source's while it is over the image (`platform_shows_drag_image` stays false: Chromium draws it). This makes a page's drags work inside a window, from a tab to Astro's interface and back, with nothing new from the compositor. A drag that leaves the window ends with no operation.
   - **Between applications, with the protocol** ([ADR 0007](./0007-clipboard)'s offers, types and pipes, for a drag):
     - *Starting:* `DragOffer { offer, serial }` with the serial of the press being held, `DragType` for each media type (as `ClipboardType`), `DragActions` (copy, move, link, and the one preferred), and `DragIcon { surface, hotspot }`, a surface the compositor moves with the pointer and shows above everything, taking no input; then `DragCommit`. A drag without a held press of the client's, or from a client without keyboard focus, is refused, as a copy is.
     - *Over a surface:* the compositor tells the client under the pointer `DragEnter { surface, selection, x, y, actions }` with the drag's types (`DragType` events naming `selection`, never the source), `DragMotion { surface, x, y }` and `DragLeave`. The target answers with `DragStatus { selection, action, mime }`, the action it would take and the type it would read; the source is told the action (`DragAction`) to show it.
     - *Dropping:* at the release over a target that accepted, the target is told `DragDrop { surface, selection, serial }`; it reads the type it chose with `DragReceive { selection, mime, serial }` carrying a pipe, exactly as `ClipboardReceive`, valid only for that drop's `selection` and only until it answers `DragFinish { selection, action }`; the source is told `DragFinished { offer, action }` (for a move, it deletes what it gave). Escape, or a release over nothing that accepted, cancels: the source is told `DragFinished` with no action.
     - *What it never reveals:* as with the clipboard, a target never learns which application a drag came from and reads nothing before the drop; the source learns only the action taken. A drag's content goes through a pipe from the source to the target, never through the compositor.
     - *Chromium:* the `WmDragHandler` above sends the offer when the drag leaves its window (or at once), and the window's `WmDropHandler` takes enters from other applications, its `OSExchangeData` filled from the types read at the drop (Chromium's `text/uri-list`, `text/html`, `text/plain`, files as `text/uri-list` of `file://` paths). Bloom's draggable views use the same requests through its adapter.

8. **File choosers: the open and save panels are a system service, a portal, as a Mac's are** ([ADR 0028](./0028-file-access) left `File.pickFileAsync` failing: OxyOS had no system picker). A browser's `<input type="file">`, its downloads' Save As, the File System Access API and Expo's `pickFileAsync`/`pickDirectoryAsync`/`getDocumentAsync` all need the person to choose files the application could not name itself. Without GTK or Qt Chromium has no `SelectFileDialog` on Linux. On a Mac the open and save panels are not the application's code but a service of the system's (`openAndSavePanelService`), shown attached to the application's window; OxyOS does the same. Decided by the platform's author on 2026-10-31, replacing the sketch that put the request in ADR 0030's vocabulary.
   - **Asking needs no grant, only the person's input.** Any application asks for one of its own toplevels with `ChooseFiles { serial, surface, input, text }` (request 220, protocol version 7, [ADR 0033](./0033-protocol-versions)), citing a press or a key it received lately; the text is the request in the session's vocabulary, in chunks:
     - `{"open": {"multiple", "directory", "types", "title", "folder"}}` or `{"save": {"name", "types", "title", "folder"}}`, every field but the kind optional, read strictly (`oxyos_compositor::choosers::Ask`: an unknown key, more than 128 types, a type that is neither a lowercase media type, `type/*`, nor an extension such as `.tar.gz`, a title or name with a control character, a name with `/`, refuses it). A folder the person's files do not hold is left out: it is the asker's suggestion.
     - The scene passes the request through to the session and refuses only what it can judge without the vocabulary, at once and with no panel: no recent input of the asker's (`needsInput`), the lock (`locked`), a window that already has a panel or eight open in the session (`busy`). A surface that is not the asker's toplevel is a protocol error. The session owns the vocabulary and refuses what it does not read (`invalidRequest`).
   - **The panel is Stash's, in its picker mode, as a sheet of the asking window.** The session starts the file manager of the image's policy (`so.oxy.stash`, a system application: `Launcher::choose` starts nothing else) as a process of its own, told what to show in `OXYOS_FILE_CHOOSER` (the mode, multiple, folders, the types, the title, the suggested name, the folder, and the asking application's id and name, so Stash keeps per application the folder it opens in and what was chosen recently). Its window asks 800×520.
     - The compositor attaches the chooser's connection to the request as it says Hello (`Compositor::expect_chooser`, by the pid the session started), before any of its requests is read, so its first toplevel becomes a **sheet**: a dialog of the asking window though another client's, at the window's top (52 px down, centred, as wide as the window less 24 px each side and no taller than it leaves, but never under 640×440), moving with it, drawn active with it. It takes the window's keyboard while the window stays the active one (`Activated`), the window's presses are kept from it (the dialog's modal scope), and every other window stays usable. A toplevel's own requests about its window from the sheet (title, application id, menus, limits, zoom, full screen, minimize) are no errors and change nothing; a drag of the sheet (`BeginMove` with a press of its own) moves the window it is attached to, as the window's own can no longer be pressed.
     - Stash learns it is the chooser only through Bloom's platform adapter: `PlatformFiles.chooser` (`request`, `choose(uris)`, `cancel()`; Bloom 15.81.0), never by asking which platform it runs on ([ADR 0028](./0028-file-access), decision 1). The host does not report `window` or `menu-bar` for it: its window is a sheet, with no controls or menus of its own. Its own views do the rest: its sidebar's places, its lists, search and previews; Open/Cancel, or a name and Save/Cancel asking before replacing. No Stash code is in OxyOS.
   - **The answer goes back through the session to the asker alone, once.** Only the chooser the session started for that request answers, with `AnswerFileChooser { input, text }` (request 222): `{"chosen": [URIs]}` citing an input it received, or `{"cancelled": {}}`. The session checks it (`choosers::check`): as many files as the request allows, of its kind (folders for `directory`), each a `file://` URI the rule applications' files follow reaches (`oxyos_files::Scope`, the same rule as ADR 0028's: the home and the volumes mounted for the person, never a Trash's insides), an opened one there, a saved one's folder there and never a folder itself. Anything else is not an answer and the panel stays. The asker is told `FilesChosen { serial, text }` (event 220): `{"chosen": [...]}`, `{"cancelled": {}}` or `{"refused": {"reason"}}`; the sheet goes at once and the session ends the chooser's process (SIGTERM). A request also ends cancelled when its asker withdraws it (`CancelChooseFiles`, request 221), when its window goes, or when the chooser exits or disconnects before answering; ended with the asker gone, no one is told.
   - **What the answer grants.** The answer is what the person chose and nothing else: the asker never sees the panel or what else is on the disk. While OxyOS has no confinement ([ADR 0028](./0028-file-access), decision 2; [ADR 0030](./0030-installing-applications), decision 15) the chosen URIs are paths the application could already reach, so a grant changes nothing the file service enforces; the session keeps no list. With confinement, the same answer becomes the grant: the session adds each chosen item to that process's scope (its read, or for a save its file's write), as a capability granted at first use holds for the process that asked, and the request does not change. **Kept across launches** (a Mac's security-scoped bookmark, Android's persistable URI permission) is decided here and comes with confinement: `oxyos-installd` keeps each account's chosen items per application beside its capability decisions, and the launch gives them to the scope; an application keeps the URI as any other, with no token, since Expo's API has none.
   - **Chromium:** Astro's engine registers a `SelectFileDialog` factory when the `oxyos` platform runs (its views depend on Ozone, so the factory cannot be the platform's own), whose dialog asks for the owning toplevel citing the latest press or key and calls `FileSelected`, `MultiFilesSelected` or `FileSelectionCanceled`; a refused answer is a cancellation, and a compositor of a version before 7 is never asked. Chromium gives Linux dialogs extensions only (`accept="image/png"` arrives as extensions), so `types` holds `.ext`. **Bloom:** `expo-file-system`'s `pickFileAsync` and `pickDirectoryAsync` (`sample/oxyos/expo-file-system.js`) and expo-document-picker's `getDocumentAsync` ask the same way instead of failing.
   - **Not in this decision:** a filter the person may widen to any file (Chromium's `include_all_files`, the hint `accept` is), named filter groups and the one chosen (Save Page As' formats); a chooser kept running between requests to open faster.

9. **Accessibility for large and changing trees: incremental updates** (the next step for Astro, before step 5). A snapshot ([ADR 0003](./0003-accessibility-protocol)) sends every node of a surface each time anything changes, at most 4096. A web page's tree is often tens of thousands of nodes, and Chromium changes it a few nodes at a time (a live region, a focus move, a value typed) through `AXTreeUpdate`s.
   - **Nodes have ids, not places:** an update names nodes by a client's `u32` id that is stable while the node lives, as Chromium's `AXNodeData::id` is; a node's parent is an id, and its children are listed in order (`AccessibleChildren { surface, tree, node, count }`, then the ids in chunks), so a move is one changed node, not a renumbering.
   - **An update is a batch:** `AccessibilityUpdateBegin { surface, tree, root }`, the changed nodes (`AccessibleNode` and `AccessibleText` as today, keyed by id) and the removed ones (`AccessibleNodeRemoved { id }`, its descendants with it), then `AccessibilityUpdateCommit`; the compositor applies it whole or refuses it (a node left without a parent, a cycle, an unknown id), and the assistive technology is told the same batch, never a half-applied tree. A snapshot stays as the first update of a tree, so ADR 0003's clients do not change.
   - **Trees inside trees:** a window holds several trees (Astro's interface and each tab's page, which Chromium keeps as separate trees joined by child tree ids). A node may host another tree of the same surface (`AccessibleChildTree { surface, node, tree }`), which updates on its own; a tab's tree is never resent because the interface changed.
   - **Limits:** at most 1024 nodes in one update and 65536 in a surface's trees together, so a page's tree fits and no client can make the compositor hold an unbounded one; a larger page is published as Chromium's own serializer limits it (its `max_nodes`), its far parts left out until scrolled near.
   - **Actions and selection** keep ADR 0003's, naming a node by its id and tree; Chromium turns them into `AXActionData` for that tree.
   - **The screen reader** (ADR 0014) keeps one tree per surface as it is told, so it reads a page as it changes without being sent the whole page again.

## Steps

1. **The platform, phase 1.** `ui/ozone/platform/oxyos` in Astro (window, popups, connection and event source, keyboard, screen, the GPU process's canvas and the browser's surface host over Mojo), client-owned buffers and key text in OxyOS, and a scenario.

   *Done.*
   - **OxyOS:** `SetKeyText`/`KeyText` (request and event 150) in the protocol and the scene, and in the C ABI `oxyos_client_set_key_text` and KEY's `text`; `oxyos_client_attach_buffer`, `oxyos_client_submit_buffer` and `oxyos_client_detach_buffer`, the buffer checked as the compositor checks it before it is sent. `tools/rn-host-spike/regress.py` runs a native client that is not a Bloom application (`client`, with `--client PROGRAM`).
   - **Astro:** the platform, its Mojo interfaces, the client staged into Chromium's tree by `engine/patches/build/oxyos-client.sh` (the pinned OxyOS commit, linked into one object with only the C ABI global) and Chromium unit tests in `ozone_unittests` (`OxyOS*`: the configure queue, the conversions, the keyboard).

4. **The menu bar, text input and the clipboard** (decision 6), each with a scenario.

   *The menu bar is done.*
   - **OxyOS:** no protocol change. The compositor reads up to 256 requests of a client in a turn instead of one: Astro's menus are about 120 entries, some 400 packets with their texts, and the frame Astro sent after them waited a turn for each, so its first frame came after the launch's deadline. The development compositor plays the session's bar: every step reports the window's menus by each entry's path (`menus`), and a `menu` step chooses a command by its path as the shell's choice is delivered (`Scene::choose_active_menu_item`).
   - **Astro:** the platform's `OxyOSMenuBar` and `OxyOSMenuItemsOf`, the engine's `astroMenuBar` and `astroEditCommand`, the interface's `menuBar.ts`; `ozone_unittests` (`OxyOSMenuBar*`: a window offering its menu bar, the entries as the protocol's items).
   - **Scenario:** `scenarios/astro-menu-bar.json` (`pages/astro-menu-bar.html`): the bar is File to Help, with chords (`Mod+T`, `Mod+Shift+W`, `Super+1`), checks (Appearance › Automatic, Show Tabs in Sidebar) and disabled commands (Go Back); the bar's Select All and Copy put the focused field's text on the clipboard and its Paste doubles it; View › Show Tabs in Sidebar moves the tabs on top and its check follows. Three runs out of three, with the other Astro scenarios passing on the same build. The test `tests/requests.rs` reads 602 requests in at most 4 turns; with one a turn, 601.

   *Outputs are done.*
   - **OxyOS** (protocol version 5): every client is told each output the session shows, when it connects and as they change: `ApplicationOutput` (event 200: size in logical pixels, scale, refresh, whether it is the primary), `ApplicationOutputWorkArea` (201: the part windows may cover, relative to it), `ApplicationOutputRemoved` (202); and each surface's client the output it is on, `SurfaceOutput` (203), before its first configure and whenever it moves, with its `Refresh`. An output's place in the global space stays the shell's (ADR 0018, amended): what a display list needs, nothing of other clients.
   - **Astro:** Chromium's display list is the outputs, each a display of its size, scale, refresh (`display_frequency`) and work area, laid side by side in id order (Chromium's display list needs places; OxyOS tells none, so they are Chromium's alone). A toplevel's origin is its output's display's, so a window moved onto another output moves in Chromium's space too and its pages are told their new screen (`screen.width`, `devicePixelRatio`, `availHeight`) as a move on any platform tells them. A window's display is the output it is on (`GetDisplayForAcceleratedWidget`). Its frames are paced at its output's refresh: the GPU process's canvas gives viz a VSync provider at the interval `Refresh` says, which Chromium's software compositing paces its begin frames by. Before an output is told, the window's own size and scale stand in, as before.
   - **Scenario:** `scenarios/astro-outputs.json` (`pages/astro-outputs.html`) on two outputs, the second 1920×1200 at 1.5 (1280×800 logical) paced at 120 Hz: on the first, the page's screen is 1280×720 at 1 with its frames 16.7 ms apart; moved onto the second, 1280×800 at 1.5 with its frames 8.3 ms apart. Three runs out of three. `ozone_unittests`: each output a display of its size, scale, refresh and work area, side by side; a refresh's interval.

   *Cursor images are done.*
   - **OxyOS** (protocol version 5): `SetPointerImage` (request 190): a surface's pointer image from an attached buffer (premultiplied ARGB8888, at most 256 on a side), its hotspot and the scale it was drawn for. The compositor reads the pixels when the request arrives, so the buffer may go at once, and keeps them for the surface until a shape replaces them; the scene keeps only which surface has which image (`Scene::pointer_image`). A display puts the image on its cursor plane (`Display::replace_pointer_image` reuses one slot), resized to its scale by the nearest pixel, or shows the arrow if its plane cannot take it; the session forgets it when it chooses the display's own pointer images again. The C ABI's `oxyos_client_set_pointer_image` puts the pixels in a buffer of their own, sets the image and destroys the buffer. The development compositor reports the image under the pointer (`pointer_image`).
   - **Astro:** a cursor type OxyOS has a shape for stays a shape; for the others the platform's cursor factory gives Chromium no platform cursor, so Chromium loads its own image of it, and every image, a page's custom cursor among them, is sent with its hotspot and scale (larger than 256 pixels, it is resized and its scale with it). `cursor: none` is a transparent pixel. `ozone_unittests`: the shapes, the types that are images, a bitmap's premultiplied pixels and scale, one larger than a plane takes.
   - **Scenario:** `scenarios/astro-cursors.json` (`pages/astro-cursors.html`): `pointer` is the hand; a 32×32 PNG custom cursor with hotspot 4,4 is that image at scale 1; `copy` is Chromium's image; `none` a transparent pixel; `text` the shape again; at scale 1.5 the custom cursor is Chromium's 48×48 image with its hotspot at 6,6. Three runs out of three, with `astro.json`, `astro-clipboard.json` and `astro-text-input.json` on the same build. Control: a compositor that does not keep a client's image fails the four image steps.
   - **Not verified:** the cursor plane on the ThinkPad (the development machine has no DRM).

   *Text input is done.*
   - **OxyOS** (protocol version 5): `KeyboardLayout` (event 180) in the protocol, the scene (`Scene::set_keyboard_layout`: told to each client on connecting and on a change) and the C ABI (`OXYOS_EVENT_KEYBOARD_LAYOUT`, in chunks); the session tells its layout, the development compositor its `--layout`, and `regress.py` passes a scenario's `layout` without `--uinput` too.
   - **Astro:** `OxyOSInputMethodContext`, the conversions in `oxyos_text_input` (the field told, its purpose, a transaction in UTF-16, the field after an edit) and the keymap (`oxyos_keymap`), with `ozone_unittests` (`OxyOSTextInput*`, `OxyOSKeymap*`: a French layout's Ctrl+Z at US W and its `q` at US A, Spanish's dead acute, the US position before any layout).
   - **Scenario:** `scenarios/astro-text-input.json` (`pages/astro-text-input.html`, layout `fr`): a focused field told empty, typing one transaction, a composition shown and left out of the field told, converted with a segment selected, committed, a deletion of whole characters, a dead key's composition and its character, Ctrl at US Q as Ctrl+A, and a password field telling nothing. Three runs out of three, with `astro.json` and `astro-clipboard.json` passing on the same build. Controls: with the layout `us`, the shortcut step fails; without the field told after an edit, the deletion counted the old text and removed two characters too many.
   - **Not Chromium's:** Astro's own shortcuts are matched by the physical key (`ac_window_keys.cc`, its window's `code|modifiers`), so on AZERTY the key at US W still closes a tab although Chromium now says it is Ctrl+Z. That is Astro's shortcut table's decision, not the platform's.

   *The clipboard is done.*
   - **OxyOS:** `oxyos_client_copy` (and `Client::copy` refusing more types than an offer takes, so a bad copy never closes the connection). For scenarios, the session can copy content it holds as a client of the scene it plays (`Scene::copy_for_session`, no input asked of it) and read what the clipboard holds through its owner's pipe (`Compositor::read_clipboard`); the development compositor plays another application's clipboard with them: a `clipboard` step copies, and every step reports what the clipboard holds as a receiver reads it (`regress.py`'s `clipboard` expectation).
