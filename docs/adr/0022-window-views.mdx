# ADR 0022: Windows live in the overview

Status: **accepted**; steps 1 to 3 implemented. Decides the thumbnails [ADR 0009](./0009-session-shell) left out (decision 3). Builds on [ADR 0004](./0004-gpu-composition) (composition on the CPU and a Vulkan device, byte for byte), [ADR 0005](./0005-damage) (damage), [ADR 0010](./0010-lock-screen) (the lock), [ADR 0011](./0011-transitions) (the overview's arrival and departure) and [ADR 0016](./0016-windows) (corners).

## Problem

On real hardware the overview (`apps/shell/src/components/Overview.tsx`) shows a card per window with its icon, its title and "Vista previa no disponible": nothing of what the window shows. The shell's model has a `thumbnail` for each window, but only the browser preview's fixture fills it; the compositor gives the shell nothing, as ADR 0009 left it.

Mission Control shows every window as it is, live: a video keeps playing in its card, text typed appears there. On a Mac this is the window server's work: WindowServer composes the windows' own layers, scaled into the places Mission Control's layout gives them; the Dock process, which draws Mission Control's chrome, never reads a window's pixels. Windows' DWM thumbnails (`DwmRegisterThumbnail`: an application names a source window and a destination rectangle, opacity and visibility, and DWM composes the window there), GNOME Shell's overview (clones of the windows' actors in the compositor's scene) and ChromeOS's overview (mirror layers) are the same design.

## Options

**(a) The compositor sends the shell images.** For each window the overview shows, the compositor scales a copy of its last frame down to the card's size into a sealed memfd (as clients' buffers go, but compositor to shell), at a bounded rate, only while the overview is open and only when the window changed; the shell's host decodes it into an `Image`.
- *Privacy:* the shell holds every window's pixels. It is the session's trusted program, but anything it does with them (a crash dump, a bug that keeps a buffer, an extension later) carries them out of the compositor.
- *Memory:* a copy per window at its card's size (a 380 × 240 card is 365 KB; ten windows, 3.6 MB), in both processes.
- *CPU:* a downscale per window per update in the compositor; then, on every update, the host draws the overview's surface again around the new image (the Bloom host draws on the CPU, about 20 ms for a frame of a window, ADR 0004) and submits it, and the compositor composes it.
- *Latency:* the rate bound (10 to 15 Hz to keep that cost down), plus the host's frame, plus a composition: 80 to 150 ms behind the window, never live.

**(b) The compositor draws the windows.** The shell says where on its surface each window goes; the compositor composes the window's own frame there, scaled, over the shell's pixels, in the same pass that composes everything else.
- *Privacy:* the shell never receives a window's pixels; it only knows where it asked for them.
- *Memory:* nothing new. The compositor reads every shown surface's frame for each composition already; a window shown only in the overview (on another workspace, or minimized) is read the same way while it is.
- *CPU/GPU:* one more layer per window, only where the damage reaches. The Vulkan compositor uploads a window's pixels once whether it is drawn once or twice (the same `Source`).
- *Latency:* none added: a window's new frame is in its card in the very composition that first shows it.
- *Cost:* the protocol (where), the compositor (drawing scaled, clipped, through the overview's transitions) and the host (finding where each card's window is) all change, and composition needs a filtered downscale: composition samples by nearest neighbour, which pixelates text at a quarter of its size.

## Decision

1. **(b): the compositor draws the windows live where the shell places them.** As Mission Control, DWM's thumbnails and GNOME's overview do. The shell (the `shell` grant, and only on its own shell surfaces) lists the windows a surface shows: `ClearWindowViews` begins the list, each `PlaceWindowView` adds one above those before it (at most 64): the window's number (ADR 0009's), its rectangle in the surface, a clip, a corner radius and an opacity. The list is shown with the surface's next `Submit`, so a card that moves and the window drawn in it move in the same frame. Any other client asking is closed (`Unauthorized`); on a surface not a shell surface, `InvalidRole`; a view outside a list begun, `InvalidOrder`.
2. **How a view is drawn.** Over its surface's pixels and under the surface's popups (a card's menu shows above the windows). The window's own surface, as shown now (in flight while a frame is composed), fitted into the rectangle with its proportions kept and centred, cut to the clip (and to the rectangle and the surface), its corners rounded by the radius, at the opacity times the surface's own in its transition. A window on another workspace or minimized is shown too, from its last frame: the overview shows every workspace's windows. A window gone, or a number naming none, draws nothing. A view takes no input: the surface under it does. On several displays ([ADR 0018](./0018-several-displays)) a view is placed on each screen as every layer is, its clip with it, and filtered from the window's buffer straight to the screen's pixels.
3. **Composition filters what it draws smaller.** `oxyos_gpu::Layer` gains a `filter` and a `clip`. `Filter::Box` draws each output pixel as the mean of the source pixels its footprint covers, at most 8 along each axis evenly spread (an exact box down to an eighth of the size, and the overview's cards are a third to a sixth of their windows' widths; a stratified one beyond), premultiplied pixels averaged with their alpha, in integers on the CPU reference and in the shader alike, so the two agree byte for byte. At a surface's own size it reads the one pixel nearest neighbour does. Every surface but a view is drawn as before (`Filter::Nearest`), and a clipped layer touches nothing outside its clip. The frame file is `OXYFRAME4`; older ones read with every layer nearest and unclipped.
4. **The shell is told each window's size** (`WindowSize`, when it is first told of the window and whenever its size changes) so it lays the cards out in the windows' proportions.
5. **Never under the lock.** Views are drawn only over a shell surface being drawn, and none is while the session is locked: nothing of them is composed, nor goes in a transition the lock drops.
6. **They arrive and go with their surface.** Arriving, a view is placed and faded as its surface is (the overview settling from 104 %); when the surface goes, its views go with it, from their windows' frames as they were when it began going, drawn through its fade.

## Steps

1. **Filtering and clipping in composition.** `Filter::Box` and `Layer::clip` in `oxyos-gpu`, on the CPU and in the shader, the frame file carrying them.

   *Done.* Tests: a one-pixel checkerboard drawn at a quarter of its size is grey (each pixel the mean of 4 × 4, 128) where nearest neighbour is black or white; opaque red beside nothing averages to red at half alpha over the background; a 32-pixel footprint is read at its 2nd, 6th … 30th pixels; at its own size the box reads what nearest neighbour does; a clipped layer leaves every pixel outside its clip as it was. On lavapipe (`VK_ICD_FILENAMES` to Mesa's), the Vulkan composition matches the reference byte for byte for opaque and premultiplied windows reduced to 160 × 100, 75 × 47, 37 × 23 and 13 × 9 from 320 × 200, at their size and enlarged, clipped and not, whole and from damage; with the shader's rounding changed, it fails.
2. **The protocol and the compositor.** Requests 90 and 91, event 80; views in the scene's render list (`RenderItem::View`); the compositor composing them, damaged where they change, through the overview's transitions.

   *Done* (`scene/window_views.rs`, `oxyos-compositor`). A view is in the frame's list right after its surface; its window's pixels are read once when the window is drawn too (the view's layer reads the window's), and with the window's `Source`, so the device uploads them once. Its damage is its clip where it came, went, moved or shows a new frame. Scene tests: a window fitted where the shell placed it (1280 × 800 in 400 × 400 is 400 × 250, centred), not before the frame it was sent with; its next frame in the view in the frame being composed; clips; a window on another workspace or minimized shown, one gone or unnamed not; the list gone with its surface; an application refused even on its own window, a toplevel of the shell's refused, a view outside a list, the 65th; nothing while locked, even a list sent then; the shell told each window's size, once per change, and applications never. Through real sockets on the compositor's clock (`tests/window_views.rs`): a 200 × 100 window whose left half is red and right half a checkerboard shows in the overview's 100 × 100 card as red and #808080 at 100 × 50, the desktop above and below; its next frame is in the card in the frame that first shows it, that frame composed only where the window and the card are; an open overview composes nothing when nothing changes; locked, the output is the lock's covers alone, and unlocked the card shows the window again; closed, the overview's card fades with it (red faded over the desktop at 75 ms, the desktop at 200). With the views drawn by nearest neighbour, or not going with their surface, those tests fail.
3. **The host and the shell.** `oxyos_client_show_windows` in the C ABI and `OXYOS_EVENT_WINDOW_SIZE`; the host's `OxyOSWindowView`, whose place, clip, radius and opacity the host finds as it draws a shell region and sends with the region's frame when they change; the overview's cards showing it; a scenario.

   *Done.* The platform's `WindowView` (`apps/shell/src/platform.tsx`) is the shell's: the OxyOS platform renders the host component (`sample/oxyos/shell-surface.js`); the overview uses it where the platform has one, else a still `thumbnail`, else the icon. The host records each `OxyOSWindowView` it draws on a region's canvas (or in a layer only moved and scaled, as the dragged card is: through its map) and not one drawn in a mask, a blur, a modal's animation or a view turned or skewed. A region whose drawing did not change but whose windows did (a card moved with nothing of its own drawn there) is walked without painting and submitted again, damaged where they were and are. `ShellSession` gives each window its size as `thumbnailSize`, so cards are in the windows' proportions. `scenarios/shell-thumbnails.json` (measured below) opens the overview from the dock with Allo's window on the desktop and checks the card shows the window's own pixels where the overview drew it; with the compositor ignoring the shell's views, it fails.

## Measurements

On the development machine (WSL2; no GPU reachable from Linux, so composition runs on the CPU reference and on lavapipe), release builds:

| | Without views | With the overview showing the window |
| --- | --- | --- |
| Memory kept by the compositor or the shell for it | — | none: no copy of any window is kept; a window drawn only in the overview (another workspace, minimized) is read for each frame composed, as a shown one is, and dropped |
| CPU reference, a 1280 × 720 frame with a 600 × 360 window (Allo) and its 477 × 286 card | 1.5 ms | 4.5 ms (2.1 ms drawn by nearest neighbour) |
| CPU reference, 1920 × 1200 with a 1280 × 800 window and a 380 × 237 card | 5.7 ms | 9.0 ms (5.9 ms nearest) |
| CPU reference, 1920 × 1200 with a full-screen window and a 380 × 237 card | 10.5 ms | 16.5 ms (11.5 ms nearest) |
| A window's new frame in its card | — | in the same composition that first shows it on screen (0 frames later) |
| Frames composed while nothing changes | 0 | 0 |
| `shell-thumbnails`, input to the answer on screen (the CPU fixture, five runs each, medians of the runs' medians and maxima) | 85 / 109 ms (the compositor drawing no views) | 92 / 113 ms |

The CPU reference composes every frame whole; a session composes on the device, from the damage, where a card costs its own pixels' taps (at most 64 reads each) and the window's pixels are uploaded once for both layers. On lavapipe, `shell-thumbnails` and `shell-overview` run with every frame composed on the Vulkan device identical to the reference (56 and 42 frames). Composition time on a real GPU is still to be measured on the ThinkPad, as ADR 0004's were.

## Consequences

- The overview shows windows live, at no latency, with no copy of any window outside the compositor; the shell knows only where it put them.
- Composition can draw a surface smaller without pixelating it; nothing else changes how it is drawn.
- The compositor rounds a view's every corner by one radius (the host sends the view's largest), not each corner by its own: a card rounded only at the bottom shows its window rounded at the top too.
- A view inside something the host draws apart (a mask, a blur, a turned view) is not shown: the overview uses none of them over its cards.
- Not in this decision: a window's popups and dialogs in its card (Mission Control shows sheets with their window); the windows of other workspaces drawing again while not shown (they show their last frame, as a Mac's spaces do until visited); the window shown live anywhere but the shell's surfaces.
