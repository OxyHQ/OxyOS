# ADR 0041: Input methods

Status: **accepted** (chosen with the platform's author); steps 1, 2 and 3 implemented, the rest built in the steps below. Builds on [ADR 0008](./0008-input-method) (the field's state, transactions, the `input_method` role and the candidates surface, which this decision amends), [ADR 0037](./0037-text-editing) (whose first remaining item this is), [ADR 0024](./0024-system-shortcuts) (Super is the system's; amended for Super+Space), [ADR 0014](./0014-screen-reader) and [ADR 0039](./0039-keyboard-access) (the reader, live regions), [ADR 0019](./0019-settings) (preferences, Settings), [ADR 0040](./0040-language-and-region) (the session's language) and [ADR 0033](./0033-protocol-versions) (version 18).

## Problem

ADR 0037 ends with what OxyOS cannot type: "CJK input methods… no input-method service exists; the protocol, the input-method role and the candidate popup exist, but the session can't grant the role yet." A person who writes Chinese, Japanese or Korean cannot use OxyOS, and nobody can type an emoji except by pasting one.

ADR 0008 made room for an input method and left the engine to "a separate project (a port of an existing engine's core)". Writing one is not an option: a pinyin engine is a language model, dictionaries and years of tuning; Japanese conversion is a morphological analyser and a dictionary; Hangul composition has a dozen keyboard layouts. The platforms that do this well use an engine built for it: macOS its own, Android its keyboards, ChromeOS Google's, the Linux desktops fcitx5 or IBus.

## Options

| | fcitx5 | IBus |
| --- | --- | --- |
| Core | a C++ library and daemon with addons (`libfcitx5core`) | a GLib daemon (`ibus-daemon`) |
| Debian's core package | `fcitx5` → `fcitx5-modules`: Cairo, Pango, GdkPixbuf, xcb, libwayland-client | `ibus`: GTK 3, ATK, dconf, libnotify, Python with GObject introspection |
| Built without a toolkit | yes: `ENABLE_X11=Off`, `ENABLE_WAYLAND=Off` leave no UI addon that draws | no: the panel (candidates, menus) is a GTK 3 process; engines are GLib programs, ibus-hangul and ibus-anthy Python with GTK |
| Frontend API | D-Bus `org.fcitx.Fcitx.InputContext1`: `ProcessKeyEventBatch` answers a key with everything it did (commit, preedit, deleted surrounding text, forwarded keys) in its reply; `UpdateClientSideUI` gives a client that draws its own candidates their list, highlight and paging; `SelectCandidate`, `PrevPage`, `NextPage` | D-Bus `org.freedesktop.IBus.InputContext`: signals for commit and preedit apart from the key's answer; candidates go to a panel process, a client draws them only as a panel |
| Engines | pinyin and shuangpin (libime), Anthy, Mozc, libhangul, rime, tables, emoji (CLDR's annotations in its languages) with QuickPhrase | libpinyin, Anthy, Mozc, libhangul, rime, typing-booster |
| Without a display server | fcitx5-android runs its core with a frontend and candidate UI of its own, no X11 or Wayland | the daemon and engines run, but candidate display assumes the panel |

**fcitx5.** Its core, its D-Bus frontend and its engines need no toolkit and no display server; its frontend API was made for clients that draw their own candidates; and one key's whole effect arrives in one reply, which is ADR 0008's transaction. IBus brings GTK 3 and Python into the session even before an engine, which the image rules forbid.

## Decision

1. **The engine is fcitx5**, with Debian Trixie's versions: fcitx5 5.1.12 (its keyboard engine, D-Bus module and frontend, emoji and QuickPhrase modules), libime 1.1.10 with its 2025-03-27 dictionaries and language model, fcitx5-chinese-addons 5.1.8 (pinyin and punctuation only), fcitx5-anthy 5.1.6 (Japanese, Anthy) and fcitx5-hangul 5.1.6 (Korean, libhangul).

   - **Japanese is Anthy, for now.** Mozc converts better, but Debian's `mozc-server` depends on GTK 2 and Mozc builds with Bazel. Mozc, its server built without its renderer, replaces Anthy when it is built here (What remains).
   - **Built from source, toolkit-free.** Debian's `fcitx5` depends on `fcitx5-modules`, which links Cairo, Pango, GdkPixbuf, the X11 client libraries and libwayland-client, and every engine package depends on `fcitx5`; none can be installed. `tools/input-methods/build.sh` builds the stack from Debian's own `.orig` tarballs (pinned by SHA-256) with X11 and Wayland off (no classic UI, XIM, Wayland frontend, xcb or wayland modules), no Enchant, no Qt configuration tools and no cloud pinyin, installs it at `/usr/lib/oxyos/input-methods`, and refuses the result if anything in it links X11, xcb, Wayland, GTK, Qt, Cairo, Pango, GLib or Enchant. What it needs at run time and Debian ships toolkit-free comes from apt: `dbus-daemon`, `libhangul1` and `libhangul-data`, `libanthy1t64` and `anthy-common`, and libraries a Trixie base already has (`libjson-c5`, `libxkbcommon0`, `libuuid1`, `libexpat1`, `libsystemd0`, `libfmt10`, `libboost-iostreams1.83.0`, `libzstd1`, `xkb-data`, `iso-codes`). The image gains them, and the engine, when the session joins it.

2. **The session runs the engine and is its frontend.** `oxyos-session` (and the development compositor, so scenarios run the real engine) starts, in a directory of its own under the session's runtime directory (mode 0700):
   - a **private D-Bus daemon** (`dbus-daemon` with a configuration of its own: this user only, no activation, no system services), which only the session and the engine use; applications are never told its address, and nothing in it is reachable from the user's session bus or the system bus;
   - **fcitx5**, headless: `--disable=all` and only the addons it needs enabled (`dbus`, `dbusfrontend`, the engines, `punctuation`, `quickphrase`, `emoji`, `keyboard`), so no UI, notification, virtual-keyboard, IBus or fcitx4 frontend addon loads. Its configuration is the session's, written before it starts: no trigger or enumeration keys (the session switches, decision 6), the candidate keys of decision 5, no shared state between fields. Its learning (pinyin's user dictionary, Anthy's history) is kept in the person's data under `oxyos/input-methods`.

   The session's frontend is a **client of the scene holding the `input_method` grant**, in the session's process, as the development compositor's own input method is: it receives what ADR 0008 gives an input method (the served field's purpose, surrounding text and selection, the keys first) and sends what an input method sends (transactions, keys given back). This is how the session grants the role: to itself. Passwords, PINs and sensitive fields never reach it (ADR 0008, decision 4). Its D-Bus calls run on a worker thread of their own and wake the compositor's turn when answered, as the controls' worker does (ADR 0025); the compositor never waits on the engine. If the engine stops, the keys it held go on (ADR 0008's rule for an input method that disconnects), the field keeps typing with the layout, and the session starts it again, at most once every few seconds.

   Only while an **input method** is the current input source (decision 6) is the frontend connected to the scene: with a keyboard layout current, keys type as they do today, the compositor's dead keys and compose sequences (ADR 0037, decision 1) included, with no round trip.

3. **One input context, the field's state in it.** The frontend makes one fcitx5 input context, named `oxyos` (never the application's id: ADR 0008, decision 2). Activation focuses it in (`FocusIn`), deactivation resets and focuses it out (`Reset`, `FocusOut`), each field starting with no composition. Its capabilities are preedit with formatting, the surrounding text, a client-side input panel (decision 5), the key-order fix, and the field's purpose and hints (email, URL, number, digits, phone, name, date, time, multiline, no prediction). The field's surrounding text and selection go to `SetSurroundingText`, its byte offsets turned into the characters fcitx5 counts.

4. **A key is one transaction.** Each key the scene gives the frontend goes to `ProcessKeyEventBatch` as fcitx5 takes a key from any frontend: its keysym, its XKB keycode, the modifiers in effect and press or release. Its reply becomes one ADR 0008 transaction, applied before the key's answer, so the field changes and then the key is taken or given back:
   - committed text → `InputMethodCommitText`;
   - the formatted preedit → `InputMethodPreeditText` with its cursor and its segments: an underlined segment `Composing`, a highlighted one (the part being converted, Anthy's selected clause) `Converting`; the Bloom host already draws both (ADR 0008; #243);
   - deleted surrounding text (characters around the caret) → `InputMethodDelete`, in bytes before and after the selection;
   - the key itself forwarded → the key given back (`InputMethodKeyHandled` with `used` false); a forwarded key of another kind is never typed into the field;
   - and the answer: `used` as fcitx5 says.

   So React hears what it hears for any composition (ADR 0037, decision 2), as Android's `InputConnection` makes `ReactEditText` hear it: `onChange` with the composition while it lasts, `onChange` once more with the committed text when it ends, and no key event for a key the engine took. No key the engine takes reaches the application, press or release.

   For this the scene tells an input method more of a key: **`InputMethodKeySymbol { serial, keysym, modifiers }`** (protocol version 18) before each `InputMethodKey`, the keymap's symbol for it and the modifiers in effect (XKB's depressed, latched and locked, as one mask in X11's bits), so an engine reads a key as the person's layout types it. An input method of version 17 is not sent it.

5. **The shell draws the candidates.** ADR 0008 let an input method make one candidates surface of its own; an engine that draws nothing hands its candidates to the system instead, and the session's always does. fcitx5's `UpdateClientSideUI` gives the candidates of the current page (each with its label, `1` to `9`, and its text), the highlighted one, whether there is a page before and after, the auxiliary text (pinyin's reading, Anthy's mode) and the layout. The frontend sends them to the scene, which tells the shell; the shell draws them in a candidates surface of its own (role `InputCandidates`, made with `CreateInputCandidates`, which the scene now allows the shell while the input method hands its candidates to it), which the compositor places at the field's caret rectangle as ADR 0008 places any: below the caret, above it with no room below, slid to stay on the caret's output, following the caret as it moves and the window as it moves.
   - **Bloom-styled**, as macOS draws its candidate window: a horizontal strip of numbered candidates in the session's text style, the highlighted one on the accent, the reading above, a chevron each side when there is a page before or after; light and dark; crisp at every scale (the shell is a Bloom application like any).
   - **From the keyboard**, all fcitx5's (the keys reach the engine first): ← → move the highlight, ↑ ↓, Page Up, Page Down and the engine's own (`-` `=` in pinyin) turn the page, 1–9 choose, Space and Return as the engine does (pinyin's Space takes the highlighted, Return the letters), Escape cancels.
   - **With the pointer**: a candidate pressed is chosen (`SelectCandidate`), a chevron turns the page. The surface never takes focus (ADR 0008): the field keeps its focus and its composition.
   - **Said by the screen reader.** The candidates are a list whose highlighted row says its text, its place and the count ("你好, 1 de 9"), and the highlight is a polite live region (ADR 0039), so the reader says each candidate as the highlight or the page changes, and a commit is said as typed text is (ADR 0037, decision 7).

   **Protocol (version 18):** from the input method, `InputMethodCandidate { label, text }` in chunks, then `InputMethodCandidates { highlighted, flags }` (a page before, a page after, vertical) closing the list, `InputMethodCandidatesAux { text }`, and an empty list to hide them; to the shell (its `shortcuts` grant), `InputCandidate`, `InputCandidates` and `InputCandidatesAux`, the same; from the shell, `ChooseInputCandidate { index }` and `TurnInputCandidatesPage { forward }`, which the scene passes to the input method as `InputMethodCandidateChosen` and `InputMethodCandidatesPage`. **Version 21:** from the shell, `ResizeInputCandidates { surface, size }`, its candidates surface at a new size as its list changes, its frame of the old size shown until one of the new is presented (the size of a candidates surface was fixed when it was made).

6. **Input sources, as on a Mac.** The person's input sources are their keyboard layout, always first and always there, then the input methods they added, in order: **Pinyin – Simplified** (`pinyin`), **Japanese – Romaji** (`japanese`), **2-Set Korean** (`korean`). They are preferences (ADR 0019): `input_sources`, the added ones (by default none), and `input_source`, the current (by default the layout). The session maps each to fcitx5's input method (`pinyin`, `anthy`, `hangul`), which types with the person's layout, and refuses one its engine does not have.
   - **Super+Space switches.** On a Mac, Control-Space selects the previous input source and, held, goes on through them; that is the owner's habit, and OxyOS keeps it on the system's key: **Super+Space** chooses the input source used before the current one, and each further Space while Super is held the one before that, by when each was last used. **Super+Alt+Space** chooses the next in the list, as a Mac's Control-Option-Space. With only the layout, both do nothing. Super is the system's (ADR 0024), so these never reach an application or the engine. The switch is at once: the current composition is committed as the engine commits it on focus out, and the next key types with the new source.
   - **The launcher's search moves to Super alone.** ADR 0024 gave Super+Space to the launcher's search, Spotlight's ⌘Space; a Mac has both because its input sources are on Control. OxyOS's Control is the applications' ⌘ (ADR 0024, decision 1), so the search takes the key ChromeOS, GNOME and Windows give their launcher: **Super pressed and released alone**, with no other key, button or scroll while it was down. ADR 0024's table and decision 5 are amended to say so.
   - **Emoji: Control+Super+Space**, as a Mac's Control-Command-Space, and the emoji key some keyboards have (Linux's `KEY_EMOJI_PICKER`). In any field that takes text, it starts fcitx5's QuickPhrase with emoji for the session's language (ADR 0040): the person types a word ("sonrisa", "smile"), the shell's candidates show the emoji CLDR names for it, and choosing one inserts it; Escape cancels. The input source does not change.
   - **The top bar shows the current input source** when there is more than one, as a Mac's Input menu: the layout's short name (`ES`, `US`), 拼, あ or 한. Its menu lists the sources with the current one checked, then "Show Emoji & Symbols" and "Open Keyboard Settings…"; the reader says it as "Input source, Pinyin – Simplified" and each switch as the new source's name.
   - **Settings › Keyboard › Input Sources** lists them, the layout first: **+** adds one of those the session has and the person has not added, **−** removes the selected one (never the layout); removing the current one makes the layout current.
   - **The session's language does not change them.** Choosing Chinese as the language (ADR 0040) adds no input source, nor does an input source change the language, as on a Mac.

7. **The fixture runs the same engine.** `oxyos-offscreen` starts the engine as the session does when given its prefix (`--input-methods PREFIX`, or `OXYOS_INPUT_METHODS`), with a configuration and data directory of the run's own, so scenarios type real pinyin, Japanese, Hangul and emoji through the real fcitx5 and its dictionaries. A machine that runs the scenarios without the engine installed uses one built by `tools/input-methods/build.sh` into the toolchain, as Skia's and Hermes's are.

## Consequences

- OxyOS types Chinese, Japanese and Korean and inserts emoji, with the engines the Linux desktops use, and nothing that draws comes with them.
- Every key with an input method current takes a round trip to the engine through D-Bus, off the compositor's turn; with a layout current, none.
- The engine is trusted as the session is: it sees what is typed into fields that are not secure. It runs as the person, on a bus nobody else is on.
- The search moves from Super+Space to Super alone; the scenarios and documentation that pressed Super+Space for it change with the step that moves it.

## Steps

1. This decision.
2. **The engine and the service.** `tools/input-methods/build.sh`; the private bus and fcitx5 started and restarted by the session and the fixture; the frontend as a scene client with `input_method`; keys, `ProcessKeyEventBatch` and transactions; `InputMethodKeySymbol` and the candidates' requests and events (version 18); input sources as preferences, Super+Space and Super+Alt+Space, the search on Super alone, emoji on Control+Super+Space. Scene tests for each, an engine test against the built fcitx5.

   *Done.* `tools/input-methods/build.sh` builds Debian Trixie's `.orig` tarballs (pinned by SHA-256) into a relocatable tree of 68 MB: nothing in it names where it was built (no RPATH, which it checks), and the session gives fcitx5 and libime where its libraries, addons and data are (`LD_LIBRARY_PATH`, `FCITX_ADDON_DIRS`, `FCITX_DATA_DIRS`, `XDG_DATA_DIRS`, `LIBIME_MODEL_DIRS`), so the tree the scenarios run is the one a machine installs (the deploy copies it to `/usr/lib/oxyos/input-methods`); it refuses anything linking X11, xcb, Wayland, GTK, Qt, Cairo, Pango, GLib or Enchant, and keeps only `bin/fcitx5`. `crates/oxyos-input-methods` starts the bus and fcitx5 and is the frontend on a thread of its own (one queue for the bus's messages and the compositor's commands, so a signal sent before a reply is handled before it); a key's answer is given after its transaction, a key the engine forwarded is given back, keys while the engine is down are given back at once, and an engine that stops or does not answer within 5 s is started again (at most every 3 s). `crates/oxyos-compositor/src/input_methods.rs` connects the frontend to the scene (`CLIENT`, `ClientId::MAX / 2`, an id nothing else takes: applications count up from 1, shells down from the top) while an input method is current or emoji are searched, turns fcitx5's character offsets into the protocol's bytes, keeps a composition the engine left unchanged, hands the candidates to the system, keeps the input sources (`input_sources`, `input_source`, ADR 0019; the recency order Super+Space goes back through), tells the shell and Settings `{"inputSources": …}` (`SystemText`, serial 0, as each connects and as it changes) and answers `{"inputSources":{}}`, `{"selectInputSource":{"id"}}` and `{"showEmoji":{}}` (`{"emoji":{}}`). The seat's keyboard leaves dead keys to the engine while an input method is current (`Keyboard::set_composing`). `InputMethodKeySymbol` carries `Action::Key`'s keysym and modifiers (`oxyos-input`). Pinyin's composition is underlined with its caret where typed (`PreeditCursorPositionAtBeginning=False`), and switching while composing commits it as typed (`SwitchInputMethodBehavior`); Anthy's clause being converted is fcitx5's highlighted part, `Converting`. `oxyos-offscreen --input-methods PREFIX` runs the engine as the session does, in the run's directory, waiting for it before the first step; `regress.py` passes it for a scenario with `input_methods`. Tests: the scene's candidates handed to and drawn by the shell, its presses, refusals, the shortcuts and the search on Super alone (`scene/tests/input_sources.rs`); version 18 never reaching an older peer; the preferences; and, with the engine built, `crates/oxyos-input-methods/tests/engine.rs`: "nihao" committed as 你好 with Space, "nihongo" to にほんご then 日本語 with its clause highlighted and committed with Return, g k s composing 한, and no descriptor or process left once the service is dropped.
3. **The shell's candidates and indicator.** The candidates surface in the Bloom host and the shell, its keys and pointer, the reader; the top bar's input source item and menu.

   As implemented: the client library gathers a page (`Client::candidates`) and the C ABI gives it as one `INPUT_CANDIDATES` event (`oxyos_client_input_candidates`), with `oxyos_client_create_input_candidates`, `oxyos_client_resize_input_candidates` (protocol version 21: the window grows and shrinks in place, its old frame shown until the new one; an older compositor has it made anew), `oxyos_client_choose_input_candidate` and `oxyos_client_turn_input_candidates_page`. The Bloom host draws a shell region of kind `candidates` in that surface, exactly the region's size in whole pixels, and tells JavaScript each page (`OxyOSShellCandidates`). The shell's candidate window is Bloom's menu surface in the person's accent: numbered candidates, the reading above, chevrons for the pages before and after, laid out down when the engine says so; a press chooses, a chevron turns the page. It stays mounted (a point while there is no list), so its list is one view for the screen reader from one composition to the next: named by its highlighted candidate with its place ("你好, 1 de 5"), a polite live region said at each change, its rows list items, the highlighted one selected. The top bar's input source item shows ES, 拼, あ or 한 with more than one source, named Input source with the current one as its value; its menu (Bloom's dropdown menu) lists the sources, the current checked, then Show Emoji & Symbols and Open Keyboard Settings… (Settings opened as the Oxy menu opens it: it has no page to open at by name yet); each switch is said politely by the new source's name. The Bloom host's fallback fonts gain Noto Sans CJK (`fonts-noto-cjk`, each face of the collection, the paragraph's language choosing among them: kana Japanese, Hangul Korean, else the session's language, else Simplified Chinese) and Noto Color Emoji. The development compositor's input method hands candidates to the system with `--im-candidates`, and `--input-sources-available` answers the top bar's requests; `scenarios/shell-candidates*.json` and `shell-input-sources*.json` check them at 1 and 1.25.
4. **Settings › Keyboard › Input Sources.**

   *Done.* Settings' Keyboard page lists the sources as the session tells them (`inputSources`, asked once as the page mounts and followed as told) in Bloom's `ChoiceList`, one keyboard stop moved by the arrows: the layout first, named as people read it ("Español", "U.S.", from Settings' catalogue; a variant, or a layout it does not name, as XKB names it) and drawn with its short name, then each input method added, drawn with its glyph; the current one checked and said "in use" ("Coreano de 2 conjuntos, en uso, seleccionado, 2 de 2"). **+** opens a sheet (Bloom's `Dialog`) of the input methods the engine has and the person has not added, the keyboard on the first, chosen; Add adds the chosen one after the others. **−** removes the selected one, never the layout: it is disabled with the layout selected, and the keyboard goes to **+** when it goes disabled under it. A change is `input_sources` through `SetPreference`; an addition or a removal is said once it is in effect ("Se ha añadido Pinyin – Simplificado"), and an addition selects the new row. Without input methods installed the section says so and **+** is disabled. Its words are in both catalogues; its model is `apps/settings/src/input-sources.ts`, with unit tests. The development compositor plays the session's state without the engine (`--input-sources-available METHOD,...`, refused beside `--input-methods`), and a step's `preferences_file` now checks the file as that step left it. The Bloom host clamps a scroll view it scrolled to its content once it is laid out again, as Android's ScrollView does, so a Bloom dialog opened from the keyboard shows its content (it opened empty, its scroll left where the dialog's first, narrower layout put it). Scenarios `settings-input-sources` and `-scaled`, with the screen reader in Spanish. The input methods' glyphs (拼, あ, 한) wait for the host's CJK font fallback, step 3's.
5. **Scenarios**, with fcitx5 running in the fixture, each at 1 and 1.25 where the caret is placed: "nihao" typed and committed as 你好; romaji to kana to kanji with a candidate chosen; Hangul composed; an emoji from its name. Each checks the exact React events (`onChange` during the composition, its end), the preedit's segments, the candidates' place under the caret, the reader's words for the candidates, and that no key reached the application while composing. In the deploy gate, and the deploy installs what the ThinkPad needs.

## What remains

- **Mozc** for Japanese (its server without its GTK renderer); **rime**, **shuangpin**, **Traditional Chinese** (Zhuyin, Cangjie) and other engines fcitx5 has.
- A switcher shown while Super is held through several input sources (a Mac's palette); the top bar's item says each one meanwhile.
- **Handwriting** and **voice input**.
- The candidates' reading in the candidate's own language (the reader speaks them with the session's voice; eSpeak NG's `cmn`, `ja` and `ko` voices per utterance).
- **Astro** (Chromium, ADR 0029) uses its own text input with Chromium's Linux input-method path, which this does not reach yet.
