# ADR 0021: The menu bar

Status: **accepted** (the global menu bar was chosen with the platform's author); steps 2, 3 and 4 implemented; step 1 in Bloom ([OxyHQ/Bloom#518](https://github.com/OxyHQ/Bloom/pull/518), not released yet). The `menu-bar` capability of [ADR 0015](./0015-application-model). Builds on [ADR 0002](./0002-bloom-platform-surface-api) (Bloom's platform adapter), [ADR 0009](./0009-session-shell) (the shell and its top bar), [ADR 0013](./0013-launching-applications) (applications' names) and [ADR 0016](./0016-windows) (the active window).

**10 November 2026 (step 5):** every frontmost application has its own menu, its name in bold, even one that declares no menus: About *App* (the application's own, or the system's standard About panel), Settings… (Ctrl+,; the application's own, else not offered), Hide *App* (Super+H), Hide Others (Alt+Super+H), Show All and Quit *App* (Super+Q); with no window active, the desktop's own menu. Every menu of the shell writes chords one way (Ctrl, Alt, Shift, Super, then the key, by their names in the session's language).

**9 November 2026 ([ADR 0064](./0064-sleep-restart-shut-down-and-log-out)):** the shell's own Oxy menu, the bar's first, is the Apple menu's equal: System Settings, Applications, Show Desktops, then Sleep, Restart…, Shut Down…, then Lock Screen (Ctrl+Super+Q) and Log Out *name*… (Shift+Super+Q), with Alt's alternates (no ellipsis, no question). Its commands are the session's to decide (`endSession`, `sleep`), never the shell's.

## Problem

On a Mac, the bar at the top of the screen shows the active application's menus: its name in bold, then File, Edit, View and the rest, with each command's shortcut. The application declares them; the system draws them, and a command chosen there runs in the application. OxyOS's shell has the bar (its `TopBar` takes `menus` and calls back with a command's id), but nothing fills it: applications have no way to say what their menus are, and the shell shows a fixture's.

Bloom already has a menu bar (`@oxy.so/bloom/menubar`, shadcn's): an application that wants menus declares them with it, and it draws them in the window. On the web, natively on a phone, and on a platform without a global bar that is right, and must not change.

## Decision

1. **The application declares its menus once, with Bloom's `Menubar`.** Its menus, items, check items, radio groups, separators, submenus, disabled states and shortcuts, and what each does (`onSelect`, `onCheckedChange`, `onValueChange`), as it does today. No other API, no platform test.
2. **Bloom presents them by capability.**
   - **Without `menu-bar`:** `Menubar` draws itself in the window, exactly as now.
   - **With it:** `Menubar` draws nothing in the window. It gives the platform a description of its menus whenever they change, and runs an item when the platform says it was chosen. The description is plain data:

   ```ts
   interface PlatformMenuBar {
     /** The window's menus now; replaces the last. An empty list: none. */
     setMenus(menus: readonly PlatformMenu[]): void;
     /** An item the person chose in the platform's bar, by the id Bloom gave it. */
     onActivate(listener: (id: string) => void): () => void;
   }
   interface PlatformMenu { id: string; label: string; items: readonly PlatformMenuItem[] }
   type PlatformMenuItem =
     | { kind: 'item'; id: string; label: string; enabled: boolean; shortcut?: string;
         checked?: boolean /* check and radio items */ }
     | { kind: 'submenu'; id: string; label: string; enabled: boolean; items: readonly PlatformMenuItem[] }
     | { kind: 'separator' };
   ```

   Ids are Bloom's own, stable while an item is mounted; labels are the items' text. A radio group is its items, each `checked` or not.
3. **Shortcuts are Bloom's, on every platform.** An item's shortcut is declared as a key chord (`Mod+N`, `Mod+Shift+Z`; `Mod` is the platform's command modifier: ⌘ on a Mac, Ctrl elsewhere, OxyOS included). Bloom matches it against the window's keys and runs the item, with or without a bar showing it, so a command works the same on every platform. The bar only shows the chord. A focused text field keeps the keys it uses (Ctrl+C in a field copies, as ADR 0008's editing does), and the menu's item for them acts through the field: the Edit menu's standard items are the first responder's (amended, step 4).
4. **On OxyOS the shell shows the active window's menus.**
   - **The message.** The application's host sends its window's menus to the compositor as one message, in chunks, the way an accessibility snapshot is sent ([ADR 0003](./0003-accessibility-protocol)): each item's kind, parent, state, label and shortcut. A new message replaces the last.
   - **What the shell is told.** The compositor tells the shell (its `shell` grant) the menus of the active window ([ADR 0016](./0016-windows)), and tells it again when they change or another window becomes active. The shell's top bar shows them after the application's own menu.
   - **The application's own menu,** in bold, is the shell's, for every application whether it declared menus or not. It holds the application's name from the registry (ADR 0013), About, Settings…, Hide, Hide Others, Show All and Quit (the application's close request, as the close bubble's); the application's own About and Settings… are shown there (step 5). An application's first declared menu is not that menu.
   - **Choosing an item.** The shell sends the item's id. The compositor gives it to the window's client only if that window's menus have that id; the host hands it to Bloom, which runs the item.
   - **When nothing is active,** the bar shows the desktop's own menu and View (step 5).
   - **From the keyboard,** Super+F2 moves the keyboard to the bar, as a Mac's Control-F2, and its menus are opened and chosen with the arrows, Return and Escape; the window stays the active one, and a choice or Escape gives it the keyboard back ([ADR 0024](./0024-system-shortcuts), decision 9).
   - **What is never sent.** Menus carry labels and chords, never the application's data; the compositor and the shell never run an application's command themselves.
5. **Elsewhere,** a desktop's native runtime gives the menus to the system's bar (a Mac's `NSMenu`), and the web and phones keep Bloom's in-window bar; each with its own adapter, the application unchanged ([ADR 0015](./0015-application-model)).

## Steps

1. **Bloom:**
   - the capability and `PlatformMenuBar`;
   - `Menubar` describing itself instead of drawing when it is reported;
   - shortcuts as chords, matched on every platform;
   - tests that the same declaration draws in the window without the capability and describes itself with it.
2. **The protocol and the compositor:**
   - an application's menus, in chunks with a commit;
   - the shell told the active window's menus;
   - the shell's choice delivered only for an id the window declared;
   - the C ABI.

   Tests: menus follow activation, an id not declared is refused, and a client without the `shell` grant hears nothing of other windows' menus.

   *Done.* The pieces:
   - **The message.** A toplevel's menus are `MenusBegin { surface, serial, items }` (request 80), one `MenuItem { surface, index, parent, kind, flags }` (81) per entry in order, `MenuText { surface, index, field, text }` (82) chunks for each entry's label and a command's shortcut, and `MenusCommit { surface }` (83), which replaces the window's menus; none (0 entries) is none. `kind` is a menu of the bar, a command, a submenu or a separator; `flags` are disabled (a command or a submenu), checkable and checked (a command). Limits (`oxyos-protocol`): 256 entries, nested 4 deep (a menu of the bar, its entries, two submenus), 128 bytes of label and 32 of shortcut. The compositor refuses as a protocol error an entry out of order, a root that is not a menu or a menu that is not a root, a parent that is not an earlier menu or submenu, flags its kind cannot have (a check without `checkable`, anything on a menu or a separator), text on a separator, a shortcut on anything but a command, an entry with no label, a commit before every entry came, a serial not above the window's last, and menus on anything but a toplevel.
   - **Ids as indices, per commit.** Bloom's ids never leave the application. Each commit's serial rises, and a command is named by that serial and its index in the commit; the host's adapter keeps the ids of its latest commits. A choice the shell made from menus the application has since committed again names an older serial and is refused, so it can never run whichever entry took that index; the application's own table maps an index of a recent commit back to the id Bloom gave it, which Bloom keeps while the item is mounted. Carrying the ids as text would have sent the application's own strings to the compositor and the shell, and made every choice a message in chunks.
   - **What the shell is told** (`scene/menus.rs`). To each client granted `shell`: `MenuBar { window, serial, items }` (event 70), the entries as `MenuBarItem` (71) and their texts as `MenuBarText` (72), then `MenuBarCommitted { window }` (73), whenever the active window ([ADR 0016](./0016-windows)) or its menus change, after the windows themselves (so the shell knows the window's number); `window` 0 when none is active, `serial` 0 and no entries when it declared none. A shell that connects is told at once. Applications are never told any of these.
   - **Choosing.** `ActivateMenuItem { window, serial, index }` (request 84), from the `shell` grant alone (any other client is refused as unauthorized). The compositor sends `MenuItemActivated { surface, serial, menus, index }` (event 74) to the window's client only if the window is the active one, its menus are still that commit, the entry is a command and neither it nor anything it is in is disabled, and the session is not locked; anything else is answered with nothing. `serial` is a new input serial, recorded as the client's input as an assistive technology's activation is, so a command (Edit › Paste, a popup) may cite it.
   - **The active window, minimized from the bar.** A window minimized (or left on another workspace) while the shell's top bar had focus was still the active one, as focus on a panel kept it; it is no longer: a panel keeps the active window only while it is shown, and minimizing and workspace changes look again.
   - **The C ABI.** `oxyos_client_set_menus` (an `OxyOSMenuItem` per entry: parent, kind, flags, label, shortcut; a label too long is cut at a character, a shortcut too long left out), `oxyos_client_activate_menu_item`, the `OXYOS_EVENT_MENU_BAR*` events and `OXYOS_EVENT_MENU_ITEM_ACTIVATED`, and the `OXYOS_MENU_*` constants.

   Tests on the scene (`scene/tests/menus.rs`): the shell told nothing active at first, then each window's menus as activation moves, a recommit replacing them, the top bar's focus keeping them, the lock, a minimized window and a late shell; a choice reaching the window's client alone, once, its serial a recent input, and refused for a menu, a separator, a disabled command, a command in a disabled submenu, an index past the end, another serial (one from before a recommit included, which would otherwise have named another entry), another window, an inactive window and the lock; serials that do not rise; applications never told any window's menus, and an application choosing refused; a window that goes taking its menus off the bar; every limit taken at its edge and each malformed message refused. Through the C ABI: the header's constants and `OxyOSMenuItem`'s layout, each event field by field, and menus and a choice through a socket (with the cut label and the dropped chord). The development compositor counts a delivered choice as `menu.activated`, for scenarios.
3. **The Bloom host and the shell.** The host's adapter. The shell's top bar shows the active window's menus, its application menu, checked items and chords. A scenario:
   - a sample declares File and Edit with shortcuts;
   - the shell's bar shows them while the sample is active, and its own menus while nothing is;
   - choosing New runs the item in the sample (React receives it once);
   - the sample's Ctrl+N does the same without the bar;
   - a check item toggles in both.

   *Done* with Bloom's step 1 as [OxyHQ/Bloom#518](https://github.com/OxyHQ/Bloom/pull/518) (not released yet; the scenario's bundle is built from its branch). The pieces:
   - **The adapter's menus.** `sample/oxyos/platform-surface.js` reports `menu-bar` and gives `menuBar` (as above) when the host runs an application in a window of its own. `setMenus` turns Bloom's menus into entries in order (menus, commands with their check and chord, submenus, separators; entries past the protocol's limits, or without a label, are left out rather than refused whole), sends them as a new commit unless they are the same as the last, and keeps that commit's ids by index (the last eight commits'); a choice (`OxyOSMenuActivated`, from the host's `OxyOSMenuBar` module) runs `onActivate`'s listeners with the id of that index in that commit.
   - **The adapter's keys.** Bloom matches chords itself (decision 3) on the keys its platform's `keyboard` offers. The host offers each key press of an application's window to JavaScript before anything else sees it (`OxyOSKeyboard`, `key-chords.h`): synchronously, as a W3C `KeyboardEvent` (`key`, `code`, the modifiers, `repeat`); a press Bloom takes, and its release, are delivered to nothing else (not the focused field, a popup or Escape's close). The compositor sends Linux key codes and the host has no keymap yet, so a code's key is read on the US layout: a chord is matched by its key's place on a US keyboard, whatever the layout.
   - **The shell.** The host run as the shell keeps the bar in its state (`menuBar`); `ShellSession` (`sample/ShellProbe.tsx`) builds the top bar from it: the application's own menu in bold (its name from the registry, else the window's title; About, shown but not offered until there was an about panel, step 5; Hide, the shell's minimize; Quit, the window's close request as the close bubble's; since [ADR 0024](./0024-system-shortcuts), Hide hides the application and Quit asks each of its windows, as Super+H and Super+Q do), then the menus it declared. `TopBar` (`apps/shell`) is Bloom's own `Menubar` (Bloom 15.80.0): the Oxy menu first, then the application's, each a `MenubarMenu` with the shell's title as its trigger, and the commands with their check (`MenubarCheckboxItem`) and chord (`MenubarShortcut`, `Mod` shown as Ctrl, a hint the shell never runs), submenus and separators. With platform popups Bloom opens each menu as the web's desktop menu in a compositor popup, hanging under its title, and a submenu as a flyout beside its row in a popup of its own, a child of the menu's (the host places a popup anchored inside another of its popups on that popup, `popup.cpp`); the shell's adapter reports `pointer`, so the bar's menus take a desktop's compact rows. Since Bloom 15.83.0 the bar follows the pointer with a menu open, as a Mac's: moving onto another title opens its menu in place of the open one with no press, and ← → from a menu a press opened open the next ones. The menu names the bar as its `trackingRef`; the host asks the compositor that the bar's surface go on receiving the pointer's movement during the grab (`TrackPointer`, [ADR 0001](./0001-native-platform-boundaries#input-focus-and-grabs)) and gives it only to the bar; the menu that replaces another takes the grab straight from it, so the application hears nothing between the two (`scenarios/menu-bar-pointer.json`, at 1 and 1.25). Since Bloom 17.12.0 the bar's menus are ONE popup, as a Mac's bar has one menu at a time (the owner: the menu should be the same one, changing into the next): moving to another title with a menu open changes the open popup into the next menu instead of closing it for another. Bloom (`menubar/viewport.tsx`) moves the box the popup hangs from in the bar, from title to title, and the panel's size, frame by frame on the menu motion (150 ms ease-out, never overshooting), while the two menus' rows crossfade; with Reduce Motion it changes at once. The host places the same popup again each frame (`Reposition`, request 8, in the protocol since version 1: no new version, ADR 0033) and draws it only once the compositor has configured it for its new place and size (`PopupHost::observe`: a frame drawn before would answer a configure already replaced, and be discarded); the compositor shows each place and size with the frame drawn for it, never the old frame at the new place. The popup keeps its grab, the keyboard and the bar's `TrackPointer` throughout, so neither the window nor any other client hears anything (`a_menu_bar_menu_changes_into_the_next_in_its_one_popup`, which also presents a frame for the replaced configure and finds it not shown). The screen reader says a popup whose pane changed in place (its named menu's title) as it says one appearing, once, then what is focused in it (`oxyos-reader`, `a_menu_changing_into_another_in_its_popup_is_said_once_by_its_new_title`). `scenarios/menu-bar-morph.json` (`sample/MenuBarMorphProbe.tsx`: File, Edit and a View wider than the menus' floor), at 1.25 (`-scaled`) and with Reduce Motion (`-reduce-motion`): each move and ← → checks the menu the compositor composed in every frame (`menu_frames`: one popup, the same surface, its rectangle monotonic from the one menu's to the other's with places between, none with Reduce Motion), the frames that drew both menus' rows (`menu_crossfade`: at least two, none with Reduce Motion, the old rows gone at the end, no popup opened or closed), the rows shown, that the application was delivered nothing and React received nothing, and the reader's words: the new menu's title once, then the row the reader's focus moved into, its first (from a press, a move or the keys; Bloom 17.13.1: 17.12.0 sent that focus to a view Fabric flattens, so it landed nowhere and `desktop-accessibility` found no row of the Oxy menu focused). Before, the bar drew Bloom's `DropdownMenu` with the shell's own size, width and corner, and a phone's rows and inline submenus. `scenarios/menu-bar.json` also opens Open Recent's submenu with the pointer (a `move_output` step), checks the two panels' extents, the seam between them and the lit row, closes it after its grace by moving onto New, and chooses notes.txt in it. With no window active, or one that declared no menus, it showed the shell's own; since step 5 every application has its own menu, with Settings… when it declares one, and the desktop's shows while none is active.
   - **The scenario.** `scenarios/menu-bar.json` (`sample/MenuBarProbe.tsx`: Bloom's `Menubar` with File and Edit, their shortcuts, a disabled Undo, a submenu and a check item, launched as Allo):
     - Bloom draws no bar in the window, and the shell's bar shows Allo in bold, File and Edit while the window is active;
     - File opens with New Ctrl+N, Open… Ctrl+O and Open Recent;
     - choosing New runs it once (one `menu.activated` from the compositor, one event to JavaScript, the page counting one document);
     - with a text field focused and typed in, Ctrl+N runs New again without the bar: Bloom takes the key before the field (React receives nothing but the shortcut, the field keeps its text), and Ctrl+A stays the field's, selecting its text;
     - Edit shows Undo disabled with Ctrl+Z, and Wrap Lines unchecked; chosen, the page turns it on, Bloom describes the menus again and Edit shows it checked; chosen again, off;
     - minimized, no window is active and the bar is the shell's own (OxyOS, Ver); restored from the dock, the application's again.

     It passes. With the adapter's `menuBar` and `keyboard` taken away (Bloom then draws its bar in the window), every step but the minimized one fails (48 failures); with only `keyboard` taken away, the Ctrl+N step fails (and the counts after it). Every other host scenario that runs without a display (30) passes with the same build and bundle. On the way, `shell-windows` and `lock-screen` sometimes found the application's window placed before the shell's panels had taken their room. The development compositor started the application once the shell's surfaces stopped changing, and under load that could be the shell's background alone. It now waits for the panels to set the work area, as `oxyos-session` does; four runs at once, which failed every time before, pass.
   - **Not checked yet.** That a key Bloom took would have done something in the field had it been delivered: Ctrl+N does nothing in a field today, so the scenario shows the field received nothing, not that it was spared a change. Chords on layouts other than US.

4. **The Edit menu acts on the focused text field** (3 November 2026, the desktop-interaction audit against macOS). Decision 3 said an Edit item "acts through the field", but nothing did it: an application's Edit › Copy ran the application's own `onPress`, which cannot reach a `TextInput` (React Native has no first responder an item can address), so from the bar it copied nothing and stayed enabled with no selection. And the keyboard did not come back: a press on the top bar gave the bar's panel the keyboard, so after any of its menus was used with the pointer the window's field received no keys, and its Copy was refused (the clipboard changes only for the client the user types into).

   *Decision,* as a Mac's responder chain and Android's `onTextContextMenuItem`:
   - **Bloom: `MenubarItem action`** (`undo`, `redo`, `cut`, `copy`, `paste`, `pasteAndMatchStyle`, `delete`, `selectAll`; Bloom 17.1.0, [OxyHQ/Bloom#622](https://github.com/OxyHQ/Bloom/pull/622)), which the runtime now requires (`framework.mjs`), a nil-targeted action. While a text field has focus it is the item's target, whatever component draws it: the item is enabled exactly as the field validates it (NSTextView's `validateMenuItem:`, the same rules as the field's context menu, ADR 0037 decision 8, plus Delete with a selection in an editable field and Paste and Match Style as Paste) and choosing it performs it there; the application's `onPress` and `disabled` are not used then. With no field focused it is the application's item (its `onPress`, so Dropsea's Copy copies the selected files), disabled with no handler. Each action brings its standard chord (Ctrl+Z, Ctrl+Shift+Z, Ctrl+X, Ctrl+C, Ctrl+V, Ctrl+Alt+Shift+V, Ctrl+A; Delete none); the field keeps the chords it edits with, so it acts on them itself, once. **Find** is no editing action: no field claims it, and it is the application's command.
   - **The platform says who the first responder is:** Bloom's adapter gains an optional `editing` (`PlatformEditing`: `getState`, `subscribe`, `perform`), which OxyOS's runtime supplies from the host (`OxyOSEditing`): the host's text editing (`TextEditing::responder`, the context menu's `Commands`) tells JavaScript what the focused input can do whenever it changes (`OxyOSEditingChanged`: focus, text, selection, history, the clipboard), and `perform` does the action as the input's own key, citing the latest input (the bar's choice, which the compositor records as the client's input) for the clipboard. The host reports each change (`editing.responder`).
   - **The top bar never takes the keyboard by a press** (`Scene::pointer_button`): a press on a shell panel (the top bar, the dock) leaves the keyboard where it is, as a click on a Mac's menu bar or Dock leaves the key window key; a menu it opens grabs the keyboard and gives it back to the window as it closes, chosen or dismissed. The shell still takes the keyboard for a panel by asking (`FocusShellSurface`: Super+F2, F3, F8).
   - **The key window's clipboard:** while the keyboard is on a shell panel or one of its menus, the active window is still the one the user types into for the clipboard (`Scene::typing_into`), as it stays the key window (ADR 0037, decision 6), so an Edit › Copy that arrives before the bar's menu has closed is the window's own. Any other client is still refused.

   *Tests.* Bloom: `MenubarEditActions.test.tsx` (the application's item with no field, the field's validation and its actions, described again once per change, never reaching a field that lost focus, the standard chords, the field keeping its own and Paste and Match Style's taken, drawn rows). Scene: `a_menu_of_the_top_bar_gives_the_keyboard_back_to_the_active_window` (chosen and dismissed by an outside press, the window told once, never deactivated, its clipboard offer taken while the menu has the keys and another client's refused); the menus and active-window tests now take the panel's keyboard by `FocusShellSurface`. `scenarios/edit-menu.json` and `edit-menu-scaled.json` (at 1.25), `sample/EditMenuProbe.tsx` launched as Allo with `EditMenuPeer` as a second application: each step checks both windows' menus exactly as the shell is told them (every Edit item's state), the text and selection React receives, both applications' exact React events, what each client was delivered, focus and the clipboard:
     1. no field focused: every editing item disabled but the application's own Copy (enabled once its item is selected, and run once from the bar, the clipboard untouched) and Find…;
     2. a field focused takes them over (Copy disabled with no selection though the page has its item), typing turns on Undo and Select All;
     3. Edit opened in the shell's bar with the pointer and Select All chosen there selects the field's text, and the window has the keyboard again (Right then moves its caret);
     4. Copy chosen in the bar copies the field's selection (the clipboard holds it), Paste comes on; Ctrl+X is the field's own; Edit › Paste, Undo, Redo and Delete act on it, each once;
     5. Ctrl+Alt+Shift+V is taken by Bloom and pastes as plain text, once; Find… runs the application's command and leaves the field alone;
     6. a secure field: Paste, Delete and Select All, never Cut or Copy; `Keyboard.dismiss` gives the items back to the application;
     7. the clipboard's round trip: Paste chosen in the second application's Edit menu puts the first's text in its field, its Copy replaces the clipboard, and the first application's Paste takes it back.

     With the adapter's `editing` taken away, the run fails at the bar's first Copy for the field (the item is the application's again, and disabled); with the top bar taking the keyboard on a press, the bar's Copy is refused and the run fails at the Paste that needs it.
   - The development compositor's `menu` step now chooses in the active window, as the shell does, and the director reports the companion's menus (`companion_menus`, `in_companion`'s `menus`).
   - Scenarios that used the top bar or the dock with the pointer now expect the window's keyboard to stay with it: `menu-bar`, `menu-bar-pointer` (and at 1.25), `dock-menu` (and at 1.25), `dock-keep` and `dock-trash` see the window told `focus.out` as a bar's or the dock's menu opens and `focus.in` as it closes (and `focus.out` as the Trash's click opens Dropsea over it), and Control held after the dock's menu has closed reaches the window, not the dock. The pressed panel is still raised within the panel layer, so the top bar's menus are drawn over the dock (`lock-screen`, `session-two-outputs`).

5. **Every application's own menu** (10 November 2026, the macOS details audit). The bar showed an application's own menu only when it had declared menus: Settings, Inbox and the login program, which declare none, left the bar showing the shell's "OxyOS · Ver", so the frontmost application was never named. And its menu was About (shown, never offered), Hide and Quit with no chords, though Super+H and Super+Q work: no Settings…, Hide Others or Show All.

   *Decision,* as a Mac's application menu (HIG › The menu bar):
   - **Every application has its own menu**, first after the Oxy menu, its name in bold (weight 700), whether it declared menus or not: **About *App*** · **Settings…** (Ctrl+,) · **Hide *App*** (Super+H) · **Hide Others** (Alt+Super+H) · **Show All** · **Quit *App*** (Super+Q), separators between the groups as a Mac's. No Services menu: OxyOS has no services. Hide Others is not offered with no other application shown, nor Show All with none hidden, as a Mac's.
   - **The application's own About and Settings…** are Bloom's `MenubarItem action="about"` and `action="settings"` (Bloom 17.40.0, [OxyHQ/Bloom#721](https://github.com/OxyHQ/Bloom/pull/721)): standard actions as the editing ones of step 4, which no text field takes, ending at the application (its `onPress`, disabled with none). Settings… brings the standard chord `Mod+,` (Ctrl+,). An application declares them in any menu, where Bloom draws them in a window (the web); with `menu-bar` each is described with its `action` (`PlatformMenuItem.action`), the host's adapter sends it as the entry's role, and the shell **hoists** it into the application's menu, the separators its going left at an end or doubled tidied and a menu that held only it left out. Chosen there it runs in the application as any command does; Ctrl+, is Bloom's, as every declared chord, so it reaches the application once, whether the bar shows it or not.
   - **Without its own About,** About *App* opens the system's **standard About panel** (`AboutPanel`), as AppKit's `orderFrontStandardAboutPanel:`: the application's icon, its name and "Version 0.1.0 (1)", its package's `version` and version code, from its registry entry (`X-OxyOS-Version`, which the install service now writes, and `X-OxyOS-Package-Version`). The shell draws it in an overlay of its own size, centred a quarter of the way down the output, so a press elsewhere reaches what is there; it takes the keyboard, its close button, Escape and Ctrl+W (the applications' ⌘W) close it and give the keyboard back to the window, and the keyboard going elsewhere (a press in a window) closes it. It is the system's, not a window of the application's: it is in no Window menu and not hidden with the application.
   - **Without Settings…,** the row is shown, Ctrl+, beside it, and not offered, as a Mac's application with no settings shows it.
   - **Hide Others and Show All** are the compositor's (`HideOtherApplications { window }`, request 113, every application but the window's, window 0 every one; `ShowAllApplications`, request 114, every hidden application back where it was in the stack, the active window staying the active one), the shell's (`shell` grant) as Hide is, through `oxyos_client_manage` (`OXYOS_MANAGE_HIDE_OTHER_APPLICATIONS`, `_SHOW_ALL_APPLICATIONS`) and the platform's `hideOtherApplications`, `showAllApplications`. **Alt+Super+H** is Hide Others from the keyboard, the compositor's own as Super+H ([ADR 0024](./0024-system-shortcuts)): every application but the active window's, every one with none active.
   - **With no window active,** the bar is the **desktop's own menu**, in bold, then View, as a Mac's is Finder's when no other application is: the desktop is the shell's (ADR 0047), so the desktop's menu (Escritorio, Desktop) holds Empty Trash… (where the platform has a Trash; not offered when it is empty; the session asks first, as the dock's), Hide Others (every application) and Show All. There is no About there: the computer's is the Oxy menu's. While the desktop has the keyboard its File and Edit follow its menu, as before.
   - **One chord notation** (`apps/shell/src/chord.ts`, `chordLabel`), for the application's menus, its own menu, the Oxy menu and the desktop's: **key names joined by "+",** as a PC keyboard labels its keys and as Windows, ChromeOS and GNOME write chords (a Mac writes ⌃⌥⇧⌘ because its keys carry those symbols; a PC's carry their names); **one order**, a Mac's ⌃⌥⇧⌘ with Super in ⌘'s place: Ctrl, Alt, Shift, Super, then the key, whatever order a chord was declared in (Ctrl first is also how every PC writes it); **in the session's language**, each name as that language's keyboards print it: Mayús, Retroceso, Supr, Intro, Espacio in Spanish, a letter in capitals, the arrows as arrows. An application's `Mod` is Ctrl, Bloom's `Meta` is Super. Bloom's own in-window rows keep Bloom's formatting (`formatChord`); the bar's rows are the shell's.
   - **The shortcut column** is Bloom's row: `MenubarShortcut` as the row's trailing hint, laid out and styled by Bloom's menu rows (`floating/menu-rows`), which the shell does not restyle; the shell hands it the formatted text. A row is named by its label alone, its chord drawn beside it (as the Oxy menu's).
   - **Where the code is.** The bar's menus are the shell's (`apps/shell/src/app-menu.ts`: `applicationMenus`, `desktopMenus`, `appMenuCommand`, `applicationName`, pure and tested); the session's shell (`sample/ShellProbe.tsx`) only feeds it the compositor's state and sends what a choice asks. A system Window menu (Minimize, Zoom, the application's windows, the tiling commands) is appended after the declared menus by the same function when it comes; it is not part of this step.

   *The protocol* (version 40): `MenuItemRole { surface, index, role }` (request 85, `MenuRole` About or Settings), after the entry and before `MenusCommit`, only on a command without a check, each role once in a commit, an entry at most one (anything else a protocol error); the shell is told it as `MenuBarItemRole { window, index, role }` (event 75) after the entry, never a shell of version 39, which shows the entry where it was declared; the client library says it only to a compositor of version 40 or newer. The C ABI: `OxyOSMenuItem.role` (`OXYOS_MENU_ROLE_*`), `OXYOS_EVENT_MENU_BAR_ROLE`.

   *Tests.* Bloom: `MenubarApplicationActions.test.tsx` (each action described, the application's with a field focused, About disabled with no handler, Ctrl+, once with and without a field, a declared chord winning, drawn in the window where declared). Scene: `the_applications_about_and_settings_are_told_to_the_shell_with_its_menus` (the roles told with the menus, a choice of Settings… delivered once, a recommit without them, each malformed role refused) and `alt_super_h_hides_the_other_applications_and_the_shell_shows_them_all_again` (the other applications hidden, the minimized window left in the dock, the active window kept with the keyboard, no key to any application; Show All, Hide Others by a window and by 0, Show All with none active, the shell alone, nothing while locked). The C ABI: the role's constants, the entry's layout and event, a role sent through a socket and an unknown one refused, Hide Others and Show All through `oxyos_client_manage`. The registry: an entry's version and build. The shell: `app-menu.test.ts` (the notation in English and Spanish, an application with no menus, the hoisting, Hide Others and Show All's states, the desktop's menu, the application's name). Scenarios:
   - `menu-bar.json`: the probe's Settings… (declared at the end of File) shown in Allo's own menu with every row and chord; chosen there, it runs once; File no longer shows it; Ctrl+, in the window, its field focused, runs it once more without reaching the field; minimized, the bar is Escritorio and Ver.
   - `app-menu.json`: Allo (no menus) and Inbox: Allo's own menu with every row and chord; Settings… pressed does nothing; Acerca de Allo opens the standard panel (Versión 0.1.0 (1)) with the keyboard, Escape closes it and the window has the keyboard again; Alt+Super+H hides Inbox, the menu's Mostrar todo shows it, Ocultar otros hides it again; Ocultar Allo leaves nothing active and the bar Escritorio and Ver, whose Mostrar todo shows both, the bar left giving the keyboard to the window used last that is shown (Allo's), as before; every window's state, focus and deliveries at each step.
   - `shell.json` (the desktop's menu in the window probe), `system-shortcuts.json` (the bar shows Allo's menu while Allo is active) and `language-*` (Settings' own menu, named in the session's language where the bar showed the shell's View, and renamed at once when the language changes: the host now tells the shell the applications it reads again for the new language, which it had read and kept to itself until the next change) follow.

## Not in this decision

- Menus' icons, and items whose content is not text.
- A Help menu's search, and the services menu (OxyOS has no services).
- A system Window menu (Minimize, Zoom, Bring All to Front, the application's windows): appended to every application's menus by `applicationMenus` when tiling's Window commands come.
- Context menus (they stay Bloom's, opened as popups, [ADR 0002](./0002-bloom-platform-surface-api)).
