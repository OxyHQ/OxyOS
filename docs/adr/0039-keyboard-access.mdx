# ADR 0039: Full Keyboard Access and the accessibility audit

Status: **accepted; implemented** (the host's keyboard focus and ring, the accessibility tree's modal rules, Super+F3 and Super+F8, the shell's and Settings' fixes, Bloom's; decisions 8 to 26, the audit's follow-up of 2 and 3 November 2026, implemented). Builds on [ADR 0003](./0003-accessibility-protocol) (the accessibility tree), [ADR 0014](./0014-screen-reader) (the screen reader), [ADR 0024](./0024-system-shortcuts) (Super+F2, decision 9) and [ADR 0034](./0034-the-dock).

**6 November 2026: the dock's icons are arranged without a pointer** ([ADR 0034](./0034-the-dock), decision 10). With the dock's keyboard (Super+F3), Option and ← or → move the focused icon kept a place along those kept, the keyboard staying on it and its new place said once, politely (*Atlas, posición 3 de 3*); at an end nothing moves and nothing is said. An application's icon offers the screen reader *Mover a la izquierda* and *Mover a la derecha* where it can move, *Quitar del Dock* when kept and *Mantener en el Dock* when not, beside its menu's own action (decision 12). `keyboard-dock-arrange.json` and `keyboard-dock-arrange-scaled.json` check each, the person's list as the session keeps it and what is said.

**2 November 2026:** Stash, named below, was renamed **Dropsea** ([OxyHQ/Dropsea](https://github.com/OxyHQ/Dropsea), [dropsea.net](https://dropsea.net)). Its application id is now `so.oxy.dropsea`, its URL scheme `dropsea://` (the dock's Trash opens `dropsea://trash`), the variable its package is built with `DROPSEA_DIR`, and its scenarios `dropsea*.json`, `keyboard-dropsea*.json` and `perf-dropsea*.json`. The decision stands as written; its text keeps the name it was taken under.

## Problem

A Mac can be used without a pointer. With Full Keyboard Access on, Tab and Shift+Tab move a focus ring through every control of the window, Space presses the control the ring is on, the arrows move a slider; Control-F2 reaches the menu bar, Control-F3 the Dock, Control-F8 the status menus; Escape closes what is on top and the keyboard goes back where it came from; a sheet holds the keyboard until it is answered. VoiceOver's cursor follows the keyboard's focus and reads each control by its name, value, state and role.

OxyOS had only part of it. The menu bar was reachable (Super+F2, ADR 0024) and Bloom's menus and popups drove themselves from the keyboard (ADR 0021, `floating/popup-navigation.tsx`); a text field could be focused by a press. Nothing else could be reached from the keyboard: no Tab between controls, no ring, no way to press a button, no way into the dock, the status items, Control Center or the Notification Center, and only the system sheet and Launchpad took the keyboard at all. The accessibility tree also published the window behind an open modal and behind a view marked modal, so a screen reader could leave a dialog without closing it.

## Decision

1. **Keyboard focus is the platform's, as Android's keyboard navigation and a Mac's key view loop are** (`tools/rn-host-spike/keyboard-focus.h`). The Bloom host keeps one focused control per client, beside the text field it already focused:
   - **What is focusable:** a view React Native's Android view would let the keyboard focus (`focusable`, which `Pressable` and the touchables set) that is also an accessible element, enabled, shown (not transparent, not `pointerEvents: none`, not hidden from assistive technologies) and of some size; an editable text input. A backdrop pressed to close a panel (`accessible={false}`) is no stop, as VoiceOver and a Mac's key view loop go through the same controls.
   - **Where Tab goes:** through the focusable views of the surface that has the keyboard, in reading order (each parent's children in order, as the accessibility tree reads them), round the ends; Shift+Tab back. The surface's content is the window's, or the topmost modal's while one is shown, or the topmost view marked modal for assistive technologies (`accessibilityViewIsModal`, a Bloom overlay's and the system sheet's root): a modal holds the keyboard as it holds the screen reader. A popup's keys stay its own (Bloom's popup navigation, where Tab closes a menu).
   - **What acts:** Space and Return press the focused control (React Native's accessibility click, which Pressability answers with `onPress`, as an assistive technology's activation); the arrows step an adjustable control that declares increment and decrement. The focused control has these keys before the application's own, as a Mac's first responder has them before the window: a list's Space (Stash's Quick Look) never takes a toolbar button's. Tab always moves focus; no text field types a tab.
   - **What is told:** the control left receives `onBlur` and the one reached `onFocus` (React Native's focus events, `BaseViewEventEmitter`); a text input reached by Tab is focused through the text editing with its whole text selected, as a Mac's field is. The assistive technology's focus follows (the tree marks the control focused), so the screen reader says each control once as Tab reaches it, as VoiceOver's cursor follows the keyboard's. While the keyboard is navigating, the application's own accessibility focus moves (Bloom giving a closed menu's or dialog's trigger the focus back) move the keyboard's too.
   - **The ring:** drawn by the host around the focused control while the keyboard moved it, as a Mac draws its keyboard focus ring: a band of the system blue at 55%, 3 pixels wide, a pixel off the control's edge and following its corners, over the control and within what clips it (`TextInputEdit::focusRing`, `kFocusRingReach`; damage covers it, `damage.cpp`). It shows only while the surface it is in has the keyboard (or a popup of it, a menu opened from it), never in a window or a panel the keyboard left. A press of the pointer hides it and takes focus off a control that is no text field, as Android's touch mode hides its focus highlight.
   - **Modals:** a modal coming over the control with the keyboard remembers it; while the ring shows, the keyboard moves to the modal's first control, as a Mac's sheet takes it. The modal leaving gives the keyboard back to the control it came from. A focused control that goes takes focus with it.
   - **Scroll views** bring the focused control into view, as Android's `requestChildFocus` does: each scroll view it is in, its ring with it ([ADR 0042](./0042-scrolling), decision 4). The keys a focused control leaves scroll the scroll view it is in ([ADR 0042](./0042-scrolling), decision 3).

2. **The accessibility tree hides what a modal covers.** While a modal is shown the window's tree is the topmost modal's alone (Android's dialog window is all TalkBack reads); a view marked `accessibilityViewIsModal` is all of its surface's tree (as VoiceOver reads it). A navigation landmark (`role="navigation"`, a sidebar's sections) is published as a group of its controls, as VoiceOver reads it, not as a nameless generic node.

3. **The dock and the status items from the keyboard: Super+F3 and Super+F8,** as a Mac's Control-F3 and Control-F8, with Super for Control as Super+F2 is (ADR 0024, decision 9). Protocol version 12 adds `SystemShortcut::Dock` (9) and `StatusMenus` (10) to the shortcuts the compositor sends the shell of the active window's output; a client of version 11 or older is never sent them (`event_since`), as its reader would refuse a value outside its set. A menu open in a window closes first; the window stays active.
   - The shell's regions ask for the keyboard as the top bar does (`keyboard`), and say where its focus goes once they have it (`focusTarget`, `"first"` or a control's testID; each new `focusRequest` asks again). Of several regions asking, the newest has it (a sheet over the Control Center).
   - **The dock:** Super+F3 puts the keyboard on its first icon with the ring; ← → go along it; ↑ opens the focused icon's menu, as a Mac's Dock (Bloom's context menu, driven from the keyboard); Space and Return open it; Escape gives the window the keyboard back.
   - **The status items:** Super+F8 puts the keyboard on the first (the network's item, else the search); ← → go along them; Space and Return open one; Escape leaves them.
   - **Control Center, the Notification Center and the overview** have the keyboard while open, as a Mac's status menus and Mission Control do: Tab goes through their controls, Escape closes them, and the keyboard goes back to the window, or to the status items they opened from. Control Center opened from the keyboard starts on its first control, and moving between its modules and Wi-Fi's view keeps the keyboard in it.

4. **System sheets** are alert dialogs (`alertdialog`, named by their title, which is not read again) and say themselves as they appear: their title, what went wrong (a wrong password), and what they say, once; no live region says the error again. Return is still no answer (ADR 0030, decision 9), but the answer's button is reached with Tab and pressed with Space, as any control is: a consent that only a pointer could give would shut out everyone who cannot use one.

5. **The screen reader says a focused control changed in place** (ADR 0014): a switch or a box toggled by Space or a press says its new state ("activado"), a slider stepped by the arrows its new value, once; a trigger's expanded state is said by the menu it opens, never as a word before it.

6. **Live changes said once:** Wi-Fi joined ("Conectado a Vecinos", from Control Center by the shell, from Settings by Settings, politely, once as it connects); a join that failed in Settings (its note's title and why); a sheet as it appears; a notification's banner (as before).

7. **Bloom** (15.92.0, OxyHQ/Bloom#590): a dialog's panel and a named centred card carry `role="dialog"`; a grouped section's row reads its value with its name, and a row without a press is one element (its title and value) or, holding a control of its own, no element at all, never a role-less container whose title is read again inside it; a select's trigger reads its chosen value; a meter ring says how far along it is as a share when its caller gives no words.

8. **Hints and an item's place in its collection** (protocol version 13, [ADR 0033](./0033-protocol-versions)). An element publishes its hint, React Native's `accessibilityHint` (what activating it does when its name does not say: VoiceOver's help, TalkBack's hint), as `AccessibleField::Hint`, and an item its place among its collection's items, `AccessiblePosition` (request and event 251: 1-based, of a count). The host gives a `listitem` its place among the `listitem`s of its nearest `list`, and a view that declares Android's `accessibilityCollectionItem` (row and column) its place in the nearest view that declares `accessibilityCollection` (rows and columns): a list that shows only some of its rows (a virtualized one) says where each is among them all. The screen reader says an item's place last ("notas.txt, seleccionado, 3 de 21", "3 of 21"), and a hint after the element, politely, as a separate utterance that moving on cuts off, as VoiceOver says help after a pause. Neither is sent to a peer of version 12 or older (`event_since`, `request_since`; the client library leaves them out); the C ABI adds `oxyos_client_publish_accessibility_detailed` with an `OxyOSAccessibleDetail` beside each node, so `OxyOSAccessibleNode` stays as applications built against it have it.

9. **The context menu from the keyboard.** The Menu key and Shift+F10 open the focused control's context menu, as a PC keyboard's do (a Mac's Control-Return with Full Keyboard Access): the host performs React Native's `longpress` accessibility action on the focused control or its nearest ancestor that declares it, as TalkBack's long press reaches a view; Bloom's `ContextMenuTrigger` declares it ("Mostrar menú") and opens its menu at the trigger. With none declared the key is the application's. Space and Return activate only a control that answers a click (Pressable's); any other focused control (a list that is one Tab stop) has them as its own keys, as a Mac's first responder passes on what it does not handle. A modal with no control of its own gives the keyboard back with the ring it took.

10. **The ring in the accent colour**, as a Mac draws its keyboard focus ring: the session's accent's `ring` token, light or dark, as Bloom's own design tokens resolve it (`color.<preset>.<scheme>.ring`); the runtime's framework build writes them beside the framework (`framework/focus-rings.json`), so the host never copies Bloom's colours, and the system blue stays where an accent has none.

11. **A popover is a popover.** Bloom's native `Popover` opens, on a platform with popups, beside its trigger in the platform's popup, a `dialog` named by its label (Bloom 16.2.0, OxyHQ/Bloom#600), instead of a bottom sheet whose drag handle was a Tab stop said "Descartar, Toca para cerrar". The host traverses a popup holding a dialog as it does a window: Tab and Shift+Tab go round its controls and never leave it, as a popover's key view loop; opened from a control with the ring, the keyboard goes to its first control, and back to that control as it closes. A menu's popup keeps its keys (Bloom's popup navigation). The reader says the popover by its title, then its focused control after it.

12. **The dock by name.** Each icon is named by its application, as VoiceOver names a Dock item ("Dropsea", not "Abrir Dropsea"), "en ejecución" as its value while its application runs ("Inbox, en ejecución, contraído, botón", as VoiceOver says "Safari, running"), the Trash "Papelera", "vacía" or "llena" when the platform says how many items it holds (Bloom 16.5.0's `Button` passing its caller's value), with the hint that ↑ opens its menu ("Para abrir su menú, pulsa Flecha arriba"); each says whether its menu is open ("Dropsea, contraído, botón"), as a menu button does (Bloom 16.5.0, OxyHQ/Bloom#602: a control with a context menu says it; an area with one, a list, does not), and its menu opens from the screen reader's actions too (Bloom's `ContextMenuTrigger`, OxyHQ/Bloom#599). A tooltip is no element for the screen reader: what it shows is its trigger's name, as a Mac's help tag is its control's help, so the reader's cursor and a press by name never land on it.

13. **Settings' sidebar and segmented controls by the arrows** (Bloom 16.1.0, OxyHQ/Bloom#597; OxyHQ/OxyOS#262). Bloom's `SegmentedControl` and `RadioGroup` are one Tab stop on a native host that gives Bloom the window's keys: only the chosen option is focusable, and the arrows choose the next one (← → a segmented control, all four a radio group), the keyboard moving once the value lands, so the option is said once, already chosen. Bloom's `SettingsLayout` rail is one Tab stop on its selected row: ↑ ↓ Home End select a row and show its pane; its rows are `listitem`s of one `list` (said with their place, decision 8) and its group labels headings. The host moves the keyboard with an application's focus move onto a view that becomes focusable in that same commit, once mounted.

14. **Launchpad, the overview, Control Center's sliders, the lock's wait** (OxyHQ/OxyOS#265 and #267; Bloom 16.2.0, OxyHQ/Bloom#601). Launchpad's highlight is the screen reader's focus, each icon said by its name as the arrows move it; typing gives the search field the focus back; an open folder is modal for the reader and Tab. The overview's window is one button named by its title, its close button the next stop, the backdrop none; opened from the keyboard it starts on its first control, and a window chosen has the keyboard. Bloom's native slider is itself adjustable and focusable (`keyboardStep`, `formatValue`'s spoken value), so a level card is read once and says its new value once as the arrows step it. The lock screen's wait is no live region: a wrong password says the wait at once ("Contraseña incorrecta. Vuelve a intentarlo en 30 segundos"), then politely at each whole minute left, at 30 and 10 seconds and when it ends, as a Mac's lock screen says its wait once rather than counting; the lock screen's announcements reach the reader while locked. The reader follows focus by the element, not by its place in the tree.

15. **The screen reader at the lock and login screens:** Super+F5 turns it on there as anywhere ([ADR 0014](./0014-screen-reader), decision 6; [ADR 0020](./0020-oxy-account-login)), tested in the scene and the login program, and in scenarios that start with the reader off (`oxyos-offscreen --reader-off`).

16. **What waited for Bloom on npm.** Bloom's releases stopped at `@oxy.so/color` (its npm trusted publisher was not configured) until 16.5.0, which is on npm and has everything 16.4.0 had. With it: the dock's running and Trash states (decision 12, OxyHQ/OxyOS#268), Dropsea's list (OxyHQ/Dropsea#15) and its scenarios (OxyHQ/OxyOS#264). Atlas (OxyHQ/Atlas#56, scenarios OxyHQ/OxyOS#261) keeps one control from Get through the install to Open, says the install and the update as they start and end ("Installing Inbox", "Inbox installed") and at most each quarter, five seconds apart, and keeps a finished update's row, said "Inbox updated".

17. **A dialog over a window says itself, and a live region is said for its changes, not its coming back** (the screen reader, [ADR 0014](./0014-screen-reader)). A named dialog shown in a surface that was showing something else — a modal over a window, whose tree is then the modal's alone (decision 2) — is said by its title as it appears ("Quick Look, dialog"), as a popup's is and as TalkBack says a dialog window's title, with what is focused in it said after it; a dialog with no control to focus (Dropsea's Quick Look) is no longer silent. A live region is compared with itself as the same view (the window, or the same modal) last showed it, so one hidden under a modal and shown again unchanged ("1 of 3 selected" behind a closed Quick Look) says nothing, as VoiceOver says a live region's changes; a view's first showing says nothing, as a surface's first tree never did. The screen reader at the login screen stays off until the image ships it (ADR 0020): the image has no session, login program, reader or eSpeak NG yet, and its speech as the `oxyos-login` user needs that user's own PipeWire, not yet heard on a machine; a reader that cannot start leaves Super+F5 doing nothing rather than ending the login screen's session.

18. **The accent swatches and Dropsea's column headers** (Bloom 16.6.0, OxyHQ/Bloom#603; OxyHQ/Dropsea#18; OxyHQ/OxyOS#270). Bloom's `RadioGroup` has a `swatch` variant (`RadioSwatch`: a disc of its colour named by its label, a dot in the chosen one) on the same radio-group keys, so Settings' accents are one Tab stop moved by the arrows, each said once ("Blue, seleccionado, botón de opción"), the ring's colour following the accent chosen; Bloom owns the interaction, Settings passes colours and names. Bloom's `Button` takes `tabIndex` on native too (React Native's `focusable`, which the host reads), so Dropsea's column headers (`tabIndex={-1}`) are no Tab stops, as a Mac's table headers are not, yet pressed by the pointer and the screen reader; `Stepper`'s value is its one keyboard stop, stepped by the arrows, its buttons out of the order.

19. **The session locking said, and a column header** (protocol version 14, [ADR 0033](./0033-protocol-versions)). Assistive technologies are told the session's lock state (`LockState`, which the lock screen was already told), as it changes and as they connect; the screen reader says the session locking ("Pantalla bloqueada", as VoiceOver says "Screen locked"), never as it connects to a session already locked (the login screen), and says the lock screen's focused field after it. `AccessibleRole::ColumnHeader` (27) is a table's or a list's column header: the host publishes React Native's `role="columnheader"`, the reader says it ("Name, ascending, column header", "encabezado de columna"), Bloom's `Button` takes `accessibilityRole="columnheader"` (Bloom 16.7.0, OxyHQ/Bloom#605) and Dropsea's list's headers are column headers (OxyHQ/Dropsea); a client sends an older compositor the button a sorting header was.

20. **The login's accounts by the arrows, and a description said after its control** (Bloom 16.8.0, OxyHQ/Bloom#606, OxyHQ/OxyOS#276; Bloom 16.9.0, OxyHQ/Bloom#607, OxyHQ/OxyOS#275). The login screen's accounts are Bloom's `ChoiceList`, as a Mac's login window: one Tab stop on the chosen account; ← → Home End move between the accounts without choosing, as choosing on each press would put another account's password field in and pull the keyboard into it; Return or Space chooses, and the chosen account's password field takes the keyboard; the accounts are a list's items, said with their place ("Ada Lovelace, seleccionado, 1 de 3"). The host moves the keyboard with an application's focus move onto a view created in that same commit, once mounted. A control's description is its hint, as VoiceOver reads a help tag after the control: React Native drops `aria-describedby`, so on native Bloom turns the texts a control's `aria-describedby` names into its `accessibilityHint`, after the caller's own hint, in that order, a text equal to the control's name or already said left out; every Field's description, then its error once it replaces it, is said after the field ("Nombre de usuario, campo de texto", then "Entre 3 y 20 letras o números"), and a tooltip after its trigger, never when it is the trigger's name (the dock's). The web keeps `aria-describedby`.

21. **Alerts said as they appear, live regions by their role** (the host and the screen reader, OxyHQ/OxyOS#280; [ADR 0003](./0003-accessibility-protocol); Bloom 16.11.0, OxyHQ/Bloom#612, and 16.12.0, OxyHQ/Bloom#613). A view's role implies its live region, as ARIA's: an `alert` is assertive, a `status` or a `log` polite; its own `accessibilityLiveRegion` (`aria-live`) wins. A live region appearing in a view shown before is a change, said once, as VoiceOver and TalkBack say ARIA's: a Bloom `Field`'s error at once as the name typed is taken, interrupting the typed letters' echo, the field keeping the keyboard; a status line politely as it changes. A live view that is no element (Bloom's toast row) is a node with no words of its own, which the reader's cursor passes; the reader says the text the nodes within it show, not its controls' names, as TalkBack says a live view group. What a view showed is matched by its text, not its place, so a region appearing before others (a toast above the window's content) leaves them unsaid; the view is its first node that is not live content. React Native 0.88 kept a role an application removed, so an error's text that became the field's description stayed an alert: the host compiles upstream's fix in place of React Native's file. What an application announces itself is no alert: the lock screen's wait, which counts down, and a system sheet's error, said with the sheet as it appears (decision 4). Bloom gives each of its messages the role a Mac user expects (Bloom 16.11.0): an error that answers what the user did (a field's, a card form's, a rejected file) is an `alert` on its text; news (a tag field full, a section that could not load, a log's failed step, a payment's state) a polite `status`; a toast polite, an error or important one assertive; a callout that is part of the page (`Admonition`, `EmptyState`) no live region; a tooltip a `tooltip`, never an alert. A Bloom toast on a native host is drawn above the application and goes still once shown (Bloom 16.12.0: it was drawn under the window's content, and re-measured itself without end).

22. **The top bar and Control Center said as a Mac's** (OxyHQ/OxyOS#282; protocol version 15, [ADR 0033](./0033-protocol-versions)). The clock is named by what it shows, in whole words ("martes, 3 de noviembre, 14:05"), as VoiceOver names the menu bar's clock, with the Notification Center as its hint ("Abre el centro de notificaciones"); the network item is "Wi-Fi" (or "Ethernet") with the network joined as its value; the network, Control Center and clock items say whether their panel is shown ("contraído", "expandido"), as menu buttons do. The battery is a level indicator ("Batería, 64 %, 3 h 20 min restantes, indicador de nivel"): `AccessibleRole::Meter` (28), ARIA's `meter`, which the host publishes for React Native's `role="meter"` and a client sends an older compositor as a progress bar. Control Center is a dialog named "Centro de control", not a menu; each switch module is said once (its title and status no elements of their own), Bluetooth one element with its status as its value; "Redes Wi-Fi" has the network joined as its value ("Desactivada", "Sin conexión" with none). The Notification Center opened from the keyboard starts on its first control.

23. **Notifications, the switcher, the overview and Launchpad** (OxyHQ/OxyOS#284; protocol version 16; [ADR 0024](./0024-system-shortcuts)). Super+N opens and closes the Notification Center with the keyboard on its first control, as a Mac's Fn-N (`SystemShortcut::Notifications`, 11, never sent to a shell of version 15 or older). A card's close button says what it closes ("Borrar la notificación de Allo: Ana"; on a banner "Ocultar …"), as VoiceOver reads a notification's ✕ within it; a banner stays while the pointer is on it or a reply is typed, and leaves five seconds after. The switcher's chosen name is no element, so each application is said once; the overview's current desktop is selected. A surface that appears as a named dialog is said by its title, then its description, then what is focused, and not again when a modal over it closes (Launchpad's folder): Launchpad ("Launchpad, diálogo"), Control Center, the Notification Center and the system sheets, whose error and body are now their description rather than the shell's announcement. Launchpad's result count is a status ("2 resultados", "Ningún resultado"), said once per change, after a new focus rather than under it. A focused field's echo comes from its live text and caret, so a deletion is said once ("b, borrado").

24. **Tabs by the arrows, meters, a value's share** (Bloom 16.13.0, OxyHQ/Bloom#614; OxyHQ/OxyOS#288). Bloom's `Tabs` and `CategoryBar` are one Tab stop on a native host, as its segmented controls are (decision 13): ← → Home End select the tab they reach, the keyboard moving once it is selected, so each is said once, with its place among its tab list's tabs ("General, seleccionado, pestaña, 1 de 3"; the host places a `tab` in its nearest `tablist` as a list's items); `Tabs` wraps round its ends, `CategoryBar` stops at them, and a tab that navigates (expo-router) is opened by Space or Return. Bloom's `Meter` and `MeterRing` are meters (decision 22's `meter`, "indicador de nivel") unless their caller says they are a task's progress (`role="progressbar"`), and say their share as Bloom formats it. A value with a range and no words (`accessibilityValue`'s minimum, maximum and current value) is said as its share of the range, as VoiceOver says a progress bar's, rounded half to even and formatted in the session's language ("25 %"); words always win.

25. **Settings' trial, arrangement, updates and Privacy** (OxyHQ/OxyOS#289; Bloom 16.14.0, OxyHQ/Bloom#615). Displays' trial dialog takes the keyboard on Revert, the safe answer while the picture may be unreadable; Return, Escape and waiting revert, Keep Changes is a Shift+Tab away, and the keyboard returns to Resolution, said with the mode it went back to; its title and countdown are said as it appears, the countdown again at 10 and 5 seconds and its end, never each second (a modal over a window is matched by its title alone). Bloom's `AlertDialog` runs `onCancel` for Escape, its backdrop and Android's Back, and `defaultAction="cancel"` starts it on its cancel button. Each arranged display is a keyboard stop whose value is where it stands ("OxyOS Monitor, right of Built-in Display"), moved by the arrows, each move said once. Software Update's row says its update as Atlas's does ("Updating Inbox", "Inbox updated"), keeping the keyboard and its row. Privacy's switches are named with their application ("Notifications for Permission", "Cámara para Allo"). Bloom's `SettingsLayout` "Saved" toast is in the tree only while shown, a polite status said once. The host gives the keyboard to a modal that replaces another in one commit and to one whose controls mount after it.

26. **The menu bar's title is focused and said once, whatever reaches the host first** (5 November 2026, after OxyHQ/OxyOS#316). Super+F2 is a chain: the compositor sends the shell the shortcut; the shell's top bar sets Bloom's `focusValue` on the Oxy menu and asks for the keyboard (`keyboard` on its region) in one React commit; Bloom's effect moves the assistive technology's focus to that title (`sendAccessibilityEvent`); the host mounts the commit, asks the compositor for the keyboard, publishes the bar's tree with the title focused; the compositor gives the keyboard; the reader moves its cursor and says the title. Two of these arrived in an order that depended on timing, and each order lost:
   - **The focus before the commit's mount.** React Native's Scheduler hands an accessibility event over at once but mounts a commit only at the end of the JavaScript task. When React flushes the effect with its commit (a re-render from a layout effect flushes pending passive effects first, which is what Bloom 17.12.0's first viewport did), the host took the focus move against the tree before the commit asking for the keyboard: a bar that had given the keyboard back (Escape, a row chosen, a press elsewhere) was still not asking for it, so the move was declined as one into a released bar (the host's guard, since OxyHQ/OxyOS#207, against a bar the keyboard has left taking the focus back from Bloom, `a11y.focus.declined`). The title kept no focus and nothing was said. **Now** the host handles JavaScript's accessibility events in order with the mounting of the commits made before them (`Mounter`, `a11y.event.queued`), as Android's mounting layer runs its accessibility event behind the mount items queued before it and as the Scheduler already orders view commands; a focus move is judged against the tree that asked for it.
   - **The focus where the reader's cursor was left.** The reader leaves its cursor where the last focus put it when the focus goes without moving it (a press in the window takes the keyboard from the bar, saying nothing). The bar taking the keyboard again focuses the same title at the same place, which the reader took for its own activation (the cursor already there) and did not say. **Now** only a cursor the reader's own commands put there, with no focus arriving since, makes a focus there silent; whatever focuses an element after its focus left is said, once.
   - **The keyboard's grant** is no longer an input to either: the focus is judged against the region's request, which the commit carries, never against the compositor's answer, and the reader follows a tree's new focus whichever surface has the keyboard.
   - **Forced in tests:** a scenario's `host_order` (`OXYOS_HOST_TEST_ORDER`, the shell's host only) forces each order without timers. `focus-first` mounts commits only at the host's frame, after everything JavaScript runs in the turn (the focus always comes before the commit's mount), and asks for the region's keyboard only once its tree is published with that focus (`test.keyboard.held`); `grant-first` holds a focus move into a region asking for the keyboard until the compositor has given it (`test.focus.held`). `regress.py`'s `first_order` checks the order each step had.
