# ADR 0019: Settings

Status: **accepted** (chosen with the platform's author); steps 1 and 2 implemented. Decision 3's grant is amended by [ADR 0030](./0030-installing-applications), decision 7: system grants come from the image's policy, never from an entry's ownership alone. Builds on [ADR 0001](./0001-native-platform-boundaries) (grants from the session authority), [ADR 0011](./0011-transitions) (reduce motion), [ADR 0012](./0012-solar-wallpaper), [ADR 0013](./0013-launching-applications) (launch records), [ADR 0014](./0014-screen-reader), [ADR 0015](./0015-application-model) and [ADR 0016](./0016-windows).

## Problem

Nothing in an OxyOS session can be changed while it runs:
- the appearance is the shell's own;
- the wallpaper is the one `OXYOS_WALLPAPER` names;
- the screen reader is on or off from its flag;
- the keyboard is what `/etc/default/keyboard` said at start;
- the time zone is the system's.

Transitions cannot be reduced, although ADR 0011 left room for it.

A Mac has System Settings: one application whose sidebar lists the pages and whose changes take effect at once, in every application, with no restart. Bloom's settings modal already has that shape ([ADR 0016](./0016-windows): `SettingsLayout`). What is missing is where preferences live, who may change them, and how applications are told.

## Decision

1. **The session owns the user's preferences.** They are one file, `$XDG_CONFIG_HOME/oxyos/preferences` (`~/.config/oxyos/preferences`):
   - **Format:** `key = value` lines, read and written by `crates/oxyos-preferences`.
   - **One writer.** The session reads the file when it starts, and is its only writer: it validates each change against the key's type and range, applies it, writes the file whole (to a temporary file, then renamed) and tells the clients.
   - **Bad values.** A missing or unreadable file, or an unknown key or bad value in it, is the default for that key, never an error: preferences cannot stop a session from starting.
   - **The keys** are listed by `oxyos-preferences`, each with its type and default:
     - `appearance` (`light`, `dark`, `auto`; `auto` follows the sun of [ADR 0012](./0012-solar-wallpaper));
     - `accent` (one of Bloom's accent colours);
     - `reduce_motion` (every transition of [ADR 0011](./0011-transitions) is a crossfade: nothing grows, shrinks or slides);
     - `reduce_transparency` (glass is drawn opaque);
     - `wallpaper` (a folder under the wallpapers' directory);
     - `lock_after` (minutes idle before the session locks; 0 never);
     - `screen_reader` (on at login);
     - `clock_24h`;
     - `do_not_disturb` and `notification_previews` (`always`, `unlocked`), added by [ADR 0026](./0026-notifications).
2. **The system's settings stay the system's.** The time zone and automatic time (systemd-timedated), the keyboard layout (systemd-localed, which writes `/etc/default/keyboard`) and the computer's name (systemd-hostnamed) are changed through those services, as their own command-line tools change them. The session calls them over the system bus as the user, and polkit decides. A change that needs an administrator is asked for by the session's own authentication dialog, never by the application. Until that dialog exists ([Not in this decision](#not-in-this-decision)), Settings shows these settings and their current values and says they cannot be changed yet. The session follows a change it learns of (the keyboard layout of new strokes; the time zone of the clock and the wallpaper).
3. **Only Settings may change them, by its launch record.** A new grant, `settings`:
   - **Who gets it.** The session gives it to a client whose process it launched ([ADR 0013](./0013-launching-applications)) as the system application the **image's policy** names for it: `/usr/share/oxyos/system-apps.json`, in `/usr`, which is the image's (read-only on a published install, [ADR 0023](./0023-installing-oxyos)). The policy names each system application's id, its entry, what it runs (an absolute program, or a Bloom host and bundle) and its grants. It is the one source of system grants ([ADR 0030](./0030-installing-applications), decision 7, which amends this decision).
   - **Not decided by ownership alone.** This decision first gave the grant to any entry asking for it (`X-OxyOS-Grants`) that only an administrator could have written. Ownership proves that an administrator wrote a file, not that its contents are an administrator's choice: an installer running as root writes root's files from what it downloads ([ADR 0030](./0030-installing-applications)), and any such entry could then ask for `settings`. So an entry asks for nothing: `X-OxyOS-Grants` is not read.
   - **The policy, the entry and what it runs are judged too.** Each must be an administrator's: a file, not a link, and it and every directory from it up to `/` (directories' links resolved) owned by root and writable by no group and no one else, since whoever else could change any of them could change what it says. The policy is read at the real path it was judged at. The entry is read at the path the policy names, which must be its real path. What runs must be what the policy names, an administrator's at its real path, and is started there: an `Exec` whose program is the policy's (one the `PATH` finds is whatever the `PATH` finds), or the policy's Bloom host and bundle, whatever the session's are. A system application whose program, host or bundle is not the policy's or not an administrator's is not started. A policy that is not an administrator's, or not valid (read strictly: an unknown key, an id or key named twice, an unknown grant, a path that is not absolute and plain), gives no system application, and the session says why as it starts.
   - **A system application's id is its own.** The registry lists the policy's applications first, from the entries it names; another directory's entry with that id is ignored, even when the policy's cannot be read, so a profile's directory in `$XDG_DATA_DIRS` cannot make its own program Settings.
   - **Everything else grants nothing.** Any other entry, root's included, runs as an application, with an application's grants.
   - **What it is not.** It keeps the protocol's changes to the one application the system ships for them. It does not shield Settings from other programs running as the user, which can write the preferences file or trace its process; that is sandboxing's ([Not in this decision](#not-in-this-decision)).
   - **What it allows.** With it, a client may change preferences (`SetPreference`) and ask for system changes (`SetSystemSetting`).
   - **What it is told.** Every preference as the session keeps it (`Preference`, `key=value`), all of them when the grant is given and each one that changes, so Settings shows what is kept.
   - **Everyone else.** Every client is told the preferences that change how it draws; none can change them, and a client that asks without the grant is closed.

   This is the first grant given by a launch record, as ADR 0013 left for its own decision.
4. **Every application follows them at once.** The compositor tells every client the preferences that change how it draws: `appearance` (resolved to light or dark), `accent`, `reduce_motion` and `reduce_transparency`. It tells them when the client connects and whenever they change (`Preferences`, an event). The Bloom host gives them to React Native's own APIs, which Bloom and applications already follow:
   - `Appearance` and `useColorScheme` (with its change event);
   - `AccessibilityInfo.isReduceMotionEnabled` and `isReduceTransparencyEnabled` (with theirs);
   - the accent, through Bloom's platform adapter, as the seed of Bloom's palette.

   No application restarts, and none reads the preferences file. The compositor applies `reduce_motion` to its own transitions; the shell follows the rest as an application does.
5. **The Settings application** (`so.oxy.settings`) is a Bloom application in the session's registry, built as [ADR 0015](./0015-application-model) says.
   - **Its window** is Bloom's `SettingsLayout` in an application window ([ADR 0016](./0016-windows)): the pages' rail as its sidebar, with the window's controls at its top.
   - **Its pages:**
     - **Appearance:** light, dark or auto, and the accent;
     - **Wallpaper;**
     - **Lock screen:** lock after;
     - **Displays:** as a Mac's, each display the session shows: their arrangement (dragged, or moved to a side by its accessible actions) and the main display, and for the one chosen in it its scale ("Larger text" to "More space", each choice what the display looks like then), resolution and refresh rate, a resolution kept only once confirmed ("Keep these display settings?"). Changed through the session, which applies them live and keeps them by each display's identity ([ADR 0018](./0018-several-displays), decision 10); not preferences of this file's keys;
     - **Keyboard:** the layout;
     - **Date and time:** the time zone, automatic time, the 24-hour clock;
     - **Accessibility:** the screen reader, reduce motion, reduce transparency;
     - **About:** the computer's name, OxyOS's version from `os-release`, the processor, memory and display.
   - **Its model.** Like the shell, it reads its state and sends its changes through a model of its own (`SettingsSnapshot` and its actions):
     - on OxyOS, the host module `OxyOSSettings`, which only a client with the grant has;
     - in the browser preview and natively, a fixture, so its layout and pages are built and tested where that is cheap.

## Steps

1. **Preferences:**
   - `crates/oxyos-preferences`: the keys, the file, validation, defaults, writing whole;
   - the session reading and applying them;
   - `reduce_motion` in the compositor's transitions.

   Tests on files written by the tests.

   *Done.* `crates/oxyos-preferences`:
   - **The keys and the file.** The keys with their types and defaults (`auto`, `oxy`, no reduced motion or transparency, the session's own wallpaper, locking after 5 minutes, the reader off, a 24-hour clock); `set` validates a change from its text and leaves everything as it was if it is refused. Names are lowercase letters, digits and dashes, so a wallpaper cannot name a path. `lock_after` is at most a day.
   - **Reading.** The file is read line by line, and a bad line keeps its default.
   - **Writing.** The file is written whole, to `preferences.new`, then renamed.
   - **Where it is.** `$XDG_CONFIG_HOME`, or `~/.config` when that is unset or relative.

   `oxyos-session` reads it as it starts: `reduce_motion` makes every transition a crossfade (`Transitions::set_reduce_motion`: windows, menus, overlays, the lock and the splash fade in and out where they are, a zoom is at once; ADR 0011, step 6), and `screen_reader` starts the reader as `--reader-on` does, when the session has one. Tests cover the defaults with no file, a file with bad lines, refused changes leaving everything as it was, a round trip through the file, the paths, and reduce motion (nothing runs, nothing is recorded; turned off, windows fade in again).
2. **The grant and the protocol:**
   - `settings` from launch records of the system application the image's policy names;
   - `Preferences` to every client;
   - `SetPreference` from the grant, handed to the session as launches are;
   - the C ABI.

   Tests:
   - a user entry claiming the grant gets none;
   - a client without it is refused;
   - every client is told a change.

   *Done.*
   - **The grant.** `crates/oxyos-apps` reads the image's policy (`Policy`, `/usr/share/oxyos/system-apps.json`, `serde_json` with unknown keys and repeated ids refused, at most 64 KiB) and never an entry's `X-OxyOS-Grants`. `registry` takes the policy and the rule a file is judged by: in a session `administrator_written`, which is `trusted_by` over `lstat`, a seam the tests give a described filesystem. It lists the policy's applications first, from their entries (`Application.system`), and ignores other directories' entries for their ids. `Launcher::launch` reads the policy at each launch, as the registry is read, and starts a system application only running what the policy names, an administrator's, by its real path, with the policy's grants; `application_of` says what a process was launched as. The shell's list (`oxyos_applications`) is the same registry, so the dock never shows an entry the session would not launch as that application. `Compositor::name_clients` takes a `LaunchRecord` (the application and its grants) and gives them with `Scene::grant`, the counterpart of `revoke`, which only the program running the compositor calls.
   - **The protocol.**
     - `SetPreference` (request 62: a serial, `key=value` in chunks) is accepted from the `settings` grant alone (`Unauthorized` otherwise) and handed whole to the program running the compositor (`Scene::take_preference_changes`). It answers with `preference_set` (event 52, `PreferenceResult`); text with no `=` is refused by the scene itself.
     - `Preferences` (event 53: dark, reduce motion, reduce transparency, the accent) goes to every client when it connects and whenever they change.
     - `Preference` (event 54, `key=value` in chunks) goes to clients with the grant.
     - The accent is now at most 32 bytes, one chunk, so a change of how clients draw arrives in one event.
     - The C ABI has `oxyos_client_set_preference`, `OXYOS_EVENT_PREFERENCE_RESULT`, `OXYOS_EVENT_PREFERENCES` (`OXYOS_PREFERENCES_*` bits, the accent as its text) and `OXYOS_EVENT_PREFERENCE`.
   - **The session.** `oxyos_compositor::settings::Settings` keeps the preferences for the program running the compositor:
     - a change is validated, written whole, applied (reduce motion to the transitions) and told; one that cannot be written is refused, and nothing changes;
     - an automatic appearance is dark while the sun is below the horizon where the system's time zone is (`oxyos_solar::night_at`), looked at again only when it next crosses it; it is light where the zone has no place.

     `oxyos-session` uses it with the user's file, and starts or stops its reader when `screen_reader` changes. `lock_after` is kept and told, and the idle lock follows it ([ADR 0010](./0010-lock-screen), step 4): a change arms it again from the change. The development compositor plays the session with `--preferences FILE` (never the developer's own file). For scenarios, whose entries are the developer's, it has a fixture, `--grant-settings ID`.

   Tests:
   - **The trust rule,** over a described filesystem: each way someone else could change the entry refuses it (the user's entry; an entry or directory its group or anyone may write; a link as the entry or on the way). Over the real one, a user's entry and a link to it are not trusted.
   - **The policy:** read strictly (an unknown key at either level, a key or an id twice, an unknown grant or another spelling of one, a grant twice, no grants, a relative or `..` path, both or neither of `exec` and `bloom`, an entry named for another id, not JSON); a policy that is the user's, a link to one, one larger than 64 KiB, and the real filesystem's user file all give nothing; no policy gives no system application.
   - **The registry:** root's entry asking for `settings` and named by no policy is an application with nothing (the hole an installer would open); the policy's Settings wins over the user's own Settings in a directory before it; with the policy's entry the user's, or reached through a link, Settings is left out and said, never the user's instead.
   - **Launches:** the policy's program, an administrator's, is granted; a program the `PATH` finds, a program other than the policy's, and the policy's program when it is the user's are not started; with a policy anyone could have written, Settings runs with nothing. A Bloom application runs the policy's host and bundle, whatever the session's and its entry's are, by their real paths, and not with a host that is not an administrator's, nor as a native client.
   - **The scene:**
     - a client without the grant, the shell included, is refused;
     - chunks are assembled and handed over;
     - a revoked or departed client's changes are dropped;
     - every client is told on connect and on a change, Settings every preference;
     - a grant one client holds at a time is refused whole.
   - **The session's preferences:** a change is kept in the file, applied and told; a refused one or one that cannot be written changes nothing; the appearance follows the sun.
   - **Through real sockets:**
     - Settings, granted by its launch record, is told every preference and changes the appearance;
     - the file holds it;
     - an application connected before follows with no restart;
     - one asking without the grant is closed.

   Not verified yet: a Bloom application following `Preferences` (step 3), Settings itself (step 4), and the session on a seat; no scenario runs this step.
3. **The Bloom host:** `Appearance`, `AccessibilityInfo` and the accent from `Preferences`. A scenario changes the appearance and checks that a running application redraws dark, with no restart.

   *Done, but the accent and reduce transparency.* The host's window keeps the drawing preferences from the connection's first events (`PREFERENCES`), and, for Settings alone, every preference as kept (`PREFERENCE`).
   - **What JavaScript is told.** React Native's `Appearance` answers `getColorScheme` from them and is told `appearanceChanged` when the appearance changes, as Android's configuration change tells it. `AccessibilityInfo.isReduceMotionEnabled` answers from them and `reduceMotionDidChange` follows, as Android's animator scale does. `OxyOSPreferences` gives the accent and reduce transparency.
   - **Not yet drawn.** Bloom does not draw the accent or reduce transparency yet: that needs an `appearance` capability in Bloom's adapter, its own step.
   - **Settings.** `OxyOSSettings` gives Settings every preference, the change it asks for (only once the session has given it the preferences, so a client without the grant never sends one the compositor would refuse) and the machine's facts. The facts come from where the system keeps them: `/etc/hostname`, os-release's `PRETTY_NAME`, `/proc`'s processor and memory, `/etc/localtime`'s zone, systemd-timesyncd's synchronized flag and `/etc/default/keyboard`.
4. **The Settings application:** its pages on `SettingsLayout` in an application window, its fixture in the browser, `OxyOSSettings` on OxyOS. A scenario changes reduce motion and the appearance through it and checks:
   - the shell and another application follow;
   - the file holds the change;
   - a session started again keeps it.

   *Partly done.*
   - **The application.** `apps/settings` draws its pages (Appearance, Wallpaper, Lock Screen, Displays, Accessibility, Keyboard, Date & Time, About) as Bloom's grouped sections in `SettingsLayout` in an application window, in Spanish or English. Its model is the session's (`sample/SettingsApp.tsx`: `OxyOSSettings` when granted, a fixture otherwise), and the Oxy menu's System Settings opens it.
   - **The scenario.** `scenarios/settings.json` runs it granted (the development compositor's `--grant-settings`, with a preferences file of the run's own) and checks, step by step, what the session tells the application (`preferences`, from the host's report):
     - choosing Dark makes it draw dark at once (a pixel of its page);
     - Light makes it light again;
     - an accent is told;
     - at the end, the file holds the last choices.

     It passes; granted to another application instead, every step fails.
   - **Not yet:**
     - the Accessibility and Date & Time pages, whose switches need React Native's native animated module in the host;
     - the shell following the appearance;
     - a second application in the scenario;
     - a session started again.
5. **The system's settings,** with the session's authentication dialog: their own decision.

## Not in this decision

- The session's polkit authentication agent (the dialog an administrator's change asks for), and changing the system's settings through it.
- Sound, networks, Bluetooth, users and the Oxy account: each comes with the decision that adds what it sets. Notifications' preferences are [ADR 0026](./0026-notifications)'s, the displays' [ADR 0018](./0018-several-displays)'s (decision 10): the session keeps them in this file, by each display's identity, but they are no preference Settings sets with `SetPreference`.
- Preferences of applications (each keeps its own); syncing preferences with the Oxy account.
- Sandboxing applications from one another (#35, #36): without it, any program running as the user can write the preferences file or trace Settings.
