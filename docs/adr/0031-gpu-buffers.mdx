# ADR 0031: GPU buffers for applications

Status: **accepted; steps 2 and 3 implemented**, direct scanout (decision 8) included, proven on a virtual display and lavapipe but not yet on the reference GPU; step 4 to come. **Amended 2026-10-31:** decisions 12 and 13, the Bloom host draws with Skia (step 5, in progress). Builds on:
- [ADR 0001](./0001-native-platform-boundaries): surfaces, configures, the presentation invariants and buffer lifetime.
- [ADR 0004](./0004-gpu-composition): Vulkan composition, DRM/KMS output and its order of work, whose step 2 ("client buffers as Vulkan images, then DMA-BUF import with modifiers") and step 3 ("explicit synchronization") this is.
- [ADR 0005](./0005-damage): damage and buffer age.
- [ADR 0018](./0018-several-displays): each output composes and flips on its own, at its refresh.
- [ADR 0029](./0029-chromium-on-oxyos): Astro's Ozone platform, whose decision 3 sketched this path. This ADR is that sketch decided; where it differs (decision 6), it says why.

## Problem

Every application draws on the CPU and hands the compositor shared memory: the Bloom host rasterizes each frame (`tools/rn-host-spike/renderer.cpp`) into a sealed memfd, and Astro's engine composites in software (ADR 0029, decision 3). The compositor composes on the GPU (ADR 0004) and uploads those pixels every time they change.

That costs twice. The application's CPU draws every pixel, and the CPU and the memory bus then carry the pixels into the GPU. Measured on the development machine (i9-14900K, `perf.py`, three runs pooled, CPU composition), a frame the host draws whole is a few milliseconds of the host's work:

| interaction | host draw per frame (p50 / p95) | host's whole frame work (p50 / p95) |
|---|---|---|
| live resize (Inbox, every size drawn whole) | 3.1 / 7.4 ms | 11.3 / 34.6 ms |
| overview opening (the shell's surface drawn whole) | 5.5 / 6.2 ms | 6.3 / 7.2 ms |
| Settings scroll (damage-limited, ADR 0005) | 0.7 / 0.8 ms | 2.1 / 2.5 ms |

The ThinkPad's i5-1240P draws the same frames several times slower: before damage, its host drew a frame in 19–20 ms (ADR 0004, "A live app on the display"), more than a 60 Hz refresh. Damage made the small changes cheap; the frames a person watches most (a resize, a transition, a scroll that moves everything, the overview) are still drawn whole on a CPU while an Iris Xe composes a whole 1920×1200 frame in 0.5 ms.

Nothing in the protocol lets a client hand the compositor memory its GPU wrote: no DMA-BUF, no format or modifier the compositor accepts, no fence. ADR 0029 sketched one; this decides it, for every client, and decides how the Bloom host draws on the GPU.

## Decision

### The buffers

1. **One GPU path for every client.** A client's GPU buffer is a DMA-BUF: one or more planes, each a descriptor with an offset and a stride, a DRM format and a DRM format modifier. The Bloom host, Astro's GPU process (through its browser process, ADR 0029) and any other native client use the same requests and the same C ABI, which names nothing of Bloom's. Shared memory stays, unchanged, for clients that draw on the CPU and as every client's fallback (decision 9).

2. **The compositor says what it can take, and clients allocate only from that.** After `Welcome`, and again whenever it changes, the compositor tells each connection its GPU, as linux-dmabuf v4's feedback does:
   - `GpuDevice { device, formats }`: the composing device's DRM render node as a `dev_t` (0 when the device has none, as Mesa's lavapipe), and how many formats follow;
   - `GpuFormat { index, format, modifier }`, `formats` times: each DRM format and modifier the compositor can import and compose.

   A connection that hears no `GpuDevice` has no GPU path, and a `GpuDevice` with no formats withdraws it (the compositor lost its GPU, decision 9). The table is the Vulkan device's: for each format the protocol knows, each modifier `VkDrmFormatModifierPropertiesListEXT` lists whose `vkGetPhysicalDeviceImageFormatProperties2` answers importable from DMA-BUF and sampled, with single-plane and multi-plane layouts both described. Composing on the CPU, the compositor lists the linear modifier alone (decision 10).

   **The table is best first**, the driver's order kept within each kind: tiled modifiers of a single plane, then linear, then those with auxiliary planes (compression). The driver lists linear first (Intel's: linear, X-, Y- and 4-tiled, then Y-tiled with its compression planes), and a client taking the first it can share would draw every frame into linear memory, slow for the compositor to read: a GPU reads a tiled image's neighbourhoods from a few cache lines, a linear one's from as many rows as the neighbourhood is tall. Compressed modifiers come last because both sides must carry their planes and agree on their state, and handing a compressed image between queues (decision 6) may cost the driver a pass over all of it. A client offers its driver the best kind it shares with the table, never all of them at once (a driver given linear, tiled and compressed modifiers together may take any): the Bloom host's painter (`oxyos-paint`) offers the tiled ones and lets its driver pick among them, which knows its own tilings best, falling back to linear, and to compressed ones only when nothing else is shared.

   Formats are DRM fourccs, the ones the protocol's `Format` already uses: `Argb8888` (premultiplied, B, G, R, A in memory, Vulkan's `B8G8R8A8_UNORM`) and `Xrgb8888` (opaque). Others (`Abgr8888` for GL clients, YUV for video) join the list when a client needs them; the compositor never lists a format it cannot compose.

   A client allocates on the GPU the compositor names, when it has one of its own. Linear memory can be read by any device; a tiled modifier only by the device it was made for. So a client picks its Vulkan device by `VK_EXT_physical_device_drm` matching `device`, and, failing that (another GPU, or `device` 0), allocates only linear buffers. On the ThinkPad, whose NVIDIA T550 has no outputs, applications draw on the Iris Xe the compositor composes on.

3. **A buffer is attached plane by plane, and the compositor imports it before using it.** The transport carries one descriptor per message (`oxyos-ipc`), so:
   - `AttachDmabufPlane { buffer, plane, offset, stride }` with the plane's descriptor, once per plane;
   - `AttachDmabuf { buffer, format, modifier, extent, planes }` then makes them a buffer.

   The compositor checks it before anything else (decision 11) and imports it: on its Vulkan device as a `VkImage` with `VkImageDrmFormatModifierExplicitCreateInfoEXT` and the planes' memory (`VK_EXT_external_memory_dma_buf`), or, composing on the CPU, as a read-only mapping. An import that fails for a well-formed buffer (memory exhausted, a layout the driver refuses) answers `BufferFailed { buffer }` and is not a protocol error: the client allocates again or falls back. A submit naming a failed buffer is discarded (`Feedback Discarded`, `Released`). `DestroyBuffer` ends a GPU buffer as it ends a shared one.

4. **Damage, feedback and release are the protocol's own.** `Damage` before `Submit` (ADR 0005), `Submit` with its configure serial, `Feedback` with the outcome and time, and `Released` keep their meaning for GPU buffers, with one addition from explicit synchronization (decision 6): `Released` means the compositor holds no more references to the buffer. Without a release point, it is sent only once the GPU no longer reads it; with one, it may come first, and the point says when the GPU is done.

5. **Resizes.** A client draws a new size into new buffers allocated after the `Configure` asking for it, never into one the compositor still shows: invariant 2 of ADR 0001 (the last valid content stays until the new frame is ready) holds for GPU buffers because the compositor keeps the old buffer referenced until a frame of the new size latches. A client keeps a few buffers per size (three for the Bloom host, double or triple buffering as its frame pacing needs), allocates the new size's lazily as the live resize asks for it (one configure in flight, ADR 0016), and destroys the old size's once they are released. Buffer age (ADR 0005, decision 4) is per buffer: a new buffer's is unknown and it is drawn whole.

### Synchronization

6. **Explicit only, on DRM syncobj timelines.** A client registers timelines and names points on them with each frame, as wp-linux-drm-syncobj-v1 does; no fence is inferred from the buffer (no implicit synchronization).
   - `ImportTimeline { timeline }` with a DRM syncobj's descriptor, and `DestroyTimeline { timeline }`. Timelines are the connection's, numbered by the client.
   - `SetSync { surface, acquire_timeline, acquire_point, release_timeline, release_point }`, before `Submit`, as `Damage` is: the next frame of the surface is ready to read when the acquire point signals, and the compositor signals the release point once it no longer reads the buffer. The release point must be later than the acquire point when both are on one timeline. A timeline's points signal in order (a later point signalled means every earlier one is), and buffers are released out of order (a frame superseded while the one before it is still shown), so a client gives each buffer a timeline of its own, its acquire and release points alternating on it.
   - A GPU buffer submitted with no `SetSync` is ready when submitted (a buffer the CPU wrote, or one the client waited for), and its `Released` comes once the GPU no longer reads it. That is still explicit: the client states the buffer is ready.

   **The compositor never waits for a client's fence, on the CPU or the GPU.** A frame's acquire point is watched with an eventfd (`DRM_IOCTL_SYNCOBJ_EVENTFD`) in the compositor's event loop; the frame becomes the surface's queued frame only once it signals, and until then the surface shows its last frame. Nothing of a client's fence enters the compositor's own GPU submissions. This differs from ADR 0029's sketch ("imports the acquire point as a Vulkan semaphore and waits on the GPU") on purpose: a semaphore wait in the compositor's submission puts a slow client's work in front of every output's frame and every other client's, and a Vulkan wait cannot be withdrawn once submitted, so a fence that never signals would hang composition instead of being dropped. Waiting for readiness costs one wake of the event loop (well under a millisecond) and keeps ADR 0001's rule, the compositor never waits on a client, exact. A frame still waiting when the next one arrives is superseded as a queued frame is (ADR 0001, one queued replacement): `Feedback Discarded`, and its release point signalled once its acquire point has (the compositor never read it).

   **Ownership follows the buffer, not the frame.** A Vulkan image written by another queue (the client's) is acquired from it (`VK_QUEUE_FAMILY_FOREIGN_EXT`, a queue family transfer with the layout the shader reads) before it is sampled, and released back before its writer uses it again. The compositor acquires a buffer in the first composition that shows it, which is the composition of a newly latched frame (a client writes a buffer again only after `Released`); holds it while frames show it unchanged; and releases it once, when it lets the buffer go (`release_dma_buf`), in the next composition or, when none comes, in a submission of its own, before the release point is signalled. The first version acquired and released every shown buffer in every composition: on a driver that keeps tiled or compressed images (Intel's), each hand-over can resolve or re-initialise the image, a pass over all of it, which multiplied the composition's cost by the number of windows shown, whether they changed or not. A frame sampling no client buffer composes with the shader that reads shared memory alone: the one that also reads clients' buffers indexes an array of images per layer, which a driver may turn into a loop at every texel read.

   **Release.** The composition that last read a buffer gives its completion as a sync file (ADR 0004's `compose_to_scanout`, `VK_KHR_external_semaphore_fd`), and the compositor imports it into the release point (`DRM_IOCTL_SYNCOBJ_FD_TO_HANDLE` with a sync file, then a transfer to the point), so the point signals when the GPU finishes, with no CPU between. A buffer read by several outputs' compositions is released when all of them are done: their sync files are merged (ADR 0001's invariant 6, per-consumer references). A device that exports no sync file, and the CPU compositor, signal the point from the CPU once they know the reading is done.

   **Why timelines rather than a sync file with each frame.**

   | | A sync file each way per frame (linux-explicit-synchronization) | Syncobj timelines (chosen) |
   |---|---|---|
   | Descriptors on the socket | One with every submit, and one back with every release | One per timeline, once; each frame names two points (integers, within one 64-byte packet) |
   | The release | Comes back as a descriptor in an event; the client's GPU work waits for it only once it has arrived | A point the client's next frame can wait on before the compositor has signalled it (wait-before-signal): the client queues its next frame at once |
   | Vulkan | Binary semaphores imported per frame (`SYNC_FD`) | Timeline semaphores imported once (`OPAQUE_FD`, a syncobj on Mesa and NVIDIA's driver) |
   | Drivers that need it | | NVIDIA's driver, for which Wayland compositors (Mutter, KWin, wlroots) moved to wp-linux-drm-syncobj-v1 |
   | Needs | A sync file | A DRM device with `DRM_CAP_SYNCOBJ_TIMELINE` on both sides (i915/xe, amdgpu, nouveau and NVIDIA's, panfrost/panthor, msm, v3d, virtio-gpu) |

   The cost is the DRM device: a machine without one has no GPU buffers at all, and the client draws into shared memory (decision 9). For clients whose API speaks sync files (GL's `EGL_ANDROID_native_fence_sync`, Chromium's GPU fences, a Vulkan driver without timeline export such as lavapipe), the C ABI bridges both ways: it imports a sync file into a point, and exports a point the compositor has given a fence as a sync file. A timeline is a kernel object of its own, not of a device: the client imports it into its own GPU's descriptor, whichever render node that is.

7. **Presentation feedback is the display's.** `Feedback Presented` carries the flip's time on `Clock::Monotonic` for the frame that first showed the buffer (ADR 0004's flip timestamps), on whichever output it was shown first; `Discarded` for a frame superseded or answering an obsolete configure. A frame waiting for its acquire point has no feedback until it is shown or superseded, so a client pacing itself by feedback (the Bloom host, Chromium's swap acknowledgement) never draws faster than its GPU finishes.

### Scanout and composition

8. **Direct scanout of a full-screen window.** When a surface is all an output shows (`Scene::scanout_candidate`: full screen, on top, covering the output, nothing over it), the compositor puts the client's buffer on the output's primary plane instead of composing: a KMS framebuffer made once per buffer and card (`drmPrimeFDToHandle`, `AddFB2` with the modifier; with none on a card without modifiers, for a linear buffer), flipped with the frame's acquire already signalled, released when a later flip replaces it. Only an opaque buffer (XRGB8888) is scanned out: nothing is under the primary plane, so a translucent window composed over what is beneath it would look different on the plane. The buffer must be the frame's topmost layer, at the screen's size and at its own, at full opacity, uncut (with Vulkan, the very import the frame samples), on the composing device or linear (which any device reads). A buffer the card refuses, at the framebuffer or at the commit, is composed from then on, never shown black or stale. The pointer stays on the cursor plane. Anything over the surface (a popup, a notification, the lock screen, a transition) composes again, the next frame; nothing is ever shown over a scanned-out buffer by mistake, because the decision is the scene's for each frame.

   So that a client can allocate buffers the plane takes, the compositor tells a surface that could be scanned out which formats and modifiers its output's primary plane takes (from the plane's `IN_FORMATS`, intersected with decision 2's table: opaque, and on the composing device or linear): `GpuScanout { surface, formats }` and `GpuScanoutFormat { surface, index, format, modifier }`, sent when the surface becomes a candidate or its output changes, and with no formats when it stops being one. A client that ignores it is composed as before. Applications still never learn which output they are on (ADR 0029, step 6): the formats are the surface's.

9. **The fallback is shared memory, chosen at run time, per surface.** A client uses shared memory when the compositor named no GPU (`GpuDevice` absent or withdrawn), when no device of the client's can share with it (decision 2), when no format and modifier of the table can be allocated, when an import fails (`BufferFailed`), or when its own device is lost. It may come back to the GPU when the compositor names one again. The compositor keeps showing a surface's last content composed when a GPU buffer can no longer be read (its device lost, a VT switch that reopens it): the CPU copy the CPU compositor read, or the frame composed last, until the client's next frame.

10. **The CPU compositor reads linear buffers, and lists only those.** The development compositor and a session that could not open a Vulkan device compose on the CPU (`compose_cpu`). They list the linear modifier alone, map a linear buffer read-only once at import, and read a new frame's rows, bracketed by `DMA_BUF_IOCTL_SYNC` (start and end of a read), into the copy they compose from, once per frame, as shared memory is read with `pread` today. Mapping is safe where a mapping of shared memory is not: a DMA-BUF's size cannot change, so no client can make the compositor fault by shrinking it, and only descriptors that are DMA-BUFs are mapped (decision 11). The GPU compositor never maps a client's buffer. With `--gpu`, the development compositor's check of every frame against the CPU reference still holds: the reference reads the same buffer through its mapping.

### Security

11. **Every buffer is checked before it is used, and belongs to one connection.**
    - **Descriptors.** A plane's descriptor must be a DMA-BUF (the kernel's `fdinfo` of it names its exporter, which no other file has; a memfd or any other file is refused), a timeline's a DRM syncobj (the kernel's import refuses anything else). Each is received close-on-exec, kept by the compositor, and closed with its buffer.
    - **Sizes.** The extent is within `MAX_DIMENSION`; the planes are the format and modifier's count (`drmFormatModifierPlaneCount`), each plane's offset and stride aligned to 4 and, for the linear modifier, each plane's `offset + stride × rows` within its descriptor's size (`lseek(SEEK_END)`) and its stride at least a row; for tiled modifiers, Vulkan's import checks the layout against the memory. The format and modifier must be in the table the compositor sent (decision 2), not merely importable.
    - **Quotas.** A connection holds at most 64 GPU buffers, 16 timelines and 1 GiB of GPU buffer memory (each plane's descriptor size, counted once per buffer), and at most one acquire point waited for per surface; the transport's own bounds on messages hold.
    - **No sharing between clients.** Buffer and timeline numbers are the connection's: no request names another connection's, and the compositor never gives a client's buffer, timeline or pixels to another client (the shell's window views are composed by the compositor, ADR 0022). A client that hands its own descriptors to another process it trusts (Chromium's GPU process to its browser) shares only its own content.
    - **Faults.** A client's buffer cannot fault the compositor (decision 10), its fence cannot stall it (decision 6), and a buffer it writes after submitting changes only its own surface, as shared memory does.

### The Bloom host on the GPU

12. **Skia draws the Bloom host: on the GPU through its Vulkan backend (Ganesh), on the CPU through its raster backend** (amended 2026-10-31; the first version of this decision chose a renderer of OxyOS's own, below).

    **Why it changed.** The host's job is to draw what Bloom asks for (React Native's view props and styles) as React Native's Android implementation draws it. Bloom is drawn by Skia everywhere else it runs: in Chromium (react-native-web: Astro's interface, Atlas) and on Android, whose `ReactViewGroup` paints through `BackgroundStyleApplicator`'s drawables (`BorderDrawable`, `BackgroundDrawable`, `OutsetBoxShadowDrawable`, `InsetBoxShadowDrawable`, `OutlineDrawable`, `BackgroundImageDrawable`) onto an `android.graphics.Canvas`, a thin layer over Skia. Bloom on OxyOS looked unlike Bloom in a browser: no box shadows (Bloom's `Surface` edge light and glow are inset and outset `boxShadow`s), one colour for all four borders, no border styles, circular corners only, no gradients, no filters, `Image.blurRadius` ignored, opacity applied per draw where a group was asked for, text shaped with hinted whole-pixel advances. Each of those, in OxyOS's own renderer, was a new primitive written twice (a CPU painter and a compute shader with the same arithmetic) and checked against itself; none was checked against what Bloom looks like elsewhere. With Skia, each prop is drawn with the same canvas calls React Native's Android code makes, by the engine Chromium and Android draw with, and the host's CPU and GPU paths are two backends of one engine rather than two renderers kept in step.

    What the first version held against Skia, and what answers it now:
    - *Not in Debian, built from source with its own toolchain.* Built from source as Hermes is (`tools/rn-host-spike/build.sh`): Skia's own repository (`skia.googlesource.com`), pinned to the revision a Chrome stable release ships (Chrome 156.0.8078.79: `aa789d9bd566`), with `gn` and `ninja` and the clang the host already builds with, against Debian's FreeType, HarfBuzz, ICU, libpng, libjpeg-turbo and zlib (one FreeType in the process, the system's). Bumping it is changing that revision to a later Chrome stable's.
    - *Tens of megabytes in every image.* A static library linked into `oxyos-bloom-host`, measured when it lands (step 5).
    - *Replaces the CPU path too.* That is now the point: one renderer, its raster and Vulkan backends agreeing by construction, not by a second implementation of every primitive.
    - *Parity with today's frames is a new problem.* Parity with today's frames is not the goal; looking as Bloom does in Chromium and on Android is (decision 13).

    **Ganesh, not Graphite.** Ganesh's Vulkan backend is Android's renderer (HWUI's `SkiaVulkanPipeline`), so it draws React Native's Android drawables on the very backend Android draws them on, and it is Chrome's Vulkan rasterizer on Linux and ChromeOS, exercised on Mesa's ANV (the ThinkPad's Iris Xe) and on lavapipe (the regression's virtual machine). It wraps images it did not allocate (the surface's exported images, with their DRM format modifier) and signals semaphores it can export at a flush, which is all the present path needs (below). Graphite ships in Chrome over Dawn (Metal, Direct3D); its own Vulkan backend is the less exercised one. The host draws with Ganesh until that changes.

    **Text** stays Android's: Minikin's line breaking (the host's `text.cpp`: ICU's break opportunities, the optimal breaker for `highQuality` and `balanced`, greedy for `simple`), which is what Yoga measures (`TextLayoutManager`'s contract: what is measured is what is drawn). Skia's paragraph module is not used for it: it is Flutter's layout, breaks greedily only, and would drop Android's default strategy. Glyphs are shaped by HarfBuzz with the font's unhinted, fractional advances, as Minikin shapes over Skia's fonts (`MinikinFontSkia`), and drawn by Skia from the same font files (`SkTypeface`, the weight on a variable font's `wght` axis), anti-aliased in gray with slight hinting and subpixel positioning, as Chromium draws text on Linux.

    **How it draws.** `renderer.cpp`'s traversal walks the view tree onto an `SkCanvas` in logical pixels (the canvas scaled by the output's scale), and each view draws as React Native's Android code does: outset shadows, background colour, background image (gradients), border, inset shadows and outline in `CompositeBackgroundDrawable`'s order; `opacity` as Android applies it (a layer only when `needsOffscreenAlphaCompositing` asks for one, as `ReactViewGroup.hasOverlappingRendering` answers); transforms through the canvas's matrix; children clipped to the padding box's rounded rectangle, anti-aliased; images by `resizeMode`, tinted (`SRC_IN`) and blurred (`blurRadius`); `filter` and expo-blur's views through Skia's image filters; masked views through a layer kept by the mask (`DstIn`). Damage (ADR 0005) is a device-pixel clip on the canvas, so a frame drawn from its damage is the frame drawn whole within it.

    **How it presents** is unchanged (#178, #212): the host allocates its buffers on the device the compositor shares (decision 2), exported as DMA-BUF with a modifier from the compositor's table (the scanout table first, for a full-screen window), each with a timeline of its own; Skia draws the frame on that device, its flush signals a semaphore exported as a sync file into the acquire point, and a buffer is drawn into again only once its release point has signalled. The device and the buffers are `oxyos-paint`'s (now only that); Skia is given its instance, device and queue. On the CPU, Skia's raster backend draws into the canvas shared memory carries (decision 9); `OXYOS_HOST_RENDERER=cpu|gpu` forces one. **Shadows** of windows stay the compositor's (ADR 0016).

    The first version, for the record: a renderer of OxyOS's own on Vulkan (`ash`), a compute shader working out each of the CPU painter's primitives with the CPU painter's arithmetic, so the two agreed byte for byte (step 3). It was chosen over Skia ("not in Debian; tens of megabytes; replaces the CPU path; parity is a new problem") and over a Rust renderer on wgpu (wgpu hides the DMA-BUF export and sync files this path needs; vello had no blur). It met its own goal, GPU and CPU frames identical, and missed the one that matters: Bloom looking like Bloom.

13. **Fidelity and parity are tested, not assumed** (amended with decision 12):
    - **Fidelity:** a gallery of Bloom's components in their main states (`sample/FidelityGallery.tsx`), light and dark, at scales 1 and 1.25, drawn by Chromium through react-native-web, as Astro and Atlas draw Bloom, and by the host; each component's difference, per pixel and perceptual, is held under a threshold of its own (`tools/rn-host-spike/fidelity.py --check`, `scenarios/fidelity-thresholds.json`). What differs on purpose (Android's behaviour where it is not Chromium's) is listed in `docs/react-native-android-adaptation.mdx` with its reason.
    - **Both backends:** every regression scenario runs on the raster and the Vulkan backend, and every expectation holds on both (texts, focus, pixels within `pixel_tolerance`, damage).
    - **Parity:** with `OXYOS_HOST_RENDER_CHECK`, the host draws each frame on both backends and reports the largest difference of any channel and the share of pixels differing by more than 3 levels; Skia's backends rasterize edges and blurs each its own way, so the budget is the one measured on Skia's own backends, stated where it is set, and still fails an edge a pixel off, a glyph missing or a layer misplaced.
    - **Damage:** a frame drawn from its damage equals the frame drawn whole on the same backend (`OXYOS_HOST_DAMAGE_CHECK`).

## Testing

- **On any machine:** the protocol's codec and state (attach, plane counts, quotas, sync before submit, superseded frames waiting for their points), the scene's latching, the client library's tables and swap bookkeeping, and every check of decision 11 with descriptors that are not DMA-BUFs.
- **In a disposable virtual machine** (`tools/gpu-vm/gpu-vm`): the development machine (WSL2) has no DRM device and no udmabuf, so the GPU path's tests run under KVM on Debian Trixie's own kernel, with this machine's root shared read-only and its freshly built binaries. The guest has udmabuf and the system dma-heap (DMA-BUFs from memfds), virtio-gpu's render node (DRM syncobj timelines with eventfds and sync-file transfer), vgem's fences, and Mesa's lavapipe, which in the guest exports and imports DMA-BUF with the linear modifier and exports sync files. Nothing is loaded or changed on the host. There, `oxyos-gpu`'s import is checked against the CPU reference byte for byte, the compositor's latching against real fences, and `regress.py`'s scenarios run with a minimal Vulkan client (`tools/oxyos-gpu-client`) and the Bloom host on both painters.
- **On the ThinkPad** (Iris Xe, Mesa's ANV and iris, kernel 6.12): tiled modifiers, timeline semaphores imported natively, direct scanout of a full-screen window, and the host's frame times on a real GPU; each step names what to verify there.

## Steps

1. This decision.
2. **The protocol, the client and the compositor:** the requests and events of decisions 2, 3, 6 and 8 (requests and events 170 to 174; 160 to 163 went to ADR 0030's sheets), `oxyos-client` and the C ABI (tables, attaching, timelines, synchronized submits, the sync-file bridge), the scene's latching on acquire points and release on completion, `oxyos-gpu` importing DMA-BUFs and composing them in the same pass as shared memory (byte for byte with the CPU reference), the CPU compositor's linear reads, the development compositor, `tools/gpu-vm`, `tools/oxyos-gpu-client` and scenarios for them. Direct scanout's framebuffers and flips in `oxyos-kms` and the session.

   *Done.*
   - **Protocol:** requests 170–174 and events 170–174, one descriptor per message as before.
   - **`crates/oxyos-dmabuf`:** DMA-BUF checks (the exporter `fdinfo` names), linear planes within their descriptors, read-only mappings read within `DMA_BUF_IOCTL_SYNC`, timelines on a render node through `drm` (signal, query, eventfd, export and import, sync files into points and points out as sync files), sync files merged, udmabuf.
   - **`oxyos-gpu`:** the device's importable formats and modifiers (`B8G8R8A8_UNORM` as ARGB8888 and XRGB8888, each modifier sampled and importable from a DMA-BUF), imports with explicit plane layouts and dedicated memory, refused when the DMA-BUF is smaller than the image; the shader reads a layer from an array of 64 sampled images (a second SPIR-V build, non-uniform indexing), with the same arithmetic, so composition stays byte for byte the CPU reference; each frame acquires the images it samples from the foreign queue family and releases them back.
   - **The compositor:** the offer after `Welcome` (the Vulkan device's formats; linear ones it maps when it composes on the CPU, or checks with `--gpu`), planes and buffers checked as decision 11 says, imported or mapped before use, `BufferFailed` for a well-formed buffer it cannot import; timelines per connection; a frame whose acquire point has not signalled kept out of the scene and latched in the turn its eventfd wakes; a frame arriving meanwhile supersedes it; `Released` of a GPU buffer held while the frame in flight or a transition reads it, its release point given the composition's sync file or signalled from the CPU. The session offers GPU buffers on the device it composes on.
   - **The client and the C ABI** (`oxyos-client`, `oxyos_client.h`): the tables, `oxyos_client_attach_dmabuf`, timelines created or imported, the sync-file bridge both ways, `oxyos_client_submit_buffer_synced`; checked locally as the compositor checks them. Nothing in it names Bloom: Astro's Ozone platform uses it as it is.
   - **`tools/oxyos-gpu-client`:** a window Vulkan draws into images exported as DMA-BUF with a modifier from the compositor's table, a timeline per image, the submission's completion as the acquire point, the release point waited for before an image is drawn into again; shared memory when there is no GPU path.
   - **Tests:** the protocol's codec and descriptors; the client's tables, attaching, refusals and synced submits through sockets; in `tools/gpu-vm` (lavapipe, udmabuf, virtio-gpu's timelines, nothing skipped): every test of `oxyos-dmabuf`, `oxyos-gpu` (a DMA-BUF sampled in place is byte for byte its pixels uploaded, opaque and premultiplied, filtered, rounded, translucent and clipped), the compositor through sockets (a frame not shown before its acquire point, shown once it signals, its buffer released with its release point; a frame superseded while it waits discarded and released, its release point signalled only after its acquire point; on the CPU and checked on lavapipe; every refusal of decision 11), the client and the C ABI, and `scenarios/gpu-client.json` (presses answered by frames drawn on the GPU, a live resize answered at every size by new buffers) composed on the CPU, with `--gpu` (every frame identical to the CPU reference) and with `--gpu-only`.
   - **Direct scanout** (decision 8): `oxyos-kms` makes a framebuffer of up to four DMA-BUF planes with their modifier, once per buffer and display, removed with the buffer or the display, and finds a card's render node in sysfs; each display knows its primary plane's formats. For each frame on a display the compositor tells its candidate surface its scanout formats (or that it has none any more) and scans its buffer out when decision 8 allows; anything over it composes, and the display's scanout targets are then composed whole. The display holds the buffer until a later flip replaces it, so its `Released` waits even once its surface is gone. Tested in `tools/gpu-vm` on virtio-gpu's KMS (`tests/scanout.rs`): a buffer of the display's own card is flipped onto the plane, composed under the splash and scanned out again once it is gone, and released only after the flip that no longer shows it; a udmabuf buffer, which virtio-gpu cannot import as a framebuffer (it takes no foreign DMA-BUF without blob resources, which QEMU here cannot give without the host's udmabuf), is composed instead and shows what the client drew. The session logs `[compositor] output N shows a full-screen window's buffer directly (modifier …)` and `… composes again`.
   - **Not verified:** a real GPU (tiled modifiers, ANV's import, timeline semaphores imported natively, i915 scanning a client's buffer out): the ThinkPad's.
3. **The Bloom host on the GPU** (decisions 12 and 13): `oxyos-paint`, the host's painter split in two, the regression on both painters, and `perf.py` before and after (frame time for scroll, resize and transitions; memory).

   *Done* (the reference GPU not yet run):
   - **How it draws.** Each of the CPU painter's operations carries the device pixels the CPU painter would visit for it (worked out by the host with the CPU painter's own expressions), and each pixel is worked out with the CPU painter's arithmetic (`crates/oxyos-paint/shaders/paint.wgsl`: the same coverage, the same bilinear sampling, the same rounding; a pixel's logical position and size, its coordinate divided by the scale, read from a table the host divides as the CPU does, other divisions refined towards the CPU's). That replaces decision 12's quads and fragment shaders: with the same arithmetic per pixel the two painters agree byte for byte, not merely to the eye. Consecutive operations on one canvas that write only their own pixel (fills, images, layers, glyph runs, smooth draws, masks, clears) run as one dispatch: binned into tiles of 16 × 16 pixels, in order, each pixel working out its tile's operations in order, so they need no barrier between them; blurs' passes and copies run on their own, a barrier after each step. Canvases, pictures, glyph masks, blur planes and bins live in one heap of host-visible memory (device-local where the device has both, as an integrated GPU does), so an upload is a write in place and a check reads a canvas back by copying it.
   - **How it presents.** The canvas stays on the device and keeps the frame, as the CPU canvas does (damage draws onto it). A frame copies what changed since a buffer last held it (its age, ADR 0005) into one of the surface's exportable images (`TRANSFER_DST`, a modifier from the surface's scanout table when it has one, the composition table otherwise; XRGB8888 for the window, so a full-screen window can be scanned out), attached once, each image with a timeline of its own; the submission's sync file is the acquire point, and an image is copied into again only once its release point has signalled. The copy costs one pass over the changed pixels on the GPU and lets any modifier the device exports be used.
   - **The host.** `renderer.cpp`'s painter is an interface with two painters; the view tree, layout, damage and traversal are one; layers, blurs, masks and modal frames ask the painter for canvases of its own kind. The window chooses once it is configured, before the application starts. Where the compositor names a GPU the process shares buffers with, the GPU's painter is started on a thread of its own (`oxyos_paint_new` takes the render node, not the client), beside the runtime and the application loading; frames until it is ready are drawn on the CPU, and once it is, its descriptor wakes the host's loop and every surface is drawn whole on it. Started on the thread that answers the application, at the first frame, it held that frame back for the whole start (3.8 s on lavapipe in the guest, compiling its pipelines with no shader cache), long enough for an application's own timers to run out before its network answers were drawn: the network and expo-modules scenarios failed on the GPU painter alone. `OXYOS_HOST_RENDERER=cpu|gpu` forces one; forced, the GPU's painter is waited for before the application starts, so every frame is its own and its start delays no timer, and it is an error when it cannot start. The regression keeps the GPU driver's shader cache where the machine keeps it (`MESA_SHADER_CACHE_DIR`), as a session does, rather than in each run's fresh cache: the start is 4.7 s with a cold cache on lavapipe and 0.14 s with a warm one. A failed present (no shared modifier, `BufferFailed`, the device lost) presents that frame from its pixels in shared memory and draws on the CPU from then on.
   - **Parity** (`regress.py --renderer gpu --check-render`, every scenario of the Bloom host in `tools/gpu-vm` on lavapipe, Stash's included, the session's shell and the applications it launches included, with the runtime and packages as installed, ADR 0030): of 2,971 frames compared, 2,524 are byte for byte the CPU's and the other 447 within budget (446 differ by at most one level; one, a live resize at 1.25, by up to 10 levels in 0.09 % of the frame); none is over it. The first version had 21 frames over budget, all at fractional scales: one column of a glyph, at the left edge of its text's clip, drawn by the CPU and not by the GPU (the top bar's clock, a label in the dock). The cause was the shader dividing a pixel's coordinate by the scale itself. The CPU painter keeps a glyph's pixel where `px / scale`, divided in single precision and correctly rounded, is within the clip; a device's division need not be correctly rounded (Vulkan allows 2.5 ulp), and the residual step meant to correct it is exact only with a fused fma, which Vulkan does not promise. Where a clip edge falls exactly on a column, the CPU's quotient equals the edge and keeps the column, and the GPU's, an ulp below, dropped it. `oxyos-paint`'s test drawing a glyph at each of 2,048 columns at six scales, a clip edge on each, found 334 such columns on lavapipe (at 1.1 and 1.75, none at 1.25 or 1.5). The host now divides: each scale's quotients `i / scale`, as the CPU divides them, are a table in the heap the shader reads for every pixel's position, and for its size (`i = 1`); the test finds none. The scenarios that showed it (scaled-text, displays, shell-follows-display) pass, but with main's layout since then no text clip there falls on a column, so they passed before the fix as well: the test, not they, shows it. The budget was not changed.
   - **Functional regression on the GPU painter** (`tools/gpu-vm`, lavapipe, every scenario of the Bloom host, with the runtime and packages as installed, Stash's included): every scenario that passes on the CPU painter in the guest passes on the GPU painter. Seventeen fail on both there, the same way, and pass on the CPU painter on the development machine: the install service's (its socket never appears in the guest) and files another program changes (no change is heard through the guest's 9p share). The terminal's needs a real display and uinput (`--kms --uinput`) and runs in neither. The machine was loaded by other builds through most runs (load 15 to 55 on 32 threads), and timing expectations missed on both painters by turns (frames in a 120 Hz animation, a launched window's arrival, a press's latency); each that missed on the GPU painter alone passed when run again with the machine quieter. Once in seven runs of `shell`, the host exited with a failure after the director closed its connection mid-frame at the end, its expectations met; not seen again in six runs of it alone, and not explained. Two failed on the GPU painter alone, every time: network and expo-modules, whose applications race their own 5 s timers while the painter's start held the first frame back (above); they pass. On the development machine the CPU painter passes all 87 others.
   - **Measured** (`perf.py --renderer cpu|gpu`, two runs each in the guest, lavapipe, which draws on the same CPU cores it shares with everything else, so the GPU path's numbers here say nothing of a GPU's speed). The host thread's drawing per frame (`render_ms`, p50 / p95) falls from 2.7 / 6.0 to 0.63 / 0.94 ms in a live resize, from 0.66 / 0.96 to 0.20 / 0.33 ms in a scroll, from 0.11 / 6.9 to 0.03 / 0.64 ms for the overview's shell. A live resize's whole frame work went from 10.1 / 14.2 ms on the CPU painter to 36.7 / 402 ms on the GPU painter's first version, and is 16.7 / 23.7 ms now. Each present now says where its time goes (`oxyos_paint_last_present`, in the host's report): a new size's exportable image, its export, attaching it and its timeline cost 0.3 + 0.05 + 0.01 ms, freeing the old size's 0.2 ms, so the protocol's buffer-is-the-configured-size rule costs about 0.5 ms a size, not what was slow. What was slow was the frame's operations, about 0.16 ms each on lavapipe, each a dispatch behind a full barrier (138 for a resize's frame: 20 ms); binned into tiles they run in a few dispatches, and a new size's present went from 21 to 7.4 ms. What remains of it (6.8 ms, `sync`) is lavapipe drawing the frame: its sync-file export returns once the work is done (the measured `sync` grows with the frame's operations and area), where a GPU's returns at once and draws on its own. Each process holds 60 to 170 MiB more resident memory (the Vulkan driver and the heap). Real numbers are the ThinkPad's.
   - **Not done:** an application's first frames, until its painter has started, are the CPU's (lavapipe compiles a pipeline when it first runs, so both are run once at start: 3.8 s in the guest; a GPU compiles them when made); the render check is a separate pass from timing expectations (it draws each frame twice); `tools/oxyos-gpu-client` keeps its own Vulkan code rather than oxyos-paint's; timelines are made per image (0.01 ms each here: a pool would save nothing measurable).

## Consequences

- An application drawing on the GPU costs the CPU its layout and its commands, not its pixels, and the compositor reads its pixels where they are. The frames drawn whole (resizes, transitions, the overview) stop being bound by the CPU.
- A full-screen application is shown with no composition at all.
- Shared memory remains a complete path: a machine without a DRM device, a GPU the compositor cannot share with, or a lost device shows every application as today, drawn by Skia's raster backend, which is never removed.
- The protocol grows by ten messages and two descriptor-carrying requests; descriptors are still one per message.
- One renderer, Skia, with two backends: what the host gains is drawn once, and decision 13's checks fail the regression when the backends part or when Bloom stops looking as it does in Chromium. Skia is a pinned dependency, built from source, bumped with Chrome's stable releases.
- Tests of the GPU path need KVM or a GPU; without either they are skipped and say so, never passed by a stand-in.
