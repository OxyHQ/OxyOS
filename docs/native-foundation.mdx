# Build and verify the native foundation

The root Rust workspace is independent of the `config/` image configuration. Its third-party Cargo dependencies are `rustix` (safe system-call bindings), `ash` and `naga` for Vulkan composition (`crates/oxyos-gpu`), `drm`/`drm-fourcc` for DRM/KMS (`crates/oxyos-kms`) and `drm` for clients' GPU buffers' syncobj timelines (`crates/oxyos-dmabuf`), `input` (libinput) and `xkbcommon` for device input and the keymap (`crates/oxyos-input`), `evdev` for the development compositor's virtual devices (uinput), `signal-hook` for the terminal's switch requests (`crates/oxyos-vt`), `zbus` for systemd-logind over D-Bus (`crates/oxyos-seat`), `ureq` (HTTP, with TLS through rustls), `cookie_store` and `url` for applications' requests (`crates/oxyos-net`), `png`, `zune-jpeg` and `moxcms` (colour management) for applications' images (`crates/oxyos-image`), `kurbo` (SVG path data) and `tiny-skia` (anti-aliased rasterizing) for their vector graphics (`crates/oxyos-vector`), and ICU4X (its `icu_*` crates with CLDR's data compiled in, `icu_experimental` among them for its currency and percent data, and `fixed_decimal`, `tinystr`, `writeable` and `zerovec`) and `jiff` (time zones from the system's database) for their `Intl` (`crates/oxyos-intl`), and `libc` (PAM's C types and the account database) and `zeroize` (passwords overwritten in memory) for the lock's authentication (`crates/oxyos-auth`, `crates/oxyos-compositor-core`), and `serde` and `serde_json` (Oxy's API, the service's socket and its files are JSON) with `ureq`, `url`, `zeroize` and `rustix` for setting up Oxy accounts (`crates/oxyos-account`), and `ring` (Ed25519 and SHA-256) with `rustix` for packages (`crates/oxyos-package`), and with `serde` and `serde_json` too for installing them (`crates/oxyos-install`). Building `oxyos-input` needs the libinput, libudev and libxkbcommon development files; the keymaps come from `xkb-data`. `oxyos-auth` links Linux-PAM's `libpam.so.0` itself, with its own declarations of PAM's interface, so it needs no PAM development files. The workspace forbids `unsafe` code, except in the C ABI (`crates/oxyos-client-ffi`), Vulkan (`crates/oxyos-gpu`), DMA-BUF mappings and their ioctls (`crates/oxyos-dmabuf`), the terminal's ioctls (`crates/oxyos-vt`) and PAM (`crates/oxyos-auth`), which deny it and allow it item by item, each with its safety contract. It loads no display toolkit. The compositor core verifies protocol, policy and ownership state and draws no pixels. The offscreen fixture composes client buffers with `oxyos-gpu`'s reference.

Requirements: Rust from `rust-toolchain.toml`, a native linker and Python 3. Linux is the target. Unix socket tests also run on macOS for development; Windows is not currently supported.

```sh
cargo fmt --all --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
python3 scripts/check-native-boundary.py
cargo run --locked -p oxyos-platform-probe
cargo run --locked -p oxyos-offscreen -- --out target/oxyos-offscreen
```

The probe launches two independent client processes that speak protocol version 5 over Unix sockets to one shared compositor `Scene`. Each creates a toplevel and presents three frames; one also opens a popup larger than its window, checks that the compositor placed it beyond all four parent edges, and waits for its buffer to be released after destroying it. The probe then requires that no surface, client or held buffer remains. It uses a private temporary directory, socket timeouts, connection/exit deadlines and child cleanup. No DISPLAY/WAYLAND_DISPLAY is passed to its children. Completion is synthetic and labeled `Clock::Synthetic`. The probe is a finite developer tool, not an installed service or authenticated compositor.

Expected result:

```json
{"mode":"headless-metadata","protocol":5,"clients":2,"frames":7,"popups_beyond_parent":1,"graphics":false,"bloom":false,"status":"passed"}
```

## Wire contract (version 5, experimental)

Each packet is a 4-byte little-endian payload length followed by one opcode byte and fixed-width little-endian fields. Payload length is 1–64 bytes. Requests (client → compositor) and events (compositor → client) have separate opcode spaces and decoders. The table is generated from `crates/oxyos-protocol/src/schema.rs`; a test fails if this table and the schema differ.

Field rules: sizes are 1–16,384; coordinates and offsets are within ±2^20; booleans are 0 or 1; enums and adjustment flags reject unknown values; anchor rectangles have a positive size; surface id 0 is invalid. Encoders run the decoder's validation, so a peer never emits what it would reject. Pointer and touch coordinates, and scroll distances, are surface-local logical pixels in 24.8 fixed point. Scale is in 120ths.

Input semantics:
- **Time.** Every input event (`Pointer`, `Key`, `KeyText`, `Touch`, `Scroll`, `Pinch`, `Hold`, `InputMethodKey`) carries `time_ns`: when its device registered it, on CLOCK_MONOTONIC in nanoseconds (libinput's time, the kernel's evdev timestamp; the development compositor's director gives a paced step's events the time each is due), as Wayland's input events carry `time` and Android's MotionEvent `eventTime`. A client times input by it, never by when it read the event: behind a slow frame, two presses keep the time between them. A key the input method gives back keeps its own. Version 3 added it. A version 2 peer is still served ([ADR 0033](./adr/0033-protocol-versions)): its events leave it out, and a client reading a version 2 compositor's events gets 0. Version 4 added `Hold`, which a client of version 3 or older is never sent. Version 6 added screenshots (opcodes 210 to 215 both ways, [ADR 0024](./adr/0024-system-shortcuts), decision 10), never sent to an older client.
- **Scroll** goes to the surface under the pointer, like motion. It is not a press: it authorizes no popup grab and activates nothing. Positive distances move the view right and down.
- **Text** carries committed text for the focused surface: 1 to 32 bytes of UTF-8 that never split a character, with longer text arriving as consecutive chunks. The compositor turns keys into text through its keymap (and, later, an input method), so clients never translate key codes. `Key` stays for layout-independent keys such as Backspace, Enter, Tab, Escape and the arrows.
- **Key text** ([ADR 0029](./adr/0029-chromium-on-oxyos)): a client that sends `SetKeyText` takes each key's text with the key, in `KeyText` (a key as `Key`, with up to 32 bytes the session's layout typed with it, compose sequences included; empty for a modifier, an editing key, a control character or a dead key). That text is then never sent again as `Text` or in a text input transaction; text no key typed (an input method's) still comes as before. A browser's keydown carries its key: it needs the text when the key arrives, not in a later event it cannot know is coming.
- **GPU buffers** ([ADR 0031](./adr/0031-gpu-buffers)): after `Welcome`, a compositor that imports DMA-BUFs sends `GpuDevice` (its render node as a `dev_t`, 0 for none, and how many formats follow) and each `GpuFormat` (a DRM format and modifier it composes), again whenever they change; none, or no formats, means shared memory only. A client attaches a DMA-BUF plane by plane (`AttachDmabufPlane`, each with its descriptor, then `AttachDmabuf` with the format, modifier, size and plane count); the compositor checks the descriptors are DMA-BUFs, the format and modifier are in its table, the plane count is the modifier's and a linear plane lies within its descriptor, within the connection's quotas (64 GPU buffers, 16 timelines, 1 GiB), and imports it: a well-formed buffer it cannot import gets `BufferFailed`, and a submit naming it is discarded. Synchronization is explicit, on DRM syncobj timelines the connection imports (`ImportTimeline` with the syncobj's descriptor): `SetSync` before a `Submit` names the acquire point the frame waits for and the release point the compositor signals once it no longer reads the buffer (release later than acquire on one timeline). The compositor waits for the acquire point in its event loop before the frame is queued, never in its own GPU work; a frame still waiting when the next arrives is discarded. Without a release point, `Released` comes once the GPU no longer reads the buffer; with one, `Released` may come first. A surface that is all its output shows is told its output's scanout formats (`GpuScanout`, `GpuScanoutFormat`: the offer's opaque formats its primary plane takes, on the composing device or linear), none when it no longer is; its buffer is then put on the plane instead of a composition, held until a later flip replaces it.
- **Preedit** carries the input method's composition for the focused surface: its current text (0 to 32 bytes of whole characters, empty to end it) and the composing cursor as a byte offset. Each `Preedit` replaces the previous one; the composition's result arrives as `Text`.
- **Text input** ([ADR 0008](./adr/0008-input-method)):
  - **The field's state:** a client enables text input on the surface whose field is focused and describes it (purpose and hints, up to 4,000 bytes of surrounding text in chunks, the selection in bytes within it, the caret's rectangle), all applied at `TextInputCommit`. Commit serials must go up; a selection outside the text or inside a character is `InvalidMessage`, more surrounding text `QuotaExceeded`. Enabling again starts the state anew.
  - **Changes:** to such a surface, while focused, every change is one transaction applied at `TextInputDone`: a deletion around the selection, the committed text in chunks, then the new composition in chunks (none ends it) with its cursor range and styled segments. `Done` carries the input's serial (a user input when it commits text, as a key press) and the field's latest commit serial. A surface that never enabled text input receives `Text` and `Preedit` as before: no deletion, and a composition only if it fits one `Preedit`, else an empty one.
- **Outputs** ([ADR 0018](./adr/0018-several-displays)): a client granted `shell` is told each output (`Output`: its rectangle in the global space, in logical pixels, its scale and refresh, and whether it is the primary, which has the dock) when it connects and as one is added or changes, and its removal (`OutputRemoved`). Applications are not told the arrangement, but every client is told the refresh of the output each of its surfaces is on (`Refresh`, in millihertz), before the surface's first `Configure` and whenever it changes, and paces its frames by it. A client granted `settings` is told each display the session shows (`DisplayName` in chunks, its `DisplayMode`s, its `DisplayScale` choices, then `Display`: its rectangle, scale, mode, physical size, whether it is the primary and whether it is built in; `DisplayRemoved`) and changes them (`SetDisplayMode`, `SetDisplayScale`, `SetDisplayOrigin`, `SetPrimaryDisplay`, each answered by a `PreferenceResult`): a mode is shown at once and kept only once `ConfirmDisplays` keeps it within the seconds `DisplayConfirmation` says, otherwise the display goes back to what it showed.
- **The session's shell** ([ADR 0009](./adr/0009-session-shell)): applications name their windows (`SetTitle`, `SetAppId`, in chunks). A client granted `shell` is told each mapped window by a number the compositor gives it, with its workspace, state, title and application id, and the workspaces, only what changed since it was last told; it focuses, minimizes, moves and closes windows (the application is asked, `CloseRequested`) and manages workspaces. Only the active workspace's windows are shown, take input and can have focus. On its shell surfaces it places windows to be shown live ([ADR 0022](./adr/0022-window-views)): `ClearWindowViews` and `PlaceWindowView`s (a window's number, a rectangle and clip in the surface, corner radius and opacity), shown with the surface's next `Submit`, which the compositor draws over the surface's pixels, the window fitted in its proportions and box-filtered; it is told each window's size (`WindowSize`) for those proportions, and never receives a window's pixels. Nothing of them is drawn while the session is locked.
- **The input method** ([ADR 0008](./adr/0008-input-method)): a client granted `input_method`, at most one, serves the focused field while it has text input enabled and is not a password, PIN or sensitive. It is told the field's state, never its surface, client or place on screen; receives the keys first (after the compositor's shortcuts) and answers each, the keys it gives back reaching the application in order; and sends changes that apply at `InputMethodCommit`, naming the field state they were made for. Deactivation delivers the keys it holds first; past 64 unanswered keys every held key goes on. Its one candidates surface (`CreateInputCandidates`) is placed by the compositor below the caret, never focused, and shown only while it serves a field with a known caret; its configure carries only its size.
- **Preferences** ([ADR 0019](./adr/0019-settings)): every client is told the preferences it draws with (`Preferences`: dark, reduce motion, reduce transparency, the accent) when it connects and whenever they change. A client granted `settings` (by its launch record, never by a request) is told every preference as kept (`Preference`, `key=value` in chunks) and changes one with `SetPreference`, answered by `PreferenceResult`; any other client that asks is closed (`Unauthorized`).
- **System shortcuts** ([ADR 0024](./adr/0024-system-shortcuts)): Super, and every key pressed while it is held, is the system's: no application or input method receives it, press, release or text, and while locked none acts. Keys are matched by their place (Linux key codes). The compositor acts on the active window itself (Super+W its close request, Super+Q every window of its application, Super+M, Super+H hiding the application until it is activated, Super+\` its next window, Super+Ctrl+F full screen); the application switcher (Super+Tab while Super is held), the search (Super+Space) and the menu bar from the keyboard (Super+F2, as a Mac's Control-F2) are sent to the shell of the active window's output, granted `shortcuts`, as `SystemShortcut` commands with a serial of its own. The shell is told each window's latest activation and whether it is hidden (`WindowUse`), hides and quits applications by a window (`HideApplication`, `QuitApplication`), and may focus its own panel or overlay citing an input it received (`FocusShellSurface`).
- **Hardware keys and the Control Center** ([ADR 0025](./adr/0025-hardware-keys-and-control-center)): the volume, mute, microphone, display brightness and keyboard backlight keys (Linux key codes 113–115, 224, 225, 228–230, 248) are the system's, taken before the system shortcuts, the input method and every application, press and release, with any modifier and while locked; each press goes to the session, which acts on the machine. A client granted `shell` is told each level (`ControlLevel`: 0 to 65536, muted, available; `bezel` to the shell of the output in front for a key), the battery (`Power`), the network (`Network`, its SSID in one chunk) and Bluetooth (`Bluetooth`) when it connects and as they change, and asks for a level (`SetControlLevel`), a mute (`SetControlMuted`), Wi-Fi (`SetWifiEnabled`), the appearance (`SetAppearance`, a change of the `appearance` preference answered by `PreferenceResult`) and a fresh look (`RefreshControls`); none is taken while locked but the last, and any other client asking is closed (`Unauthorized`).
- **Notifications** ([ADR 0026](./adr/0026-notifications)): an application posts one as its own serial, its texts in chunks (`NotificationText`: identifier, title, subtitle, body, data, each action's id, label and reply placeholder) then `PostNotification`, answered by `NotificationResult` (posted with the session's number for it, refused, throttled). Only a client whose process the session started is an application: the notification is its launch record's, never its claim. The session keeps them, at most 32 an application and 256 in all, 5 an application in any 10 seconds. A client granted `shell` is told each (`NotificationText`s, its application among them, then `Notification`: whether to show it as a banner now, its actions, its age, whether its texts are withheld while locked), their removal (`NotificationRemoved`) and the policy (`NotificationPolicy`: Do Not Disturb, previews on the lock screen); it removes them (`WithdrawNotification`) and activates one or an action citing an input it received (`ActivateNotification`, with a reply in chunks before it, `NotificationReply`). From its Control Center it turns Do Not Disturb on or off (`SetDoNotDisturb`), a change of the user's preference answered by a `PreferenceResult`, as `SetAppearance` is. The application gets one `NotificationResponse` after the notification's texts, the chosen action's id and the reply; its windows come forward, and the session starts it first if none of its clients runs.
- **The menu bar** ([ADR 0021](./adr/0021-menu-bar)): a toplevel's menus go as one message in chunks, as an accessibility snapshot does (`MenusBegin` with a serial above the window's last, `MenuItem`s in order with parents first, a menu of the bar having none, `MenuText` chunks for labels and shortcuts, `MenusCommit`), replacing the last. Limits are 256 entries, nesting 4 deep, 128 bytes per label and 32 per shortcut, with closed sets of kinds and flags. A client granted `shell` is told the active window's menus (`MenuBar` … `MenuBarCommitted`, window 0 for none) whenever they or the active window change; it chooses a command by the window, the commit's serial and the command's index, and the compositor sends `MenuItemActivated` to the window's client only if that window is still active, that commit is still its menus and the index is an enabled command.
- **Accessibility** ([ADR 0003](./adr/0003-accessibility-protocol)):
  - **Publishing:** an application publishes one snapshot per surface (`AccessibilityBegin`, `AccessibleNode`s in reading order with parents first, `AccessibleText` chunks for names and values, then `AccessibilityCommit`). Limits are 4096 nodes and 1024 bytes per text, with closed sets of roles and states.
  - **Reading:** only a client granted `accessibility` receives committed snapshots, with global rectangles, and their removal.
  - **Acting:** that client's `AccessibilityAction` (activate, focus) reaches the owning application as an event. Its serial is the user's activation, as a key press's is, so an activation can open a grabbing popup; a focus move authorizes nothing.

The connection starts with Hello (a version range) answered by Welcome (the highest common version) or ProtocolError; the compositor serves every version from `MIN_VERSION` (2) to `VERSION` (6), each connection's events encoded as its version defines them, and refuses a request newer than the connection's ([ADR 0033](./adr/0033-protocol-versions)); anything before Hello, a second Hello or anything after Goodbye is `InvalidOrder` and closes the connection. A protocol error closes the connection and the compositor removes every resource of that client. These messages carry no pixels or privileges. Five carry a file descriptor, and every other carries none: AttachBuffer (a sealed memfd), AttachDmabufPlane (a DMA-BUF), ImportTimeline (a DRM syncobj), ClipboardReceive (the write end of a pipe) and the ClipboardSend event (that pipe, passed to the clipboard's owner).

Not yet in the contract: the compositor's keymap itself (applications are told its XKB names, `KeyboardLayout`, ADR 0029) and IME (offscreen sends text and preedit directly; input methods are decided in [ADR 0008](./adr/0008-input-method): the field's state and transactions are in the protocol, an input method is not), accessibility bridging, and outputs' places told to applications (the shell is told them, [ADR 0018](./adr/0018-several-displays); applications are told each output's size, scale, refresh and work area, and which output each surface is on, ADR 0029). Versions only add: new opcodes and fields at the end of existing messages, as ADR 0033 says; do not freeze a version as an SDK ABI yet.

## Transport and buffers

`oxyos-ipc` carries one protocol message per `SOCK_SEQPACKET` packet, so a descriptor always arrives with its message and oversized or concatenated packets are rejected. Only `AttachBuffer` carries a descriptor, exactly one; any other descriptor is closed and the message rejected. Peer credentials are read from the kernel (`SO_PEERCRED`); the session authority turns them into grants, never the peer's own claims.

Shared-memory buffers must be regular files sealed against shrinking (`memfd` with `F_SEAL_SHRINK`) and at least as large as their layout (`offset + stride × (height − 1) + row`, checked arithmetic, 256 MiB cap, 4-byte aligned stride and offset). The compositor reads them with `pread`, so a client cannot fault it. `Scene` keeps a per-client buffer registry (128 per client): submissions must name a registered buffer of the submitted extent, a buffer backs one surface at a time, and `DestroyBuffer` on a displayed buffer defers retirement until it is replaced. `Released` means the client may reuse a buffer; `drain_retired` means the backend may close its descriptor.

## Offscreen development compositor

`oxyos-offscreen` runs the protocol, transport and scene with real processes and memory: a `poll` loop that never blocks on a client, bounded per-client outboxes (1,024 unread events disconnect the client), CPU composition of the in-flight frame (`Scene::frame_list`) and recomposition when the scene changes. A scripted director injects synthetic input: one client opens a context menu larger than its window; the fixture samples composed pixels beyond all four window edges over the other client, presses a menu row outside the window, presses outside the menu, and checks that the other client received no press, that no menu pixels remain, and that scene resources and the process's open descriptors return to their starting counts. It writes four PNG snapshots.

`oxyos-offscreen --launch [--gpu] [--press X,Y | --press-popup X,Y | --scroll X,Y,DY | --type TEXT | --key CODE | --expect-popup | …]... -- COMMAND` (the full list is in its usage text) launches one application process instead, passing the socket in `OXYOS_COMPOSITOR_SOCKET`. It waits until the application's surfaces stay unchanged for 750 ms, then runs each step in order:
- a left-button press at a window-local point, or at a point of the application's popup;
- a scroll with the pointer at a point;
- committed text;
- a key press and release.

An input step passes only when the application answers with changed pixels anywhere on the output (its window or a popup). `--expect-popup` asserts that a popup of the application is shown, and reports how far it extends beyond the window on each edge; it fails if the popup stays inside. The same descriptor and scene-resource checks apply at the end. `tools/rn-host-spike/build.sh` uses it to run the native Bloom host in a window.

```json
{"mode":"offscreen-cpu","drm":false,"gpu":false,"bloom":false,"clients":2,"frames":5,"popup_beyond_parent_edges":4,"menu_row_pressed_over_other_client":true,"outside_presses_delivered":0,"descriptors_settled":true,"snapshots":["..."],"status":"passed"}
```

With `--kms CARD`, every composed frame is shown on the card's first connected output through DRM/KMS. The compositor hands it over and goes on serving, and the frame completes at the kernel's flip time, one frame on the display at a time (feedback timestamps are then `Monotonic`, not synthetic). The summary reports the mode, the frames shown, the handover-to-flip times and the flips later than one refresh. It needs DRM master: run it as root on a virtual terminal with no login, one past logind's `NAutoVTs` such as 8 (a terminal with a getty is refused). It takes that terminal (`oxyos-vt`): the console draws nothing over the frames, and on a switch to another terminal the compositor releases the display and the devices; frames then complete without being shown. On return it modesets again, turning off planes another session left on the CRTC, and shows the frame again. With `--input`, the console's keyboard is off and Ctrl+Alt+Fn (the keymap's `XF86Switch_VT_n`) switches terminals without reaching any application. The run fails if the console counted any typed line, and the summary reports what it counted (`console_input_bytes`). `--switch-terminal N` goes to terminal N and back through the devices. With `--seat` as well, the compositor runs as the user of the caller's logind session instead of as root. The card and the input devices come from logind, logind owns the terminal, and the compositor follows logind's pauses and resumes ([ADR 0006](./adr/0006-seat)). The session must be on a seat and shown. With `--gpu` as well, the display is composed on the Vulkan device straight into DMA-BUF scanout buffers, and the summary says so (`"composition":"vulkan-dma-buf"`).

With `--input`, the seat's devices drive the scene through libinput, with the keymap of `--layout` (an XKB layout, `us` by default): the pointer, buttons, wheel and keys, and the text keys type. With `--uinput`, the director's steps go through the kernel instead of into the scene: it creates a virtual wheel mouse (absolute, three buttons) and a keyboard, and points, scrolls, drags and types with them, so each step reaches the scene through libinput as a real device's does. The compositor reads each event as it is sent, as its event loop would from a person: a whole step sent at once can overflow the 64 events the kernel holds for each reader. A character no keys type on the layout is committed as text instead, and the summary counts it per step (`typed_as_text`). A dead key and its vowel count as keys ('ó' on `es`). The compositor composes with the compose table of the locale in the environment (`LC_ALL`, `LC_CTYPE`, `LANG`), and the trace says whether it found one. The image ships the UTF-8 compose tables where xkbcommon looks for them ([Base image configuration](./iso-build)), and the tests read those (`XLOCALEDIR`). While a sequence waits, the field shows it as the composition (a dead key as its accent, as GTK shows it). What it composes replaces the composition, and the keys the table takes reach no application as keys. Without a table, dead keys type nothing. `regress.py --uinput` types with the layout its scenario names. `--commit TEXT` is an input method's committed text, which no keyboard types, so it is the same on both paths. Run it as root with `--kms`, so the compositor takes its terminal and the console's keyboard is off.

With `--gpu-only`, frames are composed on the Vulkan device alone, with no CPU reference. On a display, each frame is composed once, straight into the scanout buffer, with a copy kept in the same submission. The director reads that copy back after the flip, once the clients have heard the frame was shown, so its checks delay neither the frame nor the clients. This measures the compositor as it would run. On a display, every step reports `flip_latency_ms`: from input to the kernel's flip of the first frame showing the answer. The summary reports each frame's composition time (`compose_ms_*`) and the device's (`device_ms_median`, from GPU timestamps), with `--gpu-only` the readback's (`readback_ms_median`), and a frame's parts: reading the clients' buffers (`read_ms_median`), the host's copy into the upload buffer and its wait from submission to fence, and the device's time before and after the composition pass. Frames compose only the output's damage ([ADR 0005](./adr/0005-damage)); the Bloom host draws only what changed, and `regress.py --check-damage` has it draw every frame whole too, failing the run on any difference, and the summary reports the fraction of the output each frame damages (`damaged_fraction_median`).

With `--outputs WxH[@SCALE],...` (`1280x720,1920x1080@1.5`), the session has those outputs, of those pixels at those scales, arranged as the session arranges its displays: left to right, top-aligned, the first the primary ([ADR 0018](./adr/0018-several-displays)). Each is composed on its own, a shell started with `--shell` runs on each, the director's points are in the global space, and each output's frame is written beside the primary's (`launch-N.output-ID.png`). With `--kms` it still shows one output.

With `--gpu`, every composed frame is also composed on the best Vulkan device present and must match the CPU composition byte for byte. Any difference fails the run, and the summary names the device and its kind. On a machine without a Vulkan driver, Mesa's lavapipe (`mesa-vulkan-drivers`, a CPU device) runs it: that proves the Vulkan path and the semantics, not a GPU.

Without `--kms` and `--input`, this is the headless development path: no DRM/KMS output, scripted input injected into the scene, and synthetic feedback timestamps. With them it is still a development fixture with one application and scripted steps, not a session. The test clients draw flat rectangles.

## The session

`oxyos-session [--greeter] [--layout LAYOUT] [--pointer FILE.cur|SCHEME[,SIZE]] [--shell PROGRAM,ARG...] [--reader PROGRAM [--reader-on]] [-- COMMAND [ARGS]...]` runs the compositor on the seat of the caller's logind session, as its user: start it from a login on a text terminal, or let the login program start it ([ADR 0020](./adr/0020-oxy-account-login)).
- **Displays** ([ADR 0018](./adr/0018-several-displays)): every connected output of the first card with one, each on a CRTC of its own at its native resolution and the fastest refresh it offers there that the card takes (120 or 144 Hz where it has them), every frame paced by it: side by side, left to right, top-aligned, the built-in panel first (the primary), each at a scale from its density (its pixels per inch over 135 for a built-in panel, 110 for a monitor, to the nearest quarter, from 1 to 3; the ThinkPad's 14-inch panel is 1.25). Each composes and flips on its own, at its own refresh. A monitor plugged in comes at the right end (the card's hotplug uevents); one unplugged goes, its windows to the primary and those right of it moving left.
- **Composition:** on the GPU straight into the display's scanout buffers where Vulkan exports DMA-BUF, otherwise on the CPU, only what changed ([ADR 0005](./adr/0005-damage)). Frames are never read back, and no per-frame measurement is kept.
- **Input:** the seat's devices through logind and libinput, with the system's keyboard (`/etc/default/keyboard`: its layout, variant and options, as the console and a login use them, so the lock takes the password typed there) or `--layout`'s, and its dead keys.
- **The pointer:** it moves within the outputs, crossing where they meet, and is shown on the cursor plane of the display it is over, in the shape the surface under it asks for (`SetPointerShape`; the move shape while the compositor moves a window). Its images are the display's own arrow, or a Windows cursor file's or cursor scheme folder's (`--pointer`: each role its `Install.inf` names, the 32-bit image closest to SIZE pixels at the display's scale, 32 by default; an animated cursor's (`.ani`) steps, each its frame for its duration, looping with the clock). Moving the pointer, changing its shape or an animated cursor's next step commits the frame already shown again, with no composition. A display without a cursor plane shows no pointer, and the session says so.
- **Switching:** Ctrl+Alt+Fn switches terminals, and logind's switches are followed ([ADR 0006](./adr/0006-seat)).
- **The lock** ([ADR 0010](./adr/0010-lock-screen)): Ctrl+Super+Q (the key that types `q`), the shell's `LockSession`, logind's `Lock` (`loginctl lock-session`) and the machine about to sleep lock the session at once: only lock surfaces, or the compositor's covers, are shown and reached. Sleep waits for the lock to be on screen (a logind delay inhibitor). A lock surface's password is checked by PAM under the service `oxyos` (`tools/oxyos-session/pam.d/oxyos`, installed as `/etc/pam.d/oxyos`: the system's `common-auth` and `common-account`) as the session's user, off the compositor's thread; only an acceptance unlocks. logind's `Unlock` is not followed.
- **Applications:** the shell's dock and launcher list the session's registry and start its applications ([ADR 0013](./adr/0013-launching-applications)): the session starts an id only if the registry lists it, a Bloom application with the Bloom host `OXYOS_BLOOM_HOST` names and the bundle `OXYOS_BLOOM_BUNDLE` names, and stops them when it ends.
- **The screen reader** ([ADR 0014](./adr/0014-screen-reader)): with `--reader PROGRAM` (or `OXYOS_READER`), Super+F5 starts it and stops it again; `--reader-on` starts it with the session. It runs on a socket of its own that grants `accessibility` and `screen_reader`, so the compositor sends its keys (Ctrl+Alt with Right, Left or Space) to it alone. For OxyOS's reader: `--reader oxyos-reader`, which speaks with eSpeak NG.
- **The application:** COMMAND runs with `OXYOS_COMPOSITOR_SOCKET` naming the compositor's socket, in `XDG_RUNTIME_DIR`. With a shell it may be left out: the session is then the desktop alone, and lasts as long as its shell.
- **The start:** the Oxy mark, white on black, from the session's first frame until its shell is on screen; it fades out over the shell ([ADR 0011](./adr/0011-transitions)).
- **The shell:** with `--shell`, the session's shell ([ADR 0009](./adr/0009-session-shell)) starts first, one on each output ([ADR 0018](./adr/0018-several-displays)): PROGRAM with its ARGs and `--shell OUTPUT`, on a socket of its own that grants `shell` and `lock` (it is the lock screen as well). Each output has the top bar; the primary alone has the dock. An output plugged in gets a shell of its own, and one unplugged has its shell stopped. A shell that exits while the session is locked is started again, at most once a second; the session stays locked meanwhile. COMMAND starts once the shells' panels have set the work areas, so its window is placed between them. For the Bloom host: `--shell HOST,BUNDLE,OxyOSShell`.
- **The end:** the session ends when COMMAND or the shell exits, on Ctrl+Alt+Backspace (XKB's `terminate:ctrl_alt_bksp`), or on SIGINT or SIGTERM. The application is asked to stop (SIGTERM, then SIGKILL after two seconds), and the display, devices and seat are given back.
- **The login screen** (`--greeter`, [ADR 0020](./adr/0020-oxy-account-login)): as the login program runs it, in a logind session of class `greeter` as its own user. Locked from the start, its shell (`--shell HOST,BUNDLE,OxyOSLogin`) the one client and its lock surfaces all there is to see; it waits for them, not panels. A lock surface's password, for the account it names (`AuthenticateAccount`), goes to the login program on `OXYOS_LOGIN_SOCKET` (`/run/oxyos/login/greeter`), never to PAM from here; accepted, the splash is shown and the login screen ends. It launches nothing, holds no sleep, and tells the login program when its first frame is on a display.

It is a session program, not yet a desktop. It runs its shell, an application, or both. Locked, the shell draws the lock screen ([ADR 0010](./adr/0010-lock-screen)); until it has, and if it is gone, the compositor's covers are shown. The login program (`tools/oxyos-login`) starts it on a seat with a person's Oxy account ([ADR 0020](./adr/0020-oxy-account-login)), not yet verified on hardware. It is not in the image: the image rules require boot acceptance tests and a package audit first ([Base image configuration](./iso-build)). Started by a `Type=notify` unit, it sends `READY=1` once its first frame has flipped, so the unit can let the boot logo go with the same pixels on screen ([ADR 0017](./adr/0017-boot-logo)).

## Core state transitions

`Presentation::submit` validates current configure, dimensions, increasing sequence and buffer availability before mutation. One replacement is queued; superseding it returns its metadata so a backend can retire that resource. `begin_present` moves the queue to an in-flight slot. Only `complete_present` updates displayed content and returns the previous metadata. `retry_present` retains existing displayed content, retries the current submission or yields to a newer valid queued frame.

The caller must establish GPU readiness before begin and actual output completion before complete. Returning metadata is not a GPU fence or permission to reuse a buffer still consumed elsewhere. The `Scene` retires every held buffer of a destroyed or dismissed surface, deferring releases requested during an in-flight frame to `end_frame`; it still knows nothing about GPU fences. Each output's frame may be in flight on its own (`begin_frame_on`, `end_frame_on`, [ADR 0018](./adr/0018-several-displays)): a release waits for the frames in flight that may read the buffer, those of the outputs the surface is shown on.

## Scope and next gate

Implemented as development paths, measured on hardware ([ADR 0004](./adr/0004-gpu-composition)): Vulkan composition, DRM/KMS output with DMA-BUF scanout, and device input through libinput, all driven by the `oxyos-offscreen` fixture with the Bloom host. Not implemented: a session process (logind or seatd seat management instead of root, the terminal and DRM taken through the session), client buffer import (DMA-BUF from applications), explicit synchronization, a secure session and a bootable image. The session locks and unlocks through PAM, with the shell's lock screen ([ADR 0010](./adr/0010-lock-screen)). No empty renderer/service crates or success-returning stubs are included.

Next gate: implement and measure the first hardware render/import/present path and the Bloom host feasibility sample described in the architecture and audit documents. The image must not turn this probe into the session executable ([Base image configuration](./iso-build)).
