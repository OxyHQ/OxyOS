# Performance

What a person feels on OxyOS (a window following the hand, a list scrolling, an application
opening, the machine silent when nothing happens) is measured here, not estimated: by a harness
anyone can run with one command, on the development compositor, and read-only on a real
session. The numbers below are from 30 October 2026; the ThinkPad's own, every part with the GPU
composing and the hosts drawing on it, are from 6 November 2026 ([below](#every-part-on-the-thinkpads-gpu)).

## Running it

```sh
python3 tools/rn-host-spike/perf.py --offscreen target/release/oxyos-offscreen \
  --runtimes WORK/runtimes --packages WORK/packages [--out DIR] [--runs 3] [--gpu-only] [--check] \
  [interactions] [responses] [shell] [cold-start] [idle] [memory] [refresh] [genie]
python3 tools/rn-host-spike/perf.py --offscreen target/release/oxyos-offscreen [--runs 3] [--check] search
```

It runs regression scenarios through `regress.py` (every step's expected result is still checked)
and writes `perf.json` and the tables below. `--gpu-only` composes on the Vulkan device instead
of the CPU: the GPU that drives the machine's displays (lavapipe where none does), which the
compositor then names to the hosts, so they draw on it too, as in a session (ADR 0031, decision
14); without it the compositor composes on the CPU and names no GPU, and the hosts' GPU painter is
lavapipe. Whatever XDG directories a scenario gives, the hosts and the compositor find the machine's
Vulkan drivers (`regress.py` names their folders in `VK_ADD_DRIVER_FILES`), and each packaged
application's registry entry is written where its package is (`oxyos-pack`, beside the offscreen
compositor), so packages built on one machine run on another. `--check` fails when a budget is
exceeded:

- every frame's work fits a refresh of the display it runs on at the 95th percentile, for the
  compositor and for each host: 16.7 ms at 60 Hz, 8.3 at 120 (the scenario's primary output's
  refresh, `regress.py`'s `display_hz`; 60 Hz for one given none);
- an application or the shell doing nothing wakes at most once a second and uses at most 0.1 %
  of a core;
- an application's first frame comes within half a second of its start, and its first frame
  showing its text within a quarter of a second;
- each host's memory, idle beside the others, within its budget (`MEMORY_BUDGETS`: its footprint
  and its PSS; [Memory side by side](#memory-side-by-side), below);
- every budget on time a scenario states for a step: a response's `latency_ms`, `js_work`'s
  JavaScript and `resize_work`'s frames. Each run checks what its steps do and enforces no time
  (`regress.py --collect`); `perf.py` measures each budget in every run and judges it over them,
  at the median of the runs' values, or at the percentile it states (`js_ms_p95_max`, the 95th of
  every run's frames pooled), and names the runs that were over it ("runs over it" in the budgets'
  table, "slow:" in what `--check` says), so one slow run is seen and does not decide.

`responses` needs packages built with `DROPSEA_DIR` ([Expo applications from their own
checkout](./react-native-android-adaptation#expo-applications-from-their-own-checkout)).

**JavaScript's profile.** With `OXYOS_HOST_JS_PROFILE=FILE` in a Bloom host's environment
(regress.py and perf.py pass theirs on), Hermes' own sampling profiler records the application's
JavaScript, 1000 samples a second (`OXYOS_HOST_JS_PROFILE_HZ` changes it), and the host writes
the profile to FILE as it ends: a Chrome trace (`traceEvents`, `samples`, `stackFrames`) that
Chrome's DevTools (Performance, *Load profile*), Perfetto and speedscope open. Each frame is named
by its function and its line and column in the bundle's source: an application's package keeps
it (`bundle/index.js`); the probes' bundle (`bundle.mjs` with `HERMESC`) deletes it once Hermes
compiled it, and building the same bundle without `HERMESC` writes it again, identical. FILE may
name a directory (a path ending in `/`, or one that exists), as `OXYOS_HOST_REPORT` may: every host
then writes its own, `<application>-<pid>.cpuprofile.json`, so a scenario with the shell profiles
the shell and the application side by side. A sample is taken by interrupting the JavaScript
thread, so a profiled host turns more often than it would: its timings are its own.

```sh
OXYOS_HOST_JS_PROFILE=$PWD/dropsea-profile.json python3 tools/rn-host-spike/regress.py \
  tools/rn-host-spike/scenarios/perf-dropsea.json --offscreen ... --runtimes ... --packages ...
```

## Reading the session's log

A session writes what is slow to its log as it happens, so a machine that feels slow says why
without anyone running a tool on it. On the ThinkPad the log is `~/oxyos-validation/probar.log`
(the session's stderr, its applications' with it). Nothing needs turning on; each line costs a
few clock reads a turn, and while nothing happens nothing is written.

**The compositor** writes a turn whose work took longer than a refresh of the fastest display, at
most once a second (`[compositor] a turn worked 38.4 ms: before its wait …, the devices …, the
clients …, the frame … (uploading …, waiting for the GPU …), events …`), and every ten seconds
in which the GPU composed frames, how long they took (`[compositor] the GPU composed N frames in
the last 10 s: … median, … at the 95th percentile, … at most`).

**Each Bloom host** (an application, the shell, the login screen) writes, named by the
application's id (else its module), lines of five kinds (`tools/rn-host-spike/frame-diagnostics.h`):

```text
[host so.oxy.frameprobe] a frame after pointer.press took 127.4 ms, 7 dropped (a refresh is 16.7 ms): events 0.6,
  JavaScript 126.2 (commits 0.2, of which Yoga layout 0.2 and text 0.0), animation 0.1, mount 0.0, drawing 0.2,
  presenting 0.2 from the CPU, other 0.1; of it on the CPU 127.0 (JavaScript 125.9), blocked 0.2 (JavaScript 0.1),
  preempted 0.2; waiting for the compositor 0.0; 2 turns; input to present 127.8 ms
[host so.oxy.frameprobe] in the last 10.0 s: 91 frames, their work 3.5 ms median, 8.5 at the 95th percentile,
  123.3 at most; input to present 129.6 ms median, 129.6 at the 95th percentile (2 inputs); 1 slow, 7 dropped
  (a refresh is 16.7 ms)
[host so.oxy.dropsea] a resize to 1102x680: its frame presented 104.5 ms after the configure (laying it out 0.8,
  settling 65.8, cut short at a refresh; the frame's work 104.6, waiting for the compositor 0.0)
[host so.oxy.dropsea] a live resize: 6 frames for 6 configures over 712 ms; configure to frame 104.5 ms median,
  187.6 at most; laying out 0.8 ms median, 1.8 at most; 6 settles cut short at a refresh
[host so.oxy.dropsea] zoom (to fill the work area): its configure 47.9 ms after it was asked, its frame presented 472.9 ms after
```

(each is one line in the log; these from `frame-diagnostics.json` and `dropsea-window.json` on the
development compositor, which draws from the CPU). How to read them:

- **A frame's work** is everything the host's loop did since the frame before, its sleeping left
  out: each moment is charged to one part. *events*: handling the compositor's events (a key's
  menu shortcut runs JavaScript there). *JavaScript*: React's handlers, render and commits, and the
  callbacks of timers and requestAnimationFrame; of it, *commits* is Fabric's commits as their
  telemetry has them, *Yoga layout* their layout and *text* the text measured in it.
  *animation*: Animated's native driver, worklets and Reanimated, a fling, gesture handlers.
  *mount*: applying a commit to the host's tree. *drawing*: the damage and the painter recording
  (on the GPU) or rasterizing (on the CPU) the frame. *presenting*: handing it to the compositor,
  on the GPU with `sync`, the wait for its buffer, or from the CPU (copying it into shared memory).
  *other*: the rest (images, accessibility, popups' placement). *Of it*: the same work by the
  loop thread's own clocks (below, *Wall time and CPU time*): *on the CPU*, and of that
  *JavaScript*'s; *blocked*, the thread asleep in the middle of its work, waiting for another
  thread, a lock, a file (and of that *JavaScript*'s); *preempted*, the thread ready to run while
  another had its CPU. *waiting for the compositor*: the time the frame was ready but the one
  before it was not yet answered, which is not work; *turns*, the loop's turns it took.
- **A frame is slow** when its work (by the wall clock: what the person waited), plus any wait
  for the compositor beyond one refresh (a frame in flight is answered within one), is longer
  than a refresh of its window's display:
  16.7 ms at 60 Hz, 8.3 at 120. Its *dropped* are the refreshes it missed. The line names what
  started the work: an input (`pointer.press`, `key`, `scroll`, `touch`, `text input`, …), *a
  resize*, *an animation frame*, *a timer*, *data arriving*, *an image arriving*, *the first
  frame*, or *JavaScript* (its own work: a promise, an event emitted the turn before). Work that
  ends without a frame (an input whose answer changed nothing visible) is said as *handling … (no
  frame)*. At most one slow line a second; the next says how many went unsaid.
- **Input to present** is from the earliest input since the frame before, by its device's time
  (libinput's), to the frame handed to the compositor: what the person waited, the compositor's
  composition and the display's flip not included. (During an animation, an input that arrives as
  a frame is drawn counts toward that frame, though its answer is in the next.)
- **The summary** comes every 10 s while the window draws: its frames, their work's median, 95th
  percentile and most, the latency from input, how many were slow and the refreshes dropped.
  Nothing is written while the window is idle; a host that ends writes the frames since the last.
- **A resize** is from the configure that changed the window's size (as received) to the frame
  presented for it: *laying it out* (Fabric's commit with the new size), *settling* (the wait
  for JavaScript's own layout at that size, up to a refresh: *cut short at a refresh* when the
  application was still laying out). The first of a live resize is written as it is presented,
  then one line when the edges stop (no frame for half a second).
- **The window's operations**: a zoom from the request to the configure that zoomed it and to the
  frame presented at the new size; a minimize to the window losing its activation; a close (the
  application's own, or the session's: the dock, the switcher) to the loop leaving and the
  process's teardown. One not answered within 3 s is said too.

What to look for: a slow frame whose *JavaScript* dominates is the application's own work (its
JavaScript profile, above, says which functions), unless most of it was *preempted* (the machine
busy with something else) or *blocked* (JavaScript waiting for another thread or a file);
*drawing* or *presenting* is the host's painter (on the GPU, a large *sync* is the GPU being slow
or busy); a large *waiting for the compositor*
with little work is the compositor not answering in time (its own slow turns, above, say why);
*input to present* far above the frame's work is the host busy with something else when the
input came. A resize whose *settling* is cut short at every size is an application laying itself
out several times per size.

**Recording every application at once.** `OXYOS_HOST_REPORT` (the host's report, `report.h`) may
name a directory (a path ending in `/`, or one that exists): every host then writes its own,
`<application id>-<pid>.jsonl`, the shell's and every application's side by side, each with its
frames' `timing` lines (the parts above, as numbers), its log lines (`log`) and its summaries
(`timing_summary`). In the session's environment (`OXYOS_HOST_REPORT=$HOME/oxyos-validation/reports/`
before `probar.sh` starts it), a profiling run records every application without any other
change. A file path is one host's report, as before (`regress.py`'s).

**Checked.** `scenarios/frame-diagnostics.json` (`sample/FrameProbe.tsx`) makes frames fast and
slow: presses answered at once write no slow line, and 90 frames of requestAnimationFrame stay
within a refresh; a press whose JavaScript holds the thread 120 ms writes one, its JavaScript at
least 100 ms and its refreshes dropped; three within a second write one, and the next says the
two unsaid; the idle window writes one summary, then nothing. Every run of every scenario also
checks that each line a host's diagnostics wrote is in the log, whole; that a frame is said to be
slow exactly when its work (and its wait beyond a refresh) passes a refresh, so a fast frame never
is, however loaded the machine; that a slow line names the work its frame's `timing` line has;
that each part's wall time is exactly its time on the CPU, blocked and preempted; and that each
summary's numbers are those of the frames since the summary before (`regress.py`,
`check_diagnostics`).

### Wall time and CPU time

Every part of a frame's work is measured with two clocks (`thread-clock.h`), and the two answer
different questions:

- **The wall clock** (`CLOCK_MONOTONIC`) is what a person waits for: a frame's work against a
  refresh, input to present, a resize's or a zoom's frame, an application's first frame, a
  response's latency. Every budget on latency or a deadline is by the wall clock, because
  whatever lengthens it, the machine's load among it, is felt.
- **The loop thread's CPU clock** (`CLOCK_THREAD_CPUTIME_ID`) is the time the host's thread ran:
  JavaScript, with the Yoga layout and the text measuring it runs on the same thread, and every
  native part. Time the thread was scheduled out, or asleep waiting for something, is not in it.
  Budgets on how fast JavaScript does its work (`regress.py`'s `js_work.js_ms_max` and
  `resize_work`'s `js_ms_p95_max`, `perf.py`'s shell budgets) are by it, and are held only on a
  `perf.py` run (below).

The rest of a part's wall time is not lost: it is either *preempted* (the thread ready while
another had its CPU, the thread's `run_delay` in `/proc/thread-self/schedstat`) or *blocked* (the
thread asleep before its work was done: waiting for another thread, such as Hermes' collector or a
painter, for a lock, a file, the compositor's answer). What another thread does while the loop
waits for it is the loop's *blocked*, in the part that waited, and `js_work` holds JavaScript's
blocked time to a bound of its own (`js_blocked_ms_max`): nothing that blocks the host's thread
becomes invisible because its budget is on the CPU. A part's wall time is exactly the three
(`check_diagnostics` checks it in every scenario). A sample is two system calls (the CPU clock
and a read of the schedstat), under a microsecond each, at each change of part.

**What CPU time does not remove: a slower CPU.** The same work takes longer on a core shared with a
busy hyperthread, on an efficiency core, at a lower clock, or on a virtual CPU the hypervisor is
running something else on, and the thread's CPU clock counts all of it. On the development machine
(WSL2 on an i9-14900K, 8 performance cores with hyperthreads and 16 efficiency cores, no hardware
counters in the guest) that is the whole of what load does to the gate's scenarios, which run in a
scope weighted far above everything else (`CPUWeight=10000`), so they are hardly ever preempted.
`shell-events.json`, 20 runs each on 3 November 2026, before and after the CPU clock interleaved,
with `CPUWeight=10000` as the deploy runs it: the most JavaScript one piece of the shell's work ran
on entering the dock (its budget is 4 ms), and the most any piece of the five budgeted steps was
preempted or blocked, in ms:

| load | before (wall) | after: on the CPU | preempted | blocked | passed, before / after |
|---|---|---|---|---|---|
| quiet (load 1–9) | 3.1–5.2, median 3.3 | 3.0–4.0, median 3.2 | 0 | 0 | 17 / 18 of 20 |
| a busy loop on each of the 32 CPUs | 5.2–13.2, median 5.9 | 5.3–9.4, median 5.5 | ≤ 0.8 | 0 | 0 / 0 |
| other sessions (load 28–55) | 3.2–9.0, median 7.6 | 3.2–16.9, median 7.5 | ≤ 0.9 | ≤ 0.3 | 3 / 1 |
| both | 5.5–11.8, median 6.8 | 5.4–13.7, median 6.1 | ≤ 0.3 | ≤ 0.02 | 0 / 0 |

A fixed loop timed the same way takes 9.2 ms by the CPU clock at the median on a lightly loaded
machine, and 13–22 ms with a busy loop on every CPU: the work is the same, the CPU is slower. A
budget on how much JavaScript does that a loaded machine cannot move needs a count of work rather
than a time: instructions retired (a hardware counter, `perf_event_open`; none in a WSL2 guest) or
what React rendered, which is what the gate now holds (below).

### What a step re-renders

Whether a step does what it claims, rendering what shows its change and nothing else, is a count,
not a time: the same on any machine, however loaded. Each host's report has a `react_render` line
for every commit of React's that rendered a component (`report.h`): where each re-render began (a
component whose nearest component above did not render: its state, a context or a store it reads
changed), how many components it rendered in all and which, read from React's own fibers as its
DevTools read them (the PerformedWork flag React sets on a component whose render ran, and a
subtree whose child is the one before not reconciled at all). A scenario's step holds them with
`renders`: `tops`, exactly where the step's re-renders began ([] for none), and `components_max`,
the most components they may render in all; a regression that renders the dock or the top bar
again adds one of them, or their count, whatever the machine. `each_minute` names what the wall
clock's minute turning renders (the shell's clock), not counted in the two seconds after a minute
began.

`shell-events.json` holds the shell so (`in_shell`): another window pressed, zoomed and restored
renders no component (the windows' sizes are the overview's alone, `useWindowSizes`, so a window
resized renders the overview when it is open and nothing while it is closed); the pointer entering
the dock's first icon renders the icon and its button (`DockIcon`, `ButtonComponent`) and the
tooltip (`PopupSurface`, its text `CssInterop.DisplayFaceText`), 37 components; moving over it,
none; leaving it, the icon and its button again, 16. Each step also has a backstop on its
JavaScript by the wall clock, two refreshes at 60 Hz (`js_work.js_wall_ms_max`: 33 ms), for a gross
regression only: ten times the hover's quiet median (3.2 ms) and fifty times a window change's,
twice the most the heaviest load measured made of it (16.9 ms).

Counting is done only where it is checked: a host walks React's commits when its environment has
`OXYOS_HOST_REPORT_RENDERS=1` beside `OXYOS_HOST_REPORT`, which `regress.py` sets for a scenario
holding `renders` alone, and never with `--no-render-counts`, which `perf.py` always passes; a
session has neither. The walk costs about 0.03 ms a commit, but its few allocations move where
Hermes' young collections fall: with it, a collection of 1.5 ms fell in the dock's hover, which
measured 5.1 ms of JavaScript instead of 3.3. Without it, a host counts React's commits alone
(`react_commits`), allocating nothing.

Budgets on speed stay where a claim is about speed (`perf-dropsea-home.json`'s JavaScript per
step, `window-resize.json`'s and `perf-dropsea-resize.json`'s per frame, the shell's in
`perf.py`, and the display's rate: how many frames fit in a motion and how far apart they come,
`refresh-*.json`'s, `perf.py refresh`), and only `perf.py --check` holds them, over its runs (above, *Running it*), on the
hardware they describe, the ThinkPad's: the deploy gate runs `regress.py` without them, so a machine
loaded by other builds fails no budget on speed, and holds what every step must do. Of the
display's rate it holds what no load moves: a motion in more than one frame, no more frames than
a claim allows, requestAnimationFrame never faster than its interval, and on a paced output
(`check_pacing`) the window told the display's refresh before its first frame and the client's
frames following on one by one, each answered once by the compositor, in order.
`regress.py --speed-budgets` holds them in one run, for a look at one machine.

## Method

**Interactions.** Five scenarios (in `tools/rn-host-spike/scenarios/`), each run three times and
pooled:

| interaction | scenario | what happens |
|---|---|---|
| window drag | `perf-window-drag.json` | WindowProbe's title area dragged 250 px at a mouse's 125 Hz (`drag_paced`): the compositor moves the window, the application draws nothing |
| window drag at 1.25 | `perf-window-drag-scaled.json` | the same beside the shell on a 1600×1000 output at 1.25, the ThinkPad's scale |
| live resize | `window-resize.json` | the Inbox's edges dragged at 125 Hz: one configure in flight, the host lays out and draws every size |
| Dropsea live resize | `perf-dropsea-resize.json`, steps 3–4 | Dropsea's right edge dragged 300 px in and out at 125 Hz, then the green bubble zooming it and back |
| zoom | `windows.json`, steps 3–4 | the green bubble: the window's frame animated to the work area and back (a compositor transition) |
| window views | `shell-thumbnails.json`, step 1 | the overview opening, Allo's window drawn live in its card ([ADR 0022](./adr/0022-window-views)) |
| Settings scroll | `perf-settings-scroll.json` | Settings' sidebar scrolled 240 px down and back at a touchpad's 60 Hz (`scroll_paced`) |

For every frame the compositor composes, the director records when it started and how long
composing it took (`composed` in each step's record: gathering the scene, reading the clients'
buffers, composing, handing it over), and the part of it reading the clients' buffers. For every
frame a host presents, its report records the loop's work since its previous frame (`busy_ms`,
never its waiting) and the part of it running JavaScript (`js_ms`: React Native's runtime and
the worklets' UI runtime, so React's render, Fabric's commit and Yoga's layout), both by the wall
clock, and that JavaScript's time on the loop thread's CPU (`js_cpu_ms`) and blocked
(`js_blocked_ms`); the rest is native (mounting, drawing, presenting, the compositor's events). Paced steps (`drag_paced`,
`scroll_paced`) send each event when its time comes and compose the frame it wakes at once, as a
device's event wakes a session's turn.

"interval" is the time between consecutive frames composed while the input lasted, and "late"
counts intervals over one and a half refreshes. The development compositor has no display: on an
output given no refresh (these scenarios) nothing paces it, a frame is composed as soon as
something changes, and the interval is how fast the whole pipeline (input, host, compositor)
answers. An output given one (`--outputs 1280x720:120`, [ADR 0018](./adr/0018-several-displays),
decision 11) is paced as a display at it, each frame shown at its next vblank, and the host paces
its own frames by it: `refresh-120-windows.json` drags a window at 125 Hz with a frame composed
each 8.3 ms, `refresh-120-animations.json` runs requestAnimationFrame at 120 a second.

**Responses.** Dropsea used as a person uses it on the ThinkPad, in `perf-dropsea.json` (a 1280 × 800
window on a 1920 × 1200 output at 1) and `perf-dropsea-scaled.json` (at 1.25): a home like the
owner's (21 items, 27 in Downloads, pictures among them), Downloads selected and opened by a
double press, an item pressed, the arrow keys, the mouse moved across the icons at 125 Hz
(`move_paced`), the list view, a row pressed, a context menu at a secondary press and Escape,
back, and a place in the sidebar. Every step checks what React received, the selection and the
focus the assistive technology holds and the popups, not only pixels. For each input, the latency
from it to the first frame that changed (held to the scenario's budget, about four times what it
takes on this machine unloaded) and the application's host's work until the step settled (each
frame's `busy_ms`, summed) and the JavaScript in it. The steps that go to another place (Downloads
opened, back to the home, Documents from the sidebar) are also held to what React renders
(`renders.components_max`, above, *What a step re-renders*), which no load moves: on 7 November
2026 the press back crossed its 450 ms budget on a loaded gate (459 and 478 ms) because Dropsea's
sidebar drew all its rows, with their menus and drop targets, at every navigation (tags had added
seven), 636 of the 3038 components it rendered, and each list row drew views for tags it did not
have; with the sidebar's tree kept the same objects and empty tags drawing nothing
(OxyHQ/Dropsea#51), and a tree row drawn only when the selection moves onto or off it (Bloom
17.20.2), it renders 2503, the sidebar two rows. `perf-dropsea-home.json` is the same home with
360,000 files under `node_modules/` and `Oxy/` (the ThinkPad's), the window zoomed to the work
area at 1.25 (1536 × 930): the launch and the press back to the home held to a budget of their
JavaScript (`js_work.js_ms_max`), half a minute left alone to a refresh in every
frame, and files another program adds to the home (`home.later` with `after_ms`), each heard by
the watch and listed again, to a budget of their own.

**The shell** (`perf.py shell`). What the session's shell pays for an event, in `shell-events.json`
on the ThinkPad's display (1600 × 1000 at 1.25): another window pressed, zoomed by its green
bubble and restored (each changes what the shell knows of that window and nothing it shows), and
the pointer entering the dock's first icon, moving over it and leaving. What each re-renders is
held by every run of the scenario (above, *What a step re-renders*); `perf.py` measures, for each,
the most JavaScript any one piece of the shell's work ran on the shell's CPU (its report's `timing`
lines: a frame's work, and work that drew none but ran JavaScript), and `--check` holds its median
to the scenario's `js_work` budget on speed, 2 ms for another window's change and 4 for the dock's
hover, and its time blocked to 1 ms.

**Cold start.** An application's process started by the compositor to its first frame on the
output, to its first frame showing its text (a window's first frame can be its background alone:
Settings' waits for its preferences), and the host's stages in between (its report's `stage`
lines): the process reaching `main`, Hermes' instance, Fabric's scheduler, the window configured,
the bundle evaluated, and React's first render, layout, mount and draw. Each run is left idle 2.5 s,
and the application's cache directory is kept from one run to the next (`regress.py --app-cache`),
as it is from its second launch on; its first launch ever is run first and said apart.

**Idle.** Each scenario with one step that waits nine seconds; two seconds after the
application's first frame, every process's CPU time (`/proc/PID/schedstat`) and context switches
(every thread's, `/proc/PID/task/*/status`) are sampled over five seconds. The development
compositor turns every 5 ms by design (its director's pace), so its idle numbers say nothing of
a session's. A session's are measured where it runs, read-only: `perf.py --check session` (no
`--offscreen`, `--runtimes` or `--packages`) finds this user's `oxyos-session` and the Bloom hosts it
started, samples every thread of each over 30 s while nothing happens on the machine, prints which
threads woke, and holds each process to the same budget (at most one wakeup a second and 0.1 % of a
core). It is not among the parts run by default: a person using the machine meanwhile is not idle.

**Memory.** Every process's resident memory while idle (anonymous, file-backed) and its peak
(`VmHWM`) over the run; and `perf.py memory` ([below](#memory-side-by-side)), each host's
footprint beside the others.

**Machine.** Intel Core i9-14900K (32 threads), Linux 6.18 under WSL2, shared with other work
(load average 9 to 22 during the runs): absolute numbers are this machine's, and a few
percent of noise. Composition is on the CPU (`compose_cpu`), the reference renderer; "Vulkan" is
Mesa's lavapipe, a software rasterizer, which shows the Vulkan path's costs on the host side but
not a GPU's.

## Results

### Interactions

Composed on the CPU, three runs pooled; "before" is `main` before the fixes below (one run).
Times in ms, p50 / p95; "work" is a host's loop's work for each frame it presented, "JS" the
part of it running JavaScript.

### JavaScript or native

Steady interactions are not JavaScript-bound. A live resize's frame is 6.8 ms of the host's work
at the median, 3.4 of it JavaScript (Fabric's commit of the new size and Yoga's layout); a scroll's
1.8 ms, 0.4 of it JavaScript; a zoom's 0.7, 0.3 of it. The worst frames were native: drawing (a
border ring visiting every pixel of the box it encloses: 19 ms of a 25 ms frame), composition
(every surface's pixels copied again, every frame) and the platform's glue (a frame loop running
60 times a second for nothing). What JavaScript does cost: a re-render of the whole layout, as the
Inbox's at its breakpoint from two panels to one (30–35 ms once, in a resize), and an
application's first render.

What changed (`memory.h`, `skia-gpu.h`, `oxyos_paint_trim`):

- **Transparent huge pages off for the host** (`prctl(PR_SET_THP_DISABLE)`). Debian's kernel
  backs anonymous memory with 2 MiB pages wherever it can (`enabled` is `always`) and khugepaged
  fills a 2 MiB range in once one of its pages is touched (`max_ptes_none` 511): a sparse heap
  (malloc's arenas, `[heap]`) became resident whole. 22 to 34 MiB of each host's anonymous memory
  on a fresh start; the session's shell, running five days, held 160 MiB of huge pages in 175 MiB
  of anonymous memory. The hosts' start is the same with them off (Settings' first frame with its
  text 166 ms with them, 165 without, the Inbox's 179 and 176, five runs each, `main`'s host).
- **malloc's mapping threshold fixed at 4 MiB** (`M_MMAP_THRESHOLD`). glibc raises its threshold
  to the size of each mapped buffer freed (up to 32 MiB), so after the wallpaper's decode every
  later large buffer stayed in its heap. With its thresholds fixed through glibc's tunables (at
  128 KiB, and two arenas) `main`'s shell held 15 MiB less on a fresh start, the other hosts the
  same; the host fixes the mapping threshold alone, at 4 MiB, so that a frame's scratch blocks stay
  in the heap rather than being mapped and faulted in at every frame, and its idle trim gives the
  heap's free pages back.
- **An idle window gives back what it keeps for frames in a row.** One second after the loop's
  last work (one wakeup, then none), the host frees the painter's GPU buffers the compositor
  released but the one each surface shows (a window keeps up to three while frames follow each
  other; each is 4 bytes a pixel), purges Skia's scratch textures (offscreen layers) and those not
  drawn for 30 s, and gives malloc's free pages back (`malloc_trim`); then writes its account. The
  next frame makes a buffer again, about half a millisecond, and copies it whole.
- **Skia's GPU cache bounded to the window**: three canvases of the largest one drawn, at least
  16 MiB, where Skia's default is 256 MiB; and its glyph atlases' pages at 2 MiB, not 4 and 8. The
  Inbox's GPU memory was 94 MiB, 46 to 58 with the idle trim alone, 26 with the bound: what Skia
  allocated past it while drawing its first frames had grown the driver's memory too.
- **Ganesh's compiled pipelines kept** in the application's cache directory (`skia/`, by the GPU,
  its driver and Skia's revision; Chrome and Flutter keep theirs so): each pipeline's SPIR-V and the
  driver's pipeline cache, written when the window is idle, never while a frame is drawn. With
  Mesa's own shader cache already warm it saves 2 to 5 ms of the first frame with text (Settings'
  drawing and presenting 15.5 ms on its first launch ever, 12.3 after), and the first drawing of
  anything an application draws again on a later launch.

**Held.** `perf.py memory --check` holds the sizes on the ThinkPad. Every run of
`scenarios/memory-idle.json`, the deploy gate's on any machine, holds the trim itself: Settings'
sidebar scrolled at 60 Hz, then left alone, the host's account written after its last frame, with

idle host wakes once for the trim: 0.2 wakeups a second over the five seconds sampled, 0.01 % of
a core (`perf.py idle`, within its budget of one a second and 0.1 %).

  a window dragged on a 1920 × 1200 desktop at 1.25 (shell, window, its shadow, the bars), the
  memory a frame moves goes from about 160 MB in 16 dispatches to 10 MB in one; a whole frame,
  from 64 to 21 MB. Byte for byte the CPU reference's (every Vulkan test, and scenarios with
  `--gpu`, which compare every frame). Lavapipe, a CPU, runs it about twice as slowly: its cost
  is arithmetic, not memory; a session never composes on it. The session now logs every ten
  seconds how long the GPU took to compose its frames (`[compositor] the GPU composed …`).

- **Dropsea's freezes (October 31).** On the ThinkPad Dropsea froze for 2 s at a press back to the

- **Dropsea (October 31).** Measured with `perf-dropsea*.json` and profiled natively (an outside

  - **Lines broke only at spaces**, so a file name without one was a line wider than its icon's

  - **The file service read the mount table for every call**: each path an application gave

## The host on the GPU

The Bloom host draws on the GPU where the compositor offers one ([ADR 0031](./adr/0031-gpu-buffers),
step 3). Measured with `perf.py --renderer cpu` and `--renderer gpu`, two runs each, in
`tools/gpu-vm` (16 vCPUs of this machine), on lavapipe: its "GPU" is the same CPU, shared with the
compositor and the host, so these numbers say what the host's own thread saves and what the GPU path
costs around it, never a GPU's speed. p50 / p95 in ms; "first" is the GPU painter's first version
(an operation per dispatch, a barrier after each), "now" with operations binned into tiles.

| interaction | host draw, CPU | host draw, GPU now | frame work, CPU | frame work, GPU first | frame work, GPU now |
|---|---|---|---|---|---|
| live resize | 2.70 / 5.97 | 0.63 / 0.94 | 10.14 / 14.17 | 36.66 / 401.7 | 16.71 / 23.72 |
| zoom | 0.18 / 0.36 | 0.12 / 0.25 | 2.02 / 15.15 | 8.36 / 20.6 | 4.62 / 22.84 |
| overview (the shell) | 0.11 / 6.92 | 0.03 / 0.64 | 2.24 / 13.1 | 6.2 / 45.1 | 1.2 / 10.63 |
| Settings scroll | 0.66 / 0.96 | 0.20 / 0.33 | 2.94 / 4.85 | 8.35 / 12.8 | 4.03 / 7.15 |

Where a live resize's present goes now (the host's report, `present` lines, median / p95 ms, every
frame a new size): the image made and exported 0.27 / 0.54, attached 0.05 / 0.13, its timeline
0.01 / 0.01, the old size's freed 0.17 / 0.51, the frame's operations recorded and submitted
0.05 / 0.12, and `sync` 6.81 / 10.30: lavapipe drawing the frame before its sync-file export returns.

- **The host's thread draws 3–20 times less.** It records operations, and the device works the
  pixels out.
- **A new size costs about 0.5 ms**: making, exporting and attaching an image, a timeline, and
  freeing the old size's. The protocol's buffer-is-the-configured-size rule is not what was slow.
- **What was slow was an operation per dispatch**: 138 dispatches behind full barriers for a
  resize's frame, 20 ms on lavapipe. Binned into tiles they are a few dispatches.
- **What remains here is lavapipe drawing**, on the CPU cores the host's frame shares, waited for by
  its sync-file export. A GPU draws on its own and its export returns at once: the ThinkPad says how
  much of the 16.7 ms that leaves.
- **Memory.** Each host holds 60–170 MiB more resident: the Vulkan driver and its heap of canvases.

## What remains

- **The Vulkan driver's own memory** is 6 to 16 MiB of each host's GPU memory, which it keeps once
  allocated (above, *Memory side by side*).
- **An application is not told that its window is hidden**: a minimized window gives back what an
  idle one does, and nothing more (its canvas, Hermes' heap). The compositor telling a client
  its window is out of sight would let it drop its canvas too.

- **Dropsea's own JavaScript is most of what a person waits for** (`perf-dropsea.json`: three
  quarters of the host's work in the list view, nine tenths in a selection). From its profile:
  - Its items view (`components/ItemsView.tsx`) is not compiled by the React Compiler: its two
    `PanResponder.create` calls in `useState` initializers read refs (`pointerType`, `dragging`,
    `bandStart`), which the compiler takes for reading them while rendering, so it leaves the
    whole component as it is; `BrowserProvider.tsx` neither (a computed key, `[familyOf(place)]`,
    in an object literal).
  - Every element styled with `className` renders twice when it mounts: react-native-css
    3.1.0-rc.0's `useNativeCss` (`src/native/react/useNativeCss.ts`, lines 112–120) drops its
    subscriptions in its state's initializer and, on mount, runs both its effects again, each a
    `setState`: about a third of the JavaScript in switching to the list view. Fixed upstream
    (nativewind/react-native-css#466, in its nightlies only); Oxy's applications take it with the
    next release candidate rather than pin a nightly (NativeWind 5.0.0-rc.0 requires exactly
    3.1.0-rc.0).
- **react-native-css re-evaluates media queries on every frame of a resize** (above, *A resize is
  native layout*): nativewind/react-native-css#550.
- **A W3C event's `timeStamp` is when the host handed it to React**, not when the hand moved:
  the protocol carries no time for input. Behind a slow frame, two presses keep their order but
  arrive closer together than they were made. Input events need the device's time (libinput's)
  from the compositor to the application.
- **The genie's mesh is the costliest layer** (4.7 ms of device time for a whole frame at
  1280 × 720, 0.57 of a 120 Hz refresh): each pixel searches the mesh's rows and filters its box.
- **A layout re-rendered whole costs 30–35 ms of JavaScript** (the Inbox at its breakpoint).
