# Performance

What a person feels on OxyOS (a window following the hand, a list scrolling, an application
opening, the machine silent when nothing happens) is measured here, not estimated: by a harness
anyone can run with one command, on the development compositor, and read-only on a real
session. The numbers below are from 30 October 2026.

## Running it

```sh
python3 tools/rn-host-spike/perf.py --offscreen target/release/oxyos-offscreen \
  --runtimes WORK/runtimes --packages WORK/packages [--out DIR] [--runs 3] [--gpu-only] [--check] \
  [interactions] [responses] [cold-start] [idle] [applications]
```

It runs regression scenarios through `regress.py` (every step's expected result is still checked)
and writes `perf.json` and the tables below. `--gpu-only` composes on the Vulkan device instead
of the CPU. `--check` fails when a budget is exceeded:

- every frame's work fits a refresh of the display it runs on at the 95th percentile, for the
  compositor and for each host: 16.7 ms at 60 Hz, 8.3 at 120 (the scenario's primary output's
  refresh, `regress.py`'s `display_hz`; 60 Hz for one given none);
- an application or the shell doing nothing wakes at most once a second and uses at most 0.1 %
  of a core;
- an application's first frame comes within half a second of its start;
- each of Stash's responses (`responses`, below) within its scenario's budget at the median.

`responses` needs packages built with `STASH_DIR` ([Expo applications from their own
checkout](./react-native-android-adaptation#expo-applications-from-their-own-checkout)).

**JavaScript's profile.** With `OXYOS_HOST_JS_PROFILE=FILE` in a Bloom host's environment
(regress.py and perf.py pass theirs on), Hermes' own sampling profiler records the application's
JavaScript, 1000 samples a second (`OXYOS_HOST_JS_PROFILE_HZ` changes it), and the host writes
the profile to FILE as it ends: a Chrome trace (`traceEvents`, `samples`, `stackFrames`) that
Chrome's DevTools (Performance, *Load profile*), Perfetto and speedscope open. Each frame is named
by its function and its line and column in the bundle's source: an application's package keeps
it (`bundle/index.js`); the probes' bundle (`bundle.mjs` with `HERMESC`) deletes it once Hermes
compiled it, and building the same bundle without `HERMESC` writes it again, identical. A sample is taken by interrupting the JavaScript thread, so a profiled host turns more
often than it would: its timings are its own.

```sh
OXYOS_HOST_JS_PROFILE=$PWD/stash-profile.json python3 tools/rn-host-spike/regress.py \
  tools/rn-host-spike/scenarios/perf-stash.json --offscreen ... --runtimes ... --packages ...
```

## Method

**Interactions.** Five scenarios (in `tools/rn-host-spike/scenarios/`), each run three times and
pooled:

| interaction | scenario | what happens |
|---|---|---|
| window drag | `perf-window-drag.json` | WindowProbe's title area dragged 250 px at a mouse's 125 Hz (`drag_paced`): the compositor moves the window, the application draws nothing |
| window drag at 1.25 | `perf-window-drag-scaled.json` | the same beside the shell on a 1600×1000 output at 1.25, the ThinkPad's scale |
| live resize | `window-resize.json` | the Inbox's edges dragged at 125 Hz: one configure in flight, the host lays out and draws every size |
| zoom | `windows.json`, steps 3–4 | the green bubble: the window's frame animated to the work area and back (a compositor transition) |
| window views | `shell-thumbnails.json`, step 1 | the overview opening, Allo's window drawn live in its card ([ADR 0022](./adr/0022-window-views)) |
| Settings scroll | `perf-settings-scroll.json` | Settings' sidebar scrolled 240 px down and back at a touchpad's 60 Hz (`scroll_paced`) |

For every frame the compositor composes, the director records when it started and how long
composing it took (`composed` in each step's record: gathering the scene, reading the clients'
buffers, composing, handing it over), and the part of it reading the clients' buffers. For every
frame a host presents, its report records the loop's work since its previous frame (`busy_ms`,
never its waiting) and the part of it running JavaScript (`js_ms`: React Native's runtime and
the worklets' UI runtime, so React's render, Fabric's commit and Yoga's layout); the rest is
native (mounting, drawing, presenting, the compositor's events). Paced steps (`drag_paced`,
`scroll_paced`) send each event when its time comes and compose the frame it wakes at once, as a
device's event wakes a session's turn.

"interval" is the time between consecutive frames composed while the input lasted, and "late"
counts intervals over one and a half refreshes. The development compositor has no display: on an
output given no refresh (these scenarios) nothing paces it, a frame is composed as soon as
something changes, and the interval is how fast the whole pipeline (input, host, compositor)
answers. An output given one (`--outputs 1280x720:120`, [ADR 0018](./adr/0018-several-displays),
decision 11) is paced as a display at it, each frame shown at its next vblank, and the host paces
its own frames by it: `refresh-120-windows.json` drags a window at 125 Hz with a frame composed
each 8.3 ms, `refresh-120-animations.json` runs requestAnimationFrame at 120 a second.

**Responses.** Stash used as a person uses it on the ThinkPad, in `perf-stash.json` (a 1280 × 800
window on a 1920 × 1200 output at 1) and `perf-stash-scaled.json` (at 1.25): a home like the
owner's (21 items, 27 in Downloads, pictures among them), Downloads selected and opened by a
double press, an item pressed, the arrow keys, the mouse moved across the icons at 125 Hz
(`move_paced`), the list view, a row pressed, a context menu at a secondary press and Escape,
back, and a place in the sidebar. Every step checks what React received, the selection and the
focus the assistive technology holds and the popups, not only pixels. For each input, the latency
from it to the first frame that changed (held to the scenario's budget, about four times what it
takes on this machine unloaded) and the application's host's work until the step settled (each
frame's `busy_ms`, summed) and the JavaScript in it.

**Cold start.** An application's process started by the compositor to its first frame on the
output, and the host's stages in between (its report's `stage` lines): the process reaching
`main`, Hermes' instance, Fabric's scheduler, the window configured, the bundle evaluated, and
React's first render, layout, mount and draw.

**Idle.** Each scenario with one step that waits nine seconds; two seconds after the
application's first frame, every process's CPU time (`/proc/PID/schedstat`) and context switches
(every thread's, `/proc/PID/task/*/status`) are sampled over five seconds. The development
compositor turns every 5 ms by design (its director's pace), so its idle numbers say nothing of
a session's; a session's are measured on the ThinkPad below.

**Memory.** Every process's resident memory while idle (anonymous, file-backed) and its peak
(`VmHWM`) over the run.

**Machine.** Intel Core i9-14900K (32 threads), Linux 6.18 under WSL2, shared with other work
(load average 9 to 22 during the runs): absolute numbers are this machine's, and a few
percent of noise. Composition is on the CPU (`compose_cpu`), the reference renderer; "Vulkan" is
Mesa's lavapipe, a software rasterizer, which shows the Vulkan path's costs on the host side but
not a GPU's.

3.1 of it reading clients), of which this fixture reads the whole frame back each time.

### JavaScript or native

Steady interactions are not JavaScript-bound. A live resize's frame is 6.8 ms of the host's work
at the median, 3.4 of it JavaScript (Fabric's commit of the new size and Yoga's layout); a scroll's
1.8 ms, 0.4 of it JavaScript; a zoom's 0.7, 0.3 of it. The worst frames were native: drawing (a
border ring visiting every pixel of the box it encloses: 19 ms of a 25 ms frame), composition
(every surface's pixels copied again, every frame) and the platform's glue (a frame loop running
60 times a second for nothing). What JavaScript does cost: a re-render of the whole layout, as the
Inbox's at its breakpoint from two panels to one (30–35 ms once, in a resize), and an
application's first render.

## The ThinkPad

Read-only, over ssh, on the owner's session (`oxyos-probar`: Intel Core i5-1240P, Iris Xe,
1920 × 1200 at 1.25, composing with Vulkan into the display's buffers), running `main` before
these fixes, idle over 60 s (`/proc` as above):

| process | CPU | wakeups/s | resident | peak |
|---|---|---|---|---|
| `oxyos-session` | 0.15 % | 21.4 | 98 MiB | 116 MiB |
| the shell | 2.29 % | 59.3 | 159 MiB | 251 MiB |

The session's main thread woke 4.5 times a second (its quarter-second wait); its controls' worker,
D-Bus connection and async threads 17 times (the 5 s status poll, by design). The shell's 59
wakeups and 2.3 % of a core were worklets' frame loop (below). An earlier session's shell held
195 MiB (peak 322 MiB). While a window was dragged, libinput logged "event processing lagging
behind by 21–47 ms": the compositor read its devices before waiting, so input that woke a turn
waited behind that turn's frame, and each frame copied every client's buffer (the shell's
1920 × 1200 background among them) before composing.

## What was fixed

- **The compositor read every client's whole buffer for every frame** (`Compositor::pixels`),
  though only a new frame has new pixels and the GPU path keeps what it uploaded: 3 ms a frame
  at 1600 × 1000 here, more at the ThinkPad's 1920 × 1200. A frame is now read once, when it is
  first shown, and shared after (`read_frame`); transitions draw their snapshots without copying.
  `perf-window-drag*.json` guard it: the compositor reads none of the application's pixels while
  its window is dragged (`drag.bytes_read_max`).
- **Input that woke a turn was read after the turn's frame.** The compositor's turn now reads the
  devices after it waits, so the frame it composes shows the input that woke it.
- **A session's turns were not measured.** A turn whose work takes longer than a refresh (of the
  fastest display) is now
  logged, at most once a second, with where the time went (`[compositor] a turn worked …`): the
  next run on the ThinkPad says what remains.
- **The CPU composition copied an opaque layer drawn 1:1 pixel by pixel through the general
  sampling** (and computed a shadow under its window): a window drag's frame at 1.25 went from
  18 to 5 ms in `compose_cpu`, pixel for pixel the same (Vulkan's output is compared with it).
- **The Bloom host woke 60 times a second doing nothing.** Worklets' UI-runtime frame loop asks
  for its next frame in every frame, and Reanimated runs its mappers in every frame: the host ran
  them whether or not anything could have changed. A frame now runs only when one is wanted: a
  frame callback was asked for (the UI runtime's `requestAnimationFrame` is watched), or the host
  did something that may give it work (`worklets-host.h`). The loop's 1 s safety wake is gone:
  it sleeps until a descriptor or a deadline (a timer, a paste's timeout, the wallpaper's next
  frame) wakes it. `perf.py --check` guards it (at most one wakeup a second).
- **The session polled every quarter second** for its children: SIGCHLD now wakes it, and it
  waits until what is due on a clock (the sun, a shell restarted, a display's trial mode).
- **A border drawn with rounded corners visited every pixel of its box** to find the ring: 19 ms
  of a two-panel Inbox's 25 ms frame. Rows now skip the ring's hole and fill what a rounded
  rectangle covers whole at once (pixel for pixel the same).
- **A wallpaper reduced to the screen held every source row reduced across at once** (another
  56 MiB in floats) and an ICC conversion copied the whole image: rows are now reduced as they
  are needed and colours converted a slice at a time; the shell's peak fell by 55 MiB.
- **The CPU composition composed the whole output every frame**, damage or not. It now composes
  only the damage, made disjoint, onto the screen's frame before (`compose_cpu_damaged`, pixel
  for pixel the same): a Settings scroll's frame 3.0 → 0.4 ms, a live resize's 3.1 → 2.8, a
  window drag at 1.25 7.0 → 5.3, the overview opening 12.9 / 17.6 → 9.9 / 16.4 ms (p50 / p95).
  Every interaction is within the 60 Hz budget on the CPU now (`perf.py --check`).
- **A JPEG wallpaper was decoded whole** before it was reduced (56 MiB for 5120 × 2880). A JPEG
  drawn at half its size or less is decoded at a half, a quarter or an eighth of it from its DCT
  coefficients (jpeg-decoder's `scale`, as libjpeg's scale-on-decode), within 0.13 levels of
  the whole decode on average: the shell's peak memory 127 → 80 MiB (182 before #153).
- **The GPU path waited for each frame on the compositor's thread** (`VulkanCompositor::run`
  submitted, then waited for the fence before the page flip): on the ThinkPad the session logged
  turns of 28–35 ms, 20–31 ms of them waiting for Iris Xe. A frame for a display now goes to it
  with its completion: the submission signals a semaphore exported as a sync file, which the
  atomic commit takes as the plane's `IN_FENCE_FD`, so the kernel flips once the device is done
  and the turn goes on at once (reading input, serving clients). The next composition waits for
  the last one first, done long before (a frame is composed once the one before flipped). A
  device that exports no sync file, and the frames the director keeps to check, are waited for as
  before; the session's log says which (`[session] composing on … each handed to the display with
  its completion (IN_FENCE_FD)`). Not yet seen on a display: lavapipe exports no sync file.
- **The GPU composed a frame layer by layer, region by region**: a dispatch per layer per
  damaged region, each reading and writing every pixel of the output it covers, with a barrier
  between dispatches, and up to eight overlapping regions composed each in full. On the
  ThinkPad, 17–44 ms of device time a frame while a window was dragged. The shader now composes
  each pixel once: one dispatch per region (the damage made disjoint, `disjoint`), each pixel
  taking the background and the layers over it from a table (a storage buffer), starting at the
  topmost one that covers it whole and opaque (the wallpaper under a window is never read). For
  a window dragged on a 1920 × 1200 desktop at 1.25 (shell, window, its shadow, the bars), the
  memory a frame moves goes from about 160 MB in 16 dispatches to 10 MB in one; a whole frame,
  from 64 to 21 MB. Byte for byte the CPU reference's (every Vulkan test, and scenarios with
  `--gpu`, which compare every frame). Lavapipe, a CPU, runs it about twice as slowly: its cost
  is arithmetic, not memory; a session never composes on it. The session now logs every ten
  seconds how long the GPU took to compose its frames (`[compositor] the GPU composed …`).

- **Stash (October 31).** Measured with `perf-stash*.json` and profiled natively (an outside
  sampler) and in JavaScript (`OXYOS_HOST_JS_PROFILE`):
  - **A view's frame was found by searching the tree from its root** (`windowFrame`,
    `ancestry`), computing every visited view's transform: every turn of the loop asked for the
    focused input's (with none focused, the whole tree), the accessibility tree once per node it
    published (quadratic), each pointer motion for its path. 12 % of the host's time in the steps a
    person waits on in Stash's Downloads, more than drawing. The tree keeps each view's parent
    and both walk up from the view; the host's native work for a double press opening a folder
    went from 52 to 25 ms, for a selection from 7 to 2 ms.
  - **Hover was sent twice, to every view.** On every motion the host sent an enter or a leave to
    each view the pointer crossed, listening or not, and never a move; React Native's own pointer
    events processor, which makes those events from a C++ platform's, took each as the pointer
    being there: listeners heard each crossing twice, and moving the mouse across Stash's icons
    sent React 117 events no one listened for, which the next press then waited behind (the list
    view 907 ms, a context menu 568 ms, on the loaded machine). The host now tells it what iOS's
    Fabric does: a `pointermove` where the pointer is and a `pointerleave` as it leaves the
    window (`pointer-hover.json`).
  - **Lines broke only at spaces**, so a file name without one was a line wider than its icon's
    label, drawn cut on both sides, and a name cut at two lines had no ellipsis. Lines now break
    and are ellipsized as Android's StaticLayout does (`text-layout.json`), and a paragraph is laid
    out once for Yoga and every frame that draws it.
  - **Stash was built without its React Compiler on OxyOS alone**: its app config asks Expo for
    it, and Expo asks babel-preset-expo through a Babel caller the OxyOS build does not have. Its
    own sources are now compiled with it as its Expo build compiles them.
  - **The file service read the mount table for every call**: each path an application gave
    (`Scope::reach`, `entry`, `folder`, the Trash's) asked which volumes are mounted, reading and
    parsing `/proc/self/mountinfo` again, about 2 % of the host's work in Stash's steps. The table
    is now read once and kept (`crates/oxyos-files/src/mounts.rs`), and read again only after the
    kernel says it changed, as util-linux's libmount monitor learns it: the table kept open polls
    with `POLLPRI` once a mount or unmount changed it, checked with no timeout before each use, so
    nothing is stale and nothing waits. On the development machine (a 44-line table), the volumes
    went from 90–97 µs a call to 0.2–0.3 µs (one `poll`), a path reached from about 100 µs to 3–7
    µs. `mounts_tests.rs` counts the reads, and mounts and unmounts a volume in a mount namespace of
    its own (`unshare`) to see each at once.

## What remains

- **Stash's own JavaScript is most of what a person waits for** (`perf-stash.json`: three
  quarters of the host's work in the list view, nine tenths in a selection). From its profile:
  - Its items view (`components/ItemsView.tsx`) is not compiled by the React Compiler: its two
    `PanResponder.create` calls in `useState` initializers read refs (`pointerType`, `dragging`,
    `bandStart`), which the compiler takes for reading them while rendering, so it leaves the
    whole component as it is; `BrowserProvider.tsx` neither (a computed key, `[familyOf(place)]`,
    in an object literal).
  - Every element styled with `className` renders twice when it mounts: react-native-css
    3.1.0-rc.0's `useNativeCss` (`src/native/react/useNativeCss.ts`, lines 112–120) drops its
    subscriptions in its state's initializer and, on mount, runs both its effects again, each a
    `setState`: about a third of the JavaScript in switching to the list view.
- **A W3C event's `timeStamp` is when the host handed it to React**, not when the hand moved:
  the protocol carries no time for input. Behind a slow frame, two presses keep their order but
  arrive closer together than they were made. Input events need the device's time (libinput's)
  from the compositor to the application.
- **The GPU path's two changes are not yet seen on a display**: the session's log on the
  ThinkPad will say whether frames went with their completion and how long the GPU composed.
- **A layout re-rendered whole costs 30–35 ms of JavaScript** (the Inbox at its breakpoint).
- **The controls' status poll** (every 5 s) wakes four threads 17 times a second in all.
