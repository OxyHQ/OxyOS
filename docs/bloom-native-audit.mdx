# BloomUI native integration audit

Static review of [OxyHQ/Bloom 658d69a](https://github.com/OxyHQ/Bloom/tree/658d69a62d6f9ac75c0a062932500852f8587dfd), package `@oxy.so/bloom` 15.56.0. No Bloom files were changed, no package was published and no native-device test was run. The revision is evidence for this audit, not an installed runtime dependency in OxyOS.

## Findings

Bloom is a React Native and web component/layout package. Its compositor composes panels inside an application. It is not a GPU renderer, display server or DRM/KMS adapter. The OxyOS display compositor must compose application surfaces without duplicating Bloom's panel engine.

| Dependency | Oxy runtime responsibility |
| --- | --- |
| React Native views/Yoga/ScrollView | Real host components, measurement, layout commits, lifecycle and native scrolling |
| Reanimated/worklets | UI execution thread, native property updates, animation scheduling, cancellation and timestamps |
| gesture-handler | Pointer streams, capture, gesture arbitration and cancellation |
| react-native-css/NativeWind | Actual native style processing; no silent unsupported className behavior |
| Text/font/image/SVG components | Resource lifecycle, shaping, font fallback, selection/editing, composition and rendering |
| Portals/focus/accessibility | Overlay modality, keyboard traversal, semantic tree, announcements and external assistive integration |
| Safe area, keyboard controller and Expo/native modules | Explicit capability matrix; implement required modules and report unavailable optional capabilities honestly |
| Provider theme/font/avatar/status infrastructure | Audit the reachable dependency graph for the minimal app, not only direct package peers |

The factory assembly in `src/app-shell/index.ts` (`createAppShell`, `createPanelLayoutView`, `createAppShellPanels`) is a useful component integration seam. It is not a complete renderer boundary: `AppShellPanelLayout.tsx` imports React Native and Reanimated directly. Replacing `View` by an alias or translating descriptor JSON into hand-written Rust widgets would not make current Bloom run natively.

The web implementation uses DOM, CSS, container queries and browser scrolling. It is not the implementation path for the new OS. Native host support should be reusable at shared owners; do not add per-app patches that emulate missing platform behavior.

## Native host feasibility findings

- React Native 0.88 ships a generic C++ host platform (`platform/cxx`) for view, text, scroll view, modal, image manager, graphics and text layout, plus CMake files for 88 ReactCommon modules. A Linux build of Fabric and Yoga is therefore an extension of an upstream-maintained path, not a fork.
- The `cxx` `TextLayoutManager` is a stub that returns the minimum constraint size. The Oxy host must provide real text measurement and rendering: shaping, font fallback, line breaking, selection and composition. These come from maintained libraries chosen in the spike, not new algorithms.
- Hermes is not in the npm package (only `hermes-compiler`); the runtime must be built from the revision React Native 0.88 pins.
- Reanimated, Gesture Handler, SVG, Safe Area and Expo modules have iOS/Android native halves only. Each needs a Linux implementation of its native interface on the Oxy host, and each is a scoped deliverable of #33.
- Astro has no Linux React Native host to reuse: its Linux UI runs on react-native-web inside Chromium, which this platform must not use as the Bloom host.

### Spike result: Hermes + Fabric + Yoga on Linux

`tools/rn-host-spike/build.sh <react-native-package> <work-dir>` reproduces it on Debian trixie x86_64. It installs nothing system-wide; it is not part of the Cargo workspace or CI. On 2026-10-28, with React Native 0.88.0 from Bloom's dev dependencies:

- **Hermes V1** `hermes-v260318099.0.2`, the version React Native pins, builds against the system ICU (`HERMES_UNICODE_LITE=OFF`, headers from `libicu-dev`), so `libhermesvm.so` also depends on `libicuuc`/`libicui18n`. Unicode-lite is not usable on Linux: Android's build delegates case mapping and normalisation to the platform's Java, and without it `toLocaleLowerCase()` and `normalize()` return their input, which broke menu typeahead. Hermes' own `Intl` stays off (`HERMES_ENABLE_INTL=OFF`): its Linux backend formatted dates but not numbers, and upstream deleted it on 2026-10-19 (`5cf80e4`). The host provides `Intl` instead, as Android's platform does for Hermes there (`react-native-android-adaptation`).
- **ReactCommon**: every module ReactAndroid builds into `libreactnative.so` compiles for Linux, except the Android-only switch, progress bar and text-input implementations. That includes Fabric's scheduler, UI manager, mounting, Yoga, the runtime, the native-module defaults and the generated `FBReactNativeSpec` components. The build uses clang 19 with libstdc++, the CMake files React Native already ships (they select `platform/cxx` off Android) and the third-party versions React Native pins. The resulting `libreactnative.so` links only libatomic, libhermesvm, libjsi, libstdc++ and libc: no X11, Wayland or GTK.
- **Host**: `host.cpp` builds the `Scheduler` with Root, View, Paragraph, RawText, Text and ScrollView descriptors. `tree.js` builds a sidebar + scroll-view tree through the real `nativeFabricUIManager` binding. Fabric commits it, Yoga lays it out and the mounting coordinator delivers create/insert mutations with correct frames: shell 800×600, sidebar 240×600, scroll view 560×600 at x=240, content 560×980.
- **Found gaps**:
  - Several React Native headers use `uint8_t`/`uint16_t` without `<cstdint>`, which only works through libc++'s transitive includes. The spike force-includes it; an upstream fix is the right resolution.
  - folly is configured for libc++ and is reconfigured for libstdc++.
  - The `cxx` text layout measures every paragraph as 0 high (208×0 in the spike).

### Spike result: actual Bloom drawn into a buffer

The same `build.sh` builds `oxyos-bloom-host` and runs it. On 2026-10-28, with Bloom `main` (15.56.0), React 19, React Native 0.88.0, Worklets 0.13 and Reanimated 4.7.1:

- **JS**: Metro bundles React Native's own JS, React and actual Bloom for an `oxyos` platform (`sample/metro.config.js`). Platform files resolve `.oxyos` first, then React Native's Android variants, the generic TurboModule-backed implementations. `@oxy.so/bloom` resolves to the checkout's source.
- **Runtime**: a bridgeless `ReactInstance` on Hermes runs it with the Fabric `Scheduler`, the `RuntimeScheduler`, timers and an event beat ticked by the host loop, as Android's Choreographer does.
- **Host modules**: `host-modules.cpp` implements what OxyOS can answer: `PlatformConstants`, `DeviceInfo`, `AppState`, `Appearance`, `I18nManager`, `SourceCode`, safe-area insets, `ExceptionsManager`, plus the font and asset loading `expo-font`/`expo-asset` call. Calls without an OxyOS counterpart are reported once and have no effect. Missing modules (Expo dev launcher and updates, `SoundManager`, …) are reported as unavailable, never faked.
- **Worklets and Reanimated**: their C++ cores are built unchanged. The OxyOS glue (`worklets-host.cpp`, `reanimated-host.cpp`) supplies what each platform must:
  - the UI scheduler (the host's single loop thread);
  - animation frames;
  - logging;
  - Reanimated's render requests;
  - an explicit failure for worklet-runtime networking.
  Animated props commit through Fabric's shadow tree; the synchronous UI-prop path stays off, as its static flags are.
- **Mounting**: each transaction is applied to a retained view tree. The host reports every mount (`Scheduler::reportMount`), as each platform's mounting layer does. The UIManager's mount hooks run there, and Reanimated resumes its own commits in them. Without it, every animated update after the first React commit is skipped.
- **Text**: FreeType + HarfBuzz replace the `cxx` `TextLayoutManager` stub, so Yoga measures text as it is drawn. Bloom's Inter faces load through `expo-font` → `expo-asset` → the host font registry.
- **Result**:
  - `BloomProvider` → `BloomScope` (md) → `AppShell` with a two-panel split (`panelLayout`), two `Screen`s with `PageHeader`s, `Card`s, typography and a primary `Button`. The panel widths animate through Reanimated to the tracks Bloom computes for the measured shell.
  - Drawn into a 1024×640 32-bit buffer and written as PNG.
  - 50 views, 14 paragraphs, no unimplemented components, no JS errors, deterministic across runs (byte-identical output), settled in about 1.4 s.

### Spike result: Bloom in a window, with pointer, scrolling and text input

`oxyos-bloom-host --window` is a client of the OxyOS display protocol (`crates/oxyos-client` through the C ABI in `crates/oxyos-client-ffi`). `oxyos-offscreen --launch` runs it as its own process and drives it with scripted input. `regress.py` checks each step of `scenarios/sample.json` against its **expected result**, not only changed pixels (see *Regression* below); `build.sh` runs it. What it covers:
- **Presenting:** the host lays out at the configured size and presents its view tree in sealed shared-memory buffers, one frame in flight, reusing released buffers.
- **Pointer:** pointer events become React Native touch events on the view under the pointer (hit-tested like the renderer draws: frames, scroll offsets, clipping, `pointerEvents`), as Android delivers them. Pressability is unchanged; Bloom's `Button` counts presses.
- **Scrolling:** the protocol's `Scroll` event moves the innermost enabled scroll view that can still move: a wheel's notch at once, a touchpad's fingers as a drag that glides when they lift, as Android 14's `ScrollView` takes them ([React Native's Android implementation](./react-native-android-adaptation), Scrolling). The host owns the offset, as a native scroll view does: it updates the ScrollView's Fabric state and emits `onScroll`. Reanimated sees every Fabric event through a Scheduler event listener (as on iOS), so Bloom's scroll-linked header animation runs on the worklet runtime.
- **Text input:** Bloom's `TextField` is React Native's Android text input (props, state and shadow node built unchanged) with an OxyOS descriptor and the native editing side Android's EditText provides. Focus and blur come from JavaScript commands. The input keeps a selection (an anchor and a caret): arrows move it, by word with Ctrl (ICU's word boundaries, as Android's `WordIterator`; a secure field is one word); Up and Down move across lines, keeping their column, Up from the first line going to the start and Down from the last to the end, as Android's `Selection.moveUp`/`moveDown`; Page Up and Page Down move by what the input shows; Home and End go to the line's edges as drawn, Ctrl+Home and Ctrl+End to the text's; Shift extends it, Ctrl+A selects everything, a press places the caret (also the press that focuses the input, on the line under it), a drag selects, a double click selects a word and a triple click a paragraph, as Android's `Editor` counts a mouse's clicks (`scenarios/text-selection.json`). Committed text (`Text`) replaces the selection. An input method's composition (`Preedit`) is part of the text while it lasts, as on Android: it emits change events, is drawn underlined and is replaced by the commit. The focused input tells the compositor what it is editing ([ADR 0008](./adr/0008-input-method)): its purpose and hints from `keyboardType`, `secureTextEntry`, `autoCapitalize` and `multiline` (not `autoCorrect`, which these props cannot tell unset from false), its text without the composition, the selection and the caret's rectangle, only what changed and before the frame that shows it; a password tells neither its text nor its caret. Changes then arrive as transactions, each applied as one edit the way Android's input connection applies a batch of `deleteSurroundingText`, `commitText` and `setComposingText`: one change event, Backspace at once for a deletion and, inside a batch, only the last commit or composition key, when it ends; the composition's cursor range becomes the selection within it; a segment being converted is drawn underlined more heavily over a tint, and an error in red. A transaction made for an older state of the field keeps its commit and drops its deletion. Typing is one transaction, so a long string typed at once is one change event instead of one per chunk. Backspace and Delete remove the selection or one character, Ctrl+Backspace and Ctrl+Delete a word. Ctrl+C copies the selection and Ctrl+X cuts it, never from a secure field, and Ctrl+V pastes through the compositor's clipboard ([ADR 0007](./adr/0007-clipboard)) as an edit of its own. Ctrl+Z undoes and Ctrl+Shift+Z redoes, as Android's `TextView`: typing, or deleting, that goes on where the last edit ended is one edit until the caret moves (as `UndoInputFilter` merges them), a composition is one edit when it ends, and each input keeps its history while unfocused unless the application gives it another value. Enter submits or, in a multiline input, inserts a newline. `autoFocus` focuses the input once it is attached, as Android's `ReactEditText` requests focus when attached to its window. Edits update the input's state and emit Android's events (`topChange`, `topKeyPress`, `topSelectionChange`, `topSubmitEditing`, `topFocus`, `topBlur`, `topEndEditing`) with Android's rules: `onKeyPress` follows React Native's Android input connection (a commit longer than one character and a forward Delete are no key press). The renderer draws the selection, the caret at its offset and the composition from the input's whole layout, so on a multiline input each is drawn on its own lines; an offset where a wrapped line ends is drawn at the start of the next. Text wider than a single-line input, or taller than a multiline one, scrolls to keep the caret in view, as Android's `TextView`; it is cut at the content box on the axis it scrolls, presses land where the scrolled text is drawn, and an input keeps its scroll when it loses focus. The wheel scrolls an input's text, focused or not, before the scroll views around it. Every scroll of an input's text is an `onScroll` event, as Android's `ReactEditText` sends. Carets are placed from the stops the text engine records while shaping (where each glyph cluster starts), not by laying out the text before them: on a line of 1,000 characters a press went from 115 ms to 20 ms from input to frame, the time a short line takes. `scenarios/text-editing.json` (`sample/EditingProbe.tsx`) checks the text and selection each key leaves, as the application receives them, and its exact events; `scenarios/text-input.json` (`sample/ImeProbe.tsx`) drives transactions directly (the director's `--transaction`) and checks the text, selection and events React receives, and what each field told the compositor. Bloom's focus ring and a controlled `value` and `selection` follow.

**Regression (`regress.py`).** The host writes a report (`OXYOS_HOST_REPORT`, `report.h`) with each presented frame's visible text and focused input, and every event it delivered to React with its target's `testID`. The director records, per step, the compositor's focused surface, the input it routed to each surface, the popups shown and the latency, on the same monotonic clock. Each step of the scenario states its expected result:
- the text shown, and text that must not be shown;
- which input and which surface have focus;
- the exact React events, as `event@testID` counts. Any extra event fails, so duplicated and leaked events are caught; for example, text typed into an open menu must reach the menu (typeahead) and not the field behind it, and the outside press that dismisses a menu must reach nothing;
- the compositor input per surface;
- the popups shown, their size and their exact lifecycle events (open, reposition, close, dismissed);
- the size in pixels of each surface's latest frame, the offset the host gave each scroll view, and how far each text input's text is scrolled;
- the accessibility tree (below): nodes that must be present with their role, name and state, a surface's exact node list, and reading order;
- a latency budget.

The director can also send key chords (`--key 42+106` is Shift+Right), a pointer drag, a composition (`--preedit`) and an input method's commit (`--commit`). The steps cover the button, wheel scrolling, the reply field (typing, Backspace, submit, caret keys, Shift selection, Delete, Ctrl+A, composition and its commit, press-to-place and drag selection), the menu by pointer and keyboard (arrows, Enter, Escape, typeahead), and an inline submenu that grows the open popup, which the compositor then places again within the output. They also cover an output scale change with the menu open (both surfaces drawn again at 1.5×, nothing moved, the menu still pressable in logical coordinates) and the wheel: exact offsets, clamping at the top, no event when nothing can move, and nothing delivered behind an open menu. The 56 steps, including the window move and resize and the screen reader steps below, pass three times out of three. With `--uinput`, every step goes through a virtual mouse and keyboard and libinput instead, with exact counts per key and wheel notch (`expect_devices`), and the scenario's two dead-key steps (its layout is `es`) check the composition shown while the sequence waits. All 58 steps pass on a ThinkPad's display ([ADR 0004](./adr/0004-gpu-composition)). Disabling the host's surface check for text makes the leak step fail on both its text and its React events.

**GPU composition.** The compositor's composition now has one definition (`oxyos-gpu::compose_cpu`). The same frames composed on a Vulkan device by a compute shader match it byte for byte: all 173 frames of the 56-step run, with `--gpu`. Inside WSL2 the only Vulkan device is lavapipe (`llvmpipe`, a CPU device). Through Windows, the 56 frames of the regression, composed again on an NVIDIA GeForce RTX 5090, are identical too. A whole frame from the host takes about 1.1–1.2 ms, including upload and readback (the CPU reference takes about 1.3 ms). The GPU's own composing time, from timestamps, is about 6 µs. DRM/KMS output, DMA-BUF import and synchronization need hardware with DRM ([ADR 0004](./adr/0004-gpu-composition)).

Before the painter's fast paths, a window frame took about 57 ms and latency was about 68 ms. Two cases are now handled directly:
- **Opaque, fully covered pixels** are written without blending.
- **Rounded rectangles** sample only near their corners: pixels whose square is inside, and clear of every corner, are full, and pixels outside are empty.

Both give exactly what sampling gave: every regression frame is byte-identical before and after. GPU composition is #32's.

**Accessibility.** Accessibility crosses processes through the display protocol ([ADR 0003](./adr/0003-accessibility-protocol)), the way pixels do. The host builds each surface's accessibility tree from React Native's accessibility props, as Android exposes a view hierarchy to TalkBack (`accessibility.h`):
- **Elements:** a view that is `accessible`, has a role or a label, or is a text input. Its name is its label, or else the text it contains. A scroll view that can still move is an element too (`scrollview`), named by its label alone, as Android's scrolling containers are nodes.
- **Merging and hiding:** text inside an accessible element is part of it. `accessibilityElementsHidden` and `importantForAccessibility="no-hide-descendants"` hide a subtree.
- **Popups:** a popup's content belongs to the popup's surface.

The host publishes each surface's snapshot to the compositor whenever it changes:
- its nodes, in reading order with parents first;
- each node's role and state, in the protocol's sets;
- surface-local rectangles;
- names, and a text input's value (never a secure field's);
- what each node offers beyond activate and focus, as Android's node info: `accessibilityActions` increment and decrement, a scroll view's scrolling on and back while it can, the first node of a modal or a popup (dismiss), an editable text input (its selection); and any other `accessibilityActions`, by label, as custom actions;
- a focused, editable text input's selection, in bytes of its value (never a secure field's);
- live regions (`accessibilityLiveRegion` polite or assertive, on a view or on loose text).

Only a client granted `accessibility`, the screen reader, receives the snapshots, with global rectangles. Its actions come back to the host:
- **activate:** React Native's accessibility click, which Pressability turns into `onPress`, as TalkBack's activation on Android. Its serial is the user's activation, so a menu it opens grabs like one opened from the keyboard.
- **focus:** moves the host's accessibility focus.
- **increment, decrement and custom actions:** React Native's accessibility action by name (`onAccessibilityAction`), as Android's delegate sends `topAccessibilityAction`. A node whose `accessibilityActions` include `activate` gets that action, not a click, on activation, as on Android.
- **scroll forward and backward:** the scroll view moves by its viewport, through the wheel's path (its offset, its `onScroll`).
- **dismiss:** a modal's topmost close request (`onRequestClose`, as Escape), or a popup's dismissal (`onDismiss`, as the compositor's).
- **set selection:** the input takes focus and selects the range, kept within its text at characters.

`AccessibilityInfo.announceForAccessibility` reaches the screen reader through the compositor, at once (assertive); a live region's text, as it changes, is announced by the screen reader itself, as TalkBack announces Android's live regions. `scenarios/accessibility-actions.json` (`sample/A11yProbe.tsx`) works each of these through the screen reader's actions and what it would say, and checks that what a node does not offer is refused.

The director plays the screen reader in the regression. With the menu closed, it activates "Open menu" by name, then moves focus to "Archive" and activates it. The steps check what the screen reader holds, as it received the trees from the compositor: the menu, its focused first row, the expanded trigger, then the chosen row and the trigger focused again.

The session's shell is read the same way (`scenarios/desktop-accessibility.json`): the screen reader opens the launcher from the dock, reads its search field and applications, closes it, opens the Oxy menu and locks the session from it, all through its actions. Locked, it holds the lock screen alone: the password field by its label, never its text, and a rejected password as an alert (`accessibilityRole="alert"`). The wallpaper is an image on the desktop and decoration (not read) behind the launcher and the lock screen; the user's picture on the lock screen is hidden, as the name under it says it in full.

The host also keeps accessibility focus, as Android does apart from input focus. `AccessibilityInfo.sendAccessibilityEvent(view, 'focus')` moves it, to the view or to the first node inside it (the behaviour Bloom's focus moves rely on). The tree marks the focused node. The host reports the tree whenever it changes, and each focus event as it happens; the regression checks both. For example, the trigger reads `button "Open menu"` with `expanded` false or true as the menu closes or opens, the popup reads `menu "Message actions"` and then its `menuitem`s, and an expanded submenu row reads `expanded`. Focus moves into an open menu (its first row) and back to the trigger when the menu closes, whether a row is chosen, Escape is pressed or an outside press dismisses it. The tree and focus checks found three Bloom defects, all fixed at the source:
- **Duplicate label:** the popup's menu name was announced twice (the panel inside the labelled popup was labelled again). Fixed in Bloom #507.
- **No focus on open:** a platform popup did not take screen-reader focus when it opened, as a sheet does, so a screen reader stayed behind the menu. Fixed in Bloom #507.
- **Reading order:** `TextField`'s flattened root let Fabric order the field's z-indexed layers among its siblings, so the input was read after the content that follows it. This is the same on Android. Fixed in Bloom #511, 15.60.5.

**Window move and resize with a menu open.** The compositor places windows itself (`Scene::move_window_to` and `Scene::resize_window`, the operations a shell's keyboard move, maximize or tiling use). The director drives them with `--move-window` and `--resize-window`:
- **Move:** the open Bloom menu moves with its window at once. The host takes no part and does not reposition it, and the menu stays open.
- **Resize:** the host lays out again at the new size, and the trigger moves. The host then repositions the popup, which the compositor places at the trigger's new edge.
- **Afterwards:** the menu still takes presses.

The steps check the window's and popup's exact rectangles.

**Secure fields.** A secure field (`secureTextEntry`) is drawn as one bullet per character, as on Android. Its caret, selection and pointer placement follow the bullets. Its text never appears in the host's report, only as many bullets as it has characters, its blur and end of editing included (they were once reported after the field stopped being the focused one, in clear text; `scenarios/secure-field.json` now leaves the field and checks). It is never published to an assistive technology, which receives the field's label and an empty value. Before this, the host drew a password in clear text.

`scenarios/secure-field.json` checks this with a Bloom password field: what is typed reaches the application, but appears nowhere in the host's report or in the compositor's snapshots. Publishing the value on purpose makes the scenario fail three ways: the screen reader's node, the host's report and the compositor's snapshot.

**Animated's native driver.** `useNativeDriver: true` runs React Native's own C++ implementation (`react/renderer/animated`: `AnimatedModule` and `NativeAnimatedNodesManager`, built unchanged), as Android runs it with `cxxNativeAnimatedEnabled`, which the host turns on (`native-animated.h`):
- **Frames:** JavaScript sends its graph to `NativeAnimatedModule` in batches. The manager asks for frames when it has work, and the host steps it once a frame on its loop (at most 60 a second, as worklets' frames) until a frame finds nothing to animate, as Android's Choreographer drives it (`driveCxxAnimations`).
- **Props:** what a frame computes for a view (opacity, transforms, colours, and the other props React Native's allowlist drives) is set on the mounted view between commits, as Android's mounting layer updates a native view synchronously: parsed by the view's component descriptor, then drawn, hit and damaged with it. Layout props, and each finished animation's last values, are committed to Fabric's shadow tree, and the props the driver manages are kept on views React commits again (React Native's `AnimatedMountingOverrideDelegate`). Scroll and other Fabric events reach `Animated.event` through the UIManager's event listener.
- **Checked:** `scenarios/native-animated.json` (`sample/AnimatedProbe.tsx`) checks every frame of three 600 ms linear animations (opacity, `translateX`, a colour interpolation) against where a linear animation is at that frame's time, then their end on the output, JavaScript told of each end once, a press where the driver moved a view, the way back, a bar moved by a native-driven `onScroll`, and Bloom's `Switch` turning on with one `onCheckedChange`. Without the module it fails seven ways (and on `main`, where every `Animated` component throws, at once); with the props computed but not drawn, on its presented frames; ticking at 30 a second, on its frames per animation.
- **Before the bundle:** Fabric's bindings are installed before the bundle runs, as iOS installs them (Android installs them after). An app that makes an animated component at the top of a module asks for the module as the bundle loads, and React Native's manager, attaching to a UIManager not yet installed, crashed the host. The probe does, so every scenario its bundle runs covers it.
- **Measured** (offscreen CPU, WSL2 x86-64, Release host, three runs): 35 or 36 frames for each 600 ms animation, 17.1 ms apart (median; 16.7 to 17.8), each window frame drawn in about 0.12 ms (at most 0.4).

Before, the module was missing, and every `Animated` component threw as it mounted ("Native animated module is not available"), whatever its driver: React Native 0.88 flushes the native queue in each one's mount effect and asserts the module there. Bloom's `Switch` (JavaScript-driven) threw, and the Settings app with it. Reported, not done: `updateAnimatedNodeConfig` (a platform colour's AnimatedColor given a new value), which React Native's C++ implementation leaves empty; `Animated.event` on gesture handlers' events (react-native-gesture-handler's own report).

**`requestAnimationFrame`, once a frame.** Bridgeless React Native installs `requestAnimationFrame` as a zero-delay timer (its `TimerManager`: "the same as setTimeout(0)"). Android's timer registry still fires it on the next Choreographer frame. The host's fired it as soon as it was due, so a JavaScript-driven animation committed as often as the loop turned. The host now installs its own `requestAnimationFrame` and `cancelAnimationFrame` after React Native's (`animation-frames.h`):
- **Pacing:** a frame begins only once the compositor has answered the window's previous frame (presented or discarded) and a display frame (1/60 s) has passed since the last. So callbacks never run faster than the compositor takes frames, nor than the display. The protocol does not tell an output's refresh rate yet, so a display frame is 1/60 s. Without a window, the display's frames alone set the pace.
- **Callbacks:** a frame runs the callbacks requested before it began, each as a task of its own (microtasks between them), all with the frame's time on `performance.now()`'s clock. A callback requested during a frame waits for the next. `cancelAnimationFrame` removes a callback until its turn, in the frame running too.
- **Sleeping:** the loop sleeps to the nanosecond (`ppoll`), so a frame due in 16.7 ms is not taken at 17. The native driver's and worklets' frames, which kept the same 60 a second, came 17.1 to 17.5 ms apart before.

Measured per press (offscreen CPU, WSL2 x86-64, Release host, host CPU over a press that changes nothing, three runs each):

| | Before | After |
| --- | --- | --- |
| A 600 ms `Animated.timing` in JavaScript | about 597 commits of the box, about 12,600 transactions, about 210 frames presented, about 0.6 s of CPU (a core throughout) | 37 commits, 44 transactions, 37 frames, about 0.05 s |
| Bloom's `Switch` (its spring) | 112 to 233 frames, 3,600 to 9,000 transactions, 0.9 to 1.3 s | 47 frames, 121 transactions, about 0.06 s |

`requestAnimationFrame`'s frames come 16.8 ms apart (median; 16.7 to 17.9). `scenarios/native-animated.json` checks three things:
- the JavaScript animation's frames: each commit where a linear 600 ms animation is at that frame's time, 30 to 42 of them, and as many frames of `requestAnimationFrame` at least 16 ms apart on `performance.now()`'s clock;
- the Switch's frames;
- `cancelAnimationFrame`, before a frame and inside one.

With React Native's zero-delay timer it fails six ways: 593 commits, 174 and 197 frames presented, and no paced frames. With a cancel inside a frame not honoured, it fails on the text.

**Bloom's styles.** Bloom maps its `className`s to styles with `react-native-css`, which needs the app's Metro to compile a Tailwind stylesheet; Oxy apps do it through `@oxy.so/app-preset` (`global.css`, Tailwind v4 through PostCSS, `inlineRem: 16`). Until the sample did the same (`sample/global.css`), every class-styled part of Bloom lost its style silently: menu rows were laid out as a column without padding, panels had no border. Parts styled with resolved tokens looked right, which hid the gap. With the stylesheet the window has more to draw (bordered, rounded panels), which the painter's fast paths absorbed (see the measurements above). The sample does not import NativeWind's theme (`nativewind/theme`), which Oxy apps add on top: NativeWind is not among Bloom's dependencies, and what an app loses without it on OxyOS has not been checked.

**React Native core runs its Android implementation on OxyOS** ([the adaptation's contract](./react-native-android-adaptation), checked by `scenarios/android-adaptation.json`). The host implements React Native's Android interfaces: TurboModule specs, component names and commands. So modules inside the `react-native` package get its own `Platform.android.js` and take their Android branches, and assets follow Android's resource layout. Everything else, including the `Platform` that `react-native` exports to apps and Bloom, reports `oxyos` (`sample/metro.config.js`). Before this rule, the 46 core modules that branch on `Platform.OS` took neither branch on `oxyos`; `TextInput` rendered nothing at all.

Defects found and fixed at their source:
- **React Native:** `AndroidTextInputProps` and `AndroidTextInputState` use Android's serialisation API without the `#ifdef RN_SERIALIZABLE_STATE` guard every other component has, so they do not build off Android. `tools/rn-host-spike/patches/react-native-androidtextinput-props.patch` adds the guard. `build.sh` applies it to a private copy; the React Native package is never modified. Upstream `main` still lacks the guard.
- **Bloom:** `FontLoader` gated rendering on `useFonts`' `loaded` alone, so one font that failed to load left the whole app blank, on every platform. Fixed in Bloom 15.59.4: the app renders in the system font and the failure is reported.

- **A Bloom menu beyond the window:** with the OxyOS platform adapter (`sample/oxyos/platform-surface.js`, [ADR 0002](./adr/0002-bloom-platform-surface-api)), Bloom's native `DropdownMenu` renders its rows in `OxyOSPopupView`. The host leaves that subtree out of the window and opens a protocol popup positioned from the anchor's frame and Bloom's placement, grabbed with the press that opened it. It is drawn in premultiplied ARGB, so the rounded corners are transparent. In the sample, the menu opens 96 px beyond the window's right edge and 40 px beyond its bottom; choosing a row closes it and updates the app; an outside press closes it through `PopupDone` and `onDismiss`.

Bloom fixes found on the way:
- **Fonts (15.60.1):** one font that failed to load left the whole app blank.
- **Accessibility (15.60.2):** focus moves used the deprecated `setAccessibilityFocus`, which throws on bridgeless Android when the legacy UIManager constants are absent.

Known gaps:
- The header's edge scrim is a `react-native-svg` gradient, so it is not drawn until SVG support lands.
- Text input: carets are placed left to right: right-to-left text is not handled.
- Touch-drag scrolling and remote images are not implemented; local PNG and JPEG images, SVG, Gesture Handler, `Modal`, `expo-blur` (blurred where a view has a blur target, as Dimezis' view does on Android; its tint alone without one) and React Native's MaskedView (`RNCMaskedView`) are ([React Native's Android implementation on OxyOS](./react-native-android-adaptation)). Bloom's bottom sheet works in both its modes (`scenarios/sheet.json`). Accessibility is **not complete**. What exists: the protocol and the Bloom host's side (publication, accessibility focus, activate and focus actions), checked by the regression. **Parked**, by decision, while desktop interaction, the open PRs and GPU output come first:
- a screen reader client: nothing speaks yet;
- announcements (live regions);
- actions other than activate and focus (scroll, increment and decrement, dismiss);
- text navigation and selection by the assistive technology;
- hiding unlocked applications' trees from the assistive technology while locked (acting on them is already refused).
- The other menu families (`ContextMenu`, `Select`, `Popover`, `Menubar`) still need the native popup panel.


### The shell in the native host

`sample/ShellProbe.tsx` renders the OxyOS shell (`apps/shell`) in one window of the Bloom host, with a small fixture in place of the compositor's snapshot; `scenarios/shell.json` checks it. Its Metro configuration resolves Bloom's subpath patterns (`./icons/Ri*`) as Node does, which Bloom's icons need.

- **Safe area.** `react-native-safe-area-context`'s `SafeAreaProvider` renders nothing until its native view reports insets. The host defines `RNCSafeAreaProvider`, which reports zero insets and its frame in the window once mounted and whenever that frame changes, as Android's does; an OxyOS window has no system insets, since the compositor keeps panels outside the area windows are placed in. `RNCSafeAreaView` lays out as a plain view for the same reason. Without the provider the shell's window stays white, which the scenario catches.
- **SVG.** `react-native-svg`'s components are built from its own C++ shadow nodes over codegen's props (`build.sh` generates them as it does Reanimated's), as Android builds them. An SVG view's subtree is drawn as one picture of its content box at the display's scale (`svg.cpp`): its elements flattened into shapes (transforms composed, the view box fitted by `align` and `meetOrSlice`, inherited fill and stroke resolved through each element's `propList`, `currentColor` from the nearest `color`, opacity folded into the colours) and rasterized by `crates/oxyos-vector` through the C ABI. The picture is kept until the subtree, its size or the scale changes, and any change inside the SVG damages the SVG view. Drawn: paths, rectangles, circles, ellipses and lines, filled and stroked, so Bloom's icons and `SvgXml` content. Reported once and not drawn: gradients and patterns (`url(#…)` paint), clip paths and masks (their content is drawn unclipped), markers, filters, text, images and `use`. A group's opacity is folded into each element's, so overlapping elements in a translucent group differ from Android's, which composes the group first. The sample's render times and latencies did not change (medians 1.31 and 0.67 ms per frame).
- **Drawn:** the wallpaper, the top bar's menus, clock and status icons, the dock and its raster and vector icons, in the shell's own sizes and colours. Tailwind generates only the classes it finds in the sources it scans, so the sample's `global.css` scans `apps/shell` too; without it, every class only the shell uses (`h-14`, `bg-[#f7f9fc]`, `bg-[#101760]/45`) had no style, and the dock, launcher and overview lost their sizes and backgrounds. `scenarios/shell-overview.json` and `scenarios/session-shell.json` check those colours on the output.
- **The overview** opens from the dock, and a window's card dragged onto another desktop moves the window there, through `react-native-gesture-handler` (`scenarios/shell-overview.json`). Each card shows its window live: the platform's `WindowView` renders `OxyOSWindowView`, where the compositor draws the window itself, scaled and box-filtered ([ADR 0022](./adr/0022-window-views), `scenarios/shell-thumbnails.json`).
- **The launcher** covers the whole screen but the dock, as Launchpad does: its own background (the wallpaper at the screen's size, dimmed) hides the top bar and the windows, and the dock's button closes it again. The dock's top corners are fully rounded, as ChromeOS's shelf. **The clock** is the real time in the session (`useMinuteClock`, one timer for each minute's start), and a fixed one in the window probe, whose regressions compare the top bar.
- **Not yet:**
  - `Intl`: the host's (`intl.h`, `crates/oxyos-intl` on ICU4X): the shell's `toLocaleDateString("es", …)` and `toLocaleTimeString` follow their locale and options. `Intl.Collator`, `PluralRules`, `RelativeTimeFormat`, `DisplayNames`, `Locale`, `ListFormat` and `Segmenter` are not provided yet (undefined).
  - The active application's menus and launching applications ([ADR 0009](./adr/0009-session-shell), decision 3); the shell's applications are still a fixture.
- **As the session's shell** ([ADR 0009](./adr/0009-session-shell), step 1): run with `--shell OUTPUT`, the host's root is the output's background surface and the regions the shell wraps in `Surface` (the top bar, the dock, the open launcher or overview) are panels and an overlay of their own, each where the shell's layout puts it and taking input only over its region; their accessibility is published per surface. `scenarios/session-shell.json` runs the shell with an application window between its panels.
- **On several outputs** ([ADR 0018](./adr/0018-several-displays)): the session runs a host on each output, each told the outputs (its shell state's `output` and `outputs`); `Shell` takes `dock`, and the shell draws the dock only on the primary, once told it is, and the top bar on every output. `scenarios/session-two-outputs.json` runs it on a primary at 1 and an output at 1.5, with the window moved onto the second output, drawn there at its scale.

## Next implementation experiment

1. Pin a compatible RN/Hermes/Fabric/Yoga/Bloom set in a disposable runtime spike and enumerate the full imported native-module graph. No invented production packages or versions before a successful build.
2. Implement a minimal Oxy host that produces an application buffer and submits it through the Oxy display contract. Keep JS out of the compositor process.
3. Import actual BloomProvider/BloomScope/AppShell/Screen and render a two-panel application with text, one control and native scrolling. No DOM/WebView aliases or lookalike fallback components. Rendering into a buffer is done (above); native scrolling and the control's input are not.
4. Prove retained identity through split/deck/responsive transitions, focus/draft/reading-offset preservation, UI-thread dragging, interrupted motion and reduced motion.
5. Verify input selection/composition, keyboard traversal, overlay modality, accessible names/states, RTL, scaling and first-frame font/theme correctness.
6. Trace input → state → layout → render → buffer-ready → physical presentation with busy JS and a stalled second client. Unit snapshots/typechecking cannot establish these properties.

No Bloom renderer or host is shipped in the initial Rust foundation. A successful metadata IPC test must never be reported as Bloom adoption or a graphics benchmark.
