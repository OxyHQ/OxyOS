# Base image configuration

`config/` is a [`live-build(7)`](https://manpages.debian.org/trixie/live-build/live-build.7.en.html) configuration for the Debian Trixie base the native platform will run on. It has **no graphical session**: no display server, compositor, greeter or desktop shell. A live boot ends at a text console. The native compositor and Bloom runtime described in the [architecture](./native-architecture) do not exist yet, and nothing here stands in for them.

## Image publication is retired

No workflow builds or publishes an ISO. The previous `build-iso.yml` built the retired Tauri shell into a labwc/greetd session and attached tagged ISOs to GitHub releases; it was removed with that stack ([#27](https://github.com/OxyHQ/OxyOS/issues/27)). `scripts/check-image-config.py` fails CI if a workflow runs `lb build` or publishes a release.

An image pipeline returns together with the native session, not before it. It must:

- install a real compositor/runtime built against the target userspace, with no placeholder login, fallback session or success on a missing binary;
- boot-test the image (graphical acceptance, not the headless probe): `tools/image/acceptance` boots the console base today and checks its boot logo and services ([Boot acceptance tests](#boot-acceptance-tests)); the session's own checks join it with the session;
- audit the dependency closure and the final package contents for X11, XWayland and Wayland: `scripts/check-image-contents.py --gate` on the built image ([Contents audit](#contents-audit));
- carry signing/provenance and the resolved repository licence and asset review.

Having the tests and the audit does not make the console base publishable: it still has no session. How an image gets onto a disk is [ADR 0023](./adr/0023-installing-oxyos).

Do not install `oxyos-platform-probe` as a compositor, session, greeter or boot check.

## What the configuration builds

| File | Role |
| --- | --- |
| `common` | apt, systemd, `live-boot` initramfs, recommends on. Sources `oxyos.conf` for `LB_IMAGE_NAME`. |
| `bootstrap` | `amd64` unless the build sets `LB_ARCHITECTURE` ([Architectures](#architectures)), Debian `trixie`, `main contrib non-free non-free-firmware` from `deb.debian.org`. |
| `chroot` | squashfs + overlay, stock `linux-image`. `LB_SECURITY="false"`; the security suite comes from `archives/oxyos.list.*`. |
| `binary` | `iso-hybrid`, syslinux (BIOS) + grub-efi (UEFI), Secure Boot `enable` (the build fails without Debian's signed shim and GRUB; `auto` would purge the shim the installed system needs), the squashfs's dm-verity hash tree (`LB_DM_VERITY`: live-boot reads it verified, and the installer and the recovery check it, [ADR 0054](./adr/0054-recovery-and-erasing), decision 3), no debian-installer (`LB_DEBIAN_INSTALLER="none"`: OxyOS installs by writing this image, [ADR 0023](./adr/0023-installing-oxyos)). |
| `binary.arm64`, `chroot.arm64` | What differs on arm64, read by live-build after `binary` and `chroot`: no BIOS bootloader, a failsafe entry without the PC's arguments, the `arm64` kernel. |
| `oxyos.conf` | OS identity (name, version, codename, URLs). `includes.chroot_after_packages/etc/oxyos/oxyos.conf` must be an identical copy; the check script enforces it. |

Live command line: `boot=live components quiet splash loglevel=3 vt.global_cursor_default=0 plymouth.ignore-serial-consoles preempt=full username=user hostname=oxyos`; an installed system's systemd-boot entries get the same `quiet splash loglevel=3 vt.global_cursor_default=0 plymouth.ignore-serial-consoles preempt=full` from its `/etc/kernel/cmdline`, which the installer writes ([ADR 0054](./adr/0054-recovery-and-erasing), decision 7), and a converted machine's from the deploy (`oxyos-recovery kernel-parameters sync`). One list holds them, `crates/oxyos-recovery/kernel-parameters`, which `scripts/check-image-config.py` holds the live command line to; `preempt=full` is [ADR 0066](./adr/0066-quality-of-service)'s (decision 2). The failsafe entry keeps `nosplash`. Why each is there: [ADR 0017](./adr/0017-boot-logo). `plymouth.ignore-serial-consoles` came with arm64: where the firmware names a serial console (an AArch64 machine's ACPI SPCR table or its device tree's `stdout-path`; QEMU's `virt` machine has both), the kernel enables it with no `console=` argument, and Plymouth, seeing a serial console, forces its text view on every display, so the screen stayed black until the login prompt. With it Plymouth keeps the boot logo on the screen; the kernel and systemd still write to the serial console.

### Architectures

One configuration builds two images: **amd64** (x86-64 PCs; UEFI, Secure Boot, BIOS) and **arm64** (AArch64 machines with UEFI: the generic arm64 UEFI image, which QEMU's `virt` machine boots with AAVMF, as do UEFI arm64 desktops and servers' firmware; Secure Boot through Debian's shim). The architecture is chosen when building (`tools/image/build.sh --arch arm64`), and nothing in `config/` is copied or edited per architecture:

- **The settings.** `config/bootstrap` takes `LB_ARCHITECTURE` from the environment `tools/image/container.sh` exports, `amd64` by default. live-build reads every configuration file's override for the architecture after the file itself (`config/<file>.<architecture>`, its `Get_conffiles`): `binary.arm64` and `chroot.arm64` hold what differs, and only that. `check-image-config.py` refuses an override for an architecture `config/` does not build.
- **The packages.** The one manifest; what only one architecture installs is in a live-build conditional, `#if ARCHITECTURES amd64` to `#endif` (not nested, the only condition allowed). `check-image-config.py` expands the manifest for each architecture as live-build does and checks each list.
- **The build is native.** An arm64 image is built in the arm64 container, live-build bootstrapping and running its chroot as on an arm64 machine; on an x86-64 host the container runs through QEMU's user-mode emulation (Debian's `qemu-user-binfmt`). Nothing is cross-built.

On arm64 the image has no BIOS bootloader (UEFI only), the kernel is Debian's `linux-image-arm64` (the generic UEFI kernel, with the device trees of the boards it supports), and the PC-only packages below are not installed. GRUB through Debian's Microsoft-signed `shimaa64.efi` is Secure Boot's chain, as on amd64.

What the generic UEFI image does not boot yet, and why (each target's own boot path, device trees, firmware and graphics, decided in the ARM ADR):
- **The Raspberry Pi** boots its own firmware from a FAT partition (`config.txt`, its device tree), not UEFI: a Pi image is its own image type. `raspi-firmware` is not in this image, and the check script refuses it.
- **Qualcomm laptops** (Snapdragon X, the ThinkPad X13s) boot Linux only with a device tree the bootloader loads; GRUB here loads none. Their firmware (`firmware-qcom-soc`) and the daemons their audio, battery and modem need (`protection-domain-mapper`, `qrtr-tools`, `tqftpserv`, `rmtfs`) wait for that boot path: the daemons' units start on every machine and fail where there is no Qualcomm remote processor, which would leave every other machine `degraded`.

### Package manifest

`package-lists/live.list.chroot` is the authoritative target-runtime manifest for every architecture; there is no metapackage. It holds the live tooling, core system tools, installing and recovering (OxyOS's own `oxyos-recovery`, systemd-repart, systemd-boot and Debian's signed shim and systemd-boot, systemd-cryptsetup, cryptsetup-initramfs, efibootmgr: [ADR 0054](./adr/0054-recovery-and-erasing); and the live medium's own GRUB, signed, which live-build would otherwise install into the build's chroot and purge after, failing systemd-boot's trigger, and which the installer purges), the boot logo (`plymouth` and the `fontconfig` its initramfs hook needs; not `plymouth-themes` or `plymouth-label`, [ADR 0017](./adr/0017-boot-logo)), NetworkManager, **PipeWire** (`pipewire-audio`, the one audio stack), UPower, BlueZ, the clock's synchronization, what the OxyOS runtime loads, command-line utilities, and the firmware and microcode.

**The clock: `systemd-timesyncd`.** systemd's SNTP client, enabled by its package (the audit checks it is); Settings reports its synchronized flag ([ADR 0019](./adr/0019-settings)). Not chrony or NTPsec: a laptop or desktop needs its clock set from the network's time servers, not to serve time or discipline it to the microsecond, and timesyncd is part of systemd, which the base already runs. Without it a machine whose clock drifts or loses its battery fails TLS, and with it the Oxy account's sign-in.

**What the OxyOS runtime loads.** `oxyos-session`, `oxyos-login` and the Bloom host are not packaged into the image yet ([ADR 0023](./adr/0023-installing-oxyos), step 5), but a machine installed from it, onto which they are deployed, must not need apt for what they load. The manifest names it, each with its reason, as found in each binary's `NEEDED` entries and in `/proc/<pid>/maps` of the running session, login program and Bloom hosts on an installed ThinkPad: the Vulkan loader and Mesa's drivers (`libvulkan1`, `mesa-vulkan-drivers`), libinput (`libinput10`), ICU, HarfBuzz and FreeType (`libicu76`, `libharfbuzz0b`, `libfreetype6`), the fallback fonts (`fonts-noto-cjk`, `fonts-noto-color-emoji`), the input-method engine's run-time packages ([ADR 0041](./adr/0041-input-methods), decision 1: `dbus-daemon`, `libjson-c5`, `libfmt10`, `libboost-iostreams1.83.0`, `libhangul1`, `libhangul-data`, `libanthy1t64`, `anthy-common`, `xkb-data`, `iso-codes`) and the screen reader's voice (`espeak-ng`, [ADR 0014](./adr/0014-screen-reader), decision 3). Everything else they load (PAM, PipeWire's client library, libpng, zlib, Brotli, GLib through HarfBuzz) is already in the base or comes with these. `anthy-common` recommends `kasumi`, Anthy's GTK 3 dictionary editor, which would bring GTK, Cairo, Pango and the X11 and Wayland client libraries: `archives/no-display-stack.pref.chroot` pins it out.

**Firmware: laptops and desktops.** OxyOS runs on laptops and desktops, so the image carries the firmware of their hardware and not a server's. The manifest names it (`LB_FIRMWARE_CHROOT="false"` and `LB_FIRMWARE_BINARY="false"`, which the check script enforces):
- **in, on both architectures** (Debian's firmware packages are architecture-independent, and a PCIe or USB device needs the same firmware in either machine): graphics: AMD's and NVIDIA's consumer GPUs (`firmware-nvidia-graphics`); Wi-Fi and Bluetooth: Intel, Realtek, Qualcomm Atheros, MediaTek, Broadcom (the Raspberry Pi's too), Marvell, and the older USB adapters, with `wireless-regdb`; Cirrus Logic amplifiers; USB TV tuners; `firmware-misc-nonfree` for everything else small (Arm's Mali CSF firmware among it).
- **in, amd64 only** (`#if ARCHITECTURES amd64`): what only PCs have: the CPU microcode (Intel, AMD); Intel's graphics (with its IPU cameras), audio DSPs (SOF) and other laptop devices; Intel's PRO/Wireless mini-PCI cards; PCI capture cards.
- **out, refused:** firmware only servers and data centres have, matched by `SERVER_FIRMWARE` in `scripts/check-image-config.py` (in the manifest) and by the built image's audit. That covers network adapters (`firmware-bnx2`, `-bnx2x`, `-cavium`, `-myricom`, `-netronome`, `-netxen`, `-liquidio`), switch ASICs (`-marvell-prestera`), storage HBAs (`-qlogic`), BMC graphics (`-ast`) and data-centre GPUs (`-nvidia-tesla-*-gsp`). `archives/no-server-firmware.pref.chroot` pins them to -1 during the build: `firmware-libertas` recommends `firmware-marvell-prestera`, and a hard dependency on one fails the build.
- **out, not firmware:** what live-build's own detection would add, since it installs every package with a file under `/lib/firmware`. In a built image that was astronomy camera drivers (`indi-dsi`, `libfishcamp1t64`, `libsbig4t64`), and through them Cairo, `libxcb-render0` and `libxcb-shm0`; the telephony cards' `dahdi-firmware-nonfree`; and the two `b43` installers, which download firmware from the internet as they install.

`LB_FIRMWARE_BINARY` is `"false"` as well: the detection would put its firmware, servers' included, in an installer's pool on the ISO, and the image has no debian-installer. OxyOS's installer copies the live system, so an installed system has the manifest's firmware.

`archives/no-display-stack.pref.chroot` pins X.org, XWayland, labwc, greetd, LXDM, `xauth`, `x11-common` and `kasumi` to priority -1 during the build, so a hard dependency on them fails the build instead of shipping silently. It has no `.pref.binary` counterpart and does not restrict apt on an installed system.

Known residue, from Debian packaging rather than this configuration: `libpipewire-0.3-modules` depends on `libpulse0`, which links the X11 client libraries (`libx11-6`, `libx11-xcb1`, `libxcb1`), and Debian's Mesa links its Vulkan drivers' window-system integration for X11 and Wayland, which brings `libwayland-client0` and `libxcb-dri3-0`, `-present0`, `-randr0`, `-shm0`, `-sync1` and `-xfixes0`. They are inert client libraries with no server, `DISPLAY` or `WAYLAND_DISPLAY`: OxyOS's processes present through the OxyOS protocol and never create an X11 or Wayland surface. Removing them needs a Debian change or our own builds (Mesa's with no X11 or Wayland platform), and is part of the native image gate. A built image's audit confirms them, with `/etc/X11/xkb` (`xkb-data`'s keyboard layouts, which xkbcommon reads) and `/etc/X11/Xsession.d` (`dbus-user-session`'s snippet for X sessions, which nothing runs), and nothing else; `scripts/check-image-contents.py` reports them as residue and `--gate` refuses them.

### Accounts and login

- **Live**: live-config creates `user` from `username=user` with its default groups and password and auto-logs in on the console. The image pre-creates no account and grants no `input`, `render` or `seat` access.
- **Installed** (`oxyos-recovery install --developer`, [ADR 0023](./adr/0023-installing-oxyos)): no user, and root locked; the first boot is setup's. A development install may make one development user, an administrator through `sudo`, whose password also unlocks the disk.

Device and seat delegation for the future compositor belongs to the session authority described in the architecture, not to group grants.

### OxyOS's own programs

A program of this repository that the image needs is built from the Cargo workspace and packaged by `tools/image/build.sh packages`, never copied in by hand or downloaded prebuilt. `tools/image/programs/<name>/program` names the package, the workspace package (`CRATE`), its binaries with where each is installed, the package's other files (laid out as installed, in the program's own directory), its `Depends` and description. The build installs rustup's toolchain of `rust-toolchain.toml` in the image's container (kept under `packages/rust/`), builds with `--locked` (the crates checked against `Cargo.lock` as they are fetched), and writes `packages/<arch>/<package>_<version>_<arch>.deb`, its version the OS's and the commit's time (`1.0.<SOURCE_DATE_EPOCH>`), its files dated by the commit; the image build puts it in live-build's `config/packages.chroot/` and the manifest names it.

| Program | Package | What |
| --- | --- | --- |
| `tools/oxyos-recovery` | `oxyos-recovery` | The development installer, the recovery, arming an erase, counting boots, and their units; Safe Mode's boot entries, written beside each kernel's by its kernel-install plugin (`91-oxyos-safe-mode.install`) ([ADR 0054](./adr/0054-recovery-and-erasing)) |

### OxyOS's patched Debian packages

A Debian package OxyOS needs changed is rebuilt from Debian's own source package with OxyOS's patches, never replaced by another program or patched in place on a machine. `tools/image/packages/<source>/` holds the pin (`source`: the Debian version, the SHA-256 of each of its files, OxyOS's version above Debian's, the binary packages the image takes) and the patches, upstream-style, applied after Debian's own. `tools/image/build.sh packages` builds them in the image's container into `packages/<arch>/` under the work directory (again only when the pin or a patch changed), and the image build, which runs it first, puts them in live-build's `config/packages.chroot/`. The build stops when Debian's archive has moved past the pinned version: the patches are then rebased onto the new one, never left on an old Plymouth. The audit fails an image whose package is not OxyOS's version.

| Source | Version | Why |
| --- | --- | --- |
| `plymouth` (`plymouth`, `libplymouth5`) | `24.004.60-5+oxyos1` | Plymouth opens only DRM devices with connectors: never a render node, nor the GPU of a hybrid laptop that drives no display ([ADR 0017](./adr/0017-boot-logo), decision 6) |

A machine installed by hand (the ThinkPad) takes the same packages from `packages/<arch>/`: `apt install ./plymouth_<version>_amd64.deb ./libplymouth5_<version>_amd64.deb`, then `update-initramfs -u`.

## Building and testing locally

For development only: the result is the console base system, not OxyOS, and it is never published. Nothing here runs in CI; `scripts/check-image-config.py` fails a workflow that builds or publishes an image. How an image will get onto a disk, and the gate it passes first, is [ADR 0023](./adr/0023-installing-oxyos).

### Building

```sh
tools/image/build.sh                  # build the amd64 image, then audit what was built
tools/image/build.sh --arch arm64     # the arm64 image, in the arm64 container
tools/image/build.sh audit [ISO]      # audit the newest image (or ISO) again
tools/image/build.sh clean [--arch A] # remove an architecture's build tree, keep its package cache
tools/image/build.sh packages [--arch A] # OxyOS's patched Debian packages alone (the build runs it first)
```

`build.sh` runs live-build in a privileged `debian:trixie` container of the image's architecture (pinned by digest: each platform's manifest in one image index, since Docker's classic image store keeps one platform per digest; `--privileged` for the chroot's mounts and device nodes), so nothing is installed on the host. An arm64 build on an x86-64 host needs QEMU's user-mode emulation registered (Debian's `qemu-user-binfmt`, whose `binfmt_misc` entry has the `F` flag, so the container needs no emulator of its own); `build.sh` says so when it is missing. The audit's extraction runs in the host's own container, whatever the image's architecture. The repository is mounted read-only; everything is written under `OXYOS_BUILD_DIR` (default `~/oxyos-build`; not `/tmp`, which is often RAM and a build needs several GB):

| Path | What |
| --- | --- |
| `build/<arch>/` | live-build's tree, a fresh copy of `config/` each build; `build/<arch>/cache/` keeps the downloaded packages and the bootstrap stage between builds (`OXYOS_FRESH=1` drops them) |
| `out/oxyos-base-<version>-<commit>-<arch>.iso` | the image; *base* because it is the console base. `.packages` (every package and version installed), `.build-info` (commit, architecture, `SOURCE_DATE_EPOCH`, live-build's and debootstrap's versions, the container), `.iso.sha256`, `build-<arch>.log` |
| `audit/<image>/` | what the audit extracted |
| `packages/<arch>/`, `packages/sources/` | OxyOS's patched Debian packages and the Debian sources they were built from ([below](#oxyoss-patched-debian-packages)); `packages/<source>-<arch>.log` |
| `acceptance/<image>/<firmware>/` | the acceptance tests' screens, serial logs and results |

What is pinned: the container image, live-build (`LIVE_BUILD_VERSION` in `tools/image/container.sh`: another version may build another image from the same configuration, so the build stops rather than use it), the configuration by commit (`-dirty` when `config/` or `tools/image/` has uncommitted changes) and `SOURCE_DATE_EPOCH`, the commit's time. Debian's packages come from the archive at build time; `.packages` records what was resolved. `build.sh` uses `docker`, or `sudo -n docker` when only that works; `DOCKER` overrides it.

### Contents audit

`scripts/check-image-contents.py` audits the built artifact, not the configuration (that is `check-image-config.py`, whose list of forbidden packages it shares). `build.sh audit` extracts from the image, in the container: the live root's dpkg database (`status`, each package's file list, the diversions), the list of every file with its size, the ISO's files, the initramfs's file list and its Plymouth configuration, and the files `config/` includes. The audit then fails when:

- an installed package is a display server, Wayland compositor, greeter, toolkit runtime or desktop application, or a file is one (`Xorg`, `Xwayland`, `libwayland-server`, `libgtk-3`, `libQt6*`, session directories), whatever put it there;
- a package is neither in the manifest nor in its dependency closure (Pre-Depends, Depends, Recommends) from what live-build installs itself (debootstrap's required and important packages, the kernel, the keyring, the firmware), or a manifest package is missing;
- a file of `includes.chroot_after_packages/` is missing or differs in the image, or `/etc/os-release` is not OxyOS's;
- the initramfs lacks the `oxyos` theme or Plymouth's script plugin, does not select `Theme=oxyos`, or carries the label plugin;
- a package OxyOS rebuilds (`tools/image/packages/`) is Debian's version rather than OxyOS's, or `systemd-timesyncd` is installed and not enabled.

It reports the sizes (the ISO, the squashfs, what packages install, the largest packages), what live-build's firmware detection added beyond firmware, files in `/usr` no package owns, and the known residue. `--gate` also fails on the residue: that is the bar a published image clears. `--json FILE` writes the report.

### Boot acceptance tests

```sh
python3 tools/image/acceptance ~/oxyos-build/out/oxyos-base-…-amd64.iso                       # UEFI
python3 tools/image/acceptance ~/oxyos-build/out/oxyos-base-…-amd64.iso --firmware secureboot  # Debian's shim
python3 tools/image/acceptance ~/oxyos-build/out/oxyos-base-…-amd64.iso --firmware bios        # SeaBIOS, isolinux
python3 tools/image/acceptance ~/oxyos-build/out/oxyos-base-…-arm64.iso                        # AAVMF
python3 tools/image/acceptance ~/oxyos-build/out/oxyos-base-…-arm64.iso --firmware secureboot  # AAVMF, Debian's shim
python3 tools/image/acceptance ~/oxyos-build/out/oxyos-base-…-amd64.iso --recovery [--firmware secureboot]  # install, recovery, erase
```

The tests boot the image as built in QEMU (`qemu-system-x86_64`, Debian's `ovmf` for UEFI: `OVMF_CODE_4M.fd`, or `OVMF_CODE_4M.secboot.fd` with `OVMF_VARS_4M.ms.fd`'s Microsoft keys for Secure Boot). KVM is used when `/dev/kvm` is usable, else TCG with longer timeouts. The display is QEMU's standard VGA (`--display virtio` for virtio-gpu) with an EDID whose preferred mode is the size under test, 1920×1200 by default, the ThinkPad's: the theme must have a `splash-WxH.png` of that size, since the mark is compared pixel for pixel.

The architecture comes from the image's name (`--arch` overrides it). An arm64 image boots in `qemu-system-aarch64`'s `virt` machine with Debian's `qemu-efi-aarch64` (`AAVMF_CODE.no-secboot.fd`, or `AAVMF_CODE.secboot.fd` with `AAVMF_VARS.ms.fd`'s Microsoft keys), UEFI only (`--firmware bios` is refused): `virtio-gpu-pci` with the EDID under test as the display (the machine has no VGA; AAVMF draws its console on it and the kernel's `virtio-gpu` driver takes it over), the medium on `virtio-scsi`, a USB keyboard for the keys QMP sends, and the PL011 serial port, `ttyAMA0`, as the test's console. Emulated on an x86-64 host (TCG, 4 CPUs, `-cpu max,pauth-impdef=on`), each wait gets 3000 s; KVM is used on an arm64 host.

On either architecture, two boots:

1. **The boot logo.** At the bootloader's menu the tests press Enter, as a person would, so the command line is exactly the shipped one. From then on the screen is read over QMP (`screendump`) many times a second and each frame classified: the bootloader's picture, black, the mark (the frame equal, byte for byte, to the theme's `splash-WxH.png` centred on black), something mark-sized in the centre that differs from it, or anything else. The checks:
   - the kernel takes the display to black, with nothing drawn;
   - from the first black frame until the mark, every frame is black: no kernel or initramfs text, no cursor;
   - the mark is the theme's pixels;
   - the console's prompt follows the mark.
2. **The system.** At the menu the default entry is edited as a person edits it (GRUB: `e`, the end of the kernel's line, `Ctrl+X`; isolinux: `Tab`) to add `console=tty0 console=ttyS0,115200` (`ttyAMA0` on arm64): the kernel's standard way to have a console on the serial port. Nothing is added to the image for the tests. systemd starts a getty there, and the tests log in as live-config's live user with its default password. Over the serial console they check:
   - the boot finishes `running` (`systemctl is-system-running --wait`), not `degraded`;
   - no failed system or user unit;
   - journald, udevd, D-Bus, logind, NetworkManager and both gettys active, and PipeWire's sockets in the user's session;
   - Plymouth has quit;
   - `/etc/os-release` is OxyOS's, and `dpkg` the image's architecture;
   - UEFI and the Secure Boot state match the firmware.

   They record systemd's boot time (`systemd-analyze`) and its slowest units, and the boot's error-level journal.

Written under `acceptance/<image>/<firmware>/`: `results.json` (each check, the boot logo's timeline with the time after Enter of each change, the command line, the boot time), the frames as small PNGs (`1-bootloader-menu`, `2-black`, `3-mark`, `5-console`, `6-console-after-boot`, and any frame that failed a check), each boot's serial log and QEMU's log. The exit status is non-zero when a check fails.

The screen is read about 35 times a second (a dump and its decoding take under 10 ms with KVM): a flash shorter than that can pass unseen. What QEMU cannot show: a real panel's mode and its firmware's logo, the time the panel is dark, the passphrase field at an encrypted disk, i915's handling of the CRTC. Those stay [ADR 0017](./adr/0017-boot-logo)'s step 3, on the ThinkPad.

### The arm64 image, built and booted

On a developer's machine (WSL2, x86-64; the arm64 container and the machine emulated by QEMU, TCG), at commit `1f6cc4d8fc17` with this configuration:

- **Built** in 2 h 6 min (7572 s, every arm64 program emulated; the bootstrap and packages cached): `oxyos-base-1.0-…-arm64.iso`, 998.5 MiB; 382 packages, 1119.5 MiB installed, of which 505.7 MiB are firmware files; a 532.1 MiB squashfs and a 104.8 MiB initramfs. The kernel package is the largest (170 MiB, with the device trees). live-build reports Secure Boot on: the ISO boots `EFI/boot/bootaa64.efi` (Debian's Microsoft-signed `shimaa64.efi`) and `grubaa64.efi` (`grub-efi-arm64-signed`).
- **Audited**: no forbidden package or file, no server firmware, every package in the manifest's closure, the includes unchanged, the boot logo in the initramfs (`usr/lib/aarch64-linux-gnu/plymouth/script.so`). The residue is amd64's: `libx11-6`, `libx11-data`, `libx11-xcb1`, `libxcb1`, `/etc/X11/xkb`, `/etc/X11/Xsession.d`. `firmware-misc-nonfree` recommends `firmware-intel-graphics` and `firmware-intel-misc`, so Debian installs those two on arm64 too, although the manifest names them for amd64 only.
- **Booted**: all 18 checks pass with AAVMF (UEFI) and with AAVMF's Secure Boot and Microsoft's keys (`SecureBoot` 1), at 1920×1200 on virtio-gpu. Emulated, after Enter at GRUB's menu: black at 15 to 16.5 s (GRUB loads the kernel and initramfs), the Oxy mark, byte for byte the theme's `splash-1920x1200.png`, at 16.2 to 17.9 s, the console at 89 to 93 s. systemd: 33 to 34 s in the kernel and 62 to 68 s in userspace. No failed unit; `dpkg` is arm64 and the kernel `aarch64`.

Building and booting found two things, fixed here:
- **No boot logo on arm64.** QEMU's `virt` machine names its PL011 as the console (ACPI SPCR, and `stdout-path` in its device tree), as many AArch64 machines' firmware does. The kernel enables that serial console with no `console=` argument, Plymouth then forces its text view on every display, and the screen stayed black until the login prompt. The command line now has `plymouth.ignore-serial-consoles` (live and installed, both architectures).
- **The audit's extraction** looked for `/live/initrd.img`, which live-build writes for syslinux only: the arm64 ISO has only the kernel's versioned name. It now takes the medium's one `/live/initrd.img*`.

The amd64 image from the same commit is unchanged by the arm64 work: the same 389 packages and sizes as [ADR 0023](./adr/0023-installing-oxyos)'s build, the audit passes, and all checks pass with UEFI (18), Secure Boot (18) and SeaBIOS (17), with the new command line.

### Installing, the recovery and erasing (`--recovery`)

`--recovery` (UEFI or Secure Boot) runs one machine through ADR 0054's whole life, on a blank 24 GiB virtual disk under the run's directory (never a disk of the host) and with its firmware's variables kept from start to start: the development installer from the live medium (encrypted, a development user, a recovery key); the installed system through shim and systemd-boot, the disk's password typed at Plymouth's field over QMP; the recovery reached by Space held on a USB keyboard at the boot menu, and by three starts cut off at the password prompt; *Erase All Content and Settings* armed by `oxyos-erase.service` and carried out by the recovery; *Erase and Reinstall* from the recovery's menu; Safe Mode chosen at the boot menu (its kernel's command line with `oxyos.safe-mode=1`, no try spent, the next start normal); and after each erase a first boot with no user, a new LUKS2 volume that neither old secret opens, and the recovery untouched. The installed system's and the recovery's consoles are asked for through the firmware's OEM strings (`io.systemd.boot.kernel-cmdline-extra`: `console=ttyS0`, and systemd's debug shell on a second serial port for the checks), not in the image. Each start's screens, both serial logs and QEMU's log are under `acceptance/<image>/recovery-<firmware>/recovery/`. Results: [ADR 0054](./adr/0054-recovery-and-erasing#results).
