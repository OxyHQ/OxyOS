# Desktop interaction coverage

This page audits the regressions behind six areas of desktop interaction in the Bloom host and the compositor. For each behaviour the ADRs promise, it lists the scenarios (`tools/rn-host-spike/scenarios/*.json`) and unit tests that check it, what they assert, and the gap. The audit was made on 9 November 2026 against main at `049e10eb`. The regressions added with it, and with the input-method fixes that came before it (`ime-preedit`, `ime-japanese-interrupted`), are marked **added**.

The bar is the owner's: a regression must check the **expected result**, the **focus**, and the **exact events delivered**, with no duplicates and no leaks. A frame that changed is not enough.

## How a scenario asserts

Read from `regress.py` (`check_step`):

- **Exact deliveries.**
  - `react` counts every event React received in the step. An event not listed fails it, so duplicates fail too.
  - `delivered` counts what the compositor delivered to each surface, exactly.
  - `transactions` lists the input method's transactions the field was given, in order and whole.
  - `popup_events`, `host_input`, `a11y_events` and `react_presses` are exact too.
  - Input that reaches another client fails **every** step, `delivered` or not.
- **Focus.**
  - `focus_input` is the focused text input.
  - `keyboard_focus` is the control the keyboard's navigation focused, with its ring.
  - `focus_surface` is the compositor's keyboard surface.
  - An `at` node whose state includes `focused` is the reader's focus.
- **Outcome.**
  - `texts`: what is drawn. The probes draw React's state, such as `Line: "abc" [3,3]`, the text and the selection React holds.
  - `field`: the text, selection and caret rectangle the compositor holds for the field, and so what an input method sees.
  - `at` and `at_absent`: what the assistive technology holds.
  - `spoken` and `announcements`: exact lists, so a duplicate fails.
  - Also `scroll_offset` (exact), `menus`, `clipboard` and `popup_rect(s)`.
  - **Added:** `composition`, the composition a field draws: its range and styled segments, as the host reports it changing.

In the tables, **O**, **F** and **D** mean outcome, focus and exact deliveries. A step that leaves focus where it was is not marked down for lacking **F**. Only steps where focus could move without being checked are.

The scenario gate runs every scenario on the gate machine (seldon) in the merge queue (`.github/workflows/scenarios.yml`). Unit tests run in `native-ci.yml`.

## Performance

`perf.py` measures and [Performance](./performance) records the numbers. In the gate every scenario runs with `--renderer cpu`, and the scenarios that hold a budget on time (`perf-*`, `refresh-*`) run alone in phase 2. **The gate holds** `latency_ms`, `content_ms_max`, the 33 ms backstop on a step's JavaScript, `zoom_presented_ms_max`, the `diagnostics` limits, commit counts, and frame bounds from above. **It does not hold** the JavaScript CPU budgets, frame spacing, or the frame-count minimums (capped at 2 by `frames_least`). Those, and `perf.py --check` (compose and host p95 within a refresh, GPU time, idle, first frame, memory), are run by hand.

| Scenario | What it bounds | Where it runs |
| --- | --- | --- |
| `perf-window-drag(-scaled)` | a window drag composed in ≥90 frames, nothing read back | CPU, gate phase 2 |
| `perf-dropsea(-scaled)` | Dropsea's latencies: opening a folder 120 ms, a view switch 600, a context menu 250, Escape 120 | CPU, gate phase 2 |
| `perf-dropsea-home` | latencies 120, 600 and 450 ms; JavaScript per step (not held in the gate) | CPU, gate phase 2 |

**Interactions with no time bound at all:**

- input methods (preedit, candidates, commit);
- text editing per keystroke (only `sample`'s whole typed string, 250 ms);
- menus from the keyboard and the bar's menus (only Dropsea's context menu and `sample`'s menu);
- popups following a move or resize;
- momentum and keyboard scrolling;
- everything the reader says.

**On real hardware.** The ThinkPad (Intel Iris Xe and an NVIDIA T550) has run `perf.py --runs 3 --gpu-only --check` with every part on the Iris Xe (6 November). All budgets held but the genie at 120 Hz: compose p95 9.98 ms against 8.3 ([Performance](./performance#every-part-on-the-thinkpads-gpu)). Nothing in CI or a deploy runs `perf.py`. A device run must never touch the NVIDIA GPU and never disturb the signed-in session. It needs:

- `VK_DRIVER_FILES` set to Intel's ICD alone, so the loader cannot load NVK. Without it, `vulkaninfo` in the gate's phase 4 enumerates every ICD, which froze the machine on 1 November ([ADR 0031](./adr/0031-gpu-buffers)). So the gate is never run there as it is.
- `/dev/dri` on a tmpfs in the run's own namespace (`unshare -rm`), with only the Iris card and its render node bound back.
- `strace -f -e trace=openat`, checking that no NVIDIA node is opened. Also check that the T550's `runtime_status` stays `suspended`.
- `--gpu-only`, never `--kms`: `--kms` needs DRM master and would take the display from the session.

## React Native's Android internals reused

[React Native's Android implementation on OxyOS](./react-native-android-adaptation) is the contract. Each reuse should be documented there, as an adaptation with a test. These are not:

- **`fbgloginit`** (ReactAndroid's first-party JNI, linked by the text input's library) is not documented. Its logcat sink is behind `__ANDROID__`, so it is harmless.
- **`android-shim/android/log.h`** (`__android_log_print` to stderr, for Reanimated's and Worklets' cores) is not documented.
- **Codegen run with `--platform android`** for OxyOS's own platform specs. The doc mentions only React Native's specs.
- **Android-only props parsed from raw props** (`android-view-props.cpp`): `focusable`, `accessibilityCollection`/`accessibilityCollectionItem`, and react-native-macos's `acceptsFirstMouse` are not in the doc. `elevation` is pinned only against Chromium, which draws no elevation, so Android's shadow is not pinned.
- **The `AccessibilityProps.cpp` backport** is documented only in the native audit, not in the adaptation's contract.
- **The ReactCommon Android text input's shadow nodes** are compiled from a patched copy. "Unchanged with `RN_SERIALIZABLE_STATE`" has no test, since there is no Android build.

**Where the host answers as Android does without doing it** (the adaptation's rule is that an API OxyOS does not provide fails visibly):

- **Closed 10 November 2026: unknown native components drawn silently.** Each is now said in the log and the report under its own name (`unimplemented-components.h`), and `regress.py` fails a scenario that draws one it does not declare (`unimplemented`).
- **"Accepted with no effect"** (`forceRTL`, `setColorScheme`, and untested others such as `allowRTL`, `setAccessibilityFocus`, `exitApp` and StatusBar's setters) contradicts the doc's own rule. `android-adaptation` asserts them as `ok`.
- **`BackHandler`**: `hardwareBackPress` is never emitted, so its listeners never fire, and `exitApp()` resolves doing nothing. Neither is documented as such.
- **Closed 10 November 2026: `AccessibilityInfo`** answers from the session's screen reader and Reduce Transparency (section 6).
- **The adaptation doc contradicts the code**:
  - It says AppState is "always active", but `background` is reported.
  - It says Appearance is "the light scheme", but the session's dark setting is followed.
  - It says `canOpenURL` is false and `openURL` rejects, but both now open by scheme through the session.
  - It does not mention that `Dimensions.get('screen')` is the window's size, or that `KeyboardObserver` (an iOS name) is served with listeners that never fire.

These are listed for their owners to decide. The audit's change fixed none of them; two are closed since.
